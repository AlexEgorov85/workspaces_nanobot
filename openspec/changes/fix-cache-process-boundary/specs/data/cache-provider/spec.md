## ADDED Requirements

### Requirement: Skill получает доступ к кэшу через интерфейс, а не через реализацию

Skill `audit_analyzer` MUST получать доступ к данным кэша **исключительно
через интерфейс `CacheProvider`**. Skill MUST NOT создавать собственное
соединение с файлом кэша, MUST NOT разрешать путь к файлу кэша
самостоятельно и MUST NOT называть конкретный класс storage-реализации.

Принцип: **какая реализация стоит за интерфейсом — не важно и не видно
вызывающему**. DuckDB или иная СУБД — деталь runtime, а не skill'а.

Применение правила **симметрично**: тем же интерфейсом и той же точкой
создания провайдера пользуется runtime. Skill не обязан знать, кто держит
файл, и не должен получать провайдера из отдельного, параллельного runtime-пути
(второй реализации интерфейса).

Бизнес-логика skill'а (реестр predefined-скриптов, валидация параметров,
генерация SQL, LLM-вызов, формат вывода) MUST быть сохранена без изменений.

#### Scenario: skill запрашивает данные через интерфейс

- **WHEN** skill выполняет SQL-запрос к кэшу
- **THEN** запрос MUST выполняться через `CacheProvider.query_sql()` (или другой метод интерфейса)
- **AND** skill MUST NOT вызывать `duckdb.connect` для файла кэша
- **AND** skill MUST NOT импортировать модуль concrete-реализации

#### Scenario: skill не называет конкретный класс хранилища

- **WHEN** проверяются исходники skill'ов
- **THEN** в них MUST NOT встречаться `DuckDbCacheStore`, `PostgresDuckDbProvider`, `open_cache` и иные имена concrete-реализации
- **AND** тип, с которым skill работает, MUST быть `CacheProvider`

#### Scenario: skill не разрешает путь к файлу кэша

- **WHEN** skill сообщает пользователю ошибку доступа к кэшу
- **THEN** путь MAY использоваться как часть сообщения об ошибке
- **AND** skill MUST NOT вычислять путь к файлу кэша в своём вычислительном коде и MUST NOT читать `gateway.cache.local_path` напрямую

#### Scenario: провайдер в READ_ONLY-режиме

- **GIVEN** процесс не выиграл ownership claim и работает с `CacheProvider` в режиме `READ_ONLY`
- **WHEN** skill выполняет запрос
- **THEN** запрос MUST выполняться через тот же `CacheProvider`
- **AND** skill MUST NOT пытаться обойти режим самостоятельным открытием соединения

### Requirement: Дискавери runtime-индексов не открывает файл самостоятельно

Функция дискавери runtime-векторных индексов MUST читать данные **через
интерфейс** и MUST NOT открывать storage и разрешать путь к файлу кэша
самостоятельно.

Существующий injection-шов (`fetch_fn`) MUST быть сохранён как способ передать
соединение от провайдера.

#### Scenario: дискавери читает через провайдера

- **WHEN** skill запрашивает каталог runtime-векторных индексов
- **THEN** данные MUST читаться через переданный `CacheProvider`
- **AND** функция дискавери MUST NOT разрешать `gateway.cache.local_path` самостоятельно
- **AND** функция дискавери MUST NOT импортировать `lib.core.skill_config`

#### Scenario: дискавери не скрывает сбой под пустым результатом

- **WHEN** разрешение пути к кэшу или открытие storage внутри функции дискавери завершается ошибкой
- **THEN** ошибка MUST быть поднята или залогирована с её типом
- **AND** функция MUST NOT возвращать пустой список как будто индексов нет

## MODIFIED Requirements

### Requirement: единый интерфейс доступа

Система ДОЛЖНА предоставлять доступ к кэшу **только** через `CacheProvider`.
Прямой доступ к файлу кэша из кода Skills запрещён.

Правило распространяется на **все** компоненты — runtime, skills, project
tools, standalone-утилиты — и на **любой** процесс, включая порождённый
subprocess. Запрещено не само наличие отдельного процесса, а обход
интерфейса: процесс, получивший провайдера из интерфейсной точки создания,
действует легитимно; процесс, открывший файл напрямую или назвавший
concrete-класс хранилища, — нет.

Ошибки доступа к кэшу MUST NOT конструироваться из булева признака
«open не удался»: неудачный open по причине блокировки файла другим
процессом MUST NOT сообщаться как «файл не найден».

#### Scenario: Skill запрашивает данные

- **КОГДА** Skill нужна SQL-выборка из кэша
- **ТОГДА** она ДОЛЖНА использовать `CacheProvider.query_sql()` (или другой метод интерфейса)
- **И НЕ ДОЛЖНА** открывать файл кэша напрямую ни в своём процессе, ни в порождённом subprocess

#### Scenario: ошибка блокировки не сообщается как отсутствие файла

- **КОГДА** открытие файла кэша завершается ошибкой из-за того, что файл уже открыт другим процессом
- **ТОГДА** сообщение пользователю MUST указывать на конфликт доступа
- **И НЕ ДОЛЖНО** утверждать, что файл кэша отсутствует, и предлагать запустить процесс, который и создаёт этот конфликт

#### Scenario: недоступность файла отличается от пустого результата

- **WHEN** файл кэша недоступен (отсутствует, залочен, неподдерживаемая FS)
- **THEN** исход MUST быть различим и типизирован
- **AND** он MUST NOT выдаваться за пустой результат запроса
