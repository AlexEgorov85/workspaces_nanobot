# Валидация спецификаций компонентов (Component Spec Validation)

## Назначение

Этот документ определяет правила и механизмы автоматической валидации компонентных спецификаций проекта workspaces_nanobot. Валидация обеспечивает соответствие спецификаций установленному шаблону, полноту покрытия и отсутствие противоречий.

## Ответственность

Валидация спецификаций отвечает за:
- проверку структуры каждой спецификации
- проверку наличия обязательных разделов
- проверку языка заголовков (русский)
- проверку соответствия реестра COMPONENTS.md фактическим spec
- обнаружение дубликатов и противоречий

## Граница

### Владеет
- правилами валидации структуры spec
- критериями полноты спецификации
- механизмами автоматической проверки
- отчётностью о результатах валидации

### Не владеет
- содержательной проверкой требований (это задача рецензентов)
- проверкой соответствия коду (это задача отдельного verification pipeline)
- утверждением спецификаций (это задача авторов и maintainers)

### Может зависеть от
- openspec/specs/architecture/component-model (шаблон spec)
- openspec/specs/COMPONENTS.md (реестр компонентов)
- фактических файлов spec.md

### Не должна зависеть от
- содержания требований (семантическая проверка)
- соответствия коду (требуется отдельный инструмент)

## Требования

### Требование: структурная валидация

Система ДОЛЖНА проверять наличие всех обязательных разделов в каждой спецификации:
1. Назначение (Purpose)
2. Ответственность (Responsibility)
3. Граница (Boundary)
4. Публичный контракт (Public Contract)
5. Требования (Requirements)
6. Запрещённое поведение (Negative Requirements)
7. Зависимости (Dependencies)
8. Реализация (Implementation Reference)
9. Проверка (Verification)

#### Сценарий: проверка структуры

- **КОГДА** запускается валидация
- **ТОГДА** каждая spec.md ДОЛЖНА быть распарсена и проверена на наличие обязательных заголовков
- **ИНАЧЕ** валидация ДОЛЖНА завершиться с ошибкой и указанием недостающих разделов

### Требование: языковая валидация

Система ДОЛЖНА проверять, что заголовки нормативных разделов написаны на русском языке (содержат кириллицу). Технические идентификаторы в теле spec НЕ проверяются.

#### Сценарий: проверка языка

- **КОГДА** spec содержит заголовок раздела без кириллицы (кроме технических терминов из словаря)
- **ТОГДА** валидация ДОЛЖНА предупредить о возможном нарушении
- **НО** имена классов, методов, файлов в теле spec НЕ являются ошибкой

### Требование: проверка существования spec

Система ДОЛЖНА проверять, что для каждой записи в COMPONENTS.md со статусом non-missing существует соответствующий файл spec.md.

#### Сценарий: проверка существования файла

- **КОГДА** COMPONENTS.md содержит запись со статусом draft/partial/complete
- **ТОГДА** файл spec.md ДОЛЖЕН существовать по указанному пути
- **ИНАЧЕ** валидация ДОЛЖНА завершиться с ошибкой

### Требование: проверка отсутствия дубликатов

Система ДОЛЖНА проверять отсутствие нескольких записей для одного компонента в COMPONENTS.md.

#### Сценарий: обнаружение дубликата

- **ЕСЛИ** один и тот же компонент встречается в реестре более одного раза
- **ТОГДА** валидация ДОЛЖНА завершиться с ошибкой

### Требование: проверка путей к файлам

Система ДОЛЖНА проверять, что указанные в COMPONENTS.md пути к файлам реализации существуют.

#### Сценарий: проверка пути к реализации

- **КОГДА** COMPONENTS.md содержит путь к файлу реализации
- **ТОГДА** файл ДОЛЖЕН существовать
- **ИНАЧЕ** валидация ДОЛЖНА предупредить (не ошибка, так как код может быть в другой ветке)

## Запрещённое поведение

Система НЕ ДОЛЖНА:

- требовать семантической правильности требований (это задача человека)
- требовать соответствия коду на этом этапе (это задача verification pipeline)
- блокировать создание spec из-за незначительных форматирований
- проверять каждый .py файл на наличие spec (только зарегистрированные компоненты)

## Зависимости

- openspec/specs/architecture/component-model — определение обязательных разделов
- openspec/specs/COMPONENTS.md — реестр для сверки
- Python markdown parser — для парсинга spec

## Конфигурация

Отсутствует. Валидация является script/tool.

## Жизненный цикл

Валидация запускается:
- локально перед коммитом (pre-commit hook)
- в CI при создании PR
- периодически для мониторинга состояния

## Состояние

Состояние отсутствует. Валидация является stateless проверкой.

## Инварианты

- Все spec со статусом complete прошли валидацию
- COMPONENTS.md не содержит записей без соответствующих spec (кроме missing)
- Нет двух spec для одного компонента

## Поведение при ошибке

При обнаружении нарушений валидация:
- сообщает список ошибок с указанием файла и строки
- возвращает non-zero exit code
- не модифицирует файлы

## Потребители

- Разработчики — локальная проверка перед коммитом
- CI/CD — автоматическая валидация в pipeline
- Рецензенты — отчёт о соответствии стандарту

## Реализация

Основная реализация:
- `scripts/validate_component_specs.py` — скрипт валидации (должен быть создан)

Пример запуска:

```bash
python scripts/validate_component_specs.py
```

Выходные данные:
- список прошедших проверку spec
- список ошибок с деталями
- итоговый статус (pass/fail)

## Проверка

Валидация валидации включает:

1. **Тест на структуру**: spec без обязательного раздела обнаруживается
2. **Тест на язык**: spec с английским заголовком обнаруживается
3. **Тест на существование**: отсутствующий spec.md обнаруживается
4. **Тест на дубликаты**: дублирующаяся запись обнаруживается
5. **Тест на целостность**: valid spec проходит проверку

Автоматическая проверка может быть реализована через:
- unit tests для validation logic
- integration tests с fixtures spec файлов
- CI pipeline integration
