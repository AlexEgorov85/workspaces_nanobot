# Модель компонента (Component Model)

## Назначение

Этот документ определяет модель архитектурного компонента проекта workspaces_nanobot и устанавливает единый шаблон для всех компонентных спецификаций.

## Ответственность

Модель компонента отвечает за:
- определение того, что считается архитектурным компонентом
- установление обязательной структуры спецификации
- фиксацию правил именования и размещения
- определение критериев полноты спецификации

## Граница

### Владеет
- определением понятия "архитектурный компонент"
- шаблоном спецификации компонента
- правилами ведения component registry
- словарём нормативных терминов

### Не владеет
- описанием конкретных компонентов (это задача отдельных spec)
- implementation details компонентов
- операционной документацией

### Может зависеть от
- docs/TARGET_ARCHITECTURE.md (глобальные принципы)
- openspec/config.yaml (конфигурация OpenSpec)

### Не должна зависеть от
- конкретных реализаций компонентов
- временных деталей реализации

## Требования

### Требование: каждый значимый компонент имеет спецификацию

Система ДОЛЖНА поддерживать реестр архитектурных компонентов. Каждый production-компонент, включённый в реестр, ДОЛЖЕН иметь отдельную OpenSpec specification.

#### Сценарий: обнаружен новый компонент

- **КОГДА** в коде выявлен новый архитектурный компонент
- **ТОГДА** он ДОЛЖЕН быть добавлен в COMPONENTS.md со статусом `missing`
- **И ЗАТЕМ** для него ДОЛЖНА быть создана спецификация

### Требование: спецификация на русском языке

Все новые и изменяемые component specifications ДОЛЖНЫ быть написаны на русском языке. Технические идентификаторы, имена классов, методов, файлов, конфигурационных ключей и API ДОЛЖНЫ сохранять оригинальное написание.

#### Сценарий: создание новой спецификации

- **КОГДА** создаётся новая component spec
- **ТОГДА** все заголовки разделов ДОЛЖНЫ быть на русском языке
- **НО** имена классов (`ApplicationContext`), методов (`can_handle()`), файлов (`project.json`) остаются на английском

### Требование: единый шаблон

Каждая component specification ДОЛЖНА содержать следующие обязательные разделы:

1. Назначение (Purpose)
2. Ответственность (Responsibility)
3. Граница (Boundary) — с подразделами owns/does not own/may depend on/must not depend on
4. Публичный контракт (Public Contract)
5. Требования (Requirements) — минимум одно требование с сценарием
6. Запрещённое поведение (Negative Requirements)
7. Зависимости (Dependencies)
8. Реализация (Implementation Reference)
9. Проверка (Verification)

Следующие разделы заполняются если применимо:
- Конфигурация (Configuration)
- Жизненный цикл (Lifecycle)
- Состояние (State)
- Инварианты (Invariants)
- Поведение при ошибке (Error Behavior)
- Потребители (Consumers)

### Требование: разделение ответственности

Component specification ДОЛЖНА описывать contractual behavior. Implementation details ДОЛЖНЫ оставаться в docs/ и source code, если они не необходимы для определения контракта.

#### Сценарий: описание метода

- **ПЛОХО**: "ApplicationContext имеет 17 полей: field1, field2, ..., field17" (простое перечисление реализации)
- **ХОРОШО**: "ApplicationContext предоставляет единый корень сборки общей инфраструктуры runtime" (контракт)

### Требование: single source of truth

Нормативные архитектурные правила ДОЛЖНЫ оставаться в docs/TARGET_ARCHITECTURE.md. Component-specific contracts ДОЛЖНЫ вестись в openspec/specs/<domain>/<component>/spec.md. Implementation descriptions ДОЛЖНЫ оставаться в docs/.

### Требование: отсутствие дублирования

Система НЕ ДОЛЖНА создавать второе нормативное описание одного компонента в другом файле OpenSpec.

#### Сценарий: обнаружено дублирование

- **ЕСЛИ** один и тот же контракт описан в двух разных spec
- **ТОГДА** одно из описаний ДОЛЖНО быть удалено или перемещено в docs/

## Запрещённое поведение

Система НЕ ДОЛЖНА:

- выдавать предположения за контракт (spec должна основываться на анализе кода или явно согласованных решениях)
- создавать spec для каждого .py файла (только архитектурные компоненты)
- смешивать нормативные требования с implementation details
- устанавливать статус `complete` без реальной проверки соответствия коду
- описывать желаемую архитектуру вместо фактической (без отдельного change)

## Зависимости

- docs/TARGET_ARCHITECTURE.md — глобальные архитектурные принципы
- openspec/config.yaml — конфигурация OpenSpec

## Конфигурация

Отсутствует. Модель компонента является мета-спецификацией.

## Жизненный цикл

Модель компонента создаётся один раз и эволюционирует редко. Изменения модели требуют отдельного OpenSpec change.

## Состояние

Состояние отсутствует. Модель является статичным определением.

## Инварианты

- Каждая spec соответствует единому шаблону
- Все spec написаны на русском языке (кроме технических идентификаторов)
- Нет дублирования нормативных описаний
- COMPONENTS.md отражает фактическое состояние спецификаций

## Поведение при ошибке

Не применимо — это мета-спецификация, а не runtime-компонент.

## Потребители

- Авторы новых компонентных спецификаций
- Рецензенты OpenSpec changes
- Инструменты валидации (spec-reviewer, CI)

## Реализация

Основная реализация:
- `openspec/changes/component-specification-system/design.md` — архитектура системы
- `openspec/changes/component-specification-system/proposal.md` — обоснование
- `openspec/changes/component-specification-system/tasks.md` — план работ

Связанные документы:
- `openspec/specs/COMPONENTS.md` — реестр компонентов
- `docs/TARGET_ARCHITECTURE.md` — глобальная архитектура

## Проверка

Валидация модели компонента включает:

1. **Структурная проверка**: каждая новая spec следует установленному шаблону
2. **Языковая проверка**: заголовки разделов на русском языке
3. **Проверка полноты**: обязательные разделы присутствуют
4. **Проверка на дублирование**: нет двух spec для одного компонента
5. **Проверка границ**: boundary явно определён для каждого компонента

Автоматическая проверка может быть реализована через:
- parse Markdown и проверка наличия обязательных заголовков
- проверка языка заголовков (кириллица для нормативных разделов)
- сверка с COMPONENTS.md
