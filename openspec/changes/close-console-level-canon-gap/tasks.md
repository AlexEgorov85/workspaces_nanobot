## 2. Решение владельца

- [x] 2.1 **Канал объявления.** Решено владельцем 2026-10-08: отдельный канал не
      вводится, объявление остаётся `config.json → gateway.console_level`. В
      блок настроек агента ключ не кладётся (платформа отвергнет файл как «ключ не
      объявлен»), и перекрытие им `config.json` не вводится — это вернуло бы
      второй путь к значению. Вместо нового канала назначен **владелец значения**:
      читает объявление `lib/services/operator_console.py::resolve_console_level`.
- [x] 2.2 **Единственный читатель и второй как потребитель.** Владелец —
      `operator_console`; `lib/utils/logging_utils.py::configure_loguru` больше не
      поднимает `ConfigService` и не читает конфиг, а получает значение у владельца
      (`resolve_console_level()`). Странное обратное требование старого стража
      («в `operator_console` не должно быть `settings_section`») переписано:
      теперь чтение в нём — искомое свойство (`tests/test_operator_console_levels.py:273-284`).
- [x] 2.3 **Расхождение.** Отказ с называнием обоих источников, и в коде он
      больше не проглатывается. Найденное при разборе: канон **уже** требовал
      «не заменяться дефолтом молча»
      (`openspec/specs/runtime/operator-console/spec.md:278-279`), а код этому
      противоречил — `except Exception` вокруг чтения подставлял
      `DEFAULT_CONSOLE_LEVEL`. Отказ теперь объявляется в `stderr` и доходит до
      баннера; глубина вывода не роняет процесс, но и не остаётся молчаливой
      подменой. Пункт 4 `proposal.md` (рантайм-переключение как дефект) снят по
      факту: `set_console_level` вызывается только из `configure_loguru`, второго
      пути к значению в дереве нет.
