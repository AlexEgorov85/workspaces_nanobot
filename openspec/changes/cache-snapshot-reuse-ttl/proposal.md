# Время жизни снапшота кэша `cache.duckdb` (cache snapshot reuse TTL)

## Why

На каждом старте gateway безусловно удалял снапшот `cache.duckdb` и заново
перечитывал все синхронизируемые таблицы из PostgreSQL. Решение «использовать
готовый файл» напрашивалось, но отсутствовало как явная настройка — оператор
не мог выразить «данные у меня меняются редко, не гоняй синхронизацию на
каждом рестарте» и не мог, наоборот, гарантировать свежесть.

Цена решения измерена, а не вымышлена: вычитка всех шести таблиц из PG на этой
БД занимает **63 мс** на холодном соединении и **35 мс** на прогретом. То есть
выигрыш по времени близок к нулю, а платить приходится свежестью: пока кэш
свежий, изменения в PG не видны — новые строки, новые predefined-скрипты,
**удалённые** строки, и `full_resync_every` удаления не сверяет.

Поэтому change оформляет это как **явный настраиваемый компромисс с нулевым
дефолтом**, а не как «ускорение старта». Дефолт `23.0` ч выбран владельцем
осознанно; `0` — escape-hatch, полностью возвращающий прежнее поведение.

Второй, не менее важный мотив — убрать из рантайма два решения, которые
раньше были неявными и потому невидимыми:

1. **Время жизни считалась неявно и по негодному признаку.** «Свежесть» —
   это `mtime` файла (= момент последней публикации через `os.replace`), а не
   дата создания: на POSIX дата создания — это `st_ctime`, который меняется
   при правке метаданных, в Windows семантика другая. Признак вынесен в
   чистую функцию, проверяемую тестом без БД.
2. **«Используем как есть» без проверки готовности = молчаливая работа на
   пустом кэше.** Процесс жив, каналы подняты, readiness зелёный — а данных
   нет, и заметить это можно только по косвенным признакам (пустые ответы
   агента). Теперь переиспользование допустимо только если store реально
   открыл файл.

## What Changes

1. **`gateway.cache.reuse_ttl_hours` (float, дефолт `23.0`)** — новая
   настройка времени жизни снапшота. `0` → всегда пересоздавать.
2. **`evaluate_cache_snapshot(path, ttl_hours, now=…)`** — чистая функция
   решения (один `stat`, без БД и DuckDB) + `format_cache_age()` для логов.
   Возвращает `CacheSnapshotDecision(reuse, age_sec, ttl_sec, reason)`
   с причинами `fresh` / `stale` / `ttl_disabled` / `snapshot_missing`.
3. **`gateway.py`** — решение связано с удалением снапшота: протухший файл и
   осиротевший `.tmp` удаляются, свежий сохраняется. Переиспользование
   дополнительно требует `CacheProvider.is_ready()`.
4. **`ApplicationContext.skip_data_load` + `_start_sync_or_skip()`** — при
   пропуске `PgDuckDbSyncService` не стартует **вовсе**, а не «стартует без
   `initial_load`»: poll-цикл с пустым `_last_sync` на первом такте всё равно
   выполнил бы полный `_fetch_all`, то есть «пропуск» не был бы пропуском.
5. **Гейт доводится явно.** `StartupGate` ждёт сигнал готовности данных без
   таймаутов, а синк при пропуске его никогда не поставит — gateway ставит
   сигнал сам, после проверки готовности store. Иначе ожидание висело бы
   вечно.

## Non-goals

- Не меняется формат снапшота и не добавляется его версионирование/схема.
- Не меняется механизм `full_resync_every` внутри работающего процесса: он
  продолжает сверять удаления, пока идёт синхронизация.
- Не добавляется фоновое обновление по таймеру при пропуске: до истечения TTL
  кэш не обновляется вовсе (сознательный размен, зафиксированный в спеке).

## Impact

- Affected capability: `data/cache-provider` (дельта только на неё).
- Affected code: `gateway.py`, `lib/core/application_context.py`,
  `lib/core/project_settings.py`, `project.json`.
- Affected tests: `tests/test_cache_snapshot_ttl.py` (новый, 15),
  `tests/test_application_context_skip_data_load.py` (новый, 8),
  `tests/test_gateway_startup_gate.py` (+6).
- Операционная заметка: диагностика «почему данные старые» теперь читается
  из одной строки лога `cache snapshot: path=… age=… ttl=… decision=… reuse=…`.
