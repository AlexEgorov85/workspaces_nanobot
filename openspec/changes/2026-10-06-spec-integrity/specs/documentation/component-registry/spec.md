## Purpose

Дельта превращает реестр компонентов из соглашения в проверяемое объявление.
Сейчас 12 записей на 28 спек и 102 компонента в коде, четыре записи расходятся с
кодом, а единственная запись со статусом `complete` нарушает свой же чек-лист по
пять из пяти пунктов. Статус при этом объявляется вручную и проверке не подлежит,
поэтому расхождение не видно нигде.

Дополнительно: правило паритета закрывает дыру в 17 спек без записи, включая
`runtime/entrypoints` — спецификацию двух стартовых путей системы.

## Scope

Owner: `shared`. Изменение трогает `openspec/specs/COMPONENTS.md`,
`openspec/specs/documentation/component-registry/spec.md` и
`tools/validate_component_specs.py` (разбор строки реестра, паритет). Приведение
реестра к пятиколоночной форме обязано выполняться **вместе** с требованием
«неразобранная строка реестра — нарушение» из дельты `component-spec-validation`:
сейчас `COMPONENT_ROW_RE` разбирает 4 поля, и каноническая 5-колоночная таблица
молча проходит с нулем разобранных строк, то есть исправление реестра по норме
**выключает всю реестровую проверку**.

## MODIFIED Requirements

### Requirement: каждый production-компонент зарегистрирован

Реестр MUST содержать запись для **каждой** компонентной спецификации, а не для
каждой архитектурно значимой подсистемы по усмотрению автора. Сейчас на 28 спек
приходится 12 записей, и 17 спек в реестре отсутствуют; среди них
`runtime/entrypoints`, описывающий `gateway.py` и `cli_agent.py` — два стартовых пути
системы. Расхождение не видно ни валидатору, ни читателю.

Домен спецификации MUST быть выводим из записи реестра, иначе категория не проверяется:
заголовочные секции (`### Architecture`, `COMPONENTS.md:30`) сегодня не сопоставлены
ни одной категории из закрытого перечня.

#### Scenario: добавление нового компонента

- **WHEN** обнаружен новый архитектурный компонент в коде
- **THEN** он ДОЛЖЕН быть добавлен в `COMPONENTS.md` со статусом `missing`
- **AND** для него ДОЛЖНА быть создана спецификация и статус обновлён

#### Scenario: Спецификация без записи обнаруживается

- **WHEN** в дереве есть `spec.md`, не упомянутый ни в одной записи реестра
- **THEN** валидатор MUST сообщить путь спецификации и номера ближайших записей по домену
- **AND** MUST выйти с ненулевым кодом

#### Scenario: Домен записи выводится из её текста

- **WHEN** запись реестра объявляет компонент в домене `storage`
- **THEN** валидатор MUST проверить домен по закрытому перечню и MUST извлечь его из строки, а не из заголовка секции

### Requirement: честные статусы

Статус MUST быть **вычисляемым**, а не объявляемым. Сейчас чек-лист
(`component-registry:41-47`) существует только как текст, и следствие видно прямо:
`OperationSchema` помечена `complete` при отсутствии `Boundary`, `Forbidden
Behavior`, `Implementation`, `Verification` и `Responsibility` — то есть чек-лист
нарушен по 4 из 5 пунктов (пункт «есть требование со сценарием» выполнен: три
требования, 12 сценариев), а отсутствуют **все семь** разделов полного шаблона.
Блок «Статистика» при этом сходится с таблицей до цифры, но объявляет `Missing = 0`
при требовании записи для каждого production-компонента:
счётчик жив, содержимое не проверяется.

Проверка честности статуса MUST выполняться **до** проверки дубля и не должна
исключать запись из остальных проверок. Сейчас проверка статуса выполняется раньше
с `continue`, и запись с невалидным статусом выпадает из множества `seen` целиком —
её ссылка и путь реализации не проверяются вовсе, а дубль под её именем не
обнаруживается.

Дополнительно: две записи объявляют реализацию «N/A» для компонентов, чьи
спецификации объявляют реализацией `tools/validate_component_specs.py` — файл
объёмом 10 КБ с `main()` на `:416`. «N/A» MUST означать отсутствие кода, а не
отсутствие продуктового потребителя.

#### Scenario: проверка статуса complete

- **WHEN** spec помечена как `complete`
- **THEN** она ДОЛЖНА пройти проверку по чек-листу `component-model`
- **AND** иначе статус ДОЛЖЕН быть понижен до `partial` или `draft`

#### Scenario: Заявленный `complete` проверяется по чек-листу

- **WHEN** запись объявляет статус `complete`
- **THEN** валидатор MUST проверить все пункты чек-листа честных статусов по самой спецификации
- **AND** при нарушении любого пункта MUST сообщить, какой пункт нарушен и где

#### Scenario: Невалидный статус не исключает запись из проверки

- **WHEN** запись имеет статус, которого нет в допустимом перечне
- **THEN** валидатор MUST сообщить о недопустимом статусе
- **AND** MUST дополнительно проверить её ссылку на `spec.md`, путь реализации и дубль

#### Scenario: `N/A` означает отсутствие кода

- **WHEN** запись объявляет реализацию «N/A»
- **THEN** MUST быть подтверждено, что заявленная спецификация не ссылается ни на один файл реализации
- **AND** при наличии такой ссылки MUST сообщить расхождение

#### Scenario: Блок статистики сверяется с таблицей

- **WHEN** таблица и блок «Статистика» расходятся по числу записей или по разбивке по доменам
- **THEN** валидатор MUST сообщить расхождение
- **AND** MUST NOT ограничиваться тем, что счётчик строк совпал

### Requirement: категоризация компонентов

Закрытый перечень доменов MUST соответствовать фактическим каталогам дерева
спецификаций, и расхождение в обе стороны MUST быть ошибкой. Сейчас перечень
(`:70-85`) не содержит четырёх существующих доменов — `storage`, `logging-db`,
`tools-history-search`, `upgrade-compatibility` — и при этом содержит пять
отсутствующих: `channels`, `sessions`, `observability`, `interfaces`, `security`.
Правило «неизвестная категория ДОЛЖНА считаться ошибкой реестра» (`:87-91`) при
этом не исполняется: слов «категор/category» в валидаторе ноль вхождений, а 6 спек
лежат в доменах, которых в перечне нет.

Домены с живым кодом и нулём записей (`channels`, `sessions`, `observability`,
`interfaces`, `security`) MUST быть либо заполнены, либо убраны из перечня.
Молчаливый третий вариант — оставить в перечне и не заполнять — запрещён: он
делает перечень недостижимым и заставляет читателя искать несуществующие правила.

#### Scenario: добавление записи в реестр

- **WHEN** автор добавляет запись о компоненте в `COMPONENTS.md`
- **THEN** категория ДОЛЖНА быть выбрана из закрытого списка выше
- **AND** неизвестная категория ДОЛЖНА считаться ошибкой реестра

#### Scenario: Существующий домен отсутствует в перечне

- **WHEN** в дереве спецификаций есть домен, которого нет в закрытом перечне
- **THEN** валидатор MUST сообщить о домене и числе его спецификаций
- **AND** MUST выйти с ненулевым кодом

#### Scenario: Домен перечня пуст

- **WHEN** домен из закрытого перечня не имеет ни одной записи реестра, но в коде есть
  подсистемы, для которых домен заведён
- **THEN** MUST быть запись об этом в самом перечне
- **AND** отсутствие записи при непустом коде MUST считаться расхождением, а не нормой

## ADDED Requirements

### Requirement: запись реестра разбирается однозначно

Форма записи MUST быть разбираемой в **единственное** число полей, и строка,
не разобранная ни в одну форму, MUST давать нарушение с номером строки. Сейчас
`COMPONENT_ROW_RE` (`tools/validate_component_specs.py:114-120`) содержит жёсткие
четыре группы, `finditer` (`:331`) пропускает всё остальное молча, и счётчик
(`:446`) показывает «Компонентов в реестре: 0» вместо ошибки.

Требование к числу полей расходится между нормами: `component-model:370` и
`component-registry:17-21` требуют пяти полей (компонент, категория, статус,
спецификация, реализация), а таблица в `COMPONENTS.md:32` строится в **четырёх**
колонках, причём категория вынесена в заголовок секции, а не в строку. Норма MUST
называть, где именно выражена категория, и валидатор MUST следовать тому же месту.

#### Scenario: Пять полей разбираются как пять

- **WHEN** запись содержит компонент, категорию, статус, спецификацию и реализацию
- **THEN** валидатор SHALL разобрать все пять полей и проверить каждое
- **AND** MUST считать компонент зарегистрированным

#### Scenario: Неразобранная строка не исчезает

- **WHEN** строка реестра не соответствует ни одной поддерживаемой форме
- **THEN** валидатор MUST сообщить номер строки и её содержимое
- **AND** MUST NOT ограничиваться счётчиком разобранных строк

#### Scenario: Категория выражена там, где говорит норма

- **WHEN** норма требует категорию в поле записи, а реестр выносит её в заголовок секции
- **THEN** валидатор MUST следовать месту из нормы
- **AND** MUST NOT считать расхождением форму, которую сама норма разрешает
