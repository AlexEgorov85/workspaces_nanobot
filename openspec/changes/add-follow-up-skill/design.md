## Context

Follow Up — отдельное приложение (FastAPI, SQLite+FAISS+BM25, Greenplum,
модели `bge-m3` и `bge-reranker-v2-m3`), у которого уже есть MCP-сервер по
stdio (`backend/skill/mcp_server.py`, семь инструментов). Проверено на
живом стенде: gateway поднимает его через `tools.mcpServers`, агент зовёт
`mcp_follow_up_ask`, ответ с источниками доходит в чат Единого рабочего
места за ~20 с.

Открытым оставался один вопрос: как держать подключение **в git**, чтобы
«Получить из master» в `audit_bridge` (`git reset --hard`) его не снимало,
и при этом не тащить в репозиторий пути конкретной машины.

## Goals / Non-Goals

**Goals**

- Один статичный блок в `config.json`, одинаковый на всех машинах.
- Ноль изменений в runtime-коде проекта; ноль новых зависимостей.
- Машина без Follow Up стартует как раньше — без ошибок и без правок.
- Всё машинное — в одном негитуемом файле, который умеет заполнить
  установщик со стороны Follow Up.

**Non-Goals**

- Перенос кода навыка в этот репозиторий.
- Общий venv с навыком.
- Второй механизм регистрации инструментов помимо `tools.mcpServers`.

## Decisions

**D1. Транспорт — MCP stdio, а не `Tool` в процессе.** Конфликт зависимостей
(`numpy` 2.x против `<2` + torch) делает in-process вариант непригодным.
MCP даёт отдельный интерпретатор, cwd и окружение и является штатным
механизмом `nanobot-ai` (§2.1 `TARGET_ARCHITECTURE`).

**D2. Команда в `config.json` — лаунчер внутри папки навыка, относительно
корня репозитория.** Рассмотрены и отклонены:
- `${FOLLOW_UP_PYTHON}` / `${FOLLOW_UP_ROOT}` — `resolve_config_env_vars`
  бросает `ValueError` на неизвестной переменной: машины без Follow Up не
  стартовали бы;
- `"command": "python"` / `"python3"` — имя интерпретатора различается
  между Linux/macOS и Windows;
- абсолютные пути — привязка к машине в git.
Лаунчер — файл с shebang для POSIX плюс `follow_up_mcp.cmd` для Windows;
`shutil.which` в `_normalize_windows_stdio_command` подбирает `.cmd` по
`PATHEXT` и оборачивает вызов в `cmd /c`. Допущение то же, что у
`exec`-инструмента и `workspace/AGENTS.md`: gateway запускается из корня
репозитория.

**D3. Машинное — в `follow_up.env.local`.** Формат `KEY=VALUE`
(`FOLLOW_UP_ROOT`, `FOLLOW_UP_PYTHON`, `MODELS_DEVICE`), переменные
окружения имеют приоритет. Файл уже попадает под `*.env.local` в
`.gitignore`. `NANOBOT_HOME` лаунчер вычисляет от собственного пути —
не зависит от cwd и от переменных.

**D4. Отсутствие настройки — не ошибка проекта.** Лаунчер печатает причину
в stderr (stdout — канал JSON-RPC, туда ни байта) и выходит с кодом 3;
`open_single_server` ловит исключение, пишет `failed to connect` и
возвращает `(name, None)` — gateway продолжает старт.

**D5. Реестр один.** Навык объявлен в `project.json::skills` (без таблиц
и индексов); инструменты приходят через штатный `tools.mcpServers`.
Второго реестра, fallback-пути и legacy-ветки не вводится.

## Risks / Trade-offs

- Относительный путь в `command` требует запуска gateway из корня
  репозитория — как и сегодня для `exec`. Документировано в SKILL.md
  лаунчера.
- На Windows между gateway и сервером стоит `cmd.exe` → `python`; при
  жёстком завершении gateway дочерний процесс может пережить обёртку.
  Штатное завершение (`close_mcp`) закрывает stdio, и сервер выходит сам.
- Дословность вывода — инструкция модели, не механизм (как у остальных
  навыков).
