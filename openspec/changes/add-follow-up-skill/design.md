## Context

Follow Up — приложение с MCP-сервером по stdio (`backend/skill/mcp_server.py`,
семь инструментов): SQLite + FAISS + BM25, Greenplum, эмбеддер
`bge-m3-russian-legal` и реранкер `bge-reranker-v2-m3`.

Требование к поставке — как у соседних навыков: «Получить из master» и
перезапуск gateway, без клонов, без машинных файлов и без правок конфига.

## Goals / Non-Goals

**Goals**

- Код навыка — в папке навыка; инструменты агента — обычные project tools.
- Ноль изменений в runtime-коде проекта, в `config.json` и в корневом
  `requirements.txt`.
- Настройки подключения — из настроек агента; в коде нет ничего от
  конкретной площадки.
- Машина, где сервер навыка не может подняться, стартует как раньше.

**Non-Goals**

- Встраивание кода навыка в процесс gateway.
- Второй механизм регистрации инструментов помимо загрузчика project tools.

## Decisions

**D1. Код — в `workspace/skills/follow_up/backend/`.** Так же, как код
соседних навыков лежит в их папках. Импорты внутри — абсолютные
(`backend.*`), `PYTHONPATH` ставит лаунчер; из `lib/`, `workspace/tools/` и
других навыков код сервера не импортируется, и сам он не импортирует код
проекта.

**D2. Сервер — отдельный процесс с интерпретатором агента.** Библиотеки
общие, процесс — свой: у навыка локальная SQLite с единственным писателем
и фоновые потоки синхронизации корпуса с Greenplum. Падение или зависание
навыка не должно ронять gateway, а два писателя в одной базе внутри одного
процесса — ломать её.

**D3. Регистрация — `workspace/tools/follow_up.py`, а не
`tools.mcpServers`.** В `nanobot-ai` 0.3.5 серверы из `tools.mcpServers`
поднимает `MCPProvider`, который создают только собственные CLI фреймворка
(`nanobot gateway`, `nanobot agent`); `AgentLoop` сам MCP не подключает, а
gateway проекта собирает его сам (`lib/core/agent_factory.py`). Запись в
`config.json` там просто не сработала бы. Поэтому модуль инструментов:

- семь классов `mcp_follow_up_<имя>` строятся из `tools.json`: схемы нужны
  при регистрации, когда сервера ещё нет, и берутся из его кода при сборке
  навыка, а не переписываются руками;
- мост к серверу — MCP SDK (`stdio_client` + `ClientSession`, зависимость
  `nanobot-ai`) в своём потоке со своим циклом событий: контексты должны
  открываться и закрываться в одной задаче, а сессия — жить дольше любого
  хода агента;
- сервер запускается `<Python gateway> <лаунчер>` с абсолютными путями и
  полным окружением gateway; stderr — в `logs/server.log` навыка;
- заранее сервер поднимается только в `gateway.py`, один раз на процесс
  (иначе синхронизация корпуса ждала бы первого вопроса); в CLI и тестах
  проекта — по первому вызову: лишний экземпляр на машине с корпусом стал
  бы владельцем базы;
- у каждого запуска сервера своё «поколение»: поздняя очистка гасит только
  своё, вызовы на умершем поколении сразу получают отказ; запрос, не ушедший
  в мёртвую сессию, повторяется на свежем сервере; зависший на подъёме —
  гасится; журнал сервера дописывается, хвост попадает в текст ошибки;
- ключ беседы (`session_key`) и отправитель (`user_id`) берутся из
  контекста хода nanobot (`RequestContext`), а не от модели: модель свой
  ключ не видит, а придуманный ею совпал бы у двух аудиторов.

Префикс имён `mcp_` сохранён — так инструменты названы в `SKILL.md`.

**D4. Настройки — у агента.** Лаунчер передаёт `NANOBOT_HOME` (вычислен от
собственного пути). Сервер берёт оттуда:
- модель — из `config.json` / `.secrets.env`; модель агента важнее
  настроек навыка (переопределяются только `skills.follow_up.llm.*`);
- Greenplum — из DSN канала шины `channels.postgres.dsn`, схему — из
  `channels.postgres.schema` (`public` не в счёт). Включается, если сервер
  не отвечает как обычный PostgreSQL (`SELECT version()`); недоступная база
  считается Greenplum. Явные настройки навыка важнее агента;
- модели — из `workspace/data_store/cache/caches_pipelines/`.
Пароль из DSN в журнал не пишется.

**D5. В коде нет ничего от площадки.** Витрины-источники навык читает
через представления `v_fu_assignment` и `v_fu_act_violation` в своей же
схеме; их один раз создаёт администратор площадки. Код знает только эти
имена — ни адресов, ни баз, ни схем, ни номеров реальных проверок.

**D6. Линтер и тесты.** `backend/` сопровождается в репозитории Follow Up со
своим набором тестов и линтером; вложенный `ruff.toml` (с `extend` на
корневой `pyproject.toml`) исключает его из `ruff check` проекта и включает
лаунчер. `workspace/tools/follow_up.py` проверяется линтером проекта как
обычно. Тест проекта `tests/test_follow_up_skill.py` закрепляет контракт
интеграции — в том числе настоящим загрузчиком проекта и мостом на
MCP-сервере-заглушке, — а не поведение навыка.

**D7. Навык не поднялся — не ошибка проекта.** Нет файлов навыка —
инструменты не регистрируются. Сервер не поднялся — вызов инструмента
возвращает `ToolResult.error` с причиной; `follow_up_mcp --check` называет,
чего не хватает.

**D8. Реестр один.** Навык объявлен в `project.json::skills` (без таблиц и
индексов); инструменты — через штатный загрузчик project tools.

## Risks / Trade-offs

- Библиотеки навыка (`torch`, `sentence-transformers`, `rank-bm25`,
  `pydantic-settings`, `sqlalchemy`) должны стоять в окружении агента. На
  площадке `torch` и `sentence-transformers` уже есть для соседних
  навыков; остальное — `pip install -r workspace/skills/follow_up/requirements.txt`.
- Объём: ~21 тыс. строк кода навыка в репозитории проекта. Он изолирован
  в папке навыка и не импортируется остальным кодом.
- Один каталог навыка — один gateway: второй процесс с тем же каталогом
  данных получит отказ сервера (владелец базы один).
- Дословность вывода — инструкция модели, не механизм (как у остальных
  навыков).
