# Design: кэш как снимок, чтение без удержания файла

## Context

### Назначение кэша — экономия соединений PostgreSQL

Локальный кэш обслуживает один сценарий: аналитические SQL-запросы
`audit_analyzer` к `oarb.*` (~100 000 строк) и vector search. PostgreSQL эти
запросы умеет, но **слот соединения дорог**: пул общий на весь процесс и
configured на четыре соединения.

```jsonc
"pool": { "min_conn": 1, "max_conn": 4, "pool_timeout": 5.0 }
```

Этим бюджетом делятся канал Postgres, аренда задач, логирование, сессии,
синхронизация и Streamlit. Навыкам в нём места не остаётся — и кэш существует
именно для того, чтобы чтения навыков в пул не попадали.

Отсюда всё остальное решение следует. Кэш — **прибор экономии соединений**,
а не ускоритель запросов, и критерий «меньше режимов и путей» прямо вытекает
из его назначения.

### Масштаб проблемы

Сравнение подсистемы кэша с тегом `v2.5.3` дало **+709 строк за 109
коммитов**. `cache_ownership.py` даёт +438 из них и не существовал вовсе.

В текущем дереве кэшовая подсистема расходует пул **на себя**:

| Кто | Как ходит в PG | Сколько держит |
|---|---|---|
| `PgDuckDbSyncService` | общий `lib.utils.db` | постоянно, до shutdown |
| `CacheOwnershipCoordinator` | `lib.utils.db.transaction` | claim на старте + heartbeat каждые 30 сек |

Система, чьё назначение — экономить соединения, постоянно расходует их
сама. Это и есть содержание проблемы, а не «файл занят другим процессом».

### Что было в v2.5.3

- Writer'ом был `DuckDbCacheStore._open_locked()` — `duckdb.connect(path)`,
  одно соединение на процесс.
- `PgDuckDbSyncService` держал **psycopg2**, а не DuckDB, и писал через store.
- `list_runtime_vector_indexes` при `fetch_fn=None` открывала **второе**
  соединение и глотала конфликт через `except Exception: return []`.

Последний пункт: процессный дефект был и в 2.5.3, просто молчал. Сегодня он
уже починен — функция требует `provider=`. Устарел ADR
`docs/architecture/decisions/audit-analyzer-runtime-boundary.md:140-142`,
который всё ещё перечисляет его открытым.

## Решения

### D1 — Свежесть = снимок на момент загрузки

Кэш — производная копия PostgreSQL. Загрузка берёт всё, что есть в момент
загрузки. Дельт нет.

Следствия:

- `PgDuckDbSyncService` как **фоновой поток** с очередью, reconnect-логикой и
  колбэками больше не нужен: остаётся «выгрузить N таблиц и закрыть», а это
  умещается в один синхронный вызов. Поток, очередь и
  `set_on_*_callback` — инфраструктура режима, которого не будет.
- `poll_interval_sec`, `full_resync_every`, `max_queue_size`,
  reconnect-backoff — параметры непрерывного режима, удаляются.
- `upsert_records` (доли) и `replace_records` (замена) — два пути записи.
  Остаётся один: полная загрузка.

Чем плох альтернативный вариант «пересборка по требованию»: он выглядит
изящно, но вводит второй триггер того же кода, а выигрыш даёт только в
сценарии суточной устарелости. Владелец зафиксировал семантику однозначно:
загружаем всё, что есть в момент загрузки. Режима нет.

### D2 — Процесс не держит файл

Чтение открывает файл на время операции и закрывает сразу после. Между
запросами процесс файла не касается.

Замеренное поведение DuckDB 1.5.4 (два реальных процесса):

| Сценарий | Результат |
|---|---|
| владелец **RW** + второй **RO** | `IOException: File is already open in ... (PID)` |
| **оба RO** | **оба открываются успешно** |
| повторная попытка на занятом файле | отказ за 0.6 с, ожидания нет |
| разные файлы, оба RW | ок |

Движок блокирует только writer. Поскольку writer'ов после сборки нет, файл
свободен для всех всегда.

Выбранная форма сильнее, чем «держать один RO на всё время жизни»: она даёт
гарантию «файл физически не занят» без затрат на постоянное соединение и
делает утверждение о свободе файла буквальным, а не «не мешает другим
читателям».

**Принятая цена и как она закрывается.** `search_vector` подтягивает payload
каждого FAISS-hit'а отдельным SELECT, то есть при такой форме файл будет
открываться на каждый поиск. Индексы FAISS в RAM не пострадают — они
прогреваются один раз. Если замер покажет заметную стоимость, payload
кешируется в RAM; это следствие той же схемы, а не её изменение.

### D3 — Слой владения удаляется

`CacheOwnershipCoordinator` защищал от гонки writer'ов. Решение владельца: в
системе один gateway, гонки нет. Writer один и известен — это процесс,
пересоздающий кэш при старте.

| Элемент | Чья задача исчезает |
|---|---|
| `try_claim` / `ClaimResult` | «кто владелец», если владелец один и известен |
| `heartbeat` / TTL 60 с | владелец не может оставить stale claim |
| `generation` | fencing token нужен только при takeover |
| `acquire_write_fence` | mutual exclusion takeover↔producer; takeover невозможен |
| `OwnershipLostError` | потеря ownership невозможна |
| `agent_cache_ownership` (V005) | хранит состояние, которого нет |

Отдельно: heartbeat каждые 30 секунд — это **два запроса в минуту к PG
бессрочно**, в системе, где соединения дефицитны. Удаление координатора
возвращает этот расход в бюджет.

`CacheAccessMode` **сохраняется**: стадии сборки нужен `READ_WRITE`. Он
переезжает в `lib/services/cache_provider.py` — рядом с `CacheProvider`,
режим которого описывает, и потому что это свойство доступа, а не
распределённое владение.

### D4 — Мутация и так отделена от чтения

Проверено: `CacheProvider` — только чтение (`is_ready`, `preload_indexes`,
`search_vector`, `query_sql`, `explain`, `get_schema`, `close`). Мутация
объявлена в отдельной роли `CacheIngestion` (`upsert_records`,
`replace_records`, `ensure_schema`), а `CacheStore` наследует обе. Навыки
видят `CacheProvider`, сборщик держит `CacheStore`.

То есть «кэш используется навыками только на чтение» — уже структурное
свойство, а не соглашение. Переделывать нечего.

### D5 — Слотов пула становится больше, а не меньше

| | до | после |
|---|---|---|
| постоянно занятых слотов пула кэшем | 1 (sync) + периодический (heartbeat) | **0** |
| слотов на время загрузки при старте | — | 1, ограниченно по времени |
| запросов в PG в фоне | 2/мин (heartbeat) навсегда | **0** |

### D6 — Порядок старта фиксируется явно

Загрузка выполняется **в composition root** (`ApplicationContext.create()`,
`_init_cache_runtime`), а не в `start()`: пул и валидация схемы поднимаются
там же, а провайдер обязан существовать до `start()` — иначе прогреву нечего
читать.

```
ApplicationContext.create()
  1. пул PG + валидация схемы
  2. СБОРКА:  open(READ_WRITE) → выгрузка → close()   ← единственная запись
  3. ОТКРЫТИЕ:  open(READ_ONLY) → провайдер живёт весь процесс
ApplicationContext.start()
  4. прогрев FAISS в RAM
  5. проверка подписей и состава, признак времени загрузки
  6. READY
```

Шаг 2 требует доступного PostgreSQL. При недоступности кэш остаётся пустым,
`CacheLoadError` поднимается наружу, а потребитель получает явную ошибку
отсутствия данных — осознанный размен в пользу ясности перед устаревшими
числами. Навык без PG неработоспособен в любом случае.

### D7 — Число потоков загрузки ограничено размером пула

Прежний код поднимал `max_workers = min(len(tables), 8)` потоков, каждый из
которых брал слот **общего** пула. При `max_conn = 4` восемь потоков дрались за
четыре соединения — система, чьё назначение — экономить соединения, расходовала
их сама.

Теперь `max_workers` берётся из `channels.postgres.pool.max_conn`: ограничение
выводится из фактического размера бюджета, а не из числа таблиц. Дефицит
становится видимым в коде и в конфигурации.

### D8 — Спека `logging-db` не меняется

Ни одного требования к ней этот change не трогает. Прежняя спека вносила
`MODIFIED` в «Single writer invariant» и «Uniform logging behavior» ради
буфера; с отменой буфера эти изменения снимаются.

## Goals / Non-Goals

**Goals**

1. Чтения навыков не проходят через пул PostgreSQL.
2. Кэш не занимает слот пула в рабочем режиме.
3. Свежесть обеспечена снимком, а не дельтами.
4. Один путь записи, один механизм сборки, ноль дублирования.
5. **Сокращение кода** относительно текущего дерева.

**Non-Goals**

- Не изменяются `DbLoggingService` и журналирование.
- Не появляется локальный кэш данных ядра.
- Не меняются аналитика, векторные индексы, `history_search`,
  `legal_summarizer`, схема доменных таблиц PG.
- Не удаляется DuckDB.
- Не вводится механизм координации нескольких процессов.

## Risks

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Открытие файла на каждый `query_sql` дороже постоянного соединения | средняя | низкое | измеряется до фиксации фазы; при существенной разнице — payload в RAM |
| Снимок устаревает в течение работы процесса | по определению | среднее | время снимка публикуется **одним** каналом — `cache_load_done.payload.loaded_at` журнала `agent_gateway_logs`; перезапуск процесса обновляет |
| PG недоступен на старте — кэш пуст | низкая | среднее | явная ошибка вместо устаревших данных; состав в health-summary |
| Двойной enum `CacheAccessMode` при неполном удалении `cache_ownership.py` | уже наблюдалось | **высокое** | READ_ONLY-защита молча перестаёт срабатывать, тесты падают косвенно; лечится удалением файла, проверяется `grep` |
| Ошибка при удалении `V005` ломает чистую БД | низкая | среднее | отдельная задача проверяет `tools/migrate.py` на БД без V005 |
| Гонка за файл при ручной пересборке во время работы процесса | низкая | низкое | файл не удерживается, окно узкое; не обрабатывается по решению владельца |

## Baseline (задача 2.1)

### Измерено в этом окружении

| Величина | Значение | Как получено |
|---|---|---|
| Пул соединений PostgreSQL | `min_conn=1`, **`max_conn=4`**, `pool_timeout=5.0` | `lib.utils.db.get_stats()` — единственный источник, подтверждает исходную постановку (кэш экономит 4 слота на весь процесс) |
| Плата за открытие файла на операцию | `query_sql` ≈ **14.5 мс** против ≈ 0.257 мс на постоянном соединении | замер на реальном DuckDB 1.5.4 |
| Запросов на один запуск навыка | ≈ **2** (`load_all` одним + один скрипт) | разбор пути `predefined.run()` |
| Итоговая разница на запуск | ≈ **15 мс** | 2 × 14.5 мс минус выигрыш на кэше |
| Блокировка файла | writer'а — да, читателей — нет (см. D2) | два реальных процесса |

Разница в 15 мс на запуск — не аргумент «за» или «против» варианта Б.
Решает смысл: после сборки удерживать нечего и незачем, а требование
«файл физически не занят» выполняется буквально, а не «не мешает читателям».

### Снято на живой базе (2026-09-30, PostgreSQL 13.22, DuckDB 1.5.4)

DSN: `postgresql://…@localhost:5432/postgres`. Профиль `prod`.

**Загрузка** (путь composition root: `_auto_register_skills` →
`_register_infra_resources` → `CacheLoadService.load()`):

| Величина | Значение |
|---|---|
| Таблиц в снимке | **6** (4 × `oarb.*`, `public.agent_predefined_scripts`, `oarb.audit_vectors` — vector) |
| Длительность загрузки | **6.20 с** на холодную, **1.04 с** на тёплую (первая — с прогревом соединений и кэша планировщика) |
| Ошибок / пропущено таблиц | **0 / 0** |
| Строк загружено | **325** |
| `max_workers` | **4** — ограничен `channels.postgres.pool.max_conn`, не числом таблиц |

**Файл кэша** `C:\Users\<user>\.cache\nanobot\duckdb\cache.duckdb`:

| Величина | Значение |
|---|---|
| Размер | **3 852 КБ** (3 944 448 байт) |
| Таблиц в файле | 7 (6 данных + служебная `__schema_meta`) |
| Строк в файле | **391** |

Состав снимка: `audit_vectors` 120, `violations` 100, `report_items` 79,
`__schema_meta` 66, `audits` 10, `audit_reports` 10,
`agent_predefined_scripts` 6. Сумма PG и файла совпадает — снимок полон.

**Слоты пула — Goal 2 подтверждён:**

| Момент | Занято |
|---|---|
| До загрузки | **0 / 4** |
| После загрузки (writer закрыт) | 2 / 4 — это тёплые воркеры пула, не удержание загрузчика |
| Чтение кэша: до 20 × `query_sql` | **0 / 4** |
| Чтение кэша: после | **0 / 4** |

Ключевой результат: **чтение кэша в рабочем режиме не занимает ни одного слота
пула.** Слоты, занятые после старта, — свойство ленивого пула (он держит
соединения тёплыми), а не загрузчика: загрузчик завершился и слоты вернулись
в пул. Оговорка к комментарию в коде («слот занимается только на время вызова
и освобождается сразу после»): он верен на уровне задач, но буквально слоты
остаются занятыми соединениями пула — `connected_workers` после загрузки 2,
а не 0.

**Плата за форму чтения (замер на живой базе):** `query_sql` — **13.9 мс** на
операцию при открытии соединения на время вызова. Совпадает с более ранним
замером (14.5 мс) и подтверждает оценку ≈ 15 мс на запуск навыка.

## Миграция

Данные не конвертируются: кэш производен от PG. Окно недоступности кэша равно
нынешнему времени первичной загрузки, то есть не увеличивается.

Миграция БД — обратная: файл `sql/migrations/V005__create_agent_cache_ownership.sql`
удаляется. Для уже применённых баз таблица остаётся мёртвой; для чистых бав
она не создаётся.
