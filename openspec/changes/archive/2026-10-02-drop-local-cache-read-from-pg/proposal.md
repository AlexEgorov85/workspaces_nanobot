# Кэш навыков — снимок на момент загрузки, чтение без удержания файла

## Why

Локальный кэш существует **не ради скорости запросов**, а ради экономии
соединений PostgreSQL. Это определяет всё остальное.

### Пул соединений — жёсткий бюджет

`workspace/utils/db.py` + `project.json::channels.postgres.pool`:

```jsonc
"pool": { "min_conn": 1, "max_conn": 4, "pool_timeout": 5.0 }
```

**Четыре слота на весь процесс**, и их делят все сервисы ядра: канал
Postgres, аренда задач, логирование, сессии, синхронизация, `Streamlit`.
Навыкам, которым нужны аналитические запросы к `oarb.*` (~100 000 строк) и
vector search, в этом бюджете места не оставалось.

### Кэшовая подсистема сегодня отнимает этот бюджет себе

| Кто | Как ходит в PG | Сколько держит |
|---|---|---|
| `PgDuckDbSyncService` | через общий `utils.db` | **постоянно**: `_ensure_connected()` один раз, соединение живёт до shutdown |
| `CacheOwnershipCoordinator` | `from workspace.utils.db import execute, transaction` | транзакция `try_claim` на каждом старте + heartbeat каждые 30 сек |

Итого кэшовая машинерия постоянно занимает один слот целиком и ещё один
периодически — **до половины пула**, из-за чего навыкам достаётся меньше, чем
нужно. Обслуживает система, которая должна экономить соединения, и сама эти
соединения расходует.

### Что отсюда следует

Кэш — это **прибор экономии соединений для навыков на чтение**. Отсюда три
требования, которые и определяют архитектуру:

1. Навыки читают из кэша и **не ходят в PG** за этими данными.
2. Кэш не должен занимать слот пула постоянно.
3. Чем меньше у кэша режимов и путей записи, тем меньше он расходует.

### Перегрузка 1 — два кэша вместо одного

Предыдущая спека `split-core-and-skills-cache` вводила ещё и **буфер записи
журнала** в локальный кэш. Он не нужен: `DbLoggingService` уже пишет прямо в
PostgreSQL и не теряет события при недоступности — он их отбрасывает и
увеличивает счётчик `failed` (`db_logging_service.py:817-819, 945-948`).
`history_search` тоже уже читает `agent_gateway_logs` из PG
(`workspace/tools/history_search_tool.py:383-388`). Локальная копия данных
ядра не ускоряет ничего и не защищает от того, что уже защищено: без PG агент
неработоспособен вовсе.

### Перегрузка 2 — подсистема выросла на 709 строк ради нескольких writer'ов

Сравнение с тегом `v2.5.3`:

| файл | v2.5.3 | сейчас | Δ |
|---|---|---|---|
| `cache_ownership.py` | **0** | 438 | **+438** |
| `cache_provider.py` | 113 | 425 | +312 |
| `pg_duckdb_sync_service.py` | 718 | 957 | +239 |
| `duckdb_cache_store.py` | 1195 | 1390 | +195 |
| остальные | — | — | +85 |
| **ИТОГО** | **3665** | **4374** | **+709** |

`CacheOwnershipCoordinator` в v2.5.3 не существовал. Он решает одну задачу:
сколько процессов одновременно пишут в файл кэша. Решение владельца: в
системе один gateway, гонки за файл не возникает. Writer у кэша один и
известен — это процесс, который пересоздаёт кэш при старте.

Координатор при этом heartbeat'ит каждые 30 секунд, то есть **сам является
постоянным потребителем того самого дефицитного ресурса**, ради экономии
которого кэш и существует.

## What Changes

- **Кэш — снимок.** При старте процесса выполняется полная загрузка всего,
  что есть в PostgreSQL в этот момент. Дельты нет, фонового цикла нет,
  `poll_interval_sec` и режима догоняющих изменений больше нет. Свежесть
  определяется временем загрузки и ничем больше.
- **Процесс не держит файл.** Чтение открывает файл на время операции и
  закрывает сразу после. Между запросами процесс файла не касается.
- **Один путь записи.** Полная загрузка. `upsert_records` (доли),
  `replace_records` (замена), два триггера «новые записи» / «замена» и
  `_poll_changes` упраздняются; остаётся одна операция сборки.
- **Один механизм сборки.** Дублирующаяся привязка колбэков в `gateway.py:162`
  и `benchmarks/runner.py:620` (дублирует `application_context`) убирается.
- **Слой владения удаляется:** `lib/services/cache_ownership.py`,
  `sql/migrations/V005__create_agent_cache_ownership.sql`, fencing-обёртки,
  claim в `application_context`. Тип `CacheAccessMode` **сохраняется** и
  переезжает в `lib/services/cache_provider.py` — он нужен стадии сборки.
- **Кэш данных ядра не создаётся.** `DbLoggingService` не меняется.
- **Слот пула освобождается.** Кэш занимает слот только на время загрузки при
  старте; в рабочем режиме — ноль.

## Capabilities

- `data/cache-provider` — **REMOVED**: `CacheOwnershipCoordinator как
  абстрагированный ownership`. **MODIFIED**: `локальный ext4 storage`,
  `PostgreSQL — источник истины`, `CacheAccessMode и двухуровневая защита`,
  `Storage implementation isolation`, `CacheProvider как интерфейс без
  конкретной СУБД`. **ADDED**: снимок на момент загрузки, чтение без удержания
  файла, отсутствие данных ядра, экономия соединений пула как назначение кэша,
  единственность определения `CacheAccessMode`.
- `runtime/entrypoints` — **REMOVED**: `CacheOwnershipCoordinator MUST
  определять режим cache ДО открытия`, `Ownership contract — atomic claim +
  real fencing через advisory lock`. **MODIFIED**: `CacheProvider API с
  явным mode + layered architecture`, `CacheSyncService для синхронизации
  данных` (постоянная служба заменена разовой синхронной загрузкой).
- `data/vector-indexes` — MODIFIED: файл открывается на время операции.
- `logging-db` — **дельт нет**: `DbLoggingService` не меняется.

- **Затрагивается 45 файлов** (531 вхождение по 9 паттернам), из них живого

- **Не затрагивается:** `logging-db`, `history_search`, `legal_summarizer`,

## Out of Scope

- **Не** вводится замена координатору (временный файл + `os.replace`,
  advisory-lock): гонки за файл не обрабатываются по решению владельца.
- **Не** отменяется `cache-architecture-alignment` целиком — пересматриваются
  только его пункты про владение и данные ядра.
- **Не** меняется аналитика и векторные индексы, кроме момента открытия файла.
- **Не** трогается PostgreSQL-контур доменных данных.
- **Известная неточность имени:** каталог change'а —
  `drop-local-cache-read-from-pg`, что описывает только часть решения.
  Переименование выполняется владельцем вручную: автоудаление заблокировано
  политикой среды.
