      не в stdout.** Механизм наследования определён фактом, а не выбором:
      на Windows `pass_fds` не поддерживается, а унаследованный handle не
      становится номером дескриптора в CRT ребёнка — `os.write(N)` в ребёнке
      даёт `EBADF` (проверено на этой машине и для файлового дескриптора, и
      для `os.pipe()`, с `close_fds=False` и без). Единственные слоты, которые
      Windows наследует как дескриптор, — 0/1/2, а на http-ветке stdin ничего
      не несёт (протокола на нём нет). Поэтому канал — **слот `stdin`**, и
      блок объявляет `transport.notify_fd = 0`. Тот же приём работает на POSIX
      тем же способом, то есть механизм один, а не ветка на ветку. Следствие
      для объявления: `notify_fd` — не ключ `config.json`, а номер, который
      агент открывает и подставляет сам при подъёме (см. блокер 4.1).

      которых stdout и есть продукт — `servers/enterprise/server.py` нет.
      Добавлять его туда нельзя: ослабится страж целиком.
      Проверить, что страж зелёный после печати (D14).

## Ф4. Порт: запрос, а не объявление (D3, Ф0.1)

- [ ] 4.1 **БЛОКЕР: `config.json` и `lib/services/agent_settings.py` не в
      моём владении.** Клиент читает `enterprise_mcp.transport.{mode,port,bind}`
      (внутри раздела: корневой ключ в `config.json` схема нанобота отвергает,
      а `AGENT_SECTIONS` закрыт и в `gateway.agent.*` его не объявить).
      Но `AGENT_BLOCK_PATHS` в `lib/services/agent_settings.py` читает
      `("transport","mode")` и то же для `bind`/`port`/`notify_fd` — то есть
      **корень**, которого в `config.json` быть не может. Пока это так, блок
      уходит в платформу без четырёх ключей, и http-ветка не включается.
      **Решение однострочное:** заменить четыре пути
      `("transport", …)` на `("enterprise_mcp", "transport", …)`.
      Второе, отдельное: `transport.notify_fd` не может быть ключом `config.json` —
      это номер, который агент открывает сам (`0`, слот `stdin`; см. 1.8),
      и значение обязано вычисляться при подъёме, а не объявляться.
      Исходный пункт: объявить в `config.json → gateway.agent.enterprise_mcp` ключи
      `transport` и `port` (значение по умолчанию `0`) и `bind` (loopback).
      Ключа порта в `profiles/<mode>.jsonc` **не** будет: оверлей — закрытый
      список из пяти ключей, все пять имена таблиц, посторонний ключ
      отвергается с `ConfigurationError` (`config.py:513-524`), а для `prod`
      оверлей не применяется вовсе (`config.py:697-698`).
- [ ] 4.2 Отдельной строкой в change: порт не ключ профиля, уникальность
      нужна между живыми процессами, а не между контурами (D3). Второй процесс
      одного контура после change не конфликтует нигде.
- [x] 4.3 Закреплённый порт (`port: N`) — единственный случай с проверкой
      занятости и отказом по PID. Отдельным сценарием приёмки.

## Ф6. Починка проверки порта (D4)

> **Границы объёма.** Оба дефекта существуют независимо от HTTP. Linux-ветка
> — **часть этого change**: новая проверка копирует механизм, а копировать
> одноплатформенный дефект хуже, чем его починить. Переформулировка
> сообщения — **сопутствующая правка** здесь же: текст придётся менять, когда
> проверка начнёт срабатывать чаще, и менять его задним числом дороже.

- [x] 6.1 Ветка поиска PID для Linux; на Windows поведение прежнее.
      **Проверено по коду, на этой машине (Windows) НЕ проверено.** Реализация
      одна на обе ОС и живёт у владельца (`find_listener_pid` в клиенте);
      `gateway._find_listener_pid` делегирует ей, второй копии нет. Linux-ветка
      читает `/proc/net/tcp{,6}` (состояние `0A`, локальный порт) и ищет inode
      в `/proc/<pid>/fd` — без `ss` и `lsof`, которых нет в минимальных
      образах. Windows-ветка (`netstat -ano -p TCP`) и её парсер перенесены без
      изменения поведения, это видно по проходящим тестам.
      Ветка Linux закрыта стражем по поддельному `/proc`
      (`TestPlatformPortCheck::test_linux_finds_listener_pid_by_proc`) — это
      проверка разбора, а не поведения ОС Linux.
- [x] 6.2 Подсказка по устранению соответствует платформе; `taskkill` MUST NOT
      упоминаться на Linux. POSIX-ветка названа `kill <pid>`, Windows —
      `taskkill /PID <pid> /F`; при неизвестном держателе подсказка называет оба
      средства поиска и не утверждает ни одного. Проверяется на этой машине
      вызовом с явным `posix=` — сама ветка ОС здесь не воспроизводится.
- [x] 6.3 Формулировка различает «порт держит живой процесс» и «порт держит
      неизвестный процесс». Текст «остался висеть предыдущий процесс» для
      случая живого второго gateway снимается — и в отказе платформы, и в
      отказе порта канала в gateway (один текст на оба, второй писал свой).
- [ ] 6.4 **Проверить окно глазами.** Проверка «процесс запустился, файл
      непустой» тут недостаточна: тот же класс дефекта уже стоил пустого окна
      зрителя. Снимок экрана и прочтение — часть приёмки, а не отладки.
