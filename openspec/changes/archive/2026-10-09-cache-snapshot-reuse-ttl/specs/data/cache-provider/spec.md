## ADDED Requirements

### Requirement: Свежесть снапшота `cache.duckdb` MUST определяться по `mtime` и настраиваться TTL

Gateway MUST решать, переиспользовать ли снапшот `cache.duckdb`, по времени
жизни `gateway.cache.reuse_ttl_hours` (float, дефолт `23.0`), считая возраст
по **`mtime`** файла — то есть по моменту последней успешной публикации
(`publish()` выполняет `os.replace` свежего файла поверх старого).

Дата создания файла MUST NOT использоваться как признак свежести: на POSIX
это `st_ctime`, меняющийся при любой правке метаданных, а в Windows семантика
другая — «момент создания» не равен «моменту последней публикации данных».

Решение MUST вычисляться чистой функцией без обращений к БД и DuckDB (не
более одного `stat`), чтобы оно проверялось тестом без поднятия окружения.
Пока снимок **не** протух, gateway MUST NOT удалять снапшот (включая
осиротевший `<snapshot>.tmp`) и MUST пропускать фазу загрузки данных.
П значение `0` gateway MUST пересоздавать снапшот при каждом старте — это
безопасный режим, полностью воспроизводящий прежнее поведение.

#### Scenario: свежий снапшот переиспользуется

- **WHEN** снапшот существует, его `mtime` не старше TTL, и
  `gateway.cache.reuse_ttl_hours > 0`
- **THEN** решение MUST иметь `reuse=True` и `reason="fresh"`
- **AND** gateway MUST NOT удалять файл снапшота
- **AND** MUST NOT перечитывать таблицы из PostgreSQL

#### Scenario: протухший снапшот пересоздаётся

- **WHEN** `mtime` снапшота старше TTL
- **THEN** решение MUST иметь `reuse=False` и `reason="stale"`
- **AND** gateway MUST удалить снапшот и осиротевший `<snapshot>.tmp`
- **AND** MUST загрузить данные из PostgreSQL заново

#### Scenario: `reuse_ttl_hours=0` — всегда пересоздавать

- **WHEN** `gateway.cache.reuse_ttl_hours=0`, даже при только что
  опубликованном снапшоте
- **THEN** решение MUST иметь `reuse=False` и `reason="ttl_disabled"`
- **AND** возраст снапшота MUST оставаться известным (`age_sec != None`),
  чтобы причина отказа была различима в логе

#### Scenario: снапшота нет

- **WHEN** путь снапшота не существует или недоступен для `stat`
- **THEN** решение MUST иметь `reuse=False` и `reason="snapshot_missing"`
- **AND** `age_sec` MUST быть `None` — возраст неизвестен

#### Scenario: некорректное значение настройки не ломает старт

- **WHEN** `gateway.cache.reuse_ttl_hours` нечитаем (не число) или
  отрицательно
- **THEN** gateway MUST трактовать это как `0` (безопасный дефолт)
- **AND** MUST записать предупреждение
- **AND** MUST NOT прерывать старт

### Requirement: Переиспользование снапшота MUST NOT приводить к молчаливой работе на пустом кэше

Переиспользовать снапшот допустимо **только** если `CacheProvider` реально
его открыл: решение о свежести файла MUST дополняться проверкой `is_ready()`.
Иначе «использовать как есть» превращается в процесс, который жив, принимает
вопросы и отвечает, но не имеет данных — такой отказ обнаруживается только по
косвенным признакам.

Путь переиспользования MUST NOT изменять `mtime` файла. Иначе каждый рестарт
«омолаживал» бы кэш, срок TTL никогда бы не истекал, и данные из
PostgreSQL не обновлялись бы никогда — тихая заморозка данных вместо
политики свежести.

#### Scenario: файл свежий, но store его не открыл

- **WHEN** решение о свежести дало `reuse=True`, но `is_ready()` вернул
  `False`
- **THEN** gateway MUST принудительно пересоздать снапшот
- **AND** MUST записать предупреждение с указанием возраста снапшота
- **AND** MUST загрузить данные из PostgreSQL

#### Scenario: путь переиспользования не пишет в снапшот

- **WHEN** gateway стартует со свежим снапшотом и пропускает загрузку данных
- **THEN** `mtime` файла снапшота MUST остаться неизменным

### Requirement: Пропуск фазы загрузки данных MUST быть явным решением, а не сменой режима по умолчанию

Решение «не грузить данные» MUST передаваться в runtime явным флагом
`ApplicationContext.skip_data_load`, а не выводиться внутри слоёв, которые о
нём не знают. При выставленном флаге синхронизатор MUST NOT стартовать
**вовсе**: запуск без `initial_load` не является пропуском, потому что
poll-цикл с пустым `_last_sync` на первом же такте выполняет полный
`_fetch_all`. Дефолтом флаг MUST быть `False` — прежнее поведение.

Гейт готовности MUST быть удовлетворён тем же вызывающим, который принял
решение о пропуске. `StartupGate` ждёт сигнал готовности данных **без
таймаутов**, поэтому ожидание безопасно только если сигнал поставлен
явно.

#### Scenario: флаг выставлен — синхронизатор не стартует

- **WHEN** `ApplicationContext.skip_data_load=True`
- **THEN** `ApplicationContext.start()` MUST NOT вызывать
  `PgDuckDbSyncService.start()`
- **AND** MUST NOT регистрировать незапущенный сервис в shutdown

#### Scenario: флаг не выставлен — прежнее поведение

- **WHEN** `ApplicationContext.skip_data_load=False` (дефолт)
- **THEN** `ApplicationContext.start()` MUST вызвать
  `PgDuckDbSyncService.start(initial_load=True)`

#### Scenario: сигнал готовности при пропуске ставит gateway, а не синк

- **WHEN** gateway переиспользовал свежий снапшот и пропустил загрузку
- **THEN** `ctx.cache_ready_signal` MUST быть установлен до старта каналов
- **AND** фаза подготовки MUST завершиться без ожидания таймаута

### Requirement: Решение о пропуске MUST быть наблюдаемым в логе

Gateway MUST писать ровно одну строку решения со снапшотом (путь, возраст,
TTL, причина, признак переиспользования), чтобы устаревшие данные
диагностировались по логу, а не по жалобам пользователя. Возраст MUST
выводиться в человекочитаемом виде.

#### Scenario: строка решения в логе

- **WHEN** gateway стартует
- **THEN** MUST быть записана строка `cache snapshot: path=… age=… ttl=… decision=… reuse=…`
- **AND** формат подстановки значений MUST соответствовать используемому в
  проекте логгеру (loguru, braces), а не `%s`
