# Порядок старта: DuckDB → векторы → каналы

## Что меняем

Gateway поднимает три тяжёлые вещи независимо: DuckDB-кэш (in-memory mirror
PG), FAISS-индексы (векторы) и каналы (Postgres/Redis/WebSocket). Сейчас
порядок «как получится»: `PgDuckDbSyncService` тянет initial_load в фоновом
треде, preload векторов создаётся фоновой задачей, и тут же стартует
`channels.start_all()`.

Следствие: первые вопросы из очереди уходят агенту **до** сборки
FAISS-индексов. Агент отвечает без эмбеддингов — заметно хуже обычного, и
это выглядит как «модель сегодня дурит», а не как «данные ещё не приехали».

## Решение

Вводим явную фазу подготовки **до** рабочего цикла:

```
ctx.start()                     # фоновые сервисы, sync-тред
└─ _run_startup_preparation()   # фаза подготовки (свой event loop)
   ├─ StartupGate.wait_for_cache()   # сигнал «PG→DuckDB + publish снапшота»
   └─ StartupGate.load_vectors()     # FAISS-индексы собраны
GatewayRunner.run_forever()     # рабочий цикл
└─ channels.start_all()         # ТЕПЕРЬ очередь вопросов
```

Ключевые решения:

- **Порядок держится на сигнале, а не на таймауте.** Гейт ждёт именно
  «данные загружены», а не «прошло N секунд». Таймаут здесь означал бы
  *незаметно* стартовать сломанным: процесс жив, отвечает, но без
  векторов. Поэтому в `lib/services/startup_gate.py` нет ни одного
  `wait_for`/`sleep`/`timeout=`, и это зафиксировано тестом-guard'ом
  (AST-проверка вызовов, а не текста).
- **Подготовка вынесена из `GatewayRunner`.** У неё своя семантика отказа
  (fail → exit 2), а runner перезапускает рабочий цикл по backoff и
  повторил бы ту же ошибку в лог по кругу.
- **Сигнал готовности данных выставляется после `publish()`.** Иначе
  «данные готовы» означало бы «данные только начали публиковаться».
- **`ThreadSafeSignal` вместо `asyncio.Event`.** Сигнал ставит worker-тред
  синхронизации, а ждёт его отдельный loop. Наивный `Event.set()` из чужого
  потока loop не будит, а без таймаута ожидание висело бы вечно уже после
  загрузки. Сигнал будит loop через `call_soon_threadsafe` и сам
  привязывает loop в том ожидании, которое его ждёт.
- **Отказ — это ошибка, а не повод ждать дальше.** `on_unavailable`:
  `warn` (дефолт, degraded-старт с предупреждением) | `fail`
  (`StartupGateError` → `FATAL` + `exit 2`, каналы не подняты).
- **Наблюдаемость.** Пока векторы не готовы, readiness-компонент
  `vector_search` отдаёт `DOWN` с фазой гейта; результат подготовки пишется
  событием `startup_vector_preload` в `agent_gateway_logs`.

## Что НЕ меняем

- `PgDuckDbSyncService` — по-прежнему тянет данные в фоне; гейт лишь ждёт
  его первого цикла.
- CLI (`cli_agent.py`) не ждёт ничего: каналов, а значит и очереди
  вопросов, у него нет.
- Таймауты в других местах runtime'а (пул БД, LLM, exec) не трогаем — запрет
  касается только готовности на старте.

## Конфигурация

`project.json::gateway.startup.vector_preload.*` (все ключи опциональны):

| ключ | дефолт | смысл |
|------|--------|-------|
| `enabled` | `true` | `false` — не готовить векторы на старте вовсе |
| `await_ready` | `true` | `false` — старое поведение: индексы в фоне, каналы сразу |
| `on_unavailable` | `warn` | `warn` — degraded-старт; `fail` — exit 2 |
