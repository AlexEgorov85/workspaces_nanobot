## 2. Ключевые решения

### 2.1 Ось декомпозиции — не бизнес-домен

Первая редакция плана нарезала по доменам (`audit-mcp`, `legal-mcp`,
`memory-mcp`, `document-mcp`). Это неверная ось: сервер — не «где живёт бизнес»,
а «что умеет делать агент». Модель выбирает инструмент по способности, а не по
таксономии продуктового портфеля.

Следствия отклонённой схемы:
* `audit_search` и `legal_search` рядом заставляют модель решить «это вопрос
  про аудит или про юридику?» — классификация по имени;
* `history_search` — это read по `agent_gateway_logs`, то есть обычная операция
  чтения, а не отдельная подсистема;
* документы — парсинг, а не capability: у них нет точки выбора у модели.

Правильная ось — **уровень доверия и вариативности**: инфраструктурное ядро
(библиотеки) → capability-серверы по операциям → доменная логика поверх
библиотек, без собственного протокола.

### 2.2 DuckDB удаляется целиком

Векторы уже в PostgreSQL. Цепочка `PG → DuckDB → FAISS` сокращается до
`PG → FAISS`. Следствия:

* `TableRegistry` **не умирает целиком** — у него три живых потребителя не
  про снапшота: `resources_by_label("scripts_registry")` резолвит таблицу
  PostgreSQL для `audit_analyzer`, `register_infra("vector.storage")` регистрирует
  `oarb.audit_vectors`, `tracking_column_for` описывает колонку-маркер. Умирает
  только агрегация имён в список загрузки для `CacheLoadService`.
* `duckdb_query.py` и `cache_provider.py` — **смешанные модули**. `build_faiss_index`,
  `group_vector_hits`, `build_raw_items` — единственный в репозитории код сборки
  FAISS. Извлекаются **до** удаления, иначе `vector-mcp` придётся выводить
  группировку чанков и косинусную нормализацию заново.
* `cache_provider_impl.py` (476) — бо́льшая часть векторная: `get_embedding`,
  `read_embedding_config`, `read_vector_index_config`,
  `compute/verify_index_signature`, `list_runtime_vector_indexes`. Умирает
  только `_capture_schema_meta`. Реальная цифра смерти — ~2 600, не 3 600.

### 2.3 `vector-mcp` без модели эмбеддингов

`gateway.vector.index.storage_table` = `oarb.audit_vectors` — эмбеддинги уже
посчитаны и лежат в PostgreSQL. `vector-mcp` только загружает их в FAISS.
Эмбеддинги считает отдельная задача (`tools/build_vectors.py`), которая пишет
в PG. Это снимает зависимость платформы от модели.

Персиста на диске нет, FAISS пересобирается на каждом старте процесса.

### 2.4 `data-mcp` — перенос, а не постройка

`workspace/utils/db.py` уже реализует схему «выделенное количество соединений +
очередь». Он **не владеет** моделью эмбеддингов, не знает про домены и не
импортирует `nanobot`. Переносится как есть в `libs/data`; сверху — тонкая
MCP-поверхность.

Модель угроз и границы записи:
* **сервер** умеет писать;
* **поверхность агента** — read-only инструменты плюс именованные операции
  записи, которые сервер определяет сам (`log_event`, `upsert_records`).
  Произвольный write-SQL модели не выдаётся — иначе она может вызвать
  `DROP TABLE`, а `lib/utils/sql_safety.py` с AST-политикой read-only перестанет
  иметь смысл.

`sql_safety.py` зависит только от stdlib: `sqlglot` подключается лениво через
`_get_exp()`, при отсутствии деградирует до `_regex_fallback_checks`. Жёсткой
зависимости на `sqlglot` у `data-mcp` нет.

### 2.5 Логирование не блокирует ход

```
хук → локальный буфер (ограничен) → батчевый flush → data-mcp: log_event
```

1. Недоступность `data-mcp` теряет логи, но не ходы. Переполнение — дроп, не
   backpressure.
2. Петля не замыкается: `data-mcp` пишет о своих сбоях локально (файл/stderr),
   иначе отказ самого `data-mcp` сделает недиагностируемым ровно то, что сломалось.
3. `db_logging_bus.py` **остаётся в агенте** — он знает форму сообщений
   `InboundMessage`/`OutboundMessage`. Уезжает только писатель.
4. Масштаб, который нельзя недооценить: `db_logging_service.py` (1142) — не
   лист, а хребет событий агента; на него ссылаются 19 файлов `lib/`,
   `runtime_patcher.py` содержит 26 вызовов, `application_context.py` — 38.

### 2.6 Однопроцессный агент

`agent_worker_claims` и протокол аренды удаляются. Замена — опрос с
`FOR UPDATE SKIP LOCKED`. Теряется HA-отказоустойчивость; принимается осознанно.

Побочный вопрос: теряет ли смысл `redis_channel.py` (378) и
`message_exchange.py` (171), чья задача — шерить цикл опроса между каналами.
**Открыто, см. §5.**

## 3. Патчи: хуки вместо monkey-patch

Проверено чтением `nanobot-ai==0.3.5`: 18 методов `AgentHook`, мутабельный
`AgentHookContext` (`messages`, `tool_results`, `error`, `final_content`),
`EventSink` в `AgentTurnHookContext`, `AgentTurnHookFactory`, 23 события.

| # | Патч | Решение |
|---|---|---|
| 10 | `turn_delivery_fail` | `finalize_content` (вызывается в `runner.py` трижды) подменяет текст ошибки на месте — двойной outbound не возникает. `on_error` + `context.error` дают логирование. 6 обязанностей → 2 |
| 2 | `save_turn` | `after_execute_tool` вызывается сразу после `tool.execute()` — раньше, чем upstream усечёт результат в `_save_turn` |
| 7 | `async_save` | `agent.sessions` — наш `PGSessionManager`. Обёртка делается при создании в `session_storage.py` |
| 11 | `session_content_cleanup` | Чистка NUL — забота PostgreSQL; `clean_text.py` уже делает это. Переносится в `PGSessionManager.save` |
| 8 | `session_dir_watch` | Удаляется: гейт выключен, тестов нет |
| 6 | `assemble_outbound` | События: `_final_turn` → `TurnEndEvent`; `_tool_audit` и `media` → публикация из хука через `turn_context.events` |
| 1 | `context_governor` | Выгрузка в файл → хук; остаётся только подстановка ссылки для встроенных tool'ов |
| 9 | `subagent_logging` | Остаётся: `_SubagentHook` конструируется жёстко, фабрики нет |
| 3, 5 | `exec_limits`, `tool_limits` | Остаются: конфига в 0.3.5 нет |
| 4 | `exec_timeout_cap` | Пересмотреть: legal уезжает в MCP |
| 12 | `document_text_threshold` | Уходит с документами |

### Почему `context_governor` частично остаётся

В `nanobot/agent/tools/execution.py`:

```python
result = await tool.execute(**params)
await hook.after_execute_tool(context, tool_call, tool, params, result)
return result, {...}          # возвращается ИСХОДНЫЙ result
```

`after_execute_tool` возвращает `None`, раннер отдаёт `result` без изменений.
Подменить содержимое, попадающее в контекст, через хук нельзя.

Но это **единственное** такое ограничение, и оно касается только подстановки
значения. Всё остальное хук умеет:

| Действие | Чем делается |
|---|---|
| наблюдение вызовов, параметров, результатов, ошибок | любой метод `AgentHook` |
| запись в БД, файлы, счётчики | побочный эффект в хуке |
| публикация события | `await turn_context.events.publish(...)` |
| передача per-turn данных | мутабельные `turn_context.metadata` / `.attributes` |
| подмена финального контента | `finalize_content` (возвращает значение) |
| подмена результата tool'а | **только инструментом или патчем** |

Логирование — частный случай второй и третьей строк и целиком уезжает на хуки
и события, как и предполагалось изначально.

> Правило: проверять не наличие хука, а **может ли он повлиять именно на то,
> что нужно изменить** — эффектом, событием, мутацией `metadata` или
> возвращаемым значением.

### Итог

12 → **4–5**. Шесть заменяются хуками, событиями или собственным классом
(`1` частично, `2`, `6`, `7`, `10`, `11`), один удаляется (`8`), один уходит
по миграции доменов (`12`). В
`docs/architecture/runtime-patcher-inventory.md` введена обязательная
колонка «Условие удаления».

`subagent_logging` — единственный оставшийся патч с **структурным** блокером:
`_SubagentHook` конструируется жёстко, фабрики для subagent'ов нет, то есть
точка вставки отсутствует физически, а не из-за слабости хука.

## 5. Открытые решения

1. **Документы: нативный tool агента или отдельный сервер.** `office_files` —
   skill без кода, он велит агенту импортировать `workspace/utils/office_files.py`.
   Убрав MCP, агент теряет доступ к офисным файлам. Вариант (A): нативный tool,
   и `python-docx`/`openpyxl`/`pypdf` остаются в зависимостях агента. Вариант
   (B): один инструмент на отдельном сервере, агент остаётся лёгким. Это прямое
   столкновение с целью «установка Nanobot не тянет enterprise-стек».
2. **Кто владеет LLM-выходом.** `llm_client.py` (199) + `llm_config.py` (88) —
   287 строк без владельца в новой схеме. Предлагается два независимых клиента:
   агент со своим провайдером для диалога, домены со своим в `libs/llm`.
   Обратный вызов агента через MCP невозможен — это не провайдер инструментов.
3. **Границы `data-mcp`.** Произвольный read-only SQL или только именованные
   операции. Первое проще, второе безопаснее: `ILIKE` по 24 таблицам рано или
   поздно даст стоимость на полкорпуса.
4. **Redis-канал.** Снимает ли однопроцессность смысл `redis_channel.py` и
   `message_exchange.py`.
5. **Переопределение встроенных tool'ов.** Альтернатива патчам `exec_limits` /
   `tool_limits`: свой `Tool`, наследующий `ExecTool`, вместо мутации чужого
   класса. Требует проверки правил реестра.
6. **Кто считает эмбеддинги.** `tools/build_vectors.py` как отдельная задача
   (текущий план) или часть `vector-mcp`.
