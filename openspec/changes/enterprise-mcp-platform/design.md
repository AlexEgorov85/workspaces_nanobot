# Design — enterprise-mcp-platform

## 1. Топология

```
             ┌─────────────────────────────────────────┐
             │     Nanobot 0.3.5  (не изменяется)      │
             ├─────────────────────────────────────────┤
             │LLM · диалог · сессия · сжатие           │
             │встроенные tool'ы · MCP-клиент           │
             └────────────────────┬────────────────────┘
                                  │ MCP
                                  ▼
  ┌───────────────────────────────────────────────────────────────┐
  │               enterprise-mcp   ·   один процесс               │
```

Правило, из которого следует весь рисунок: **у каждого разделяемого ресурса —
один владелец, и всё ходит через него** (§2.8). Capability получают готовый
сервис и описывают операции, а не управление ресурсами. Обход запрещён
архитектурным стражем, а не договорённостью.

## 2. Ключевые решения

### 2.1 Один сервер, а не по одному на домен

Первая редакция плана нарезала по доменам (`audit-mcp`, `legal-mcp`,
`memory-mcp`, `document-mcp`). Это неверная ось: домен — не единица
развёртывания, а единица предметной области.

Вторая редакция резала по операциям (`data-mcp`, `vector-mcp`, `llm-mcp`) и
обосновывала это «уровнем доверия». **Это обоснование не выдержало проверки.**
Граница, которая реально имеет значение, — **агент ↔ enterprise**, и её уже
проводит сам протокол MCP. Разделение на три процесса разбивало наш собственный
код от нашего собственного кода: та же машина, те же учётные данные, тот же
оператор.

Чем именно платили за разделение:

* **Кросс-процессный join невозможен.** `audit_analyzer` — это одновременно
  SQL по `oarb.*` и поиск по FAISS. С двумя серверами это два вызова, и модель
  склеивает результат у себя в голове. В одном процессе пул и индекс живут
  рядом, join выполняется на месте.
* **Один вопрос → N вызовов к N серверам.** Ровно тот антипаттерн, который
  первая редакция уже отвергла: модель вынуждена классифицировать «это аудит
  или вектор?» вместо того, чтобы вызвать одну операцию по способности.
* **Транзакционность.** Запись векторов и запись в тот же PostgreSQL: в одном
  процессе одна транзакция через сервис-владелец пула, в двух серверах — только
  компенсация.
* **Операционная поверхность.** N записей в `mcpServers`, N health-check'ов,
  N конфигов, N точек отказа при старте.

Что разделение действительно покупало — изоляцию тяжёлой загрузки FAISS и
зависшего вызова LLM-провайдера. Обе снимаются внутри процесса: **ленивая
загрузка индекса** (см. §2.3) и очередь с таймаутом на сетевом вызове.

Итог: **один процесс `enterprise-mcp`**, внутри него capability-каталоги.
Домены при этом никуда не делись — они раскладываются по capability
(`capabilities/<name>/`), а не по процессам. Расщепление процесса позже
остаётся возможным конфигурацией загрузчика: это ровно тот случай, ради
которого механизм сделан динамическим.

### 2.2 Снимок остаётся, меняется владелец

Цепочка `PG → DuckDB → FAISS` сохраняется. Меняется то, кто ею владеет:
`duckdb_cache_store.py` и `cache_load_service.py` переезжают из `lib/services/`
в `libs/enterprise_data`, и с этого момента файл снимка — ресурс capability
`data`. Следствия:

* `TableRegistry` **остаётся целиком**, включая агрегацию имён в список загрузки
  для `CacheLoadService`: список по-прежнему нужен, потому что по-прежнему есть снимок.
  Три его потребителя — `resources_by_label("scripts_registry")`, `register_infra("vector.storage")`,
  `tracking_column_for` — не меняются.
* `duckdb_query.py` и `cache_provider.py` — **смешанные модули**, и делятся по границе ролей.
  `build_faiss_index`, `group_vector_hits`, `build_raw_items` — единственный в репозитории код
  сборки FAISS, они уезжают в `libs/vectors`; `run_query`, `explain_query`, `build_schema`,
  `rewrite_duck_sql` остаются во владельце снимка.
* `cache_provider_impl.py` (476) делится тем же способом: `get_embedding`,
  `read_embedding_config`, `read_vector_index_config`,
  `compute/verify_index_signature`, `list_runtime_vector_indexes` — в `libs/vectors`, `_capture_schema_meta` — во владельце снимка.
* Прежняя оценка «~2 600 строк умирают из 3 600» была неверной по построению: из кластера
  вычиталось ровно то, что переезжает. Правильная формулировка —
  **кластер целиком меняет место жительства, ни одна строка не удаляется.**

Ограничения на снимок при этом усиливаются, а не ослабевают: у него ровно один владелец, проверка по коду
«вне владельца нет `duckdb.connect` и `ATTACH`» и запрет на возврат слоя синхронизации.

### 2.3 Векторы: предрассчитаны, но запрос эмбедится

`gateway.vector.index.storage_table` = `oarb.audit_vectors` — векторы
документов уже посчитаны и лежат в PostgreSQL. Capability `vectors` загружает
их в FAISS. Сборку эмбеддингов документов делает отдельная задача
(`tools/build_vectors.py`), которая пишет в PG.

**Но вектор запроса эмбедится в рантайме.** `get_embedding(query)` ходит в
`http://localhost:11434/api/embed` с моделью `mxbai-embed-large:latest`
(1024 измерений), и при недоступности возвращает `None`, а не исключение.
Значит утверждение «модель эмбеддингов платформе не требуется» верно только
наполовину: документы предрассчитаны, запрос — нет. Зависимость от сервиса
эмбеддингов остаётся, и её надо назвать явно, а не обнаружить в проде.

Персиста на диске нет, FAISS пересобирается — **но не на старте процесса.**

Индекс содержит сотни тысяч векторов и собирается десятки секунд. Если
грузить его на старте, `enterprise-mcp` не отвечает всё это время, а в одном
процессе с ним стоят ещё и SQL-операции. Поэтому загрузка **ленивая**: первый
векторный запрос инициирует сборку, последующие используют готовый индекс.
`list_indexes` и `index_stats` при этом отвечают сразу — из конфигурации и
метаданных, без поднятия индекса.

Сборка защищена локом: параллельные запросы ждут один прогрев, а не запускают
сборку каждый. Состояние индекса (`нет` / `собирается` / `готов` / `ошибка`)
наблюдаемо — иначе зависание неотличимо от долгого ответа.

**Ленивый путь уже существует.** `search_vector` сегодня собирает индекс при
первом обращении и кэширует его в `_index_cache`; стартовый прогрев греет тот
же самый словарь. Значит переход на ленивую загрузку — это удаление
прогрева на старте плюс наблюдаемость, а не новая подсистема.

### 2.4 Capability `data` — инфраструктура, а запрос к данным живёт в `audit`

`workspace/utils/db.py` уже реализует схему «выделенное количество соединений +
очередь». Он **не владеет** моделью эмбеддингов, не знает про домены и не
импортирует `nanobot`. Переносится как есть в `libs/enterprise_data`; сверху —
тонкая capability с файлами операций.

**Модель угроз изменилась после того, как решение было записано в первый раз.**
Первая редакция §2.4 исходила из того, что модели нужен произвольный
read-only `SELECT`: мол, это снимает с домена работу по заведению операций под
каждый новый вопрос. Разведка поверхности `audit_analyzer` показала, что
произвольный `SELECT` и контроль исполнения — взаимоисключающие вещи, и
вместе они не работают:

* `validate_sql` проверяет **вид оператора**, но не **имя таблицы**. Проверено:
  `SELECT * FROM some_other_schema.secret_table` и
  `SELECT * FROM public.agent_gateway_logs` проходят без возражений. Белый
  список таблиц существует только как текст в промпте, то есть граница держится
  на честности модели;
* у сгенерированного запроса **нет потолка строк** — `LIMIT` дописывает только
  сборщик зарегистрированных скриптов;
* `sqlglot` подключается лениво, и без него guard деградирует до трёх
  регулярных проверок, пропуская `pg_sleep`, чтение системных каталогов и
  `UPDATE`/`DELETE` после `--`-комментария.

Держать «произвольный SELECT + заявленный контроль» означало держать
несуществующий контроль. Поэтому решение перевернуто: **модель не пишет SQL**,
а получает три входа, и все три ведут внутрь платформы.

| Вход | Кто пишет SQL | Чем ограничен | Capability |
|---|---|---|---|
| `run_script` | реестр `public.agent_predefined_scripts` | шаблон из реестра; вызывающий приносит имя и типизированные значения | `audit` |
| `generate_sql` | LLM внутри сервера | список таблиц в коде, read-only, `EXPLAIN`, потолок строк | `audit` |
| `history_search` | код платформы | жёстко заданный `SELECT`, изоляция из идентичности транспорта | `data` |

Состав поверхности `data` — инфраструктура, без доступа к данным:

| Инструмент | Тип | Назначение |
|---|---|---|
| `log_event` | write | батчевая запись в журнал |
| `schema_check` | read | наличие обязательных таблиц |
| `history_search` | read | поиск по истории с изоляцией |

Состав поверхности `audit` — весь запрос к данным:

| Инструмент | Что делает |
|---|---|
| `list_scripts` | каталог скриптов с полным описанием параметров |
| `run_script` | выполнение известного запроса с типизированными значениями |
| `generate_sql` | построение и выполнение запроса по вопросу на естественном языке |

**Что это стоит.** Три операции вместо одного примитива — это работа: новый
вопрос без подходящего скрипта идёт через LLM и стоит вызова провайдера, а не
локального `SELECT`. Принимается сознательно: контроль того, что и как
выполняется, стоит дороже удобства. Смягчение — качественный few-shot из того
же реестра скриптов, поэтому типовые вопросы чаще попадают в `run_script` и
реже доходят до `generate_sql`.

**Серверный предел стоимости обязателен.** Сегодня его нет: `statement_timeout`
не встречается в репозитории, `psycopg2.connect` не передаёт `options=`, а пул
работает с `autocommit=True`, где `SET LOCAL statement_timeout` — no-op. Вводится
до выдачи `generate_sql` модели: либо на соединении в момент коннекта, либо в
замыкании задания с явным сбросом. Для порождённых LLM запросов предел ниже,
чем для зарегистрированных скриптов.

**`sqlglot` становится обязательной зависимостью платформы.** Раньше отказ от
жёсткой зависимости выглядел безобидно; после введения `generate_sql` это
означало бы, что защита выключается ровно там, где вход недоверенный. Guard
теперь охраняет не пользователя, а вывод LLM — но этот вывод исполняется в
базе, поэтому требование остаётся: сервер не поднимается без `sqlglot`.

**Порядок больше не диктует снимок.** Прежняя редакция требовала перенести
`audit` на PostgreSQL **до** удаления DuckDB: `db_loader` читает реестр через
`CacheProvider`, то есть из снимка, и без переноса `run_script` остался бы без
источника. Снимок остается, `audit` читает его через capability `data` и файл
не открывает, поэтому ограничение снято.

Существующий `query_sql` в `CacheProvider` **переезжает** во владельца снимка вместе с
ним. На поверхности агента операция не появляется: `run_script`
исполняет шаблон из реестра, `generate_sql` — построенный генератором
запрос, и оба проходят через внутренние операции capability `data`.
Граница «модель не пишет SQL» не меняется.

### 2.5 Логирование не блокирует ход

```
хук → локальный буфер (ограничен) → батчевый flush → data: log_event
```

1. Недоступность `enterprise-mcp` теряет логи, но не ходы. Переполнение — дроп,
   не backpressure.
2. Петля не замыкается: сервер пишет о своих сбоях локально (файл/stderr),
   иначе его собственный отказ сделает недиагностируемым ровно то, что
   сломалось.
3. `db_logging_bus.py` **остаётся в агенте** — он знает форму сообщений
   `InboundMessage`/`OutboundMessage`. Уезжает только писатель.
4. Масштаб, который нельзя недооценить: `db_logging_service.py` (1142) — не
   лист, а хребет событий агента; на него ссылаются 19 файлов `lib/`,
   `runtime_patcher.py` содержит 26 вызовов, `application_context.py` — 38.

### 2.6 Однопроцессный агент

`agent_worker_claims` и протокол аренды удаляются. Захват остаётся тем же
одним `UPDATE ... RETURNING` — эксклюзивность даёт внешний
`AND status = 'pending'`. Теряется HA-отказоустойчивость; принимается осознанно.

**Замена на `FOR UPDATE SKIP LOCKED` отменена** (реализовано в фазе 1). Проект
разворачивается на Greenplum 6.5 — ядро PostgreSQL 9.4, где `SKIP LOCKED`
(появился в PostgreSQL 9.5) недоступен, а Greenplum при `SELECT ... FOR UPDATE`
берёт блокировку уровня **таблицы** и заблокировал бы всех читателей и писателей
`agent_conversation_messages`. Корректности он и не нужен: он даёт только
снижение задержки при конкурентных захватах.

Побочный вопрос: теряет ли смысл `redis_channel.py` (378) и
`message_exchange.py` (171), чья задача — шерить цикл опроса между каналами.
**Открыто, см. §5.**

### 2.7 Динамический реестр инструментов

`server.py` не знает список инструментов заранее. Он поднимает реестр, отдаёт
его MCP-клиенту и завершает работу.

```
capabilities/*/tools/*.py
   ↓ discovery      (рекурсивный обход capabilities/)
   ↓ import module
   ↓ create_tool(container)
   ↓ validate
   ↓ registry.register(ToolDefinition)
   ↓ MCP — готово
```

Инструмент не регистрирует себя сам: он возвращает описание, а превращать
его в MCP-инструмент умеет реестр. Это и делает `server.py` нечувствительным
к составу.

```python
# servers/enterprise/capabilities/data/tools/history_search.py
def create_tool(container):
    def history_search(query: str, limit: int = 20) -> str:
        return container.data.history_search(query, limit)

    return ToolDefinition(
        name="history_search",
        description="Поиск по журналу agent_gateway_logs",
        handler=history_search,
        category="read",
        version="1.0",
        enabled=True,
        tags=("logs", "read"),
        permissions=("read",),
    )
```

`category` — имя capability, из которой пришёл файл. Имена инструментов
остаются плоскими и уникальными в пределах сервера: MCP-клиент Nanobot и так
приклеивает префикс `mcp_enterprise_`, а namespace внутри него только путает
модель.

`enabled` / `tags` / `permissions` на загрузку не влияют — это задел на
отключение инструмента без удаления файла и на группировку discovery-описаний.

**Валидация при загрузке:** импорт модуля, наличие `create_tool`, тип
`ToolDefinition`, непустые `name` и `description`, уникальность `name` в
пределах сервера, callable `handler`, валидная схема аргументов. Любое
нарушение — **startup FAILED целиком** с путём до файла и `name`.

> Полузагруженный сервер хуже мёртвого. Агент увидит capability в discovery
> и откажет на реальном запросе пользователя, уже без следа до причины.

**Hot reload не делается.** Реестр иммутабелен в пределах процесса: добавил
файл → перезапустил сервер. Горячая перерегистрация тянет смену схемы уже
опубликованного инструмента, удаление инструмента, состояние старого handler'а
и частично загруженные наборы. Задачи, которой это решает, у платформы нет.

**Граница безопасности.** Автообнаружение — не доверие. Каталог `capabilities/`
доверенный: туда попадает только код репозитория, и всё исполняется с правами
процесса. Манифест `tool.json` + `entrypoint` вместо угадывания точки входа —
правильное следующее усложнение, когда инструментов станет много; он меняет
loader, а не registry, и не требует переписывания инструментов.

**Capability самодостаточна** — `capabilities/<name>/{skill/SKILL.md,
tools/*.py, service/}`. Skill и инструменты параллельны и оба ведут к сервису,
но не вложены друг в друга: skill читает агент своим механизмом Skills, у
инструмента другой жизненный цикл и другой транспорт.

**Capability ≠ процесс.** Именно этот разрыв делает возможным и разделение
процессов позже: если одна capability потребует изоляции (тяжёлая память,
жёсткий SLA), она переезжает в свой процесс **конфигурацией загрузчика** —
это меняет список каталогов, а не код операций. Сейчас это не нужно
(обоснование — §2.1), но цена отказа оставить такую возможность равна нулю.

**Что это отменяет на стороне агента.** `project_tool_loader` и перечисление
tool'ов в `ApplicationContext` — тот же механизм, но вручную и внутри агента.
После перехода состав enterprise-инструментов задаётся файлами в
`mcp-platform`, и агент о них не знает.

### 2.8 Один владелец на разделяемый ресурс

Правило, из которого следует вся остальная структура: **у каждого дорогого или
разделяемого ресурса — ровно один владелец, и всё ходит через него.**

| Ресурс | Владелец | Что запрещено |
|---|---|---|
| Пул и очередь PostgreSQL | `libs/enterprise_data` | capability создаёт свой пул, свою очередь или открывает соединение напрямую |
| Векторный индекс, кэш индексов, embedding-клиент | `libs/vector_index` | capability собирает свой FAISS или ходит в эмбеддинги сам |
| LLM-клиент | `libs/llm` | capability поднимает свой HTTP-клиент и свои настройки попыток |
| Модель эмбеддингов, загрузка индексов | владелец capability `vectors` | вторая точка вызова |
| Порядок шагов исполнения, таймаут, нормализация ошибок | `libs/enterprise_common/execution` | операция делает это сама в своём файле (§2.9) |
| Файлы сессии, артефакты | `libs/enterprise_common/session` | операция пишет файлы сама (§2.9) |
| Контракт и словарь событий | `libs/enterprise_common/eventing` | параллельный формат событий в MCP или в агенте (§2.10) |

Capability получает **готовый сервис** из контейнера и вызывает его. Её файлы
описывают операции, а не управление ресурсами. Именно поэтому в примере §2.7
`create_tool` обращается к `container.data`, а не открывает соединение.

Это не стиль, а требование корректности. Три следствия:

* **Пул.** Второй пул — это удвоенное число соединений против той же базы и
  удвоенный расход на фоне, который система платит за обслуживание runtime.
  Инвентаризация уже показывает, что в проекте такой пул один и его
  размножение запрещено тестом.
* **Индекс.** Второй FAISS — это вторая копия сотен тысяч векторов в памяти и
  второй десяток секунд сборки при первом запросе. Кэш индексов общий и
  принадлежит владельцу.
* **Очередь.** Одна очередь означает, что slow и fast работа конкурируют за
  одни и те же воркеры. Это обсуждается отдельно, ниже.

**Конкуренция в общей очереди — следствие, а не дефект.** С `generate_sql`,
который делает до четырёх вызовов LLM и одно неограниченное во времени
выполнение, медленный запрос занимает воркер надолго. Если бы запись журнала
ждала ту же очередь, всплеск таких запросов глушил бы `log_event` — а журнал
теряется безвозвратно и без ошибки.

Решение: **сервис владеет и очередью, и двумя входами в неё.**

* `submit(job)` — блокирующий путь для работы с данными: запрос, скрипт,
  поиск по истории. Задание становится в общую очередь и ждёт воркер.
* `accept(event)` — неблокирующий путь для журнала. Событие встаёт в буфер
  писателя и уходит батчем, не занимая место в общей очереди.

Это по-прежнему один сервис, один пул и один владелец. Просто журнал не
становится в очередь за дорогой работой. Если позже понадобится приоритет для
тяжёлых запросов, он добавляется **внутрь** сервиса и не затрагивает
вызывающих: контракт операций не меняется.

Аналогично устроен векторный поиск: сборка индекса, кэш индексов и вызов
эмбеддингов — состояние одного сервиса. Домен получает результат поиска и не
знает, откуда взялся индекс.

### 2.9 Слой исполнения операций — общий, а не в каждой capability

Вопрос: логирование оборота, проверка качества результата, файлы сессии и
сохранение крупных результатов — это забота каждой capability или отдельного
платформенного слоя?

**Рассмотренный вариант «в каждой capability».** Он выглядит дешевле: модуль
рядом с доменом, никакого нового косвенного вызова, всё очевидно. Отклонён по
трём причинам, и все три — про корректность, а не про стиль.

* **Счёт.** Четыре capability и четыре сквозных заботы — шестнадцать
  реализаций. Расходятся они не сразу, а по мере роста: сегодня журнал пишет
  `duration_ms`, завтра одна capability добавит `attempt`, и сравнивать их станет
  нельзя. Плюс одиннадцатая копия в `legal`.
* **Порядок, который нельзя обеспечить изнутри операции.** Ссылка на артефакт
  обязана быть валидна в момент получения ответа, то есть файл пишется **до**
  возврата. Из файла операции это не выражается: там нет точки «ответ уходит
  вызывающему». Ошибка выглядит безобидно — ссылка приходит, а файла нет, и
  обнаруживается это при первом же чтении, то есть у пользователя.
* **Единый список кодов ошибок.** Нормализация отказа в шестнадцати местах — это
  шестнадцать списков кодов, и через полгода они разойдутся.

Добавляется к этому то, ради чего существует §2.8: **у каждой операции ровно одна
точка входа, и она уже существует** — конвейер исполнения. Слой не создаёт новую
инфраструктуру, он занимает пустое место.

```text
                     MCP-вызов
                         │
                         ▼
        ┌──────────────────────────────────┐
        │        ToolExecutionPipeline     │
        │  контекст → журнал → вызов →     │
        │  нормализация → качество →        │
        │  крупный результат → артефакт    │
        └────────────────┬─────────────────┘
                         │
                         ▼
                  ToolDefinition.handler
                         │
                         ▼
                    домен · capability
```

Конвейер — единственный владелец порядка шагов, единственный, кто меряет
длительность, единственный, кто нормализует отказ и единственный, кто решает,
показать результат целиком или дать ссылку. Операция получает контекст оборота и
делает доменную работу.

**Контекст — не сумка сервисов.** `ToolExecutionContext` несёт идентичность и
метаданные (`request_id`, `session_id`, `user_id`, `tool_name`, `capability`,
`started_at`, `metadata`); службы операция берёт из контейнера. Иначе через
полгода в контексте окажутся пул, клиент эмбеддингов и генератор отчётов, и
`create_tool(container)` станет вторым способом получить зависимость.

**Идентичность — в `params._meta` (§2.11).** Важно различать два разных «метаданных».
У `stdio`-сервера **нет неявной транспортной идентичности**: одно соединение
обслуживает много сессий, и взять личность из транспорта нельзя (§1
`docs/MCP-CONTRACTS.md`) — это правда и это причина, по которой идентичность вообще
приходится передавать явно. Но **явный канал метаданных у MCP есть**:
`params._meta`, и клиент Nanobot его умеет заполнять (`call_tool(..., meta=...)`).
Отсюда решение: не «метаданных нет», а «неявной идентичности нет — значит передаём
явную».

**Файлы сессии — контролируемый API, а не `Path`.** Операция получает
`context.session`, уже привязанный к сессии оборота, и не знает, где каталог и кто
его создал. Выход за пределы каталога невозможен: канонический путь сверяется с
канонизированным корнем, поэтому ни `..`, ни симлинк наружу не проходят. Практическая
причина: каталог артефактов на сетевом диске — это ещё и медленный ввод-вывод, и
решение о его размещении принадлежит платформе, а не файлу операции.

**Пороги — из конфигурации.** `max_inline_result_bytes`, `execution_timeout_sec`,
`persist_large_results`, `quality_check_enabled`, `logging_enabled`,
`preview_bytes` живут в секции `execution` файла `platform.json` и разрешаются в
порядке операция → capability → платформа. Литерал в коде сделал бы значение
декоративным: сервер поднялся бы и применил бы не тот порог, который написан в
документации.

**Проверка качества — стратегии, а не вызовы из операции.** Технические проверки
выполняются всегда; семантические определяются `quality_policy` в
`ToolDefinition`. Провал семантической проверки не превращает результат в ошибку:
пустой результат — законный исход, и подмена его на `internal` научила бы модель
переформулировать вопрос вместо того, чтобы сказать пользователю правду.

**Правило, которое и есть главный результат.** Ни одна capability не имеет права
самостоятельно реализовывать сквозные заботы исполнения. Пока это не написано,
механизм расползается по проекту — по одному файлу на операцию, без злого умысла.
Запрет закрывается стражем на AST, а не договорённостью, и страж игнорирует
docstring: ложное срабатывание на документации делает страж бесполезным.

**Сознательно не входит.** Квоты и очистка сессий по возрасту, потоковая выдача,
подконвейеры на операцию. Квоты — отдельное решение с отдельной ценой ошибки
(удаление чужой сессии); потоковая выдача меняет контракт ответа, который сейчас
описан как JSON-объект; подконвейеры размножили бы порядок шагов, ради
устранения которого слой и заведён.

### 2.10 Одна модель событий на оба процесса

Правило: **MCP не заводит модель логирования, отличную от агентской.** Формат
события и механизм записи — общие; владение остаётся раздельным.

Это не архитектурное изящество, а обнаруженный при разведке дефект. Сегодня
платформенный писатель записывает подмножество колонок:

```text
libs/…/capabilities/data/service/main.py::_write_events
INSERT INTO agent_gateway_logs
  (id, timestamp, event_type, name, level, summary, payload, session_id, user_id)
```

А агентский писатель — весь конверт:

```text
lib/services/db_logging_service.py
INSERT INTO agent_gateway_logs
  (id, level, event_type, user_id, session_id, channel, actor, summary,
   payload, metadata, request_id, name)
```

Расхождение — `request_id`, `metadata`, `channel`, `actor`. При этом сама таблица
`request_id` и `metadata` имеет: `V004` строит по ним backfill и индекс, а контракт
`log_event` (§3.1 `docs/MCP-CONTRACTS.md`) описывает `request_id` и `metadata` как
параметры — хотя сигнатура операции их не принимает.

То есть корреляция оборота теряется **ровно на границе процессов**, ради которой
перенос и делался: событие, записанное платформой, нельзя связать с вопросом
пользователя одним `WHERE request_id = …`. Для журнала, который читает
`history_search`, это не косметика.

Решение:

* **Одна структура события** — существующий конверт, без новой схемы.
  `source` и `component` передаются в `metadata`: колонки потребовали бы миграции
  Greenplum 6.5 ради значений, которые сегодня читаются из одного JSONB, а
  корреляция работает по `request_id` и индексирована.
* **Закрытый словарь типов** с префиксом по ответственности: `agent.*`, `llm.*`,
  `tool.*`, `artifact.*`, `quality.*`. Свой тип на каждую операцию — это новый
  словарь, который нигде не поддерживается.
* **Один писатель.** Инвариант `V004` («один writer `gateway_logs`») переносится
  вместе с писателем. `McpEventRepository`, `ToolLogRepository` и подобные
  реализации не заводятся.
* **`request_id` — и только он.** Отдельные `trace_id`, `span_id`,
  `parent_span_id` как сущности не заводились: это второй идентификатор с тем же
  смыслом, что уже отклонён для `question_id`. Вложенность вызовов передаётся в
  `metadata` (`span`, `parent_span`) и остаётся производной.
* **`events/` в каталоге сессии — представление, а не вторая система.** Отдельный
  `logs/mcp.log` рядом с журналом агента означал бы два источника правды о том, что
  произошло. Файловая копия выключена по умолчанию: журнал в базе уже долговечен.

Общий контракт при раздельном владении — ровно то, что нужно, чтобы не связать
внутренности двух процессов и при этом читать их журнал одним запросом.

### 2.11 Идентичность вызова — в `params._meta`

Идентичность переносится из аргументов операции в **метаданные вызова**:

```json
{
  "jsonrpc": "2.0", "id": 42, "method": "tools/call",
  "params": {
    "name": "history_search",
    "arguments": { "query": "...", "limit": 20 },
    "_meta": {
      "workspaces/request_id": "01J...",
      "workspaces/session_id": "session-...",
      "workspaces/user_id": "user-..."
    }
  }
}
```

MCP уже предоставляет этот канал, и проект на нём и останавливается: собственный
`{execution, arguments}` конверт внутри `arguments` **не вводится**.

**Четыре следствия, и каждое было целью.**

* **Граница перестаёт держаться на договорённости.** Пока идентичность была
  параметром обработчика, её приходилось объявлять в опубликованной схеме
  необязательной — иначе модель начала бы её заполнять, — и безопасность держалась
  на обещании «агент перезапишет». В `_meta` у модели этих полей нет вообще.
* **Доменная схема не меняется.** В опубликованной `inputSchema` остаются только
  доменные параметры, а `arguments` продолжает ими быть. Перенос в собственный
  конверт стоил бы BREAKING-изменения формы вызова всех существующих операций;
  `_meta` этого не стоит.
* **Валидация не видит служебных данных.** Сервер MCP проверяет `arguments` по
  `inputSchema` — служебные метаданные в проверку не попадают и не могут стать её
  причиной.
* **Разбор происходит один раз.** Метаданные читаются на границе сервера и
  становятся `ToolExecutionContext` (§2.9); домен не знает, что `_meta` есть.

**Namespace обязателен:** ключи с префиксом `workspaces/`, потому что MCP
резервирует `io.modelcontextprotocol/*` под собственный служебный обмен — это видно
и в типах SDK (`types.py:540`), и в спецификации 2026-07-28, где `_meta` переносит
`clientInfo`. Голые `session_id`/`user_id`/`request_id` рано или поздно
столкнулись бы с чужим расширением.

**Реализуемость проверена на закреплённой версии, а не на будущей.** В проекте
`mcp==1.27.1`, и в нём нужное уже есть:

```text
agent:      session.call_tool(name, arguments, meta={...})
            → CallToolRequestParams(name, arguments, _meta=Meta(**meta))
server:     session.py:367  request_meta=validated_request.root.params.meta
            server.py:756   RequestContext(..., message.request_meta, ...)
handler:    server.request_context.meta["workspaces/session_id"]
```

`RequestParams.Meta` объявлен с `extra="allow"`, то есть namespaced-ключи
принимаются без плясок. Спецификацию 2026-07-28 и SDK v2 внедрять **не нужно** —
контракт на них сохраняется, потому что `_meta` остаётся каналом application
metadata. Это отличает решение от «перейти на новую версию MCP»: версия остаётся
пиннутой, меняется только то, чем мы заполняем уже существующее поле.

Деталь реализации на сервере: low-level сервер вызывает обработчик как
`func(tool_name, arguments)` — без контекста, — поэтому `_meta` читается через
`server.request_context.meta`. Значение извлекается один раз и передаётся дальше;
повторное чтение contextvar внутри доменного кода — нарушение границы.

**Условие, при котором контракт честен.** Модель не должна видеть операции
`enterprise-mcp` напрямую: `MCPToolWrapper.execute()` вызывает
`session.call_tool(self._original_name, arguments=kwargs)` **без** `meta=`, поэтому
при прямом вызове модели метаданных не будет и каждый вызов кончится
`identity_missing`. Сегодня это так и объявлено — сервер описан в
`project.json → enterprise_mcp`, а `tools.mcpServers` в `config.json` намеренно
пуст, и весь вызов идёт через `EnterpriseMcpClient.call()`. Отсюда и требование: точка
сборки одна, а не «в каждом tool'е», потому что второе место сборки означало бы
второе правило. Появление `enterprise-mcp` в `tools.mcpServers` закрывает контракт и
проверяется стражем.

**`request_id` обязателен.** Раньше его отсутствие означало «просто не
коррелирует». Теперь отсутствие любого из трёх ключей — нарушение контракта и отказ
`identity_missing`. Причина: подстановка на стороне сервера сделала бы корреляцию
ненаблюдаемой — событие пришло бы с ключом, которого нет ни у одного оборота. Для
вызовов вне оборота `request_id` создаёт агент до отправки.

**Идентичность снимается в момент вызова, а не в момент записи.** `log_event`
вызывается батчевым flush'ом уже после того, как `RequestContext` исчез, поэтому
`_meta` для него собирается из личности, снятой при постановке события в буфер
(§3.1 `docs/MCP-CONTRACTS.md`). Сборка метаданных в клиенте не отменяет это
правило: буфер хранит готовый конверт события, а не ссылку на контекст запроса.

| 1 | `context_governor` | Выгрузка в файл → хук; остаётся только подстановка ссылки для встроенных tool'ов |

| 4 | `exec_timeout_cap` | Удаляется: `tools.exec.timeout` уже прокинут (`0` = без лимита), остаток — подкласс `ExecTool` |
| 12 | `document_text_threshold` | Удаляется: порог переносится в нативный document-tool агента — это наш код, патчить фреймворк не нужно |

### Почему `context_governor` частично остаётся

В `nanobot/agent/tools/execution.py`:

```python
result = await tool.execute(**params)
await hook.after_execute_tool(context, tool_call, tool, params, result)
return result, {...}          # возвращается ИСХОДНЫЙ result
```

`after_execute_tool` возвращает `None`, раннер отдаёт `result` без изменений.
Подменить содержимое, попадающее в контекст, через хук нельзя.

Но это **единственное** такое ограничение, и оно касается только подстановки
значения. Всё остальное хук умеет:

| Действие | Чем делается |
|---|---|
| наблюдение вызовов, параметров, результатов, ошибок | любой метод `AgentHook` |
| запись в БД, файлы, счётчики | побочный эффект в хуке |
| публикация события | `await turn_context.events.publish(...)` |
| передача per-turn данных | мутабельные `turn_context.metadata` / `.attributes` |
| подмена финального контента | `finalize_content` (возвращает значение) |
| подмена результата tool'а | **только инструментом или патчем** |

Логирование — частный случай второй и третьей строк и целиком уезжает на хуки
и события, как и предполагалось изначально.

> Правило: проверять не наличие хука, а **может ли он повлиять именно на то,
> что нужно изменить** — эффектом, событием, мутацией `metadata` или
> возвращаемым значением.

### Итог

12 → **2 полностью необходимых + 2 частичных.** Восемь патчей удаляются
(`2`, `4`, `6`, `7`, `8`, `10`, `11`, `12`), `tool_limits` остаётся частичным
(3 из 5 целей — подклассы `Tool`), `context_governor` — частичным (остаётся
только подстановка значения, которую хук не умеет). Полностью остаются
`exec_limits` и `subagent_logging`. В
`docs/architecture/runtime-patcher-inventory.md` введена обязательная
колонка «Условие удаления».

`subagent_logging` — единственный оставшийся патч с **структурным** блокером:
`_SubagentHook` конструируется жёстко, фабрики для subagent'ов нет, то есть
точка вставки отсутствует физически, а не из-за слабости хука.

1. **Redis-канал.** Снимает ли однопроцессность смысл `redis_channel.py` и

2. **Переопределение встроенных tool'ов.** Альтернатива патчам `exec_limits` /

3. **Кто считает эмбеддинги.** `tools/build_vectors.py` как отдельная задача
   (текущий план) или часть capability `vectors`.
4. **Судьба `schema_validation.py`.** Проверка шести runtime-таблиц сейчас живёт

   предстартовая проверка по определению нужна ДО того, как сервер поднялся.

5. **Показывать ли SQL в ответе `run_script`.** По умолчанию убрано: для модели
   это приглашение вернуть ручную правку. Оператору полезно — но оператора
   звать нельзя.
6. **Нужен ли `describe_script` или хватит `list_scripts` с фильтром.**
   Скрипты приходят из базы, описание MCP-инструмента статично.
7. **Лимит попыток генерации.** Сегодня `MAX_ATTEMPTS = 4` вызовов LLM на один
   вопрос; стоимость вопроса ничем не ограничена.
8. **Потолок `max_tokens` в `complete`.** Модель может заказать `10**9`.
9. **Что отдавать в `row` у `vector_search`.** Полная строка источника может быть
   большой; нужен потолок и признак усечения.
10. **Колонки под `source` / `component`.** Сейчас эти значения лежат в
    `metadata`. Отдельные колонки дали бы запрос «все события `enterprise-mcp` за

    ещё не задали. Пересматривается вместе с первым реальным запросом, а не
    заранее (§2.10).

## 7. Принятые решения по закрытым вопросам

### 7.1 Топология: один процесс `enterprise-mcp`

Все capability живут в одном MCP-сервере: `data`, `vectors`, `llm`, `audit`,
`legal`. Обоснование и разбор цены разделения — §2.1.

Принято по двум причинам:

* **Функционально.** `audit_analyzer` отвечает на вопрос, который требует
  одновременно SQL по `oarb.*` и поиска по FAISS. В одном процессе join
  выполняется на месте; в двух процессах модель вынуждена делать два вызова и
  склеивать результат у себя в голове.
* **Стоимость разделения перестала быть нулевой.** До реестра каждый сервер
  требовал ручного перечисления инструментов. Теперь разделение — это чистая
  накладная стоимость: три `server.py`, три записи в `mcpServers`, три
  health-check'а, три точки отказа при старте, невозможность транзакции через
  границу процессов.

**Что покупало разделение и чем заменено.** Изоляция тяжёлой загрузки FAISS —
ленивой сборкой индекса по первому запросу (§2.3). Изоляция зависшего вызова
LLM — очередью и таймаутом на сетевом вызове внутри процесса.

**Возврат к разделению остаётся возможным.** Capability ≠ процесс: если одна
из них потребует изоляции, она переезжает в отдельный процесс конфигурацией
загрузчика, без правки файлов операций.

**Индекс:** сотни тысяч векторов, сборка десятки секунд. Именно эта величина
сделала ленивую загрузку обязательной, а не оптимизацией.

### 7.2 Capability `llm` — операция `complete`

Доменный вызов LLM становится MCP-операцией. `llm_client.py` (199) и
`llm_config.py` (88) переезжают в `mcp-platform/libs/llm` и **в агенте больше
не используются**.

Своего процесса не получает: исходящий сетевой вызов — обычная операция
внутри capability, а не повод заводить отдельную границу.

Домены при этом ходят в `libs/llm` **напрямую в своём процессе** — по ранее
принятому правилу, что bulk-доступ доменов идёт через `libs/`, а не через
MCP-вызовы. MCP-поверхность нужна модели, а не домену.

### 7.3 Модель не пишет SQL: три входа вместо произвольного запроса

Агенту **не** выдаётся операция, принимающая SQL. Поверхность разделена:

* `data` — инфраструктура: `log_event`, `schema_check`, `history_search`;
* `audit` — весь запрос к данным: `list_scripts`, `run_script`, `generate_sql`.

Три следствия, которые видны сразу:

* **граница изоляции перестаёт обходиться** — произвольный SQL позволял выбрать
  `agent_gateway_logs` в обход `history_search`;
* **список таблиц становится границей, а не подсказкой** — сегодня он существует
  только в тексте промпта;
* **AST-guard меняет роль** — он больше не охраняет вызов снаружи, а охраняет
  вывод LLM, который является недоверенным входом. Требование «сервер не
  поднимается без `sqlglot`» сохраняется.

Подробности, включая цену решения, — §2.4. Формальная фиксация —
спецификации `data/audit` и `data/query`.

**Порядок фаз больше не зависит от снимка:** `db_loader` читает реестр
через `CacheProvider`, то есть из снимка, и capability `audit` читает его оттуда —
через capability `data`. Перенос `audit` на PostgreSQL больше не является
обязательным условием, и фаза 4 становится переездом
конвейера с сохранением его диалекта.

### 7.4 Документы — нативный tool агента

`office_files` **не переезжает** в `mcp-platform`. Доступ к офисным файлам
остаётся нативным инструментом агента, `python-docx`, `openpyxl`, `pypdf`,
`python-pptx` остаются в его зависимостях. Третий сервер не заводится и
capability `documents` не появляется.

Обоснование: разбор офисных файлов — парсинг, а не capability, и у него нет
точки выбора у модели. Цена решения измерима и невелика: четыре пакета в
`requirements.txt` агента.

**Цель «установка Nanobot не тянет enterprise-стек» в этой части сознательно
не выполняется.** Это зафиксированное исключение, а не недосмотр.

*Следствие, требующее проверки на фазе 7:* `legal_summarizer` переезжает в
платформу и тоже разбирает документы. Дублировать `office_files.py` в двух
репозиториях нельзя. Рабочий вариант — домен получает **уже извлечённый
текст** (агент извлекает, домен обрабатывает), а не второй экземпляр модуля.
Проверить до переноса, иначе получим два расходящихся парсера.

### 7.5 `media` и `_tool_audit` — событие, патч удаляется

`assemble_outbound` уходит целиком. Все три его обязанности переводятся на
события: `_final_turn` → `TurnEndEvent`, `_tool_audit` и `media` — публикация
из хука через `turn_context.events`, потребитель — канал.

**Известное последствие:** момент появления вложения у пользователя сдвигается
с этапа сборки outbound на этап обработки события каналом. Это осознанная
плата за отказ от патча.

**Непроверенное допущение, которое надо закрыть на фазе 5:** слот `media` по
коду никогда не заполняется самим Nanobot (штатный слот `_agent_ui`
записывается только на этапе сборки). Если выяснится, что слот пуст всегда,
публиковать нечего и ветка события удаляется вместе с патчем — то есть
решение снимает и несуществующую проблему. Проверяется одним реальным ходом
с вложением, а не чтением кода.

### 7.6 Сквозные заботы исполнения — платформенный слой, а не обязанность capability

Логирование оборота, проверка качества, файлы сессии, сохранение крупного
результата, таймаут и нормализация ошибок обеспечиваются **единым конвейером
исполнения** (`libs/enterprise_common/execution` + `session`), через который
проходит каждая операция. Capability такие заботы самостоятельно не реализуют.

Отклонённый вариант — реализовать их в каждой capability: локально и очевидно,
но в шестнадцати местах (четыре capability × четыре заботы), с расхождением
поведения по мере роста и без возможности выразить требование «файл записан до
возврата ответа» изнутри файла операции. Полностью — §2.9.

**Новое правило, зафиксированное здесь же:** ни одна capability не имеет права
самостоятельно реализовывать сквозные заботы исполнения. Они предоставляются
платформой через конвейер. Правило проверяется стражем, а не договорённостью.

**Последствия:**

* файл операции — доменная логика и сборка ответа; ничего больше;
* добавление операции даёт ей инфраструктуру без правок в других файлах;
* существующие capability переписываются один раз: с них снимаются их копии этих
  забот;
* появляется секция настроек `execution` в `platform.json`.

### 7.7 События MCP — часть общей модели событий агента

`enterprise-mcp` не заводит собственную модель логирования: события обоих
процессов имеют одну структуру, один словарь типов и одного писателя. Отдельные
`trace_id` / `span_id` как сущности не заводятся — корреляцией остаётся
`request_id`, вложенность передаётся в `metadata`. Обоснование и найденный при
этом дефект потери `request_id` — §2.10.

**Последствия:**

* инфраструктура событий — `libs/enterprise_common/eventing`, платформенный
  контракт, а не часть capability;
* платформенный писатель дополняется до полного конверта: сегодня он теряет
  `request_id` и `metadata`, то есть ломает корреляцию оборота на границе
  процессов;
* сигнатура `log_event` приводится в соответствие с §3.1 `docs/MCP-CONTRACTS.md`;
* отдельный `logs/mcp.log` не заводится; каталог `events/` в сессии — второе
  представление того же события и по умолчанию выключен.

### 7.8 Идентичность вызова переносится в `params._meta`

Все вызовы Nanobot → `enterprise-mcp` несут идентичность в метаданных вызова:
`_meta` с ключами `workspaces/{request,session,user}_id`. Обработчик операции
идентичность не объявляет: она приходит через `ToolExecutionContext`. Метаданные
обязательны для всех операций, включая те, кому пользовательская изоляция не нужна;
нарушение — отказ `identity_missing` до входа в домен. Полностью — §2.11.

Это решение **отменяет** прежнюю форму: идентичность была аргументом обработчика и
объявлялась в схеме необязательной, чтобы модель её не заполняла. Собственный
конверт `{request, session, user}_id` **рассмотрен и отклонён** — вместо него
используется штатный канал `_meta`.

**Последствия:**

* доменная схема операций **не меняется**: `arguments` остаётся доменным объектом,
  `inputSchema` содержит только доменные параметры. BREAKING-изменения контракта
  нет — собственный конверт его требовал бы (перенос параметров во вложенный объект);
* точка сборки метаданных — `EnterpriseMcpClient.call()`, который передаёт `meta=`
  в `session.call_tool`; агентские tool'ы (`workspace/tools/*`) перестают собирать и
  передавать личность;
* `request_id` становится обязательным, и агент создаёт его для вызовов вне оборота;
* операция `enterprise-mcp` не должна появляться в `tools.mcpServers` агента, пока
  существует контракт: `MCPToolWrapper` отправляет аргументы модели без `meta=`;
* закреплённая версия SDK не меняется — `mcp==1.27.1` уже умеет `meta=` и разбирает
  `params.meta`. Внедрять спецификацию 2026-07-28 и SDK v2 не требуется; на них
  контракт сохраняется, потому что `_meta` остаётся каналом application metadata;
* `docs/MCP-CONTRACTS.md` §1 и §3.1 переписываются — сегодня там описана старая
  форма вызова.
