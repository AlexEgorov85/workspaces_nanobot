# Менеджер каналов

## Назначение

Менеджер каналов обеспечивает централизованное управление жизненным циклом коммуникационных каналов системы, включая их регистрацию, активацию, переключение и завершение.

## Ответственность

- Регистрация доступных каналов (PostgreSQL LISTEN/NOTIFY, Redis Pub/Sub)
- Активация и деактивация каналов по запросу
- Переключение между каналами для сессий
- Мониторинг состояния каналов
- Координация подписок и публикаций через каналы

## Граница

### Владеет
- Реестром зарегистрированных каналов
- Состоянием активности каналов
- Механизмом переключения каналов

### Не владеет
- Реализацией транспортных протоколов (PostgreSQL, Redis)
- Содержимым сообщений
- Логикой обработки сообщений
- Session management

## Контракт

### Публичный интерфейс

```python
class ChannelManager:
    def register_channel(self, name: str, channel: BaseChannel) -> None
    def get_channel(self, name: str) -> BaseChannel
    def activate_channel(self, name: str) -> None
    def deactivate_channel(self, name: str) -> None
    def get_active_channels(self) -> List[str]
    def shutdown_all(self) -> None
```

### Требования

#### Требование: Регистрация канала

**Сценарий: Регистрация нового канала**
- **КОГДА** система инициализируется или динамически добавляет канал
- **ТОГДА** канал регистрируется в реестре с уникальным именем
- **И** канал становится доступным для активации

#### Требование: Активация канала

**Сценарий: Активация канала для использования**
- **КОГДА** требуется использовать канал для коммуникации
- **ТОГДА** канал переводится в активное состояние
- **И** начинаются операции подписки/публикации

#### Требование: Деактивация канала

**Сценарий: Корректная деактивация канала**
- **КОГДА** канал больше не требуется
- **ТОГДА** канал переводится в неактивное состояние
- **И** освобождаются ресурсы (подписки, соединения)

### Запрещённое поведение

Менеджер каналов НЕ ДОЛЖЕН:
- Создавать каналы неявно без регистрации
- Позволять дублирование имён каналов
- Активировать незарегистрированные каналы
- Терять сообщения при переключении каналов
- Блокировать работу системы при ошибке одного канала

## Зависимости

### Может зависеть от
- Конкретных реализаций каналов (PostgresChannel, RedisChannel)
- ConfigService для конфигурации каналов
- ApplicationContext для интеграции

### Не должен зависеть от
- Бизнес-логики Skills
- Session-specific данных
- Прямых соединений с БД/Redis (через каналы)

## Конфигурация

```yaml
channels:
  enabled:
    - postgres
    - redis
  default: postgres
  postgres:
    listen_timeout: 30
  redis:
    retry_attempts: 3
```

## Жизненный цикл

1. **Инициализация**: Создание менеджера, загрузка конфигурации
2. **Регистрация**: Регистрация доступных каналов
3. **Активация**: Активация каналов согласно конфигурации
4. **Работа**: Обработка запросов на переключение/мониторинг
5. **Завершение**: Корректная деактивация всех каналов

## Состояние

```python
{
    "registered_channels": Dict[str, BaseChannel],
    "active_channels": Set[str],
    "default_channel": str
}
```

## Инварианты

- Имя каждого зарегистрированного канала уникально
- Активный канал всегда существует в реестре
- Канал не может быть активирован дважды
- При завершении работы все каналы деактивируются

## Поведение при ошибке

- Ошибка регистрации канала → логирование, продолжение работы
- Ошибка активации канала → логирование, канал остаётся неактивным
- Ошибка получения канала → выбрасывается исключение
- Ошибка при shutdown → логирование, попытка завершения остальных

## Потребители

- ApplicationContext — инициализация каналов
- Session Context — выбор канала для сессии
- Gateway/CLI — отправка сообщений через каналы

## Проверка

### Автоматическая проверка
- Тесты на регистрацию/активацию/деактивацию каналов
- Тесты на обработку ошибок
- Тесты на жизненный цикл

### Ручная проверка
- Соответствие интерфейса спецификации
- Отсутствие утечек ресурсов при shutdown
