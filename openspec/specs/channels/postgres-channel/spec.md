# PostgreSQL канал

## Назначение

PostgreSQL канал обеспечивает коммуникацию между компонентами системы через механизм LISTEN/NOTIFY базы данных PostgreSQL, позволяя передавать сообщения без дополнительных инфраструктурных компонентов.

## Ответственность

- Подключение к PostgreSQL для операций LISTEN/NOTIFY
- Публикация сообщений в каналы БД
- Подписка на уведомления из каналов БД
- Обработка переподключений при разрыве соединения
- Сериализация/десериализация сообщений

## Граница

### Владеет
- Соединением с PostgreSQL для NOTIFY/LISTEN
- Управлением подписками на каналы
- Очередью входящих уведомлений
- Логикой переподключения

### Не владеет
- Общей пулом соединений приложения
- Бизнес-логикой сообщений
- Маршрутизацией сообщений между получателями
- Гарантиями доставки (обеспечивает только Best Effort)

## Контракт

### Публичный интерфейс

```python
class PostgresChannel:
    def connect(self) -> None
    def disconnect(self) -> None
    def publish(self, channel: str, payload: dict) -> None
    def subscribe(self, channel: str) -> None
    def unsubscribe(self, channel: str) -> None
    def listen(self, timeout: float) -> Optional[Message]
    def is_connected(self) -> bool
```

### Требования

#### Требование: Публикация сообщения

**Сценарий: Отправка сообщения в канал**
- **КОГДА** компонент вызывает `publish(channel, payload)`
- **ТОГДА** сообщение сериализуется в JSON
- **И** выполняется `NOTIFY channel, payload` в PostgreSQL
- **И** подтверждение не требуется (fire-and-forget)

#### Требование: Подписка на канал

**Сценарий: Начало прослушивания канала**
- **КОГДА** компонент вызывает `subscribe(channel)`
- **ТОГДА** выполняется `LISTEN channel` в PostgreSQL
- **И** последующие уведомления сохраняются в очереди

#### Требование: Получение сообщения

**Сценарий: Чтение уведомления из канала**
- **КОГДА** компонент вызывает `listen(timeout)`
- **ТОГДА** ожидается уведомление в течение timeout секунд
- **И** при получении возвращается десериализованное сообщение
- **И** при таймауте возвращается None

#### Требование: Переподключение

**Сценарий: Восстановление после разрыва соединения**
- **КОГДА** соединение с PostgreSQL разрывается
- **ТОГДА** канал пытается переподключиться с экспоненциальной задержкой
- **И** после переподключения восстанавливаются все подписки

### Запрещённое поведение

PostgreSQL канал НЕ ДОЛЖЕН:
- Использовать основное соединение приложения для LISTEN/NOTIFY
- Терять подписки при переподключении
- Блокировать бесконечно при ожидании сообщений
- Пропускать сообщения без логирования
- Смешивать бизнес-логику с транспортным уровнем

## Зависимости

### Может зависеть от
- ConfigService для параметров подключения
- Logger для записи событий
- ChannelManager для координации

### Не должен зависеть от
- Конкретных типов сообщений
- Бизнес-компонентов (Skills, Agents)
- Других транспортных механизмов (Redis)

## Конфигурация

```yaml
channel.postgres:
  host: localhost
  port: 5432
  database: nanobot
  user: nanobot_user
  password_env: DB_PASSWORD
  listen_timeout: 30.0
  reconnect_attempts: 5
  reconnect_delay_base: 1.0
  channel_prefix: "nb_"
```

## Жизненный цикл

1. **Инициализация**: Загрузка конфигурации
2. **Подключение**: Установка соединения с PostgreSQL
3. **Подписка**: Регистрация слушателей на каналах
4. **Работа**: Публикация и получение сообщений
5. **Переподключение**: При разрыве соединения
6. **Завершение**: Отписка от каналов, закрытие соединения

## Инварианты

- Соединение устанавливается только с выделенными параметрами
- Подписки восстанавливаются после каждого переподключения
- Таймаут ожидания сообщения соблюдается
- Максимальное количество попыток переподключения не превышается

## Поведение при ошибке

- Ошибка подключения → логирование, попытка переподключения
- Ошибка публикации → логирование, выброс исключения
- Ошибка десериализации → логирование, пропуск сообщения
- Таймаут listen → возврат None (штатная ситуация)
- Принудительное завершение → немедленное закрытие соединения

## Потребители

- ChannelManager — управление жизненным циклом
- MessageBus — передача сообщений между компонентами
- Session Context — коммуникация между сессиями
