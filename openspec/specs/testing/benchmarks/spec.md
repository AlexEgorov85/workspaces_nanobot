# Бенчмарки

## Назначение

Бенчмарки обеспечивают измерение производительности и функциональности системы через набор автоматизированных тестовых сценариев, позволяя отслеживать деградацию производительности и корректность работы компонентов.

## Ответственность

- Определение набора бенчмарк-сценариев для различных компонентов
- Измерение времени выполнения операций
- Сравнение результатов с базовыми показателями (baseline)
- Генерация отчётов о производительности
- Интеграция с CI/CD для регрессионного тестирования
- Выявление узких мест производительности

## Граница

### Владеет
- Набором бенчмарк-сценариев
- Метриками производительности
- Базовыми показателями (baseline)
- Форматом отчётов о бенчмарках

### Не владеет
- Бизнес-логикой тестируемых компонентов
- Unit-тестами (это ответственность pytest-тестов)
- Нагрузочным тестированием production (это responsibility отдельной системы)
- Исправлением проблем производительности (только выявление)

## Контракт

### Публичный интерфейс

```python
class BenchmarkSuite:
    def register_benchmark(
        self,
        name: str,
        benchmark_func: Callable[[], Any],
        category: str,
        expected_max_ms: Optional[float] = None
    ) -> None
    
    def run_benchmark(
        self,
        name: str,
        iterations: int = 10,
        warmup_iterations: int = 3
    ) -> BenchmarkResult
    
    def run_all_benchmarks(
        self,
        category: Optional[str] = None
    ) -> List[BenchmarkResult]
    
    def compare_with_baseline(
        self,
        results: List[BenchmarkResult]
    ) -> ComparisonReport
    
    def save_baseline(self, name: str) -> None
    def load_baseline(self, name: str) -> Optional[BenchmarkResult]
    def generate_report(
        self,
        results: List[BenchmarkResult],
        format: str = "json"
    ) -> str
```

### Требования

#### Требование: Регистрация бенчмарка

**Сценарий: Добавление нового бенчмарк-теста**
- **КОГДА** требуется добавить бенчмарк для компонента
- **ТОГДА** вызывается `register_benchmark()` с функцией теста
- **И** указывается категория (runtime, data, skills, etc.)
- **И** опционально указывается ожидаемый максимум времени
- **И** бенчмарк добавляется в реестр доступных

#### Требование: Запуск бенчмарка

**Сценарий: Измерение производительности**
- **КОГДА** требуется измерить производительность
- **ТОГДА** вызывается `run_benchmark()` с именем теста
- **И** выполняются warmup итерации для прогрева
- **И** выполняются основные итерации измерения
- **И** вычисляются статистики (min, max, avg, median, p95)

#### Требование: Сравнение с baseline

**Сценарий: Обнаружение регрессии**
- **КОГДА** выполнены бенчмарки после изменений
- **ТОГДА** результаты сравниваются с сохранённым baseline
- **И** вычисляется процентное изменение
- **И** при значительной регрессии (>10%) генерируется предупреждение

#### Требование: Генерация отчёта

**Сценарий: Визуализация результатов**
- **КОГДА** бенчмарки завершены
- **ТОГДА** генерируется отчёт в заданном формате
- **И** включаются все метрики и сравнения
- **И** отчёт сохраняется для анализа

### Запрещённое поведение

Бенчмарки НЕ ДОЛЖНЫ:
- Модифицировать состояние системы (только read-only или с откатом)
- Зависеть от внешних сервисов (mock/stub при необходимости)
- Выполняться бесконечно (таймаут на каждый бенчмарк)
- Влиять на работу production системы
- Игнорировать warmup итерации (для точности измерений)

## Зависимости

### Может зависеть от
- ApplicationContext для доступа к компонентам
- ConfigService для конфигурации бенчмарков
- Logger для логирования результатов
- SubprocessManager для изолированных бенчмарков

### Не должен зависеть от
- Конкретных бизнес-данных
- Внешних систем мониторинга
- Production данных (используются test fixtures)

## Конфигурация

```yaml
benchmarks:
  enabled: true
  default_iterations: 10
  warmup_iterations: 3
  timeout_per_benchmark_sec: 60.0
  categories:
    - runtime
    - data
    - skills
    - interfaces
  regression_threshold_percent: 10.0
  save_results: true
  results_dir: "/tmp/nanobot_benchmarks"
  baseline_file: "benchmarks_baseline.json"
  report_format: "json"  # json, html, markdown
  include_in_ci: true
  fail_on_regression: false  # true для strict mode
```

## Жизненный цикл

1. **Инициализация**: Загрузка конфигурации, baseline
2. **Регистрация**: Добавление бенчмарков в реестр
3. **Warmup**: Прогрев компонентов перед измерениями
4. **Измерение**: Выполнение итераций, сбор метрик
5. **Анализ**: Сравнение с baseline, выявление регрессий
6. **Отчёт**: Генерация и сохранение результатов

## Инварианты

- Каждый бенчмарк имеет уникальное имя в пределах категории
- Результаты бенчмарков воспроизводимы (при одинаковых условиях)
- Warmup итерации выполняются перед основными измерениями
- Baseline сохраняется только после успешного прохождения всех бенчмарков

## Поведение при ошибке

- Ошибка выполнения бенчмарка → логирование, продолжение со следующим
- Таймаут бенчмарка → прерывание, запись ошибки в отчёт
- Регрессия производительности → предупреждение в отчёте
- Отсутствие baseline → использование текущих результатов как baseline

## Потребители

- CI/CD Pipeline — автоматическая проверка производительности
- Developers — анализ влияния изменений на производительность
- Performance Engineers — выявление узких мест
- Release Management — принятие решения о релизе
