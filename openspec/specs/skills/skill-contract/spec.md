# Контракт Skill

## Назначение

Контракт Skill определяет единый интерфейс и требования ко всем Skills системы, обеспечивая согласованность реализации, интеграции и управления жизненным циклом предметных компонентов.

## Ответственность

- Определение обязательного интерфейса для всех Skills
- Specification режимов выполнения (predefined, vector, generated_sql)
- Требования к валидации входных данных
- Требования к форматированию результатов
- Правила обработки ошибок внутри Skill
- Интеграция с инфраструктурой через стандартные интерфейсы

## Граница

### Владеет
- Сигнатурой методов Skill
- Реестром доступных режимов выполнения
- Форматом запросов и ответов
- Правилами переключения между режимами

### Не владеет
- Конкретной предметной логикой (определяется каждым Skill)
- Инфраструктурными сервисами (использует через Dependency Injection)
- Управлением жизненным циклом (делегирует AgentFactory/AgentLoop)
- Маршрутизацией запросов к Skills (делегирует Router)

## Контракт

### Публичный интерфейс

```python
class Skill(ABC):
    @property
    def name(self) -> str: ...
    
    @property
    def description(self) -> str: ...
    
    @property
    def modes(self) -> List[str]: ...
    
    def can_handle(self, request: SkillRequest) -> bool: ...
    
    async def execute(
        self,
        request: SkillRequest,
        context: SkillContext
    ) -> SkillResult: ...
    
    def get_capabilities(self) -> SkillCapabilities: ...
    
    def validate_input(self, input_data: Dict) -> ValidationResult: ...
```

### Требования

#### Требование: Обязательные свойства

**Сценарий: Регистрация Skill в системе**
- **КОГДА** Skill создаётся
- **ТОГДА** он должен иметь уникальное имя
- **И** описание назначения на русском языке
- **И** список поддерживаемых режимов выполнения
- **И** метаданные возможностей (capabilities)

#### Требование: Проверка возможности обработки

**Сценарий: Определение применимости Skill**
- **КОГДА** поступает запрос на выполнение
- **ТОГДА** вызывается `can_handle()` для проверки
- **И** Skill возвращает true только если может обработать запрос
- **И** проверка выполняется быстро без побочных эффектов

#### Требование: Выполнение Skill

**Сценарий: Обработка запроса**
- **КОГДА** Skill выбран для выполнения
- **ТОГДА** вызывается `execute()` с запросом и контекстом
- **И** Skill выполняет предметную логику в выбранном режиме
- **И** возвращается структурированный результат
- **И** все ошибки обрабатываются внутри Skill или пробрасываются

#### Требование: Режимы выполнения

**Сценарий: Выбор стратегии выполнения**
- **КОГДА** Skill поддерживает несколько режимов
- **ТОГДА** режим выбирается на основе запроса или конфигурации
- **И** predefined — используется заранее определённая логика
- **И** vector — поиск по векторному индексу
- **И** generated_sql — генерация и выполнение SQL
- **И** переключение между режимами явно логгируется

### Запрещённое поведение

Skill НЕ ДОЛЖЕН:
- Иметь глобальное состояние (stateless или state в контексте)
- Прямой доступ к инфраструктуре (только через предоставленные интерфейсы)
- Дублировать общую инфраструктуру (кэш, логирование — через сервисы)
- Молчаливо переключаться между режимами без явного указания
- Возвращать результаты в нестандартизированном формате
- Блокироваться на неопределённое время (таймауты обязательны)

## Зависимости

### Может зависеть от
- CacheProvider для кэширования результатов
- VectorIndexService для vector mode
- DbLoggingService для логирования выполнения
- ConfigService для конфигурации режима
- SubprocessManager для внешних вызовов

### Не должен зависеть от
- Конкретных реализаций инфраструктуры
- Других Skills напрямую (через Events/Hooks при необходимости)
- Session Manager напрямую (через Context)
- Прямых соединений с БД (только через SqlSafety)

## Конфигурация

```yaml

  default_mode: "predefined"
  mode_selection: "explicit"  # explicit, auto
  timeout_sec: 60.0
  max_retries: 1
  cache_enabled: true
  cache_ttl_sec: 300

  log_input: false  # не логировать чувствительные данные
  log_output: true
  validation:
    strict_mode: true
    fail_on_invalid_input: true
```

## Жизненный цикл

1. **Инициализация**: Создание экземпляра Skill, загрузка конфигурации
2. **Регистрация**: Регистрация в реестре доступных Skills
3. **Выбор**: Router определяет применимость через `can_handle()`
4. **Выполнение**: Вызов `execute()` с запросом и контекстом
5. **Кэширование**: Сохранение результата (если включено)
6. **Завершение**: Очистка ресурсов, логирование

## Состояние

```python
{
    "name": str,
    "description": str,
    "modes": List[str],
    "current_mode": Optional[str],
    "execution_count": int,
    "last_execution": Optional[datetime],
    "is_initialized": bool
}
```

## Инварианты

- Каждый Skill имеет уникальное имя в системе
- Режим выполнения выбирается до начала выполнения
- Результат всегда соответствует declared типу
- Ошибки валидации входа обрабатываются до выполнения
- Skill не сохраняет состояние между вызовами (stateless)

## Поведение при ошибке

- Ошибка валидации входа → ValidationError с деталями
- Ошибка выполнения → Exception с контекстом, логирование
- Таймаут → TimeoutException, возможность retry
- Недоступность зависимости → DependencyError

## Потребители

- AgentLoop — выполнение Skills в рамках agent cycle
- AgentFactory — создание экземпляров Skills
- Router — маршрутизация запросов к Skills
- Gateway/CLI — прямой вызов Skills (опционально)

### Автоматическая проверка
- Тесты на соответствие интерфейсу
- Тесты на валидацию входа
- Тесты на каждый режим выполнения
- Тесты на обработку ошибок

- Проверка логирования и наблюдаемости
