# Логирование событий

## Назначение

Логирование событий обеспечивает сбор, агрегацию и распределение системных событий в реальном времени для мониторинга, отладки и аудита работы системы.

## Ответственность

- Сбор событий от всех компонентов системы
- Классификация событий по типам и уровням важности
- Распределение событий подписчикам (логи, метрики, алерты)
- Агрегация событий для снижения шума
- Обогащение событий контекстом (session_id, user_id, trace_id)

## Граница

### Владеет
- Шиной событий системы
- Реестром подписчиков на события
- Форматом событий
- Правилами агрегации и фильтрации

### Не владеет
- Персистентным хранением событий (это ответственность DbLoggingService)
- Бизнес-логикой обработки событий
- Внешними системами мониторинга
- Конкретными реализациями логирования (файлы, БД, external services)

## Контракт

### Публичный интерфейс

```python
class EventLoggingService:
    def emit(self, event: Event) -> None
    def subscribe(
        self,
        event_types: List[str],
        handler: Callable[[Event], None]
    ) -> Subscription
    def unsubscribe(self, subscription: Subscription) -> None
    def add_filter(self, filter: EventFilter) -> None
    def remove_filter(self, filter_id: str) -> None
    def set_aggregation_rule(
        self,
        event_type: str,
        window_sec: float,
        aggregator: Callable[[List[Event]], Event]
    ) -> None
```

### Требования

#### Требование: Публикация события

**Сценарий: Эмиссия системного события**
- **КОГДА** компонент генерирует событие
- **ТОГДА** событие публикуется в шину событий
- **И** обогащается системными метаданными (timestamp, source)
- **И** доставляется всем подписчикам согласно фильтрам

#### Требование: Подписка на события

**Сценарий: Регистрация обработчика событий**
- **КОГДА** компонент хочет реагировать на события
- **ТОГДА** он подписывается на типы событий через `subscribe()`
- **И** получает только события соответствующих типов
- **И** может отписаться через `unsubscribe()`

#### Требование: Фильтрация событий

**Сценарий: Снижение шума событий**
- **КОГДА** добавлен фильтр событий
- **ТОГДА** отфильтрованные события не доставляются подписчикам
- **И** фильтр применяется до агрегации

#### Требование: Агрегация событий

**Сценарий: Группировка повторяющихся событий**
- **КОГДА** поступает много однотипных событий за короткий период
- **ТОГДА** они агрегируются в одно событие по правилу
- **И** подписчики получают агрегированное событие
- **И** оригинальные события сохраняются для отладки

### Запрещённое поведение

Логирование событий НЕ ДОЛЖНО:
- Блокировать эмитента при обработке событий
- Терять события при ошибке обработчика
- Создавать циклические зависимости (событие порождает событие)
- Доставлять события после отписки
- Раскрывать чувствительные данные в событиях

## Зависимости

### Может зависеть от
- Logger для записи ошибок самой шины событий
- ConfigService для конфигурации агрегации
- ApplicationContext для интеграции

### Не должен зависеть от
- Конкретных бизнес-компонентов
- Персистентного хранилища
- Внешних систем (отправляет события, но не зависит от них)

## Конфигурация

```yaml
event_logging:
  enabled: true
  default_filters:
    - exclude_debug_in_production
  aggregation:
    enabled: true
    default_window_sec: 5.0
    max_events_per_aggregate: 100
  async_delivery: true
  max_subscribers_per_type: 50
  event_retention_in_memory: 60.0
```

## Жизненный цикл

1. **Инициализация**: Создание шины событий, загрузка фильтров
2. **Регистрация подписчиков**: Компоненты подписываются на события
3. **Работа**: Эмиссия, фильтрация, агрегация, доставка событий
4. **Завершение**: Отписка всех подписчиков, очистка буферов

## Состояние

```python
{
    "subscribers": Dict[str, List[Subscription]],

    "pending_aggregates": Dict[str, List[Event]],
    "is_shutting_down": bool
}
```

## Инварианты

- Каждое событие имеет уникальный ID
- Событие доставляется всем подписчикам атомарно (в рамках одного вызова)
- Фильтры применяются перед агрегацией
- Агрегация не превышает заданный лимит событий
- При shutdown новые события отклоняются gracefully

## Поведение при ошибке

- Ошибка обработчика → логирование, продолжение доставки другим подписчикам
- Переполнение очереди → старейшие события отбрасываются
- Ошибка агрегации → события доставляются индивидуально
- Циклическая зависимость → обнаружение и разрыв цикла

## Потребители

- DbLoggingService — персистентное хранение событий
- Metrics Collector — сбор метрик из событий
- Alerting System — генерация алертов
- Debug Console — отображение событий в реальном времени
- Audit System — аудит действий пользователей

## Проверка

### Автоматическая проверка
- Тесты на публикацию/подписку событий
- Тесты на фильтрацию и агрегацию
- Тесты на обработку ошибок обработчиков
- Тесты на отсутствие утечек памяти

### Ручная проверка
- Анализ производительности при высокой нагрузке
- Проверка корректности агрегации
- Мониторинг циклических зависимостей
