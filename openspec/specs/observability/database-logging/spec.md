# Логирование в базу данных

## Назначение

Логирование в базу данных обеспечивает персистентное хранение событий системы в PostgreSQL, позволяя отслеживать действия пользователей, работу Skills и системные события для аудита и отладки.

## Ответственность

- Запись событий в таблицу логов PostgreSQL
- Структурирование логов с метаданными (session_id, user_id, timestamp)
- Категоризация событий по типам и уровням
- Поддержка асинхронной записи для производительности
- Ротация и архивация старых записей

## Граница

### Владеет
- Схемой таблицы логов
- Форматом записываемых событий
- Механизмом буферизации записи
- Политикой хранения логов

### Не владеет
- Логами приложения в файлах (stdout/stderr)
- Метриками производительности
- Трассировкой распределённых транзакций
- Алертингом и мониторингом

## Контракт

### Публичный интерфейс

```python
class DbLoggingService:
    def log_event(
        self,
        event_type: str,
        level: str,
        message: str,
        session_id: Optional[str] = None,
        metadata: Optional[dict] = None
    ) -> None
    
    def log_user_action(
        self,
        action: str,
        user_id: str,
        details: dict
    ) -> None
    
    def log_skill_execution(
        self,
        skill_name: str,
        status: str,
        duration_ms: float,
        result_summary: Optional[str] = None
    ) -> None
    
    def get_logs(
        self,
        session_id: Optional[str] = None,
        event_type: Optional[str] = None,
        from_time: Optional[datetime] = None,
        limit: int = 100
    ) -> List[LogEntry]
    
    def flush_buffer(self) -> None
```

### Требования

#### Требование: Запись события

**Сценарий: Логирование системного события**
- **КОГДА** происходит значимое событие системы
- **ТОГДА** событие записывается в таблицу логов
- **И** включает timestamp, тип события, уровень, сообщение
- **И** опционально включает session_id и метаданные

#### Требование: Логирование действий пользователя

**Сценарий: Отслеживание пользовательских действий**
- **КОГДА** пользователь выполняет действие
- **ТОГДА** действие записывается с категорией `user_action`
- **И** включает user_id, тип действия, детали
- **И** сохраняется независимо от результата действия

#### Требование: Логирование выполнения Skills

**Сценарий: Отслеживание работы Skills**
- **КОГДА** Skill завершает выполнение
- **ТОГДА** записывается событие с категорией `skill_execution`
- **И** включает имя Skill, статус, длительность
- **И** опционально включает краткое описание результата

#### Требование: Буферизация записи

**Сценарий: Оптимизация производительности**
- **КОГДА** логи записываются асинхронно
- **ТОГДА** они буферизируются в памяти
- **И** периодически сбрасываются в БД пакетом
- **И** при shutdown буфер принудительно сбрасывается

### Запрещённое поведение

Логирование в БД НЕ ДОЛЖНО:
- Блокировать основную логику приложения при ошибке записи
- Записывать чувствительные данные (пароли, токены)
- Создавать циклические зависимости (логировать логирование)
- Прерывать работу приложения при недоступности БД
- Хранить логи бесконечно без политики ротации

## Зависимости

### Может зависеть от
- ConfigService для параметров подключения
- ApplicationContext для доступа к пулу соединений
- Logger для дублирования критических ошибок

### Не должен зависеть от
- Бизнес-логики Skills
- Конкретных типов событий домена
- Внешних систем мониторинга

## Конфигурация

```yaml
logging.database:
  enabled: true
  table_name: "system_logs"
  schema: "public"
  batch_size: 100
  flush_interval_sec: 5.0
  retention_days: 30
  async_writes: true
  include_metadata: true
  levels:
    - DEBUG
    - INFO
    - WARNING
    - ERROR
    - CRITICAL
```

## Жизненный цикл

1. **Инициализация**: Создание таблицы, загрузка конфигурации
2. **Работа**: Приём событий, буферизация, периодическая запись
3. **Ротация**: Удаление старых записей по расписанию
4. **Завершение**: Сброс буфера, закрытие соединений

## Состояние

```python
{
    "buffer": List[LogEntry],
    "last_flush": datetime,
    "connection_pool": Pool,
    "is_enabled": bool,
    "write_errors": int
}
```

## Инварианты

- Каждое событие имеет уникальный ID
- Timestamp события всегда устанавливается при создании
- Уровень лога соответствует стандартным уровням (DEBUG..CRITICAL)
- Буфер сбрасывается при достижении batch_size или timeout
- При shutdown все buffered записи сохраняются

## Поведение при ошибке

- Ошибка подключения к БД → логирование в stderr, отключение DB logging
- Ошибка записи → повторная попытка, затем пропуск записи
- Переполнение буфера → принудительный сброс
- Ошибка ротации → логирование, продолжение работы

## Потребители

- ApplicationContext — системные события
- AgentLoop — события выполнения агентов
- Skills — логирование выполнения
- Gateway/CLI — пользовательские действия
- Session Manager — события сессий
