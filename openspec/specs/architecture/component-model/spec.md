# Модель архитектурного компонента

## Назначение

Этот документ определяет единую модель архитектурного компонента проекта `workspaces_nanobot` и обязательный шаблон для всех компонентных спецификаций.

Модель обеспечивает:

- единообразие описания компонентов;
- разделение контрактной информации и деталей реализации;
- возможность автоматической проверки полноты спецификаций;
- явное определение границ ответственности каждого компонента.

## Источник истины

- Нормативные правила архитектуры: `docs/TARGET_ARCHITECTURE.md`.
- Описание текущей реализации: `docs/ARCHITECTURE.md` и другие файлы в `docs/`.
- Реестр компонентов: `openspec/specs/COMPONENTS.md`.

## Что является компонентом

Компонент — это самостоятельная архитектурная единица, которая имеет хотя бы одно из:

- собственный жизненный цикл;
- публичный контракт;
- собственную конфигурацию;
- собственное состояние;
- отдельную ответственность;
- отдельные внешние зависимости;
- возможность независимо изменяться;
- архитектурную границу.

### Примеры компонентов

```text
ApplicationContext          → компонент
ConfigService               → компонент
PGSessionManager            → компонент
MessageBus                  → компонент
PostgresChannel             → компонент
RedisChannel                → компонент
CacheProvider               → компонент
VectorIndexService          → компонент
DbLoggingService            → компонент
RuntimePatcher              → компонент
AgentFactory                → компонент
AgentLoop                   → компонент
Skill                       → компонент
Tool                        → компонент
Benchmark                   → компонент
```

### Не являются отдельными компонентами

```text
_некий_private_helper()
format_name()
маленький DTO
внутренняя константа
```

## Обязательный шаблон компонентной спецификации

Каждая компонентная спецификация **ДОЛЖНА** содержать следующие разделы:

```markdown
# <Название компонента>

## Назначение

## Ответственность

## Граница

## Публичный контракт

## Входы

## Выходы

## Состояние

## Зависимости

## Конфигурация

## Жизненный цикл

## Владение данными

## Поведение при ошибке

## Инварианты

## Запрещённое поведение

## Потребители

## Реализация

## Проверка
```

### Требования к разделам

#### Назначение (Purpose)

Одно-два предложения, отвечающие на вопрос: **зачем существует этот компонент?**

Пример:
```markdown
Предоставляет единый корень сборки общей инфраструктуры runtime.
```

#### Ответственность (Responsibility)

Что компонент **обязан** делать. Перечисление ключевых обязанностей.

Пример:
```markdown
Компонент отвечает за:
- сборку runtime-сервисов;
- координацию жизненного цикла;
- предоставление доступа к общим сервисам.
```

#### Граница (Boundary)

Явное определение того, что компонент **владеет**, что **может использовать**, и что **не должен использовать**.

Формат:
```markdown
Владеет:
- ...

Может зависеть от:
- ...

Не должен зависеть от:
- ...
```

#### Публичный контракт (Public Contract)

Открытые интерфейсы, методы, API, которые использует внешний мир.

Пример:
```markdown
- `ApplicationContext.create()` — точка входа для сборки приложения.
- `ctx.get_service(name)` — доступ к сервисам.
- `ctx.start()` / `ctx.stop()` — управление жизненным циклом.
```

#### Входы (Inputs)

Что компонент принимает извне.

#### Выходы (Outputs)

Что компонент производит или возвращает.

#### Состояние (State)

Какое состояние хранит компонент, если применимо.

Для stateless-компонентов указать явно:
```markdown
Компонент не хранит состояния.
```

#### Зависимости (Dependencies)

От каких других компонентов зависит данный компонент.

#### Конфигурация (Configuration)

Какие конфигурационные параметры читает компонент.

#### Жизненный цикл (Lifecycle)

Как компонент создаётся, инициализируется, уничтожается.

Для компонентов без явного lifecycle указать:
```markdown
Жизненный цикл не применяется (stateless utility).
```

#### Владение данными (Data Ownership)

Какими данными владеет компонент.

#### Поведение при ошибке (Error Behavior)

Как компонент ведёт себя при ошибках.

#### Инварианты (Invariants)

Условия, которые всегда истинны для этого компонента.

#### Запрещённое поведение (Forbidden Behavior)

Что компонент **НЕ ДОЛЖЕН** делать никогда.

Формат:
```markdown
Компонент НЕ ДОЛЖЕН:
- ...
- ...
```

#### Потребители (Consumers)

Кто использует этот компонент.

#### Реализация (Implementation Reference)

Ссылки на код реализации.

Формат:
```markdown
Основная реализация:
- `lib/core/application_context.py:ApplicationContext`

Связанные компоненты:
- `lib/core/agent_factory.py:AgentFactory`
- `lib/services/config_service.py:ConfigService`
```

**Важно:** Код не должен копироваться в спецификацию. Спецификация описывает контракт, а не реализацию.

#### Проверка (Verification)

Как проверяется соответствие спецификации.

Пример:
```markdown
- Архитектурные тесты: `tests/test_architecture_*.py`
- Контрактные тесты: `tests/test_<component>_contract.py`
- CI-проверки: валидация структуры спецификации
```

## Язык спецификаций

**Все новые и изменяемые компонентные спецификации проекта ДОЛЖНЫ быть написаны на русском языке.**

Технические идентификаторы, имена классов, методов, файлов, конфигурационных ключей и API **СОХРАНЯЮТ оригинальное написание**.

## Разделение ответственности документации

### OpenSpec (`openspec/specs/`)

Отвечает: **Что компонент обязан делать и какие ограничения существуют?**

- Нормативный контракт компонента.
- Архитектурные инварианты.
- Запрещённое поведение.
- Границы ответственности.

### `docs/`

Отвечает: **Как текущая реализация это делает?**

- Детали реализации.
- Операционные руководства.
- Исторические/WIP заметки.
- Implementation reference.

### Код

Отвечает: **Как это реализовано непосредственно сейчас?**

- Фактическая реализация.
- Внутренние детали.
- Алгоритмы.

### Именование файлов

- Каждая спецификация размещается в отдельном каталоге вида `<domain>/<component-name>/`.
- Файл спецификации всегда называется `spec.md`.
- Название каталога компонента используется в kebab-case (например, `application-context`, `cache-provider`).

## Реестр компонентов

Реестр компонентов (`openspec/specs/COMPONENTS.md`) **ДОЛЖЕН** содержать:

| Компонент | Категория | Реализация | Спецификация | Статус |
|-----------|-----------|------------|--------------|--------|

Статусы:
- `missing` — компонент существует в коде, но спецификация отсутствует.
- `draft` — спецификация создана, но неполная.
- `partial` — спецификация содержит основные разделы, но требует доработки.
- `complete` — спецификация полная и соответствует шаблону.
- `deprecated` — компонент устарел и будет удалён.

### Правила реестра

1. **Каждый production-компонент ДОЛЖЕН иметь запись в реестре.**
2. **Реестр НЕ содержит описание поведения** — только метаданные.
3. **Реестр не является вторым источником истины** — он ссылается на спецификации.

## Валидация спецификаций

CI **ДОЛЖЕН** проверять:

1. **Существование спецификации**: каждая запись в `COMPONENTS.md` имеет соответствующий файл `spec.md`.
2. **Обязательные секции**: каждая спецификация содержит минимальный набор разделов.
3. **Язык**: запрещены английские заголовки нормативных секций.
4. **Отсутствие дублирования**: один компонент — одна спецификация.

## Требования

### Требование: каждый архитектурный компонент имеет спецификацию

Система ДОЛЖНА поддерживать реестр архитектурных компонентов.

Каждый production-компонент, включённый в реестр, ДОЛЖЕН иметь отдельную OpenSpec specification.

#### Сценарий: обнаружен новый компонент

- **КОГДА** в коде выявлен новый архитектурный компонент
- **ТОГДА** он ДОЛЖЕН быть добавлен в `COMPONENTS.md` со статусом `missing`
- **И ЗАТЕМ** для него ДОЛЖНА быть создана спецификация

### Требование: спецификация на русском

Все новые и изменяемые компонентные спецификации ДОЛЖНЫ быть написаны на русском языке.

Технические идентификаторы, имена классов, методов, файлов, конфигурационных ключей и API ДОЛЖНЫ сохранять оригинальное написание.

### Требование: единый шаблон

Каждая компонентная спецификация ДОЛЖНА содержать:

- Назначение
- Ответственность
- Границу
- Контракт
- Зависимости
- Конфигурацию
- Жизненный цикл (если применимо)
- Состояние (если применимо)
- Инварианты
- Запрещённое поведение
- Ссылку на реализацию
- Проверку

### Требование: разделение ответственности

Component specification ДОЛЖНА описывать contractual behavior.

Implementation details ДОЛЖНЫ оставаться в `docs/` и source code, если они не необходимы для определения контракта.

### Требование: единственный источник истины

Нормативные архитектурные правила ДОЛЖНЫ оставаться в `docs/TARGET_ARCHITECTURE.md`.

Контракты конкретных компонентов ДОЛЖНЫ поддерживаться в `openspec/specs/<domain>/<component>/spec.md`.

Описания реализации ДОЛЖНЫ оставаться в `docs/`.

### Требование: отсутствие дублирования

Система НЕ ДОЛЖНА создавать второе нормативное описание одного и того же компонента в другом файле OpenSpec.

### Требование: реестр

Система ДОЛЖНА поддерживать единый реестр компонентов.

## Проверка

- Валидация структуры: будущий CI-скрипт `validate_component_specs`.
- Сверка с кодом: ручная проверка соответствия реализации и контракта.
- Архитектурный review: каждое изменение спецификации проходит review.
