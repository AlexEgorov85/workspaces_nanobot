# Управление подпроцессами

## Назначение

Управление подпроцессами обеспечивает создание, мониторинг и завершение внешних процессов (subprocess), используемых системой для выполнения изолированных задач, таких как транскрипция аудио, обработка файлов или запуск внешних инструментов.

## Ответственность

- Создание и запуск внешних процессов
- Мониторинг состояния процессов (running, completed, failed)
- Перехват stdout/stderr потоков
-Graceful shutdown процессов при завершении приложения
- Обработка таймаутов выполнения
- Ограничение ресурсов (CPU, memory) для процессов

## Граница

### Владеет
- Реестром активных процессов
- Механизмом запуска процессов с заданными параметрами
- Потоками ввода/вывода процессов
- Политикой завершения процессов

### Не владеет
- Бизнес-логикой, выполняемой в процессах
- Интерпретацией результатов выполнения
- Управлением внешними зависимостями процессов
- Файловой системой (кроме временных файлов процессов)

## Контракт

### Публичный интерфейс

```python
class SubprocessManager:
    def start_process(
        self,
        command: List[str],
        process_id: str,
        cwd: Optional[str] = None,
        env: Optional[Dict[str, str]] = None,
        timeout_sec: Optional[float] = None,
        capture_output: bool = True
    ) -> ProcessHandle
    
    def get_process(self, process_id: str) -> Optional[ProcessInfo]
    def wait_for_process(
        self,
        process_id: str,
        timeout_sec: Optional[float] = None
    ) -> ProcessResult
    
    def terminate_process(self, process_id: str, force: bool = False) -> bool
    def terminate_all(self, force: bool = False) -> None
    def list_processes(self) -> List[ProcessInfo]
    def get_output(self, process_id: str) -> Optional[ProcessOutput]
```

### Требования

#### Требование: Запуск процесса

**Сценарий: Создание внешнего процесса**
- **КОГДА** требуется выполнить внешнюю команду
- **ТОГДА** вызывается `start_process()` с командой и параметрами
- **И** процесс запускается в отдельном процессе ОС
- **И** возвращается handle для управления процессом
- **И** процесс регистрируется в реестре активных

#### Требование: Мониторинг состояния

**Сценарий: Проверка статуса процесса**
- **КОГДА** требуется узнать состояние процесса
- **ТОГДА** вызывается `get_process()` с ID процесса
- **И** возвращается информация о статусе (running, completed, failed)
- **И** включаются метрики (длительность, использование памяти)

#### Требование: Ожидание завершения

**Сценарий: Синхронное ожидание результата**
- **КОГДА** требуется получить результат выполнения
- **ТОГДА** вызывается `wait_for_process()` с опциональным таймаутом
- **И** блокировка продолжается до завершения или таймаута
- **И** возвращается результат (exit code, stdout, stderr)

#### Требование: Завершение процесса

**Сценарий: Корректная остановка процесса**
- **КОГДА** процесс требуется остановить досрочно
- **ТОГДА** вызывается `terminate_process()` сначала мягко (SIGTERM)
- **И** при неудаче через timeout применяется force (SIGKILL)
- **И** процесс удаляется из реестра активных

#### Требование: Shutdown всех процессов

**Сценарий: Завершение работы приложения**
- **КОГДА** приложение завершает работу
- **ТОГДА** вызывается `terminate_all()` для всех активных процессов
- **И** процессы получают SIGTERM
- **И** при необходимости применяется SIGKILL
- **И** все ресурсы освобождаются

### Запрещённое поведение

Subprocess Manager НЕ ДОЛЖЕН:
- Позволять запуск процессов без уникального ID
- Терминировать процессы вне реестра
- Игнорировать таймауты выполнения
- Оставлять zombie-процессы после завершения
- Блокировать основное приложение бесконечно
- Запускать процессы от имени root без явной конфигурации

## Зависимости

### Может зависеть от
- ConfigService для лимитов ресурсов
- Logger для логирования событий процессов
- ApplicationContext для интеграции lifecycle

### Не должен зависеть от
- Конкретных типов команд
- Бизнес-логики результатов
- Внешних оркестраторов процессов

## Жизненный цикл

1. **Инициализация**: Загрузка конфигурации, создание рабочей директории
2. **Запуск процессов**: Создание процессов по запросу компонентов
3. **Мониторинг**: Отслеживание состояния, таймауты
4. **Завершение**: Graceful shutdown всех процессов

## Инварианты

- Каждый процесс имеет уникальный ID в пределах сессии
- Один процесс не может быть запущен дважды с тем же ID
- Завершённые процессы сохраняются в истории до очистки
- При shutdown все процессы завершаются
- Лимит одновременных процессов не превышается

## Поведение при ошибке

- Ошибка запуска → исключение, процесс не регистрируется
- Таймаут процесса → автоматическое завершение, логирование
- Процесс упал сам → запись статуса failed, логирование stderr
- Ошибка завершения → force kill, логирование ошибки
