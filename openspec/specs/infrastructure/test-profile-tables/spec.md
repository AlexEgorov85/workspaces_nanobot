# infrastructure/test-profile-tables Specification

## Purpose
Нормативный контракт DDL для 5 runtime-таблиц, на которые переключает профиль `test`: наличие, структура, источник определения и способ применения. Capability фиксирует, что test-таблицы — это структурные клоны prod-собратьев, не отдельная схема; живут в той же схеме `public` и применяются через `tools/apply_test_profile_tables.py` или прямой `psql -f`.

## Scope

`agent` — DDL тестового контура и его runner — в агентском репозитории; платформа только повторяет объявленные имена
Реализация: `sql/*/create_public_*_test.sql`, `tools/apply_test_profile_tables.py`

## Requirements

### Requirement: Пять test-таблиц структурно эквивалентны prod-собратьям

DDL в `sql/<domain>/create_public_agent_*_test.sql` SHALL повторять prod-DDL с точностью до: имя таблицы (добавлен суффикс `_test`), `COMMENT ON TABLE / COLUMN` (упоминает «test-профиль»), колонки и их типы, индексы (включая `agent_gateway_logs_test_user_id_timestamp_idx` в `agent_gateway_logs_test`). Расхождения в колонках, типах или ограничениях относительно prod-версии ЗАПРЕЩЕНЫ (допустимы лишь семантически эквивалентные различия в дефолтах UUID-функций и именах sequences — см. `sql/README.md`).

#### Scenario: Все пять create-скриптов существуют
- **КОГДА** проверяется каталог `sql/`
- **ТОГДА** должны существовать ровно эти 5 файлов: `sql/channels/create_public_agent_conversation_messages_test.sql`, `sql/session/create_public_agent_session_meta_test.sql`, `sql/session/create_public_agent_session_messages_test.sql`, `sql/logs/create_public_agent_gateway_logs_test.sql`, `sql/logs/create_public_agent_question_runs_test.sql`

#### Scenario: В БД присутствуют test-таблицы с тем же числом колонок, что и prod
- **КОГДА** на БД применён `tools/apply_test_profile_tables.py`
- **ТОГДА** запрос `information_schema.columns` для каждой из 5 test-таблиц возвращает столько же строк, сколько для prod-аналога (с точностью до семантически эквивалентных различий)

### Requirement: Применение идемпотентно

`tools/apply_test_profile_tables.py` SHALL применять все 5 DDL-скриптов в одной транзакции, идемпотентно (через `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`). Повторный запуск SHALL быть no-op без ошибок. Поддерживается DSN из переменной окружения `DATABASE_URL`.

#### Scenario: Повторный запуск без изменений
- **КОГДА** runner запущен повторно на БД, где все 5 таблиц уже созданы
- **ТОГДА** runner завершается с exit 0 и печатает `ALL_OK` для каждого скрипта

### Requirement: В runtime-коде запрещено автоматическое создание test-таблиц

Runtime-код `lib/`, `workspace/`, `gateway.py`, `cli_agent.py` SHALL NOT содержать `ensure_tables()` / `CREATE TABLE IF NOT EXISTS` для runtime-таблиц профиля. DDL живёт ТОЛЬКО в `sql/<domain>/` и применяется через `tools/apply_test_profile_tables.py` или `psql -f`.

#### Scenario: Поиск ensure_tables не находит test-DDL в runtime
- **КОГДА** выполняется `rg -i "ensure_tables|create table if not exists" lib/ workspace/ tools/ gateway.py cli_agent.py`
- **ТОГДА** совпадений SHALL не быть (DDL — только в `sql/`)

### Requirement: Документация покрывает test-таблицы

`sql/README.md` SHALL содержать раздел «Test-профиль» с перечнем 5 DDL-файлов и командой применения. `docs/PROFILES.md` SHALL ссылаться на DDL и runner как на источник test-таблиц.

#### Scenario: README содержит раздел Test-профиль
- **КОГДА** разработчик открывает `sql/README.md`
- **ТОГДА** в разделе «Test-профиль» перечислены 5 create-скриптов и упомянута команда `python tools/apply_test_profile_tables.py`

## Responsibility

Компонент состоит из двух частей, и ответственность у них разная.

**DDL-файлы** (`sql/<domain>/create_public_agent_*_test.sql`) отвечают за структуру пяти тестовых таблиц. Их работа — создать таблицу, структурно эквивалентную prod-собете, в той же схеме `public`, в живом виде на 9.4 и на 13.22.

**Runner** (`tools/apply_test_profile_tables.py`) отвечает ровно за три вещи: разобрать имя каждой таблицы из настроек профиля `test`, применить соответствующий DDL в одной транзакции, честно сообщить результат через код возврата. Больше он ничего не делает — не проверяет схему, не создаёт пользователя, не настраивает пул.

Ключевое свойство, ради которого компонент существует: **test-таблицы — это структурные клоны prod-собратьев, а не отдельная схема данных.** Они лежат в `public`, носят суффикс `_test` и отличаются от боевых только именем. Отдельный тестовый слой схемы означал бы, что проверки идут по другой форме, чем бой, и расхождение обнаруживалось бы в проде.

Ответственность компонента **не** включает решение, что тестовые таблицы должны существовать. Это решение принимает оператор, запуская runner; runtime-код только читает их наличие при старте и сообщает подсказку, если их нет.

## Boundary

- **Входит:** пять DDL-файлов в `sql/channels`, `sql/session`, `sql/logs`.
- **Входит:** `config.runtime_table(role, "test")` — чтение имён таблиц из настроек профиля.
- **Входит:** переменная окружения `DATABASE_URL` — единственный способ узнать, к какой базе подключаться.
- **Выходит:** объекты в базе данных, код возврата процесса, диагностический вывод в stdout/stderr.
- **Не входит:** схема `test` в отдельном смысле. Таблицы создаются в `public`; слово `test` входит только в имя таблицы.
- **Не входит:** права и роли. Runner не выдаёт `GRANT`, не создаёт пользователя и не трогает `default privileges`: он владеет структурой, и только ей.
- **Не входит:** миграции. У тестового контура нет своей истории миграций; DDL всегда полный, а не инкрементальный. Драп данных, применяемый к prod, живёт в `sql/migrations/` и к этому компоненту не относится.
- **Не входит:** runtime-путь. Ни один модуль `lib/`, `workspace/`, `gateway.py`, `cli_agent.py` не содержит DDL и не вызывает runner. Между стартом и применением DDL нет автоматики — только явный запуск.
- **Не входит:** `sql/migrations/` и `tools/migrate.py`. Это прод-контур; требование запрета автосоздания в runtime расширено на `tools/`, и `tools/migrate.py` в него попадает.

## Public Contract

Контракт состоит из двух поверхностей: файловой схемы и поведения runner'а.

**Схема файла.** `<каталог>/create_public_<имя таблицы>.sql`. Имя файла **выводится из имени таблицы**, а не задаётся списком: `ddl_files()` строит путь как `ROOT / directory / f"create_public_{table}.sql"`, где `table = runtime_table(role, "test")`. Отсюда контракт: переименование таблицы в `profiles/test.jsonc` без переименования DDL обязано упасть, а не применить старую схему.

**Пять ролей и их каталогов** — единственное место в проекте, где эта раскладка объявлена для тестового контура:

| Роль | Каталог | Таблица в профиле `test` |
| --- | --- | --- |
| `conversation_messages` | `sql/channels` | `agent_conversation_messages_test` |
| `session_meta` | `sql/session` | `agent_session_meta_test` |
| `session_messages` | `sql/session` | `agent_session_messages_test` |
| `question_runs` | `sql/logs` | `agent_question_runs_test` |
| `gateway_logs` | `sql/logs` | `agent_gateway_logs_test` |

Порядок этот — порядок применения. Каталог `sql/session` отдаёт две разные таблицы, поэтому раскладка объявлена списком пар `(каталог, роль)`, а не словарём «каталог → таблица».

**Двойная движковая совместимость** — часть контракта, а не деталь реализации. Один и тот же файл применяется к Greenplum 6.5 (ядро PostgreSQL 9.4) и к PostgreSQL 13.22 тестового контура. Отсюда два правила, оба проверяемые:

- Клауза `DISTRIBUTED BY` обязана присутствовать, но **не в теле `CREATE TABLE`** — там на PostgreSQL 13 это синтаксическая ошибка. Она объявляется ограждённым шагом `EXECUTE 'SET DISTRIBUTED BY ...'`, который срабатывает только при наличии `pg_dist_partition`.
- Конструкции новее 9.4 запрещены: `ON CONFLICT` (9.5), `ADD COLUMN IF NOT EXISTS` (9.6), `CREATE [UNIQUE] INDEX IF NOT EXISTS` (9.5).

**Идемпотентность** обеспечивается механизмом, соответствующим ядру 9.4, а не только модной клаузой:

- `CREATE EXTENSION IF NOT EXISTS` и `CREATE TABLE IF NOT EXISTS` — прямые клаузы, поддержанные 9.4.
- Индексы и ALTER-шаги журнала — через `DO $$ ... IF NOT EXISTS (SELECT ... FROM pg_indexes/pg_attribute ...) THEN ... END IF; END $$;`. Это единственный способ остаться идемпотентным, не поднимая требование к ядру.

**Поведение runner'а** как функция:

```
DATABASE_URL не задан            → stderr «DATABASE_URL не задан»,            код 2
DDL-файл отсутствует            → FileNotFoundError на импорте, имя роли и путь
любой statement не применился    → stderr «FAIL stmt #i (head)», rollback,    код 1
все применились                  → commit, «ALL_OK»,                          код 0
```

`main()` печатает `ALL_OK` **один раз, после успешного коммита**, а не на каждый скрипт: на каждый скрипт печатается строка `== <путь>: <N> statements`, на каждый statement — `  ok #i: <первая строка>`. Требование выше сформулировано проще, чем работает код, и код здесь прав: признак «всё применилось» относится к транзакции, а не к файлу.

## Inputs

**Имя базы.** `os.environ.get("DATABASE_URL")`, константа `DSN_ENV`. Это единственный вход времени выполнения. Ни `config.json`, ни аргументы командной строки, ни интерактивный ввод не читаются: у runner'а нет `argparse` вообще.

**Имена таблиц.** Не литералы в SQL и не литералы в Python. `ddl_files()` вызывает `config.runtime_table(role, "test")` для каждой из пяти ролей, а тот читает `EXPECTED_RUNTIME_TABLE_NAMES["test"]`. Переименование таблицы в настройках меняет и имя файла, который runner ищет, — без правки кода runner'а.

**Пути DDL.** Вычисляются как `ROOT / <каталог> / f"create_public_{table}.sql"`, где `ROOT = Path(__file__).resolve().parents[1]`. Переопределения из CLI нет: каталог задаётся положением самого скрипта.

**Содержимое DDL.** Текст каждого файла, прочитанный целиком и разбитый `split_statements()`: построчно, строки с `--` отбрасываются, границей statement'а считается строка, чей `rstrip()` кончается на `;`, непустой остаток в конце файла сохраняется как последний statement.

**Что входом не является.** Никакого дополнительного описания таблиц: числа колонок, индексы и комментарии живут в SQL-файлах, и runner ничего о них не знает. Никакого «схема должна совпасть с prod» — runner не читает prod-DDL и не сравнивает.

## Outputs

**Объекты в базе.** Пять таблиц, индексов и расширения `pgcrypto`, созданные в схеме `public`. Это единственный результат, ради которого компонент существует.

**Код возврата.** `0` — транзакция закоммичена; `1` — отказ statement'а с откатом; `2` — не задан `DATABASE_URL` или отсутствует DDL-файл. Значений вне этого множества runner не возвращает.

**Диагностический вывод.** stdout несёт прогресс построчно и поstatement'но, stderr — отказы.

```
== sql/channels/create_public_agent_conversation_messages_test.sql: 3 statements
  ok #1: CREATE EXTENSION IF NOT EXISTS "pgcrypto";
  ok #2: CREATE TABLE IF NOT EXISTS public.agent_conversation_messages_test (
...
ALL_OK
```

Отказ выглядит так, с именем роли и полным путём, чтобы не гадать:

```
DDL для роли 'gateway_logs' не найден: <корень>/sql/logs/create_public_agent_gateway_logs_test.sql
```

Сообщение об отказе statement'а содержит его номер, первые 60 символов текста, имя исключения и первые 160 символов сообщения — этого достаточно, чтобы отличить синтаксическую ошибку от отказа в праве или уже существующего объекта.

**Коммиты и откаты.** Один `commit()` на весь прогон и один `rollback()` на первый отказ. Промежуточных коммитов нет: неудачный прогон не оставляет схему наполовину.

## State

Между запусками компонент не хранит состояния. Файлы DDL неизменяемы, runner одноразовый, кэша и журнала нет.

Состояние, которое компонент видит и изменяет, — **сама база данных**, и оно двояко:

- **Неизменяемая часть.** `CREATE EXTENSION IF NOT EXISTS` и `CREATE TABLE IF NOT EXISTS` не меняют уже существующий объект. Повторный прогон на готовой базе — no-op.
- **Изменяемая часть, и она важна.** `SET DISTRIBUTED BY` внутри ограждённого шага перераспределяет уже созданную таблицу; шаги с `pg_attribute` добавляют недостающие колонки журнала и заполняют их значениями по умолчанию. Именно здесь идемпотентность перестаёт быть тривиальной и обеспечивается проверками в самом SQL.

Полностью идемпотентным компонент является по отношению к повторному прогону, но не по отношению к более старой версии DDL: если в файл добавлена колонка, её добавление выполнится, а удаление переименованной колонки — нет. Схема движется вперёд применением, но не назад.

Внутри одного запуска состояние одно — открытая транзакция; она либо коммитится целиком, либо откатывается целиком.

## Dependencies

**Сторонних зависимостей ровно одна:** `psycopg2`, импортируется на уровне модуля `tools/apply_test_profile_tables.py`. Ни ORM, ни миграционного фреймворка, ни пула соединений: одно `psycopg2.connect(dsn)` на прогон.

**Внутренних импортов один:** `from config import runtime_table`. Перед ним скрипт делает `sys.path.insert(0, str(ROOT))` — единственная причина, по которой в `tools/` вообще допустим импорт из корня репозитория. Этот импорт несёт смысловую нагрузку: он делает переименование таблицы в настройках обязательным шагом, а не правкой кода.

**Зависимость от данных:** пять DDL-файлов. Runner проверяет их наличие и падает, если файла нет, но не проверяет их содержимое — DDL принадлежит сам себе.

**Зависимость от среды:** PostgreSQL 9.4-совместимый диалект, а также возможность создать расширение `pgcrypto`. На Greenplum 6.5 и PostgreSQL 13.22 файл одинаково применим; на 9.5+ всё так же, но новее 9.4 конструкции в файле быть не должно.

**Не зависит:** от `lib/`, `workspace/`, `gateway.py`, `cli_agent.py` и любого runtime-кода. Зависимость строго односторонняя: runtime читает наличие таблиц, runner о runtime ничего не знает.

## Configuration

Настраиваемо ровно одно — **имя таблицы**, и оно настраивается не у runner'а.

| Что | Где объявлено | Как читается |
| --- | --- | --- |
| Имена пяти test-таблиц | `EXPECTED_RUNTIME_TABLE_NAMES["test"]` в `config.py` | `config.runtime_table(role, "test")` |
| DSN | переменная окружения `DATABASE_URL` | `os.environ.get(DSN_ENV)` в `main()` |

Всё остальное не настраивается намеренно:

- **Список ролей и их каталогов** — литеральный `_DDL` в runner'е. Он не читается из настроек, потому что это раскладка файлов, а не конфигурация базы.
- **Схема** — всегда `public`. Она не параметризуется: смена схемы означала бы другой компонент.
- **Путь к SQL** — вычисляется от корня репозитория, переопределения нет.
- **Аргументы командной строки** — отсутствуют как класс: у runner'а нет `argparse`, и он не примет ни одного флага.

Отдельно: `profiles/test.jsonc` объявляет активный профиль, но runner'а он не читает. Профиль `test` передаётся ему литералом в вызове `runtime_table(role, "test")` — сознательно, потому что инструмент применяет именно тестовый контур и не должен применяться к другому профилю по ошибке окружения.

## Lifecycle

Runner одноразовый: `if __name__ == "__main__": raise SystemExit(main())`, без сервера, без демона, без фоновых потоков.

1. **Импорт модуля.** `FILES = ddl_files()` вычисляется на уровне модуля, то есть **до** `main()`. Здесь же `sys.path.insert` и импорт `config.runtime_table`. Отсутствие DDL-файла приводит к `FileNotFoundError` именно на этом шаге, до чтения `DATABASE_URL`.
2. **Проверка DSN.** `main()` читает `DATABASE_URL`; пустое значение — код `2`. Порядок именно такой: имя файла проверяется первым, потому что опечатка в настройках должна называть отсутствующий файл, а не требовать настроенного подключения.
3. **Повторная проверка наличия файлов** в `main()` для каждого элемента `FILES`. В текущем коде это проверка с двойным назначением: `FILES` уже собрано с проверкой существования на шаге 1, и второй проход недостижим при первом сбое. Оставлен как защита на случай, если `FILES` станет вычисляемым позже.
4. **Подключение.** Одно `psycopg2.connect(dsn)` в контекстном менеджере.
5. **Применение.** Для каждого файла — чтение, `split_statements()`, `cur.execute()` на каждый statement, печать `ok #i`.
6. **Отказ или коммит.** Первое исключение — печать в stderr, `conn.rollback()`, код `1`. Успех — `conn.commit()`.
7. **Вывод.** `ALL_OK`, код `0`.

DDL-файлы своего жизненного цикла не имеют: они редактируются вручную и применяются повторно сколько угодно раз.

## Data Ownership

Компонент **владеет структурой тестовых таблиц** и только ею.

**Владеет:**

- Определением пяти таблиц: колонками, типами, `NOT NULL`, значениями по умолчанию, комментариями.
- Определением индексов, включая `agent_gateway_logs_test_user_id_timestamp_idx`, `idx_agent_gateway_logs_test_seq` и `idx_agent_gateway_logs_test_occurred_at`.
- Ключом распределения `DISTRIBUTED BY` — о нём стоит сказать отдельно: на Greenplum без явной клаузы распределение выбирает движок, и первое же изменение состава колонок меняет его молча.
- Идемпотентностью повторного применения.

**Не владеет:**

- **Данными.** `test_test_profile_does_not_delete_rows` в `tests/test_journal_event_time_columns.py` требует, чтобы DDL тестового профиля не содержал `DELETE FROM`: очистка строк — отдельная операция по замеру, а не файл DDL. Удаление данных из DDL сделало бы повторный прогон разрушительным.
- **Правами и ролями.** Ни `GRANT`, ни `REVOKE`, ни создание пользователя.
- **Миграциями.** У тестовой схемы нет истории версий; DDL всегда полный.
- **Боевыми таблицами.** Prod-контур — отдельный компонент со своим DDL и своим применением.

**Не владеет фактом применения.** Runner создаёт объекты, но не ведёт реестра применений: повторный запуск определяется наличием объектов в базе, а не записью в журнале миграций. Это упрощение и есть цена отсутствия миграций в тестовом контуре.

Отношение к `test`-контуру в остальном проекте — **потребитель/производитель по имени**: платформа повторяет те же имена таблиц из своих настроек, но не создаёт их и не отвечает за их структуру. Переименование таблицы обязано быть сделано в одном месте — в настройках профиля, — и runner подхватит его автоматически, а платформа получит то же имя из своих настроек. Расхождение здесь возможно, и его ловят тесты профилей, а не этот компонент.

## Error Behavior

Отказов три уровня, и различать их важно.

**Ошибка конфигурации — до подключения.**

- Нет `DATABASE_URL`: сообщение `DATABASE_URL не задан` в stderr, код `2`. Подсказки с примером DSN в рантайме нет — она есть в докстринге модуля, а тот читается при первом запуске, когда человек ещё в состоянии исправить строку.
- Нет DDL-файла: `FileNotFoundError` на этапе импорта с указанием **роли** и **полного пути** и объяснением, что имя взято из профиля `test` и файл нужно переименовать вместе с таблицей. Это самый полезный отказ в компоненте: он отличает «опечатка в настройке» от «файл потерян», а сообщение только с путём не отличала бы.

**Ошибка применения — внутри транзакции.** Первое исключение на любом statement'е любого файла:

- В stderr — `FAIL stmt #i ('<первые 60 символов>'): <тип исключения>: <сообщение, первые 160 символов>`.
- `conn.rollback()` — вся транзакция откатывается, включая уже применённые statement'ы предыдущих файлов.
- Код `1`, выполнение немедленно прекращается: оставшиеся файлы не применяются.

Отказ на середине не оставляет схему наполовину. Это стоит проговорить, потому что порядок применения фиксирован и журнал (`gateway_logs`) идёт последним: если он падает, `conversation_messages` и таблицы сессий откатываются вместе с ним.

**Отказ совместимости — в SQL, до Python.** Синтаксическая ошибка движка приходит из базы как `psycopg2` exception и обрабатывается тем же третьим уровнем. Отдельного разбора ошибок PostgreSQL нет: компонент не различает `UndefinedTable`, `InsufficientPrivilege` и синтаксическую ошибку, он печатает тип и текст и останавливается. Это осознанно — классификация ошибок DDL не входит в ответственность инструмента.

Что компонент **не** делает: не переключает схему поиска, не ставит `search_path`, не отключает `statement_timeout`, не проверяет права до `connect`. Отказ в соединении приходит из `psycopg2.connect` необработанным исключением — traceback и ненулевой код, без красивого сообщения. Это единственное место, где поведение не приведено к общему виду.

## Invariants

1. **Имя файла выводится из имени таблицы.** `create_public_<runtime_table(role, "test")>.sql`. Нет списка файлов в коде, есть список ролей.
2. **Имена таблиц приходят из `config.runtime_table(role, "test")`.** Литерал имени таблицы в runner'е — это второй источник истины, и его быть не должно.
3. **Все пять таблиц — в схеме `public`.** Суффикс `_test` в имени; отдельной схемы нет.
4. **Одна транзакция на весь прогон.** Единственный `commit()` и единственный `rollback()`; частичного применения не бывает.
5. **DDL пригоден для 9.4 и для 13.22 одновременно.** Никаких конструкций новее 9.4; клауза `DISTRIBUTED BY` — только внутри ограждённого шага, а не в теле `CREATE TABLE`.
6. **Идемпотентность выражена средствами 9.4.** `IF NOT EXISTS` там, где он есть в 9.4; проверки в `pg_indexes`/`pg_attribute` с `DO`-блоком там, где его нет.
7. **Повторный прогон — no-op.** Уже созданная таблица, индекс и колонка не пересоздаются и не ломают прогон.
8. **DDL не удаляет строки.** Отсутствие `DELETE FROM` в DDL тестового профиля — проверяемое требование, а не соглашение.
9. **Комментарии `COMMENT ON` упоминают «test-профиль».** По таблице можно опознать, что она тестовая, читая её описание, не сверяя имя.
10. **DDL не появляется в runtime-коде.** `lib/`, `workspace/`, `gateway.py`, `cli_agent.py` не содержат ни `ensure_tables()`, ни `CREATE TABLE IF NOT EXISTS` для runtime-таблиц; запрет распространён и на `tools/`.

## Forbidden Behavior

- **Автоматически создавать test-таблицы при старте.** Компонент применяется только явно. Автосоздание в рантайме означало бы, что проверки идут по схеме, которую никто не ревьюил.
- **Хранить DDL вне `sql/`.** DDL в Python-строке — это DDL без ревью и без diff'а.
- **Параметризовать схему, роли или путь.** Переопределение из CLI или окружения означало бы, что состав применённой схемы зависит от того, кто и как запустил инструмент.
- **Выводить имя таблицы из литерала в runner'е.** Нарушение инварианта 2, и оно делается почти всегда «на всякий случай».
- **Коммитить по файлу.** Пять отдельных коммитов означают схему, наполовину обновлённую из старого DDL и наполовину из нового.
- **Удалять строки в DDL.** Повторный прогон обязан быть безопасен.
- **Использовать конструкции новее PostgreSQL 9.4.** Работать на одной боевой СУБД — обязательство, а не случайность.
- **Ставить `DISTRIBUTED BY` в тело `CREATE TABLE`.** На PostgreSQL 13.22 это синтаксическая ошибка, и тестовый контур перестанет собираться.
- **Добавлять шестую таблицу «на всякий случай».** Состав из пяти таблиц совпадает с `EXPECTED_RUNTIME_TABLE_NAMES["test"]`; шестая роль без соответствующей записи в настройках — расхождение.
- **Объявлять имена test-таблиц в платформе независимо.** Платформа повторяет объявленное агентом имя, а не ведёт свой список.

## Consumers

- **Оператор тестового контура.** Единственный прямой потребитель: ставит `DATABASE_URL`, запускает `python tools/apply_test_profile_tables.py`, читает `ALL_OK` или отказ с номером statement'а.
- **Startup-валидация схемы агента** (`lib/services/schema_validation.py`). Она читает `runtime_table(role, profile)` для активного профиля и, обнаружив отсутствие таблиц, печатает подсказку `python tools/apply_test_profile_tables.py` для профиля `test` и `python tools/migrate.py --apply` для `prod`. Компонент не вызывает валидацию и не знает о ней — связь идёт через подсказку в тексте ошибки.
- **Платформа.** Повторяет те же имена таблиц из своих настроек профиля и читает их, но не создаёт и не описывает их.
- **Тестовые прогоны боевого поведения.** Всё, что пишет в журнал, вопросы или сообщения под профилем `test`, пишет в эти таблицы; на этом стоят интеграционные проверки.
- **`tests/test_journal_event_time_columns.py`.** Живой прогон миграции на test-таблице использует DDL журнала как источник схемы, отдельную scratch-таблицу в той же базе и тот же разбор на `;`.

- `sql/session/create_public_agent_session_meta_test.sql` — DDL `agent_session_meta_test`.
- `sql/session/create_public_agent_session_messages_test.sql` — DDL `agent_session_messages_test`.
- `sql/logs/create_public_agent_question_runs_test.sql` — DDL `agent_question_runs_test`.
- `sql/logs/create_public_agent_gateway_logs_test.sql` — DDL журнала: расширение, таблица, шаги колонок события, три индекса, ограждённый шаг `SET DISTRIBUTED BY`.
- `tools/apply_test_profile_tables.py` — runner: `DSN_ENV`, `ROOT`, `_DDL`, `ddl_files()`, `FILES`, `split_statements()`, `main()`.

## Verification

- `tests/test_journal_event_time_columns.py` — основной страж DDL журнала. `TestDdlServesBothEngines` применяется в том числе к `TEST_DDL` и требует: ключ распределения объявлен (`SET DISTRIBUTED BY` присутствует, шаг ограждён `pg_dist_partition`), клаузы `DISTRIBUTED BY` вне ограждённого шага нет, конструкций новее 9.4 (`ON CONFLICT`, `ADD COLUMN IF NOT EXISTS`, `CREATE [UNIQUE] INDEX IF NOT EXISTS`) нет. `TestTestProfileKeepsColumnsNullable` требует, чтобы DDL тестового профиля не удалял строки. `TestMigrationOnTestProfile` применяет миграцию к test-таблице живым PostgreSQL при `NANOBOT_LIVE_DB_DSN`.
- `tests/test_schema_validation.py` — страж обратной стороны: `TestHintForProfile` требует, чтобы подсказка для профиля `test` была ровно `python tools/apply_test_profile_tables.py`, а для `prod` — `python tools/migrate.py --apply`. `TestSchemaValidationError` требует, чтобы сообщение об отсутствии таблиц содержало имя runner'а.
- `tests/test_startup_schema_validation_live.py` — живая проверка предела времени startup-валидации; запускается при `NANOBOT_LIVE_E2E=1` и `DATABASE_URL`, без них пропускается. Относится к компоненту через текст подсказки, а не через DDL.
- **Что проверкой не покрыто и чему стража нет:** равенство числа колонок test- и prod-таблиц в живой базе, наличие всех пяти таблиц после прогона, совпадение состава колонок для четырёх таблиц из пяти (журнал проверен отдельно и подробнее), наличие раздела «Test-профиль» в `sql/README.md` и упоминание runner'а в `docs/PROFILES.md`. Разбор на `;` в `split_statements()` тоже не имеет стража — ошибочный разбор проявился бы только на живой базе.
