# runtime/db-queue-classes Specification

## Purpose
Классификация работ, идущих в пул PostgreSQL, и управление очередью по
этой классификации.

Термины, чтобы не было двух ответов на один вопрос:

- **воркер** — поток пула, владеющий ровно одним соединением
  (`libs/enterprise_data/db.py::_Worker`);
- **аудитория** — признак «кто инициировал работу», объявлен в коде
  константами `AUDIENCE_MODEL` / `AUDIENCE_RUNTIME`
  (`servers/enterprise/capabilities/data/service/main.py:49-50`).
  Аудитория **уже** решает вопрос прав (`_require_runtime`); этим change
  она получает второе значение — к какой очереди работа принадлежит;
- **зарезервированный воркер** — воркер, который берёт только
  `runtime`-работы и не берёт `model`-работы никогда.

## Scope

`platform` — пул, класс работы и порядок обслуживания очереди — код capability `data`; агент берёт этот пул только операциями платформы
Реализация: `mcp-platform/libs/enterprise_data/db.py` (`_Worker`, `submit`, `submit_transaction`), `mcp-platform/libs/enterprise_common/settings.py`, `mcp-platform/servers/enterprise/capabilities/data/service/`, `mcp-platform/platform.json` (`pool`, `job_classes`)

## Requirements

### Requirement: Аудитория объявляется в сигнатуре операции и сверяется с реестром

Класс работы определяется **аудиторией, объявленной в сигнатуре метода
`DataService`**, и ничем иным. Реестр операций — единственное место, где
классы записаны поимённо; объявление в сигнатуре обязано совпадать с
реестром.

Границы контракта:

- Реестр объявляется в модуле
  `servers/enterprise/capabilities/data/service/registry.py` под именем
  `OPERATION_AUDIENCE: dict[str, str]`. Ключ — имя метода `DataService`,
  значение — `AUDIENCE_RUNTIME` или `AUDIENCE_MODEL`.
- **Сигнатура метода, трогающего пул, обязана объявлять аудиторию явно:**
  `audience: str = AUDIENCE_RUNTIME` (или `AUDIENCE_MODEL`). Метод без
  параметра `audience` не имеет права вызывать `submit` /
  `submit_transaction`.
- Значение по умолчанию в сигнатуре — это **объявление класса**, и оно
  обязано быть строковым литералом-константой, а не вычисляемым
  выражением.
- Каждая операция, объявленная в реестре, обязана существовать в
  `DataService`; каждая запись реестра обязана быть использована
  (мёртвая запись — дефект реестра, а не безобидная запасная строка).
- Права операций продолжают определяться той же аудиторией
  (`_require_runtime`). Реестр и проверка прав обязаны быть согласованы:
  операция, доступная только рантайму, обязана иметь аудиторию
  `AUDIENCE_RUNTIME`.

**Почему не аргумент вызова.** Если класс приходит от того, кто делает
работу, то «забыл аргумент» — штатный сценарий, и он молча даёт работе
класс `runtime`. Обязательный параметр убирает этот сценарий целиком:
забыть нельзя, `TypeError` на первой же проверке.

#### Сценарий: Новая операция без класса ломает сборку

- **КОГДА** добавлен метод `DataService`, вызывающий `self.submit(...)`,
  но не добавлен в `OPERATION_AUDIENCE`
- **ТОГДА** страж `tests/test_db_job_classes.py` SHALL упасть с указанием
  имени метода
- **И** сервер SHALL NOT подниматься с таким реестром (проверка при
  старте, не только в тестах)

#### Сценарий: Класс в сигнатуре разошёлся с реестром

- **КОГДА** в сигнатуре метода стоит `AUDIENCE_MODEL`, а в
  `OPERATION_AUDIENCE` для него `AUDIENCE_RUNTIME`
- **ТОГДА** страж SHALL упасть, назвав метод и оба значения
- **И** расхождение SHALL NOT разрешаться молча в пользу любой стороны

#### Сценарий: Права и класс не могут разойтись

- **КОГДА** операция объявлена `AUDIENCE_MODEL`, но вызывается моделью
- **ТОГДА** `_require_runtime` SHALL отказать в вызове
- **И** работа SHALL NOT дойти до пула вообще

### Requirement: `submit` и `submit_transaction` не имеют значения по умолчанию для аудитории

`DataService.submit` и `DataService.submit_transaction` SHALL принимать
аудиторию как **обязательный** именованный параметр без значения по
умолчанию.

- `def submit(self, job: Any, *, audience: str) -> Any`
- `def submit_transaction(self, job: Any, *, audience: str) -> Any`

Причина историческая и конкретная: сегодня дефолт стоит на
`AUDIENCE_RUNTIME` (`data/service/main.py:663,680`), а вызов сброса
журнала `_write_events` аудиторию **не передаёт вовсе** — то есть
сегодня он получает рантайм по счастливой случайности. Как только
появится третий класс или изменится смысл дефолта, такое молчание
станет ошибкой. Обязательный параметр делает его невозможным.

#### Сценарий: Вызов без аудитории невозможен

- **КОГДА** код вызывает `self.submit(job)` без `audience=`
- **ТОГДА** вызов SHALL поднять `TypeError`
- **И** работа SHALL NOT дойти до пула

### Requirement: Пул знает класс работы и уважает его при разборе очереди

`_Job` получает поле класса. Очередь пула остаётся **одной**, порядок
разбора — по времени постановки, но воркер берёт не всякую работу.

- Поле класса называется `audience` и заполняется при создании `_Job`.
- У воркера есть объявленный набор аудиторий. Воркер берёт из очереди
  первую работу, чья аудитория входит в его набор.
- Работа, которую не может взять ни один воркер, остаётся в очереди
  (см. следующее требование про отказ).

Обоснование: подбор воркера по признаку работы уже есть в коде — аренда
берётся только тем воркером, у которого совпал `lease_id`
(`db.py:585-599`). Обобщение на аудиторию не вводит нового механизма.

#### Сценарий: Зарезервированный воркер не берёт работу модели

- **КОГДА** воркер объявлен как берущий только `runtime`
- **ТОГДА** работа `AUDIENCE_MODEL`, стоящая в очереди, SHALL быть им
  пропущена
- **И** воркер SHALL продолжать искать подходящую работу дальше по
  очереди, а не засыпать

#### Сценарий: Порядок в очереди не ломается

- **КОГДА** в очередь поставлены работы `model`, затем `runtime`,
  затем `model`
- **ТОГДА** при наличии подходящих воркеров порядок разбора SHALL
  соответствовать порядку постановки
- **И** пропуск неподходящей работы SHALL NOT сдвигать разбор назад по
  времени постановки остальных

### Requirement: Резерв выражен числом зарезервированных воркеров

Ровно первые `reserved_workers` созданных воркеров пула берут **только**
`runtime`-работы. Остальные берут обе аудитории.

- Счётчик индекса воркера уже существует (`_worker_seq`), порядок
  создания — уже детерминирован.
- Значение обязано быть объявлено в `platform.json → pool`, а не в коде.
- Условия, которые обязаны проверяться на старте, а не в рантайме:
  - `reserved_workers <= max_conn - 1` — иначе ни один воркер не берёт
    `model`, и модельная работа невозможна вовсе;
  - при `reserved_workers >= 1` обязательно `min_conn >= 2` — резерв
    стоит воркера, который должен существовать всегда; иначе при
    низком уровне воды резерва не существует, и гарантия действует
    только на верхнем уровне, то есть молча.

**Гарантия и её честная граница.** `reserved_workers` даёт следующее:
работа модели не может занять эти воркеры. Отсюда — система ждёт
только другие системные работы, **пока системная нагрузка не превышает
`reserved_workers` одновременных работ**. Если превышает, система ждёт
работы модели — но не дольше её потолка времени.

Поэтому утверждение «система не ждёт никогда» верно **не при любом
числе соединений**. Проверка на трёх воркерах (`max_conn: 3`,
`reserved_workers: 2`): модель занимает только воркер №3, система — №1 и
№2; пока системная нагрузка ≤ 2 одновременных работ (а это условие
выполняется: путь оборота — три коротких последовательных операции, а
зеркало сессии — единственный фоновый держатель), система не ждёт
модели никогда.

При `max_conn: 2, reserved_workers: 1` воркеров два: №1 только
`runtime`, №2 обе аудитории. Модель занимает №2, система — №1. Это
работает, **но** если системная нагрузка потребует второго одновременного
воркера, она встанет в очередь и будет ждать модели — до её потолка
времени. Гарантия «не ждёт никогда» здесь не выполняется, и объявлять
её нельзя.

#### Сценарий: Резерв конфигурации несуществующ

- **КОГДА** `platform.json` объявляет `reserved_workers: 0`
- **ТОГДА** пул SHALL подняться, и все воркеры SHALL брать обе аудитории
- **И** поведение пула SHALL совпадать с сегодняшним по этому аспекту

#### Сценарий: Резерв больше пула

- **КОГДА** `reserved_workers == max_conn`
- **ТОГДА** сервер SHALL отказаться подниматься с сообщением о том, что
  модельная работа станет невозможна
- **И** отказ SHALL происходить на старте, а не при первом вызове

#### Сценарий: Резерв без второго соединения

- **КОГДА** `reserved_workers >= 1` и `min_conn == 1`
- **ТОГДА** сервер SHALL отказаться подниматься с объяснением, что резерв
  требует, чтобы зарезервированный воркер существовал всегда

### Requirement: Отказ вместо ожидания, когда класс не влезает

Ожидание работы в очереди ограничено числом, объявленным для её класса.
Исчерпание — **отказ с доменной ошибкой**, а не ожидание и не молчание.

- Для каждой аудитории в `platform.json → job_classes` объявляется
  `wait_sec`: сколько работа её класса может ждать в очереди.
- `wait_sec: 0.0` — законное объявление, и означает оно «не ждать
  никогда»: если подходящего воркера нет, работа отклоняется сразу.
- Глубина очереди класса ограничена отдельно: `queue_maxsize` в
  `job_classes`. Переполнение — отказ, а не блокировка.
- Отказ — доменная ошибка `InfrastructureError` с устойчивым кодом в
  сообщении, чтобы вызывающий отличал «занято» от «упало».
- Счётчик отказов обязателен и обязан быть виден в `get_stats()`.

Смысл: сейчас `pool.run(...)` ждёт результат без таймаута
(`db.py:1049`), а `queue_maxsize: 10000` разрешает десять тысяч
ожидающих на четыре места. Ожидание без предела не выражает приоритет,
а прячет его.

**Механика и объявленное значение — разные вещи.** Правило «`0.0` означает
не ждать никогда» остаётся в силе для любого класса, который так объявлен.
Но объявлять модель с `0.0` нельзя: мест у неё ровно одно — гибкий воркер,
каким заканчивается резерв, — и второй параллельный модельный вызов
(агент вправе звать `data.history_search` и `data.schema_check` одновременно)
отказался бы на ровном месте, пока первый идёт. Ноль ожидания и не давал
безопасности: резерв уже гарантирует системе два места, а `_take_job`
никогда не отдаёт работу модели зарезервированному воркеру, поэтому
ожидание модели на своём воркере системе повредить не может. Предел
остаётся — он и есть `wait_sec` и `statement_timeout_ms` класса.

#### Сценарий: Модельная работа отклоняется, когда истёк её предел

- **КОГДА** истёк объявленный для аудитории `wait_sec` и ни один воркер не
  может взять работу прямо сейчас
- **ТОГДА** вызов SHALL поднять `InfrastructureError` с признаком
  «занято»
- **И** работа SHALL NOT остаться в очереди

#### Сценарий: Класс, объявленный без ожидания, отклоняется сразу

- **КОГДА** для аудитории объявлено `wait_sec: 0.0` и ни один воркер не
  может взять работу прямо сейчас
- **ТОГДА** вызов SHALL поднять `InfrastructureError` с признаком
  «занято» без ожидания

#### Сценарий: Два параллельных вызова модели не отказывают

- **КОГДА** аудитория `model` объявлена с ненулевым `wait_sec` и оба её
  вызова поставлены одновременно, а резерв занят работой системы
- **ТОГДА** оба вызова SHALL получить результат
- **И** счётчик отказов по `model` SHALL остаться нулевым

#### Сценарий: Модельная работа не берёт аренду

- **КОГДА** работа аудитории `model` запрошена через `submit_transaction`
- **ТОГДА** сервис SHALL отказать до постановки в пул
- **И** соединение SHALL NOT быть зализовано

### Requirement: Потолок времени задаётся для класса, а не для пула

`statement_timeout` выставляется на сессии по аудитории работы и
сбрасывается в `finally`, как это уже делается в
`DataService._guarded` (`data/service/main.py:752-760`).

- Значение для аудитории объявляется в `platform.json → job_classes`.
- Существующий `data.statement_timeout_ms` остаётся **значением по
  умолчанию** для класса, который не объявил своё. Это не второй
  источник для уже объявленного класса: если класс объявлен, применяется
  его значение.
- Сбрасывание обязано происходить и при ошибке, и при успехе
  (существующий `finally` сохраняется).

Значение по умолчанию и раньше было общим, но одинаковым для всех —
30 секунд на одиночную вставку журнала это перекрывает с большим
запасом. Раздельные потолки нужны, чтобы одна работа не держала место
дольше, чем её класс допускает.

#### Сценарий: Потолок класса применяется и снимается

- **КОГДА** выполняется работа аудитории `runtime` с объявленным
  потолком 5000 мс
- **ТОГДА** на сессии SHALL быть выставлен `statement_timeout = 5000`
- **И** после завершения работы, независимо от результата, значение
  SHALL быть сброшено
- **И** следующая работа другой аудитории SHALL получить свой потолок,
  а не оставшийся

### Requirement: Счётчики показывают, кто занимает пул

`DBManager.get_stats()` SHALL отдавать по каждой аудитории: сколько
работ в очереди, сколько выполняется, сколько отклонено, сколько взято
всего, суммарное и максимальное время ожидания.

Дополнительно: `EventBuffer.stats()` SHALL содержать счётчик отказов
сброса из-за занятости пула, отдельный от потерь и ошибок записи.

Обоснование: сегодня в `get_stats()` есть `connected`, `jobs`,
`lease_acquired` и ничего, что отвечает на вопрос «кто занял очередь».
Вопрос «очередь забили навыки» без счётчиков нельзя ни подтвердить, ни
опровергнуть.

#### Сценарий: Отказ сброса журнала виден

- **КОГДА** сброс буфера не смог получить место в пуле
- **ТОГДА** `EventBuffer.stats()` SHALL содержать ненулевой счётчик
  отказов
- **И** события SHALL остаться в буфере, а не быть потеряны
- **И** счётчик отказов SHALL отличаться от счётчика потерь: потеря
  необратима, отказ — нет

### Requirement: Сброс журнала пишет батч одной вставкой и не занимает место напрасно

`DataService._write_events` SHALL писать батч одной операцией
`execute_values`, а не циклом `cur.execute` по одной строке.

- Сейчас батч до `data.log_batch_size` строк (1024) выполняется как
  1024 отдельных `cur.execute` в одном job'е: воркер занят на всё время
  обхода. На двух соединениях это половина пула.
- `psycopg2` в capability `data` импортировать нельзя (страж
  `test_architecture_boundaries.py`). Значит помощник обязана жить в
  `libs/enterprise_data` и принимать уже имеющееся соединение. Публичная
  функция пула `execute_values` для этого не годится: она сама
  постановлит работу в пул изнутри job'а, то есть это заведомый тупик
  (см. предупреждение в `db.run`).
- Сброс SHALL использовать неблокирующую постановку: нет места — тик
  пропускается, батч возвращается в буфер, счётчик отказов растёт.
  Принцип «переполнение — дроп, а не блокировка» уже объявлен для буфера
  (`data/service/writer.py:9`) и обязан быть доведён до самого сброса:
  неблокирующий вход есть, а запись — блокирующая.

#### Сценарий: Батч журнала уходит одной операцией

- **КОГДА** в буфере 1000 событий и выполняется сброс
- **ТОГДА** работа SHALL выполнить одну пакетную вставку
- **И** SHALL NOT выполнять 1000 отдельных `cur.execute`

#### Сценарий: Занятый пул не блокирует сброс

- **КОГДА** в момент сброса ни один воркер не может взять работу сразу
- **ТОГДА** сброс SHALL вернуть батч в буфер
- **И** SHALL NOT ждать свободного воркера
- **И** следующий тик SHALL повторить попытку

### Requirement: Обход пула закрыт стражем

Страж `tests/test_architecture_boundaries.py` (правило 8) уже запрещает
создание ресурса в обход владельца. Это change расширяет его тремя
правилами:

1. **Приватный API пула закрыт.** Ни один производственный модуль вне
   `libs/enterprise_data` не должен ссылаться на `_Job`, `DBManager`,
   `_submit`, `_get_manager`, `_acquire_lease`, `PoolTimeoutError`.
   Исключение одно и объявленное: `servers/enterprise/server.py` вызывает
   `set_pool_config` — это штатный запуск.
2. **Сырое соединение наружу не отдаётся.** `pool.run(fn)` сегодня
   отдаёт вызывающему сырой `psycopg2`-conn, тогда как аренда отдаёт
   прокси (`_ConnectionProxy`). Публичные точки входа обязаны отдавать
   прокси, и `psycopg2` не должен подниматься выше
   `libs/enterprise_data`.
3. **Классификация не обходится.** Правила 1 и 2 из
   `test_db_job_classes.py`: покрытие реестра и совпадение класса в
   сигнатуре с реестром.

Признание границы: текстовый страж ловит обход **ресурса** и обход
**приватного API**. Обход **классификации** — это не текст, а семантика,
поэтому он ловится закрытым множеством операций и сверкой с реестром.
Никакое из трёх правил не ловит намеренную правку самого стража — как и
не ловит никакой страж.

#### Сценарий: Новое подключение мимо пула

- **КОГДА** добавлен production-модуль вне `libs/enterprise_data`,
  импортирующий `psycopg2`
- **ТОГДА** страж границ SHALL упасть
- **И** новое подключение SHALL NOT появиться в процессе

#### Сценарий: Прямой доступ к внутренностям пула

- **КОГДА** production-модуль вне `libs/enterprise_data` ссылается на
  `DBManager` или `_submit`
- **ТОГДА** страж SHALL упасть с указанием модуля и имени

### Requirement: Значения пула приходят из platform.json

Секция `pool` в `platform.json` остаётся полной: неполный набор — ошибка
конфигурации, а не добор из кода (проверяет
`tests/test_pool_settings_seam.py`). Этот change добавляет в контракт
пула один ключ — `reserved_workers`, — и вводит **новую секцию**
`job_classes`, которая обязана быть полной так же.

Соответствие «контракт пула = список настроек» сохраняется: новый ключ
появляется одновременно в `_POOL_SPEC` (`db.py:92`),
`POOL_SETTING_KEYS` (`libs/enterprise_common/settings.py`) и в
`platform.json`. Значений в коде не появляется — этого требует
существующий страж `test_no_pool_values_are_declared_in_code`.

#### Сценарий: Неполная секция job_classes

- **КОГДА** из `job_classes` в `platform.json` удалён ключ
- **ТОГДА** сервер SHALL отказаться подниматься, назвав отсутствующий
  ключ
- **И** SHALL NOT подставлять значение из кода

## Responsibility

Классификация работ, идущих в пул PostgreSQL, и управление очередью по этой
классификации. Владелец — модуль `mcp-platform/libs/enterprise_data/db.py`:
он держит пул, воркеры, аудитории и пределы ожидания. Владелец имён
аудиторий — `mcp-platform/libs/enterprise_data/audience.py`, чтобы общий код
пула не зависел от capability.

## Boundary

- **Внутри:** воркер и его соединение, очередь, резервирование воркеров,
  пределы `queue_maxsize`/`wait_sec`, отказ по глубине, аренда соединения
  под транзакцию.
- **Снаружи:** классификация конкретных операций объявляется вызывающей
  стороной (`servers/enterprise/capabilities/data/service/registry.py`),
  пул о ней не знает; права по аудитории (`_require_runtime`) — отдельная
  ось; сам PostgreSQL и DSN.

## Public Contract

- Имена аудиторий — единственное место определения:
  `JOB_AUDIENCE_MODEL = "model"`, `JOB_AUDIENCE_RUNTIME = "runtime"`,
  `ALL_AUDIENCES` (`mcp-platform/libs/enterprise_data/audience.py:28-40`).
- Настройка: `set_pool_config(cfg)` (`db.py:125`) и
  `set_job_class_config(cfg)` (`db.py:223`) — обе проверяют полноту набора и
  типы, обе бросают `InfrastructureError`.
- Чтение настроек: `pool_is_configured()` (`db.py:193`),
  `job_class_config()` (`db.py:284`), `job_classes_configured()`
  (`db.py:289`), `statement_timeout_ms(audience)` (`db.py:301`).
- Работа с БД: `start()` (`db.py:1505`), `shutdown()` (`db.py:1510`),
  `get_stats()` (`db.py:1518`), `run(fn, *, audience=...)`
  (`db.py:1561`), `try_submit(job, *, audience=...)` (`db.py:1575`),
  `execute` (`:1606`), `fetch` (`:1621`), `fetchone` (`:1636`),
  `fetchval` (`:1652`), `execute_values` (`:1668`), `execute_values_on`
  (`:1693`), `transaction(*, audience=...)` (`:1724`),
  `run_transaction` (`:1747`). Аудитория по умолчанию — `model`.
- Отказы: `PoolTimeoutError` (`db.py:437`), `PoolBusyError` с кодом
  `pool_busy` (`db.py:441-453`), `InfrastructureError` от настройки.

## Inputs

- Секция `pool` из `mcp-platform/platform.json` целиком — значения в коде
  отсутствуют, `_POOL_SPEC` объявляет только ключи и типы
  (`db.py:108-122`).
- Секция `job_classes` — по одной записи на аудиторию
  (`db.py:213-218`); набор аудиторий обязан совпасть с `ALL_AUDIENCES`.
- Аудитория каждой работы — keyword-аргумент в сигнатуре операции, а не
  вычисление внутри пула.
- DSN — `resolve_dsn()` (`db.py:1476`).

## Outputs

- Счётчики на аудиторию: `queued`, `running`, `rejected`, `taken`,
  `wait_total`, `wait_max` (`_audience_bucket`, `db.py:465-474`), плюс
  общая сводка из `get_stats()`.
- Результат операции или доменный отказ; наружу выходит ровно то, что вернул
  переданный `fn`.
- `pool_busy` как код доменной ошибки, который отличает «занято» от
  «упало» (`db.py:444-453`).

## State

Модульные `_pool_cfg: dict` (`db.py:122`) и
`_job_class_cfg: dict[str, dict]` (`db.py:220`) — единственное долговременное
состояние настроек; заполняются один раз при старте. Персистентный
`DBManager` (`db.py:699`) держит счётчики аудиторий, `_reserved_workers`
(`:727`) и набор соединений. Инстанс один на процесс, под локом
(`_manager`, `_manager_lock` — `db.py:1456-1457`).

## Dependencies

- `psycopg2` — соединения и курсоры; `_Worker` владеет ровно одним
  соединением (`db.py:482-493`).
- `libs.enterprise_data.audience` — имена и множество аудиторий.
- `libs.enterprise_common.settings` — `Settings` и оверлей профиля.
- `servers/enterprise/server.py::_apply_pool_settings` (`server.py:144`) —
  единственный, кто применяет обе секции; вызывается при старте
  (`server.py:607`).
- Никаких значений настроек из кода: `_POOL_SPEC` и `_JOB_CLASS_SPEC`
  хранят только ключи и типы.

## Configuration

`mcp-platform/platform.json` → `pool` и `job_classes`.

- `pool` (`min_conn`, `max_conn`, `reserved_workers`, `pool_timeout`,
  `queue_maxsize`, `reconnect_backoff_sec`, `reconnect_backoff_max_sec`,
  `connect_max_retries`, `idle_timeout_sec`, `job_max_retries`,
  `print_activity`) — полный набор, неполнота это ошибка конфигурации
  (`db.py:174-184`).
- `job_classes` (`statement_timeout_ms`, `queue_maxsize`, `wait_sec`,
  `leases`) — полный набор для каждой аудитории (`db.py:213-218`,
  `:260-269`).
- Инварианты, проверяемые на старте: `reserved_workers < max_conn - 1`
  (`:175`), при `reserved_workers >= 1` требуется `min_conn >= 2` (`:182`).
- Профиль может переопределить пул через `read_profile_overlay`; значения
  приезжают из файла, а не из argv и не из окружения.

## Lifecycle

1. Сервер читает `Settings` и вызывает `_apply_pool_settings`
   (`server.py:607`), которая зовёт `set_pool_config` и
   `set_job_class_config` (`server.py:160-162`).
2. Неприменённая секция — не запасной путь: `job_classes_configured() == False`
   означает «классификации нет» (`db.py:289-298`), и сервер обязан был
   применить файл до старта.
3. `start()` создаёт `DBManager` и воркеры; каждый воркер один раз получает
   набор аудиторий через `_audiences_for(index)` (`db.py:492`).
4. Работа входит в пул через `submit`/`try_submit`/`run`/операции с
   аудиторией и уходит в воркер.
5. `shutdown()` останавливает пул.

## Data Ownership

Пул не владеет данными PostgreSQL: он владеет **соединениями**. Пул не
создаёт таблиц, не объявляет DDL и не мигрирует схему. Аргументы запросов
проходят через санитайзеры (`_sanitize_param` `db.py:1262`,
`_sanitize_params` `:1278`); соединение, пока отдан в аренду под транзакцию,
чужими задачами не берётся.

## Error Behavior

- Неизвестная аудитория отвергается на входе в пул (`_check_audience`,
  `db.py:327-335`): молча пропустить хуже, её не взял бы ни один воркер, и
  она стояла бы в очереди вечно — пул выглядел бы живым, а работа пропала.
- Переполнение `queue_maxsize` и невозможность дождаться воркера — отказ
  `PoolBusyError` (`db.py:441`), а не ожидание в обход объявленного потолка.
- `set_pool_config` / `set_job_class_config` бросают `InfrastructureError` с
  перечислением недостающих и лишних ключей (`db.py:243-279`).
- `PoolBusyError.__init__` написан явно: множественное наследование
  пропускает `EnterpriseError.__init__`, а адаптер MCP читает `message` у
  любой доменной ошибки (`db.py:455-462`).
- Воркер без живого соединения не отнимает задачи у подключённых: берёт
  обычную задачу, только когда в пуле нет ни одного воркера с живым
  соединением (`db.py`, module docstring, `:18-22`).

## Invariants

- Имена аудиторий определены ровно в одном модуле
  (`mcp-platform/libs/enterprise_data/audience.py:28-40`); дублировать их в
  capability нельзя — общий код не имеет права зависеть от capability.
- `_RESERVED_AUDIENCES = frozenset({JOB_AUDIENCE_RUNTIME})`
  (`db.py:81`): зарезервированный воркер не берёт `model` ни при каком
  состоянии пула.
- Резерв выражен числом воркеров, а не счётчиком «занято моделью»:
  воркер, который не берёт `model`, не может отдать его ни при каком
  состоянии пула (`db.py:487-491`).
- Значения настроек живут только в `platform.json`; `_POOL_SPEC` и
  `_JOB_CLASS_SPEC` — контракт ключей и типов, а не значения
  (`db.py:202-218`).
- `pool_timeout` — порог диагностического warning, а не лимит ожидания
  (`db.py`, module docstring `:14-15`).

## Forbidden Behavior

- Объявлять значение настройки в коде как запасной вариант: настройка,
  объявленная в двух местах, даёт два ответа на вопрос «что применяется»
  (`db.py:202-205`).
- Неполная секция `job_classes`, достроенная значениями по умолчанию:
  отсутствующий ключ останавливает сервер с его именем
  (`mcp-platform/platform.json` → `job_classes._about`).
- Дублировать имя аудитории вне `audience.py`.
- Молча пропускать работу неизвестного класса (`db.py:327-333`).
- Отдавать `model`-работу зарезервированному воркеру «по очереди, если
  модельных нет» — резерв существует именно затем, чтобы этого не было.
- Держать настройку очереди в коде вместо `platform.json`.

## Consumers

- `servers/enterprise/server.py::_apply_pool_settings` (`server.py:144`,
  вызов `:607`) — единственный применяющий обе секции.
- `servers/enterprise/capabilities/data/service/` — объявляет аудиторию в
  сигнатуре операций и берёт `_require_runtime`.
- Аудитории импортируются в `capabilities/data/service/main.py` из
  `audience.py`, а не определяются там.
- Оператор — через `get_stats()` (`db.py:1518`): счётчики занятости и
  ожидания по классам.
