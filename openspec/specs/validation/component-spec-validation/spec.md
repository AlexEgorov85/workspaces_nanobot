# validation/component-spec-validation Specification

## Purpose
Этот документ определяет правила и механизмы автоматической валидации компонентных спецификаций проекта workspaces_nanobot. Валидация обеспечивает соответствие спецификаций установленному шаблону, полноту покрытия и отсутствие противоречий.

## Scope

`agent` — валидатор структуры спек — инструмент агентского репозитория
Реализация: `tools/validate_component_specs.py`

## Requirements

### Requirement: структурная валидация

Система MUST проверять наличие обязательных разделов в каждой спецификации.

Обязательные для **каждой** спецификации разделы:

1. `## Purpose`
2. `## Requirements` — минимум одно требование, у каждого требования — минимум один сценарий `#### Scenario:` с маркерами **КОГДА**/**ТОГДА** (**WHEN**/**THEN**)

Спека, начатая по полному шаблону (в ней есть раздел `## Responsibility`), ДОЛЖНА содержать также:

3. `## Responsibility`
4. `## Boundary`
5. `## Public Contract`
6. `## Forbidden Behavior`
7. `## Dependencies`
8. `## Implementation`
9. `## Verification`

Синонимов у заголовков нет: сопоставление идёт точным именем. Русские
эквиваленты были вторым именем раздела во всём дереве, а канон при этом
объявлял их допустимыми — расхождение устранено удалением псевдонимов из
модуля, а не их принятием.

#### Scenario: проверка структуры

- **WHEN** запускается валидация
- **THEN** каждая `spec.md` ДОЛЖНА быть распарсена и проверена на наличие обязательных заголовков
- **AND** иначе валидация ДОЛЖНА завершиться с ошибкой и указанием недостающих разделов

### Requirement: языковая валидация

Система MUST проверять, что заголовки нормативных разделов совпадают с каноническими именами из шаблона `architecture/component-model` точным именем; синонимы не принимаются. Текст спецификаций — русский; технические идентификаторы в теле spec сохраняют оригинальное написание и НЕ проверяются.

#### Scenario: проверка языка

- **WHEN** spec содержит заголовок нормативного раздела, не совпадающий точным именем с каноническим
- **THEN** валидация ДОЛЖНА сообщить об отсутствии обязательного раздела
- **AND** имена классов, методов, файлов в теле spec НЕ являются ошибкой

### Requirement: проверка существования spec

Система MUST проверять, что для каждой записи в `COMPONENTS.md` со статусом non-missing существует соответствующий файл `spec.md`.

#### Scenario: проверка существования файла

- **WHEN** `COMPONENTS.md` содержит запись со статусом `draft` / `partial` / `complete`
- **THEN** файл `spec.md` ДОЛЖЕН существовать по указанному пути
- **AND** иначе валидация ДОЛЖНА завершиться с ошибкой

### Requirement: проверка отсутствия дубликатов

Система MUST проверять отсутствие нескольких записей для одного компонента в `COMPONENTS.md`.

#### Scenario: обнаружение дубликата

- **WHEN** один и тот же компонент встречается в реестре более одного раза
- **THEN** валидация ДОЛЖНА завершиться с ошибкой

### Requirement: проверка путей к файлам

Система MUST проверять, что указанные в `COMPONENTS.md` пути к файлам реализации существуют.

#### Scenario: проверка пути к реализации

- **WHEN** `COMPONENTS.md` содержит путь к файлу реализации
- **THEN** файл ДОЛЖЕН существовать
- **AND** иначе валидация ДОЛЖНА предупредить (не ошибка, так как код может быть в другой ветке)

### Requirement: проверка объявления владельца

Система MUST требовать в каждой спеке раздел `## Scope` и проверять, что
объявленный владелец входит в закрытый список `agent` / `platform` / `shared`.

Проект разделён на два дерева кода — агента и платформу `mcp-platform`, — и
переезд подсистемы между ними идёт постоянно. Спека, которая не говорит, чей
это код, не отвечает на вопрос «кто это чинит», и после переезда остаётся
описанием того, чего уже нет: именно так выглядели `data/cache-provider`,
`data/vector-indexes` и `skills/legal-summarizer-query` до появления этого
требования.

Значение берётся из первой метки в обратных кавычках тела `## Scope`, чтобы
оставалось грепабельным: `grep '`platform`' openspec/specs` отвечает на вопрос,
какие спеки об MCP, без разбора двадцати трёх файлов.

#### Scenario: спека объявляет владельца

- **WHEN** раздел `## Scope` содержит значение из закрытого списка
- **THEN** валидация ДОЛЖНА пройти по этому пункту

#### Scenario: владелец не объявлен

- **WHEN** в спеке нет раздела `## Scope`
- **THEN** валидация ДОЛЖНА завершиться с ошибкой

#### Scenario: неизвестный владелец

- **WHEN** раздел `## Scope` содержит значение, отсутствующее в закрытом списке
- **THEN** валидация ДОЛЖНА завершиться с ошибкой с перечислением допустимых значений

## Responsibility

Единственный страж структуры спецификаций: читает каталог `openspec/specs/**/spec.md` и реестр `openspec/specs/COMPONENTS.md`, сверяет их с каноном из 19 разделов и печатает нарушения построчно, с номером строки.

Границы ответственности, которые код держит жёстко:

- **Форма спеки.** 19 разделов, обязательны все безусловно; 3 базовых и 16 шаблонных проверяются раздельно, чтобы не смешивать «должен быть» с «обязан быть у полной спеки».
- **Разбор реестра построчный.** Каждая строка таблицы разбирается в своём собственном `try`; одна неразбираемая строка даёт нарушение с номером строки и не отменяет разбор остальных.
- **Паритет в обе стороны.** Запись реестра без файла спеки и файл спеки без записи реестра — разные нарушения.
- **Порядок разделов.** `CANONICAL_SECTIONS` — не только множество, но и последовательность; спека, в которой `## Implementation` стоит раньше `## Consumers`, даёт нарушение.

Не входит в ответственность: содержательная верность утверждений, существование путей из `## Implementation`, совпадение `## Implementation` с колонкой реестра сверх синтаксической проверки ссылки.

## Boundary

Компонент — однопроходный CLI, а не сервис и не библиотека с публичной поверхностью.

- **Входит:** файловая система (`openspec/specs/**`) и аргументы командной строки.
- **Выходит:** stdout/stderr и код возврата процесса.
- **Не входит:** сеть, база данных, переменные окружения, `config.json`, `platform.json`. Валидатор работает при полном отсутствии настроек — это позволяет гонять его в любом окружении, включая пустой checkout.
- **Не входит:** запись в `openspec/specs/**`. Скрипт ничего не исправляет; автоформатирования и `--fix` у него нет намеренно, потому что молчаливая правка документа делает проверку невоспроизводимой.
- **Не входит:** поиск спецификаций вне `openspec/specs/`. Каталог задаётся точкой отсчёта репозитория (`tools/validate_component_specs.py` поднимается на два уровня до корня), переопределения из CLI нет.

## Public Contract

Единственная публичная точка входа — `main(argv: Sequence[str] | None = None) -> int` плюс `if __name__ == "__main__": raise SystemExit(main())`.

Контракт, выраженный типами и константами модуля:

| Имя | Роль |
| --- | --- |
| `CANONICAL_SECTIONS` | канонический перечень из 19 заголовков; единственный источник и порядка, и состава |
| `BASE_SECTIONS` | 3 раздела, обязательных для любой спеки |
| `FULL_TEMPLATE_SECTIONS` | 16 разделов, обязательных для спеки по полному шаблону |
| `SCOPE_VALUES` | закрытый список владельцев, из которых непустой `## Scope` обязан назвать ровно один |
| `SCENARIO_MARKERS` | 8 маркеров, допустимых в строке сценария |
| `VALID_STATUSES`, `VALID_CATEGORIES` | закрытые списки для реестра |
| `TEMPLATE_SPEC` | единственный путь, исключённый из проверки полноты: носитель самого канона |
| `canonical_section()` | сопоставляет заголовок разделу **точным** именем из `CANONICAL_SECTIONS`; синонимов у разделов нет |
| `spec_path_for_issue()` | единая сборка `путь:строка` для отчёта |
| `SpecIssue` | одно нарушение: файл, раздел, сообщение, номер строки |
| `ValidationReport` | счётчики плюс списки нарушений и предупреждений |

Публичных функций проверки несколько — `validate_spec_sections`, `validate_registry_parity`, `validate_spec_category`, `parse_components_registry` — и они принимают `Path` и `ValidationReport` явно. Это сделано для стражей: `tests/test_component_spec_validation.py` собирает `ValidationReport` сам и вызывает проверку на синтетическом дереве, без подмены `SPECS_DIR` и без записи на диск.

## Inputs

Вход разделён на две части, и это разделение — часть контракта.

**Командная строка.** `main` разбирает её сама через `argparse.ArgumentParser(prog="validate_component_specs")`. Флаги: `--verbose/-v` (подробный вывод), `--strict` (предупреждения считаются нарушениями). Позиционных аргументов нет.

**Файлы.** Ровно два источника, оба вычисляются от `ROOT`:

1. `SPECS_DIR = ROOT / "openspec" / "specs"` — перебирается рекурсивно, имя файла должно быть ровно `spec.md`. Соседние `README.md` внутри `specs/` не проверяются.
2. `COMPONENTS_MD = SPECS_DIR / "COMPONENTS.md"` — единственный файл реестра; имя задано константой, а не соглашением.

Содержимое спеки перед разбором проходит через `strip_fenced_code()`, а разбор ведётся по результату `iter_code_free_lines()`. Огороженные блоки ``` исключены намеренно: строка `## Foo` внутри примера или лога не должна читаться как раздел.

## Outputs

Три артефакта, и все три наблюдаемы без парсинга исходников.

**Отчёт на stdout.** По умолчанию — только сводка: `Validated N spec file(s): M issue(s).` либо `OK: N spec file(s) validated.` при нуле нарушений. С `--verbose` — построчный список всех нарушений в формате `путь:строка: [раздел] сообщение`; для нарушений реестра в квадратных скобках стоит `registry`, потому что строка не принадлежит ни одному разделу спеки.

**Счётчики.** Поля `ValidationReport`: `specs_checked`, `registry_rows`, `issues`, `warnings`, плюс сами списки `errors` и `warning_list`. Счётчик `specs_checked` инкрементируется **до** проверки содержимого, поэтому спека с нарушениями всё равно считается проверенной.

**Код возврата.** `0` — нарушений нет (при `--strict` и предупреждениях тоже `0`, если предупреждений нет). `1` — есть нарушения; при `--strict` к ним приравниваются предупреждения. `2` — каталог `openspec/specs` не найден. Ни один другой код не используется.

## State

Неприменимо: компонент не хранит состояния.

Обоснование: валидатор — чистая функция от содержимого файлов. Между запусками не остаётся ни кэша, ни журнала, ни индексов; повторный запуск на неизменном дереве даёт тот же отчёт. Единственное, что живёт дольше одного вызова, — модульные константы, и они только читаются.

Внутри одного прохода состояние есть, и оно намеренно локально:

- `ValidationReport` накапливает нарушения по мере обхода; отчёт — единственный объект с изменяемым состоянием.
- `validate_registry_row()` передаёт наружения наружу через переданный `report`, а не через возвращаемое значение, — поэтому частичный разбор реестра не теряется на первой же плохой строке.
- Порядок обхода детерминирован: сначала реестр и паритет, затем спеки по возрастанию пути (`iter_spec_files` сортирует).

## Dependencies

**Стандартная библиотека Python.** `argparse`, `dataclasses`, `pathlib`, `re`, `collections`, `sys`. Внешних зависимостей нет.

**Файловая система.** Единственный I/O — `Path.read_text(encoding="utf-8")` и `iterdir()`. Сети, базы данных и переменных окружения нет.

**Одно исключение из стандартной библиотеки — `DuplicateExclusionError`.** Он не наследует `Exception`, а поднимает `BaseException` напрямую. Это сделано для одной цели: если когда-нибудь появится второй исключаемый из проверки путь, валидатор обязан упасть целиком, а не молча проверить один файл меньше. `exclude_spec` — ровно один такой путь, `TEMPLATE_SPEC`.

**Связи по данным, а не по импорту.** Валидатор не импортирует код компонентов, которые описывает. Он читает их спеки как текст. Поэтому правка любой спецификации не может сломать сам валидатор, а падение валидатора не может означать падение компонента.

## Configuration

Неприменимо в смысле настроек поведения: у компонента нет ни одного параметра конфигурации.

Обоснование: любой источник настроек (`.env`, `config.json`, `platform.json`, переменные окружения) сделал бы проверку зависимой от окружения, а проверка структуры документов от окружения не зависит и зависеть не должна. Единственные точки выбора зафиксированы в коде: каталог реестра (`SPECS_DIR / "COMPONENTS.md"`), имя файла спеки (`spec.md`), путь канона (`TEMPLATE_SPEC`).

Что при этом настраиваемо, так это состав самого канона, и он объявлен данными, а не кодом: `CANONICAL_SECTIONS`, `SCOPE_VALUES`, `SCENARIO_MARKERS`, `VALID_STATUSES`, `VALID_CATEGORIES`. Правка канона — это правка списков в этом модуле плюс правка `openspec/specs/architecture/component-model/spec.md`, которая является их нормативным источником. Перечень псевдонимов заголовков из модуля удалён: русский эквивалент заголовка был вторым именем раздела во всём дереве, а канон при этом объявлял его допустимым.

## Lifecycle

Процесс живёт один вызов.

1. **Разбор аргументов.** `argparse`; неизвестный флаг — стандартный отказ argparse с кодом `2`.
2. **Проверка корня.** `SPECS_DIR.is_dir()`; отсутствие каталога — `2` с сообщением.
3. **Реестр.** `parse_components_registry(report)` читает `COMPONENTS.md` построчно. Если файла нет — предупреждение `registry_missing`, а не нарушение: отсутствие реестра не должно выглядеть как «проверять нечего».
4. **Паритет.** `validate_registry_parity(report, specs_dir)` сверяет обе стороны. Здесь же отбрасывается `TEMPLATE_SPEC`.
5. **Спеки.** Для каждого файла — `validate_spec_sections(..., specs_dir=...)`, затем `validate_spec_category(p, specs_dir, report)`.
6. **Вывод и код возврата.** Печать сводки или подробного отчёта, `return 0`/`1`/`2`.

Асинхронности нет ни в одной стадии: ни файлового обхода, ни сетевых вызовов, ни потоков. Перезапуск, восстановление и горячая перезагрузка неприменимы — процесс завершается, и состояние не переносится.

## Data Ownership

Компонент **не владеет данными вовсе**, и это утверждение сильнее обычного «не владеет».

- **Чтение — единственный режим доступа.** Валидатор открывает файлы на чтение и никогда не пишет. У него нет ни `write_text`, ни операций создания/удаления, ни временных файлов рядом с проверяемым деревом.
- **За проверяемыми документами владеет другой компонент.** Правом вносить изменения в `openspec/specs/**/spec.md` и в `openspec/specs/COMPONENTS.md` обладает `documentation/component-registry`; валидатор лишь предъявляет к ним требования.
- **Копия в памяти — не владение.** Текст спеки, прочитанный в `read_text`, живёт только внутри вызова; после выхода он недоступен, и восстановить его неоткуда.
- **Отчёт — производный артефакт.** Ничего из напечатанного не является источником истины и не переживает процесс.

Граница, которую стоит проговорить: отсутствие записи означает, что валидатор бессилен как источник исправлений. Он говорит «нет раздела `## Implementation`», а не «вот какой раздел нужен». Подсказку даёт канон `openspec/specs/architecture/component-model/spec.md`, а не вывод валидатора.

## Error Behavior

Нарушения и сбои разделены, и это разделение — контракт, а не деталь реализации.

**Нарушения** (`ValidationReport.issues`) — расхождение документа с каноном. Накапливаются, печатаются, дают код возврата `1`. Каждое несёт файл, раздел, сообщение и номер строки.

**Предупреждения** (`ValidationReport.warnings`) — состояния, которые допустимы, но о которых стоит знать. Сейчас это ровно одно: `registry_missing`, когда `COMPONENTS.md` не найден. При обычном запуске предупреждение не влияет на код возврата; при `--strict` оно превращается в нарушение.

**Отказы** — состояния, из которых продолжить нельзя: каталога `SPECS_DIR` нет (`2`), неверный флаг CLI (`2`, argparse), дублирующееся исключение в `TEMPLATE_SPEC`/`exclude_spec` (`DuplicateExclusionError` — отказ целиком, а не нарушение).

Что именно ловится, перечислено в `## Requirements` этого файла; здесь важно другое — что проверки **не бросают исключений** на плохом содержимом. Неразбираемая строка реестра, несуществующая цель ссылки, неизвестный статус, чужая категория, повтор раздела, пустое тело раздела — всё это нарушения, а не падения. Единственное место, где содержимое файла влияет на успешность разбора, — ошибка чтения самого файла.

Ни одно нарушение не печатается как `WARNING` или `ERROR` уровнем логгера: отчёт идёт в stdout обычным `print`. Валидатор ничего не логирует и не настраивает logging.

## Invariants

1. **Полнота канона.** Все 19 заголовков `CANONICAL_SECTIONS` обязательны в каждой спеке, кроме единственной — `TEMPLATE_SPEC`. Условия вида «если есть `## Responsibility`, то обязательны ещё 16» в коде нет и быть не должно: набор обязательных разделов не зависит ни от чего в самой спеке.
2. **Порядок — часть канона.** Порядок разделов в спеке совпадает с порядком `CANONICAL_SECTIONS`. Это проверяется отдельно от наличия разделов.
3. **Тело раздела непустое.** Раздел, присутствующий без содержимого, — нарушение. Пустой заглушечный раздел хуже отсутствующего: он закрывает пробел и создаёт впечатление, что пробела не было.
4. **Раздел принадлежит ровно одной категории.** Классификатор `spec_category_from_path` определяет категорию по первой части относительного пути, и она обязана быть членом `VALID_CATEGORIES`. Категория из пути не выводится из текста спеки и не подменяется колонкой реестра.
5. **Владелец объявлен ровно один.** Непустой `## Scope` обязан содержать ровно одно значение из `SCOPE_VALUES`: ноль, два и более — нарушение.
6. **Паритет двусторонний.** Отсутствие записи реестра для существующей спеки и отсутствие спеки для существующей записи реестра — равноправные нарушения.
7. **Ссылка реестра указывает на файл спеки.** Цель ссылки должна существовать на диске, называться `spec.md` и лежать внутри `openspec/specs`.
8. **Ровно один H1.** Второй и последующие заголовки первого уровня — нарушение.
9. **Одна специя — один раздел.** Повтор заголовка (в том числе через псевдоним) — нарушение.
10. **Код возврата исчерпывающе перечислен.** `0`, `1`, `2`. Значение вне этого множества — признак того, что новый отказ не описан.

## Forbidden Behavior

- **Записывать в `openspec/specs/**` — запрещено.** Ни автоформатирования, ни `--fix`, ни «создать недостающие разделы». Проверка, которая правит проверяемое, перестаёт быть проверкой.
- **Молча пропускать спеку.** Исключение ровно одно и оно проверяемо: `TEMPLATE_SPEC` плюс проверка на дублирование исключения. «Забыли добавить файл в обход» исключением быть не может.
- **Продолжать после отказа.** Неразбираемая строка реестра не отменяет разбор остальных; отсутствующий каталог — отменяет всё.
- **Мягко относиться к пустому телу раздела.** Пустой раздел — нарушение, а не «формально есть».
- **Импортировать код описываемых компонентов.** Валидатор работает с текстом, а не с импортами; иначе проверка спецификации зависела бы от успешности импорта runtime-зависимостей.
- **Тихо переносить чужие нарушения.** Нарушения в чужих спеках печатаются с путём — подавление чужого шума здесь означало бы, что канон действует только избранным файлам.
- **Расширять канон из кода.** Списки `CANONICAL_SECTIONS`, `SCOPE_VALUES` и прочие объявлены данными; добавление раздела — правка этих списков вместе с `openspec/specs/architecture/component-model/spec.md`, а не правка логики проверки.
- **Логировать через `logging`.** Отчёт идёт в stdout; у валидатора нет логгера и нет уровней.

## Consumers

- **Разработчик спецификации** — тот, кто правит `openspec/specs/**/spec.md`: получает список недостающих разделов и пустых заглушек.
- **Автор или ведущий компонента** — тот, кто добавляет новую спеку и запись в `COMPONENTS.md`: получает нарушения паритета и категории.
- **Регламент `openspec/specs/architecture/component-model/spec.md`** — нормативный источник перечня; валидатор исполняет его, а не наоборот.
- **`documentation/component-registry`** — владелец `COMPONENTS.md`; валидатор задаёт формат файла, который этот компонент ведёт.
- **CI, косвенно.** `.github/workflows/ci.yml` выполняет `pytest tests/ -m "not live and not integration"`, и в этот набор входит `tests/test_component_spec_validation.py` — страж самого валидатора. Регламент требует, чтобы канон проверял CI; сегодня это происходит через тест, а не прямым вызовом `tools/validate_component_specs.py` в пайплайне — прямого вызова в `.github/workflows/ci.yml` нет.
- **Агент, работающий с `openspec/`** — использует вывод как источник структурной правды при подготовке спецификации.

Потребителей, которые читали бы вывод валидатора программно, нет: контракт — код возврата и stdout для человека.

## Implementation

- `tools/validate_component_specs.py` — весь компонент: константы канона, разбор реестра, проверка спек, печать отчёта, точка входа `main()`.
- `openspec/specs/architecture/component-model/spec.md` — нормативный источник перечня из 19 разделов; исключён из проверки как `TEMPLATE_SPEC`.
- `openspec/specs/COMPONENTS.md` — единственный читаемый файл реестра.

## Verification

- `tests/test_component_spec_validation.py` — страж самого валидатора; 44 теста на момент написания этой спеки. Покрывает: базовый обход настоящего дерева и проверку, что он действительно разобран; наличие каждого раздела из `CANONICAL_SECTIONS` и каждого из `FULL_TEMPLATE_SECTIONS`; отказ на спеке без `## Responsibility`; пустое тело раздела как нарушение; обязательный маркер в каждом сценарии; требование без сценария; `## Requirements` без требования; повтор раздела, в том числе через псевдоним; второй H1; `## Scope` без владельца, с неизвестным владельцем и с двумя владельцами; корректную строку реестра; таблицу статистики, ошибочно принятую за компонент; пятиколоночную строку; неверное число колонок; неразбираемую строку; неизвестный статус; дубль компонента; дубль при невалидном статусе; ссылку, не указывающую на файл спеки; отсутствующий файл спеки; неизвестную категорию; наличие закрытого списка категорий.
- `.github/workflows/ci.yml` — исполняет этот страж в задаче «Fast tests», поэтому канон проверяется в пайплайне.
