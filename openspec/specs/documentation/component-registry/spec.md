# documentation/component-registry Specification

## Purpose
Этот документ определяет правила ведения единого реестра архитектурных компонентов проекта workspaces_nanobot. Реестр служит индексом для навигации по компонентным спецификациям и отслеживания полноты покрытия системы спецификациями.

## Scope

`agent` — реестр компонентов и его валидатор живут в репозитории агента
Реализация: `tools/validate_component_specs.py`, `openspec/specs/COMPONENTS.md`

## Requirements

### Requirement: каждый production-компонент зарегистрирован

Система ДОЛЖНА поддерживать реестр всех production-компонентов. Каждый компонент, включённый в реестр, MUST иметь запись со следующими полями:

- Компонент (название)
- Категория (домен)
- Реализация (путь к коду)
- Спецификация (путь к `spec.md`)
- Статус (`missing` / `draft` / `partial` / `complete` / `deprecated`)

#### Scenario: добавление нового компонента

- **WHEN** обнаружен новый архитектурный компонент в коде
- **THEN** он ДОЛЖЕН быть добавлен в `COMPONENTS.md` со статусом `missing`
- **AND** для него ДОЛЖНА быть создана спецификация и статус обновлён

### Requirement: реестр не является вторым источником истины

Реестр MUST содержать только метаданные (название, категория, реализация, спецификация, статус). Реестр MUST NOT содержать описание поведения компонентов.

#### Scenario: обновление описания

- **WHEN** требуется обновить описание поведения компонента
- **THEN** изменения ДОЛЖНЫ быть внесены в соответствующий `spec.md`
- **AND НЕ** в `COMPONENTS.md`

### Requirement: честные статусы

Статус `complete` MUST устанавливаться только когда:

- все обязательные разделы spec заполнены
- spec соответствует фактическому коду
- boundary явно определён
- есть как минимум одно требование со сценарием
- есть запрещённое поведение

Статус `partial` устанавливается когда:

- spec создана, но некоторые разделы пустуют
- spec требует проверки соответствия коду

Статус `draft` устанавливается когда:

- spec создана автором, но ещё не проверена

Статус `missing` устанавливается когда:

- компонент существует в коде, но spec отсутствует

#### Scenario: проверка статуса complete

- **WHEN** spec помечена как `complete`
- **THEN** она ДОЛЖНА пройти проверку по чек-листу `component-model`
- **AND** иначе статус ДОЛЖЕН быть понижен до `partial` или `draft`

### Requirement: категоризация компонентов

Каждый компонент MUST быть отнесён к одной из категорий:

- `runtime` — runtime компоненты (`ApplicationContext`, `AgentFactory`, `MessageBus`)
- `configuration` — конфигурация (`ConfigService`, profiles)
- `channels` — каналы коммуникации (`PostgresChannel`, `RedisChannel`)
- `sessions` — управление сессиями (`PostgresSessionManager`)
- `data` — данные, кеш, векторы (`CacheProvider`, `VectorIndexService`)
- `observability` — логирование, мониторинг (`DatabaseLogging`, `EventLogging`)
- `infrastructure` — инфраструктура (`RuntimePatcher`, Hooks, SubprocessManagement)
- `interfaces` — интерфейсы (CLI, Gateway)
- `security` — безопасность (`SqlSafety`)
- `skills` — навыки (`AuditAnalyzer`, `LegalSummarizer`, `OfficeFiles`)
- `testing` — тестирование, бенчмарки (Benchmarks)
- `architecture` — архитектурные правила (`component-model`, `skill-tool-boundary`)
- `documentation` — мета-документация (`component-registry`)
- `validation` — валидация (`component-spec-validation`)

#### Scenario: добавление записи в реестр

- **WHEN** автор добавляет запись о компоненте в `COMPONENTS.md`
- **THEN** категория ДОЛЖНА быть выбрана из закрытого списка выше
- **AND** неизвестная категория ДОЛЖНА считаться ошибкой реестра

## Responsibility

Предмет компонента — сам файл `openspec/specs/COMPONENTS.md` и правила его ведения. Реестр держит ровно одно: перечень архитектурных компонентов с метаданными, по которому можно добраться до их спецификаций и судить о полноте покрытия.

Реестр отвечает за четыре вещи и не отвечает ни за что сверх них:

- **Полноту перечня.** Каждый production-компонент присутствует.
- **Навигацию.** От записи есть ссылка на существующий файл спецификации.
- **Честность статуса.** Статус `complete`/`partial`/`draft`/`missing`/`deprecated` отражает состояние спеки, а не намерение автора.
- **Формат.** Секции-категории и таблицы записей разбираются однозначно.

Чего реестр принципиально не делает — это содержательная работа. Реестр не описывает поведение, не содержит контрактов, не дублирует текст спецификации. Отдельная строка «Реализация» указывает **путь**, а не пересказ кода, и это граница, за которую заходить нельзя: вторым источником истины реестр становится ровно тогда, когда в нём появляется утверждение, которое можно перечитать иначе, чем в `spec.md`.

## Boundary

- **Входит:** содержимое `openspec/specs/COMPONENTS.md` — его секции-категории, таблицы записей и закрытые перечни.
- **Входит:** каталог `openspec/specs/**/spec.md` — только как множество целей существования, чтобы запись реестра не могла указывать в пустоту.
- **Выходит:** одна таблица, читаемая человеком, плюс нарушения, которые находит валидатор.
- **Не входит:** код любого описанного компонента. Валидатор реестра не импортирует ни `lib/`, ни `mcp-platform/`, ни `tools/apply_test_profile_tables.py`: он проверяет, что ссылка ведёт в существующий `spec.md`, а не что по этому пути что-то исполняемо.
- **Не входит:** нормативный канон разделов. Перечень из 19 разделов принадлежит `architecture/component-model`; реестр знает о нём только то, что это не его спека и не его поле.
- **Не входит:** `openspec/changes/**`. Каталог архивных и идущих изменений реестром не описывается и паритета с ним не требует.

## Public Contract

Контракт документа — его форма, потому что форма и есть всё, чем реестр пользуется как индекс.

**Структура файла.** Один заголовок первого уровня; секции второго уровня — `## Статистика`, `## Компоненты`, `## План заполнения`. Внутри `## Компоненты` — секции третьего уровня, каждая из которых либо категория компонента, либо не категория.

**Секция компонента опознаётся по таблице, а не по уровню заголовка.** Только такая секция третьего уровня, сразу за которой идёт строка, начинающаяся с `|`, считается секцией реестра. Это и есть ответ на возражение «у меня `### Wave 1`»: план заполнения состоит из секций третьего уровня без таблиц, и по признаку «любая `###` — категория» он был бы объявлен неизвестной категорией.

**Строка записи.** Основная форма — четыре ячейки:

```
| Компонент | Реализация | Спецификация | Статус |
```

плюс пятая форма с явной категорией:

```
| Компонент | Категория | Реализация | Спецификация | Статус |
```

Категория задаётся либо секцией, в которой лежит строка, либо собственной ячейкой. Допустимы только эти две формы; любое другое число колонок — ошибка реестра, а не повод угадывать.

**Значения ячеек.**

| Ячейка | Контракт |
| --- | --- |
| Компонент | `^[A-Za-z][A-Za-z0-9_]*$` — латиница, без пробелов и дефисов; именно эта форма даёт возможность найти дубль |
| Реализация | путь к коду; префикс `N/A (` допускается и проверкой, и регистром: мета-спецификация без исполняемого кода — законная запись |
| Спецификация | ссылка на файл спецификации; цель обязана существовать на диске, называться `spec.md` и лежать внутри `openspec/specs` |
| Статус | один из `missing`, `draft`, `partial`, `complete`, `deprecated` |

**Закрытые перечни** — 14 категорий и 5 статусов — хранятся в валидаторе как `VALID_CATEGORIES` и `VALID_STATUSES`. Реестр на них опирается, но объявляет их у себя в тексте списком: если перечень разъедется, виноват не валидатор, а реестр.

**Уникальность.** Повтор имени компонента — нарушение, даже если у повторной строки невалидный статус. Дубль должен называться дважды в отчёте, а не схлопнуться в один.

## Inputs

Неприменимо в смысле входных данных процесса: у реестра нет входа времени выполнения.

Обоснование: `COMPONENTS.md` не читается программой как данные и не подаётся на вход. Всё, что в него попадает, пишет человек — либо при первичном заполнении, либо при добавлении компонента. Формально единственный «вход» компонента — предлагаемая новая строка реестра, но это авторское действие, а не данные, которые что-то принимает.

Стоит развести два смысла: реестр как **индекс** читается поиском и вручную, реестр как **проверяемый артефакт** читается `tools/validate_component_specs.py`. Во втором случае вход — файл, и этот случай описан в `## Dependencies`.

## Outputs

Неприменимо: реестр не производит выход в смысле артефакта, который создаётся его выполнением.

Обоснование: `COMPONENTS.md` не имеет точки выхода. Он не пишет, не печатает и не порождает производных файлов. Единственное, что получается при работе с реестром, — его содержимое само по себе, то есть он сам и является результатом; называть результатом компонента документ, который авторят вручную, значит раздувать раздел.

Что действительно можно считать наблюдаемым результатом проверки реестра — это нарушения и код возврата валидатора, но они принадлежат `validation/component-spec-validation`, а не этому компоненту, и здесь они описаны в `## Error Behavior`.

## State

Состояние компонента — содержимое файла, и оно целиком хранится в git. Ни базы данных, ни кэша, ни внешнего индекса у реестра нет.

Состояние складывается из трёх слоёв, и каждый виден в файле:

1. **Перечень записей** — таблицы внутри секций-категорий. Это и есть перечень компонентов.
2. **Сводные числа** — секция `## Статистика` в начале файла. Это производная от первого слоя, и она **не проверяется**: расхождение статистики с фактическими строками валидатор не видит и увидеть не может. Ответственность за её честность лежит на авторе.
3. **План заполнения** — секция `## План заполнения` со волнами. Это история и намерение, а не описание текущего состояния; валидатор её пропускает по отсутствию таблиц.

Промежуточного состояния нет: реестр не ведётся инкрементально и не поддерживает частичное заполнение «в полёте». Любая правка — это правка файла целиком.

## Dependencies

Зависимости реестра — это ровно два пути, и оба проверяемы.

**Прямая зависимость — валидатор.** `tools/validate_component_specs.py` читает `COMPONENTS.md` и сверяет его с каталогом спек. Построчный разбор, закрытые перечни категорий и статусов, проверка ссылок и паритет живут там, а не в самом документе.

**Данная зависимость — каталог спек.** `openspec/specs/**/spec.md`. Реестр не может быть проверен в отрыве от него: запись без файла и файл без записи — два нарушения паритета, и обе стороны проверяются.

**Косвенная, через данные ячейки — спецификация компонента.** Статус `complete` обязан соответствовать чек-листу `architecture/component-model`, а проверку соответствия коду реестр выполнить не может: это работа человека или отдельного стража. Реестр фиксирует утверждение автора о статусе, но не является средством его проверки.

Что **не** является зависимостью: код описываемых компонентов, `config.json`, `platform.json`, переменные окружения, сеть. Реестр разбирается без единого обращения куда-либо, кроме двух перечисленных файлов.

## Configuration

Неприменимо: у реестра нет настраиваемых параметров.

Обоснование: единственное, что можно было бы настроить, — путь к самому реестру и к каталогу спек, но оба заданы константами (`COMPONENTS_MD`, `SPECS_DIR`) в валидаторе и не переопределяются ни из CLI, ни из окружения. Это сделано намеренно: у документа-индекса не должно быть режимов работы, при которых часть реестра проверяется, а часть — нет.

Настраиваемым здесь является только **содержание** самого файла: состав категорий, набор записей, статусы. Это данные, а не конфигурация — они меняются правкой документа, а не передачей параметров.

## Lifecycle

У документа нет жизненного цикла процесса, но есть жизненный цикл содержания, и он самый обычный: **правка файла, затем прогон валидатора, затем коммит**.

Порядок добавления компонента задан требованиями выше и сводится к трём шагам:

1. Создать `openspec/specs/<категория>/<имя>/spec.md` и написать её по канону `architecture/component-model` — все 19 разделов, непустые тела, хотя бы одно требование со сценарием.
2. Добавить строку в секцию соответствующей категории, выбрав категорию из закрытого перечня и статус по чек-листу.
3. Прогнать `tools/validate_component_specs.py`; нарушение паритета «запись есть, спеки нет» или «спека есть, записи нет» означает, что один из двух шагов пропущен.

Обратный путь — `deprecated` — это не удаление строки, а её перевод: удалённая строка оставляет за собой спецификацию без записи и порождает нарушение паритета. Перевод в `deprecated` сохраняет оба конца связанными и говорит, что компонент больше не развивается, но его история ещё разрешена читать.

Чего на этом цикле нет: миграций, версионирования формата, автоматического пересчёта статистики, синхронизации с `openspec/changes/`.

## Data Ownership

Разделение владения здесь единственное и строгое, потому что вся ценность компонента в том, что он реестр, а не описание.

**Владеет:** перечнем записей и их метаданными — именем компонента, категорией, путём к реализации, ссылкой на спецификацию, статусом. Это единственный в проекте список компонентов, и второго списка быть не должно.

**Не владеет:** описанием поведения. Всё, что можно прочитать и получить неоднозначность, принадлежит `spec.md` компонента. Реестр не пересказывает контракт, не приводит примеров и не цитирует требования.

**Не владеет:** нормативным каноном. Перечень из 19 разделов принадлежит `architecture/component-model`; реестр — его потребитель и индексатор, а не второй источник.

**Не владеет:** фактическим составом системы. Реестр утверждает, что компонент есть, со ссылкой на спеку; соответствие кода спецификации он не проверяет и проверить не может.

**Не владеет:** сводной статистикой в строгом смысле — секция `## Статистика` присутствует в файле, но не выводится и не проверяется, то есть её достоверность обеспечивается дисциплиной автора, а не механизмом.

Право вносить изменения в файл имеют авторы компонентов; право **проверять** их изменения имеет валидатор. Это разделение и не даёт реестру стать местом, где описние живёт рядом со спецификацией.

## Error Behavior

Реестр сам не обрабатывает ошибок — он документ. Ошибки в нём обнаруживает `tools/validate_component_specs.py`, и все они формулируются одним способом: `путь:строка: [registry] сообщение`. Метка `registry` в квадратных скобках означает, что строка не принадлежит ни одному разделу спецификации, и появляется у всех нарушений реестра, независимо от вида.

Перечень обнаруживаемого — исчерпывающий для формы:

| Ситуация | Что сообщается |
| --- | --- |
| Строка не распарсилась как таблица | номер строки и «не удалось разобрать строку реестра» |
| Число колонок не 4 и не 5 | номер строки, ожидаемое число колонок и фактическое |
| Имя компонента не совпало с `^[A-Za-z][A-Za-z0-9_]*$` | номер строки и недопустимое имя |
| Статус вне `VALID_STATUSES` | номер строки, значение и допустимые статусы |
| Категория вне `VALID_CATEGORIES` — в секции или в ячейке | номер строки, значение и отсортированный список допустимых категорий |
| Секция третьего уровня без таблицы не считается категорией | молча пропускается: это `## План заполнения` |
| Ссылка ведёт не в `spec.md` | формулировка «ссылка должна указывать на файл spec.md» |
| Ссылка ведёт на несуществующий файл | имя записи, категория и ожидаемый путь |
| Дубль имени компонента | обе строки; дублируются и при невалидном статусе |
| Запись реестра без файла спецификации | категория, имя и ожидаемый путь |
| Файл спецификации без записи реестра | имя и «ни одна запись на неё не ссылается» |
| `COMPONENTS.md` отсутствует | предупреждение `registry_missing`, а не нарушение |

Последняя строка — единственное предупреждение во всём валидаторе, и она важна для понимания владения: отсутствие реестра не должно выглядеть как «проверять нечего». Остальное — нарушения с кодом возврата `1`.

Поведения при ошибке у самого документа нет: он не падает, не восстанавливается и не сообщает о проблемах сам.

## Invariants

1. **Реестр не содержит описаний поведения.** Утверждение, которое можно прочитать как контракт, принадлежит `spec.md`. Это жёстче требования «не дублировать»: дублирование запрещено даже в сокращении.
2. **Ссылка ведёт в существующую спецификацию.** Не в каталог, не в `README.md`, не в `changes/`.
3. **Категория принадлежит закрытому перечню.** Одновременно в секции и в ячейке; в реестре категория всегда одна.
4. **Имя компонента уникально.** Дубль — нарушение независимо от прочих дефектов строки.
5. **Статус честен.** `complete` означает заполненные обязательные разделы, соответствие коду, явный boundary, требование со сценарием и запрещённое поведение; иначе статус понижается.
6. **Паритет двусторонний.** Ни записи без спеки, ни спеки без записи. Удаление строки при живой спеке — нарушение, а не приведение в порядок.
7. **Категория спеки выводится из пути.** Каталог `spec.md` и секция реестра обязаны называть одну и ту же категорию: путь определяет категорию, и реестр за ним следует.
8. **План заполнения не часть реестра.** Секции без таблиц не объявляются неизвестными категориями — иначе сам план заполнения был бы ошибкой.

## Forbidden Behavior

- **Дублировать содержание спецификации в реестре.** Даже одной строкой «в двух словах»: она устареет первой и станет вторым источником истины.
- **Описывать поведение, контракт, границы или ошибки компонента** в реестре.
- **Оставлять запись без спецификации и наоборот** — оба состояния одинаково нарушение.
- **Удалять строку вместо перевода в `deprecated`.** Спека переживает запись, и паритет после удаления нарушается.
- **Ставить `complete` неполной спеке.** Статус — утверждение о состоянии, а не о намерении довести.
- **Вводить новую категорию «на месте».** Перечень закрыт; новый домен требует правки `VALID_CATEGORIES` и этого документа одновременно.
- **Хранить перечень компонентов в другом месте.** Второй список — это уже дрейф, и обнаружить его нечем: валидатор проверяет один файл.
- **Переписывать секцию категории как повествование** вместо таблицы. Секция без таблицы перестаёт быть реестром и её записи перестают проверяться.
- **Заполнять `## Статистика` вручную числами, расходящимися с таблицами.** Статистика не проверяется, и ошибка в ней не будет замечена ничем.

## Consumers

- **Человек, впервые попавший в проект.** Реестр отвечает на вопрос «что здесь вообще есть» за один проход по шести секциям, не открывая ни одной спеки.
- **Автор нового компонента.** Ему нужен чек-лист: в какую категорию, какой статус, какая спека — и это перечислено здесь, а не в коде валидатора.
- **`tools/validate_component_specs.py`** — главный машинный потребитель. Он разбирает формат реестра построчно и строит из него множество компонентов для сверки с каталогом спек.
- **`architecture/component-model/spec.md`** — связан с реестром по статусу: `complete` обязан соответствовать чек-листу этого документа.
- **CI.** В цепочку проверок входит страж `tests/test_component_spec_validation.py`, который и разбирает реестр на синтетических деревьях, проверяя каждое правила формы. На настоящем реестре страж проверяет базовый обход.

## Implementation

Реализация этого компонента — **сам документ и валидатор, который его читает**. Отдельного исполняемого кода у реестра нет, и объявлять его здесь было бы враньём: перечислить нечего.

- `openspec/specs/COMPONENTS.md` — реализация компонента целиком: файл и есть реестр.
- `tools/validate_component_specs.py` — валидатор формы реестра и паритета со спецификациями (`parse_components_registry`, `validate_registry_parity`, `validate_registry_row`, `_parse_registry_row`, `_resolve_category`, `_row_category`).
- `openspec/specs/architecture/component-model/spec.md` — чек-лист, на который опирается статус `complete`; владеет перечнем разделов, по которому определяется, заполнена ли спека.

## Verification

Проверяется форма и паритет, а не содержание.

- `tests/test_component_spec_validation.py` — страж правил реестра. Из них к этому компоненту относятся: корректная строка реестра даёт чистый отчёт; таблица статистики не принимается за компонент; строка действительно разбирается; пятиколоночная строка разбирается; неверное число колонок — нарушение; неразбираемая строка — нарушение; неизвестный статус — нарушение; дубль компонента обнаруживается; дубль обнаруживается и при невалидном статусе; ссылка должна указывать на файл спецификации; отсутствующий файл спецификации — нарушение; неизвестная категория — нарушение; закрытый список категорий существует. Все тесты работают на синтетическом дереве во временном каталоге, а не на настоящем реестре.
- `.github/workflows/ci.yml` — исполняет этот страж в задаче «Fast tests», поэтому форма реестра проверяется в пайплайне.
- Что **не** проверяется и чему нет стража: достоверность секции `## Статистика`, соответствие статуса фактической полноте спецификации, существование пути, указанного в колонке «Реализация», и совпадение описания компонента с его кодом. Для колонки «Реализация» проверяется только синтаксис ячейки, а не её содержимое.
