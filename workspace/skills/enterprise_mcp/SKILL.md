# Операции платформы (MCP)

Все операции платформы приходят в реестр инструментов как `mcp_enterprise_*`.
Это **штатные инструменты нанобота**: у каждого есть своя `description` и своя
`inputSchema`, и модель видит их напрямую. Отдельной обёртки над ними нет и
не нужно — навык объясняет, **когда и как** звать, а не заменяет вызов.

## Что доступно

Объявление — `config.json → tools.mcpServers.enterprise`, белый список —
`enabled_tools`. Всё, чего в нём нет, модель не видит: операцию нельзя вызвать
«по памяти», даже если она существует на платформе.

| Инструмент | Что делает | Обязательные аргументы |
|---|---|---|
| `mcp_enterprise_list_scripts` | Каталог готовых скриптов аудита | — |
| `mcp_enterprise_run_script` | Выполнить скрипт каталога | `script` |
| `mcp_enterprise_generate_sql` | Ответить на вопрос по данным аудита обычной фразой | `query` |
| `mcp_enterprise_vector_search` | Семантический поиск по снимку | `query`, `index_name` |
| `mcp_enterprise_query_operation` | Догрузить разобранный документ по `operation_id` | `operation_id` |
| `mcp_enterprise_history_search` | Поиск по журналу текущей сессии | — |
| `mcp_enterprise_read_result` | Прочитать результат, сохранённый из-за размера | — |

Доменный разбор — в навыке `audit_analyzer`. Здесь только контракт, общий для
всех вызовов.

## Личность вызова — не твой аргумент

У операции **нет** параметров `session_id`, `user_id`, `request_id`, и
добавлять их нельзя. Личность оборота подставляет хук `McpIdentityHook` перед
вызовом; платформа вырезает эти ключи из аргументов до вызова домена, и до
операции они не доходят вовсе.

Отсюда два правила:

- **Не передавай личность сама.** В опубликованной схеме таких полей нет, так
  что в аргументах они могут появиться только снизу — от тебя. Любое твоё
  значение будет перезаписано, а попытка «подменить сессию» ничего, кроме
  отказа, не даст.
- **`identity_missing` — не твоя ошибка.** Это значит, что у оборота не было
  контекста вызова. Придумывать значения и повторять бессмысленно: сообщи
  пользователю, что операции в этом обороте недоступны.

## Конверт ответа

Успешный ответ — тело операции плюс блок `_execution`:

```json
{"...тело операции...",
 "_execution": {"request_id": "...", "tool": "run_script", "capability": "audit",
                "duration_ms": 812, "result_size": 40960,
                "quality": {"ok": true, "flags": []}}}
```

- `_execution` — метаданные вызова, а не данные. Не пересказывай их
  пользователю, если он не спросил про «как это отработало».
- `quality.flags` — предупреждения платформы о форме результата. Неигнорируемые
  флаги означают, что тело надо читать осторожно (например, усечено).
- `request_id` связывает вызов с вопросом в журнале. Полезен, когда
  пользователь спрашивает «почему это заняло столько времени».

## Крупный результат

Ответ больше порога (`platform.json → execution.max_inline_result_bytes`) не
режется молча, а уезжает в файл: в теле появляется `_execution.artifact` с
`uri` вида `session://results/...`, а может стоять `large_result: true`.

Читать его — отдельным вызовом `mcp_enterprise_read_result`: передай
`uri` (или `artifact_id`) и, если нужно, постранично — `offset` и `limit`.
Ответ вернёт следующую страницу по `next_offset`; на последней он `null`.

**Молчаливого усечения нет:** если `artifact` есть, а модель не прочитала файл,
она видела не всё. Не делай выводов о полноте данных по такому ответу.

## Коды отказа

Отказ приходит конвертом `{"error": {"code": ..., "message": ...,
"retryable": ...}}`. Список кодов закрыт — новый код без записи в платформу не
появится:

| Код | Что значит | Что делать |
|---|---|---|
| `invalid_params` | Аргумент не прошёл проверку | Сверься со схемой операции, исправь, повтори |
| `invalid_request` | Запрос не имеет смысла в такой формулировке | Переформулируй задачу |
| `not_found` | Имени нет (скрипт, файл, артефакт) | Возьми имя из каталога, а не из памяти |
| `no_match` | Данных по запросу нет | Это результат, а не сбой — скажи пользователю |
| `not_answerable` | Запрос нельзя построить по доступным данным | Сузь или переформулируй вопрос |
| `registry_unavailable` | Реестр недоступен | Инфраструктура; повтор позже |
| `identity_missing` | У вызова нет личности | Не твоя ошибка, см. выше |
| `timeout` | Операция не уложилась в срок | Повтори с более узким запросом |
| `upstream_unavailable` | Нет снимка или проверяющего слоя | Инфраструктура; повтор позже |
| `index_build_failed` | Индекс не собрался | Инфраструктура; сообщи пользователю |
| `queue_full` | Очередь переполнена | Повтори позже |
| `internal` | Дефект платформы | Не чини повтором, сообщи пользователю |
| `infrastructure_error` | Ошибка ввода-вывода или прав | Инфраструктура; повтор позже |

Повторять имеет смысл только при `retryable: true` — то есть для `timeout`,
`infrastructure_error`, `upstream_unavailable`, `index_build_failed`,
`queue_full`. Остальные коды повтором с теми же аргументами не лечатся.

## Жёсткие правила

- Не вызывай операции вне белого списка и не подставляй их имена в другие
  инструменты: неизвестного имени нет ни в одном реестре.
- Не пиши SQL: операции аудита принимают вопрос обычной фразой, а проверку
  запроса платформа делает сама.
- Не переключайся молча на другую операцию после отказа: у каждого кода своя
  реакция (таблица выше).
- Не вызывай `exec` / `python` ради данных — операции платформы единственный
  путь, и обходной путь не увидит ни изоляции, ни журнала.
