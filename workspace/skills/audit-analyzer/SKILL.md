# Audit Analyzer

Используй tool **`audit_analyze`** для всех запросов по анализу аудиторских проверок.

## Режимы

| Режим | Когда использовать |
|:------|:-------------------|
| `predefined` | Стандартные отчёты. Передаёшь `script` (имя скрипта) + `params` |
| `vector` | Поиск по смыслу в документах. Передаёшь `query` + `index_name` |
| `sql` | Сложные нестандартные запросы. Передаёшь `query` на русском — LLM сама сгенерирует безопасный SQL |

## Правила выбора режима

1. **Нужен быстрый стандартный отчёт?** → `predefined`. Выбери скрипт из реестра ниже.
2. **Нужен поиск по содержанию нарушений/рекомендаций?** → `vector`. Работает по готовому FAISS-индексу.
3. **Нужна сложная аналитика, которой нет в шаблонах?** → `sql`. LLM генерирует запрос, EXPLAIN проверяет корректность, retry до 3 раз при ошибках.

## Реестр скриптов (predefined)

Выбор по имени через параметр `script`. Параметры передаются через `params`.

### `analytics_by_year_month`
- **Описание:** Аналитика проверок по годам и месяцам
- **Параметры:**
  | Параметр | Тип | Описание |
  |:---------|:----|:---------|
  | `year` | `number` | Год проверки (например 2024) |

### `violations_by_type`
- **Описание:** Статистика нарушений по кодам
- **Параметры:**
  | Параметр | Тип | Описание |
  |:---------|:----|:---------|
  | `date_from` | `date` | Дата начала периода (`2024-01-01`) |
  | `violation_code` | `like` | Тип нарушения (ILIKE, можно часть слова) |

### `top_audited_objects`
- **Описание:** Топ проверяемых объектов по количеству проверок
- **Параметры:**
  | Параметр | Тип | Описание |
  |:---------|:----|:---------|
  | `auditee_entity` | `like` | Название объекта (ILIKE) |
  | `date_from` | `date` | Дата начала периода |
  | `limit` | `number` | Количество записей (по умолчанию 10) |

### `audit_effectiveness`
- **Описание:** Оценка эффективности проверок по выявленным нарушениям
- **Параметры:**
  | Параметр | Тип | Описание |
  |:---------|:----|:---------|
  | `date_from` | `date` | Дата начала периода |
  | `date_to` | `date` | Дата конца периода |
  | `min_violations` | `number` | Минимальное количество нарушений (HAVING) |

### `audit_dynamics`
- **Описание:** Динамика проведения проверок по периодам
- **Параметры:**
  | Параметр | Тип | Описание |
  |:---------|:----|:---------|
  | `period` | `enum` | Период: `month` (по умолчанию), `quarter` или `week` |
  | `date_from` | `date` | Дата начала периода |

### `audit_types_stats`
- **Описание:** Статистика по типам проведения проверок
- **Параметры:**
  | Параметр | Тип | Описание |
  |:---------|:----|:---------|
  | `audit_type` | `like` | Тип проверки (ILIKE) |
  | `date_from` | `date` | Дата начала периода |

### Форматирование параметров

| Тип | Что передавать | Пример значения |
|:----|:---------------|:----------------|
| `number` | целое число | `2024` |
| `date` | строка `YYYY-MM-DD` | `"2024-01-01"` |
| `like` | строка (авто-оборачивание в `%...%`) | `"финансовые"` |
| `enum` | строка из допустимых значений | `"quarter"` |

## Режим sql — генерация SQL через LLM

Pipeline:
```
Запрос → Схема БД → LLM генерирует SELECT
  → validate_sql (запрет DDL/DML, мульти-запросов)
  → EXPLAIN (FORMAT JSON) — проверка синтаксиса и объектов
  → Если EXPLAIN упал: LLM получает ошибку PostgreSQL (например "relation xxx does not exist")
    и свой прошлый SQL → исправляет на следующей итерации
  → Если EXPLAIN успешен → execute_query → результат
```

- **До 3 попыток** (1 генерация + 2 исправления)
- EXPLAIN не выполняет запрос, только строит план — безопасно
- LLM получает конкретную ошибку PostgreSQL и самостоятельно её исправляет

## Векторные индексы (vector)

Поиск выполняется по FAISS-индексам. Обязательный параметр: `index_name` — имя индекса (без `.faiss`).

Опциональные параметры:
- `top_k` — вернуть N наиболее релевантных результатов (по умолчанию 5)
- `threshold` — вернуть все результаты со score >= порога (игнорирует top_k)

Индексы загружаются из директории, указанной в инструментальных настройках.

## Примеры

**predefined:**
- `audit_analyze(mode="predefined", script="analytics_by_year_month", params={"year": 2024})`
- `audit_analyze(mode="predefined", script="violations_by_type", params={"date_from": "2024-01-01", "violation_code": "финансовые"})`
- `audit_analyze(mode="predefined", script="top_audited_objects", params={"limit": 5})`
- `audit_analyze(mode="predefined", script="audit_dynamics", params={"period": "quarter"})`
- `audit_analyze(mode="predefined", script="audit_effectiveness", params={"date_from": "2024-01-01", "date_to": "2024-12-31"})`

**vector:**
- `audit_analyze(mode="vector", index_name="violations_index", query="финансовые нарушения в университетах", top_k=3)`

**sql:**
- `audit_analyze(mode="sql", query="покажи объекты с повторными нарушениями за последний квартал")`
- `audit_analyze(mode="sql", query="сравни эффективность плановых и внеплановых проверок")`
