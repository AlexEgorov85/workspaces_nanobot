Миграция на MCP · аудит завершён

Один сервер.
Агент теряет данные, код и патчи.

Всё enterprise-слой живёт в одном MCP-процессе enterprise-mcp, наполняемом динамическим реестром: capability добавляется файлом. PostgreSQL — единственный стор, DuckDB удаляется, FAISS собирается в памяти лениво. Из двенадцати патчей Nanobot остаётся четыре.

01

Целевая схема

Цепочка данных потеряла один hop: векторы идут из PostgreSQL прямо в FAISS, без снапшота на диске. Capability — каталог, а не процесс, поэтому добавление домена не трогает ни реестр, ни сборку.

Домены audit и legal — capability, а не процессы: у них нет собственного протокола, только операции и инструкция для агента.

02

Почему один сервер, а не три

Предыдущая редакция резала по операциям и обосновывала это «уровнем доверия». Обоснование не выдержало проверки: граница, которая реально имеет значение, — агент ↔ enterprise, и её уже проводит сам протокол MCP. Разделение разбивало наш собственный код от нашего собственного кода.

Что разделение покупало и чем заменено: изоляция тяжёлой загрузки FAISS — ленивой сборкой индекса, изоляция зависшего вызова LLM — очередью и таймаутом на сетевом вызове.

03

Реестр: состав сервера задаётся файлами

Раньше набор enterprise-tool'ов был зашит в код: project_tool_loader сканировал каталог, но регистрация и подключение к AgentLoop выполнялись вручную. Теперь добавление операции — это один файл.

Контракт операции

Инструмент не регистрирует себя сам — он отдаёт описание.

# capabilities/data/tools/history_search.py
def create_tool(container):
    def history_search(query, limit=20):
        return container.data.history_search(query, limit)

    return ToolDefinition(
        name="history_search",
        description="Поиск по журналу agent_gateway_logs",
        handler=history_search,
        category="read",
    )

Превращать описание в MCP-инструмент умеет реестр. Именно это делает server.py нечувствительным к составу.

Три границы

Где реестр принципиально останавливается.

  • Автообнаружение — не доверие. Каталог capabilities/ доверенный: туда попадает только код репозитория, и всё исполняется с правами процесса
  • Hot reload нет. Реестр иммутабелен в пределах процесса: добавил файл — перезапустил сервер. Горячая перерегистрация тянет смену схемы уже опубликованного инструмента и состояние прежнего handler'а
  • Имена плоские и уникальные. Capability не входит в имя — MCP-клиент и так приклеивает префикс сервера, а вложенный namespace только затрудняет выбор моделью
Следующее усложнение, когда инструментов станет много: манифест tool.json с полем entrypoint вместо угадывания точки входа. Он меняет загрузчик, а не реестр, и не требует переписывания операций.

05

12 патчей → 4: переиспользование важнее хуков

Сначала проверял хуки, потом — глубже. Настоящая находка не в хуках: два патча переписывали функции, которые Nanobot 0.3.5 уже поставляет и уже настраивает. Доказательная база по каждой строке — в docs/architecture/nanobot-reuse-catalog.md.

Что даёт 0.3.5

Точки, которых не было в прежней редакции.

  • finalize_content(ctx, content) → str | None — вызывается в runner.py трижды, подменяет финальный контент
  • AgentHookContext мутабельный: messages, tool_results, error
  • AgentTurnHookContext.events: EventSink — публикация событий из хука, штатный механизм
  • turn_context.metadata / .attributes — мутабельные dict, второй канал per-turn данных
  • AgentTurnHookFactory — официальная фабрика per-turn хуков
  • TurnEndEvent, TurnCompleted с outcome, failure_kind, failure_error_kind

Что хук не может

Ровно одно ограничение — и оно узкое.

В execution.py вызов идёт так: result = await tool.execute(...) → await hook.after_execute_tool(context, ..., result) → return result. Хук результат получает, но возвращаемого значения не имеет, а раннер отдаёт result без изменений. Подменить содержимое результата tool'а через хук нельзя.

Вот и всё ограничение. Наблюдать, писать в БД, публиковать события через turn_context.events.publish, менять turn_context.metadata — хук умеет всё.

Правило: проверять не наличие хука, а может ли он повлиять именно на то, что нужно изменить. Возвращаемое значение требуется только для подстановки значения.

06

Порядок работ

Исправлен после аудита lib/: FAISS собирается из снапшота, поэтому capability vectors обязана читать из PostgreSQL раньше, чем снапшот исчезнет. Один механизм за раз, старая реализация удаляется только после прохождения интеграционных тестов.

  1. ШАГ 0

    Принятые удаления: agent_worker_claims с протоколом аренды, benchmarks/, streamlit вместе с subprocess_manager.py, example.py, сломанный и мёртвый код. Каждый набор — отдельный коммит с DROP-миграциями и пересборкой baseline.

  2. ШАГ 1

    Реестр: ToolDefinition, ToolRegistry, загрузчик capabilities/*/tools/*.py, fail-fast на любом нарушении. Идёт раньше любой capability, иначе состав придётся перечислять руками.

  3. ШАГ 2

    libs/enterprise_data ← workspace/utils/db.py + sql_safety + jsonb + clean_text. Это перенос готового модуля, а не постройка.

  4. ШАГ 3

    Capability data: операции поверх библиотеки, statement_timeout на стороне сервера.

  5. ШАГ 4

    Capability vectors: сборка FAISS напрямую из PostgreSQL и лениво — по первому векторному запросу, с локом на прогрев и наблюдаемым состоянием. Переносит build_faiss_index, group_vector_hits и векторную половину cache_provider_impl.py.

  6. ШАГ 5

    Capability llm: libs/llm + операция complete. Убирает 287 строк LLM-клиента из агента.

  7. ШАГ 6

    Удаление DuckDB одним коммитом, без MCP-работы. Векторный поиск к этому моменту уже не зависит от снапшота. Baseline пересобирается здесь, не раньше.

  8. ШАГ 7

    Логирование через enterprise-mcp: log_event: буфер в агенте, батчевый flush, дроп при переполнении. db_logging_bus.py остаётся в агенте — он знает форму сообщений Nanobot.

  9. ШАГ 8

    Патчи → хуки и события. assemble_outbound уходит первым, у него все три обязанности уже выразимы событиями. Проверяется реальным ходом с вложением, заполняется ли вообще слот media.

  10. ШАГ 9

    Document-tool агента и перенос legal_summarizer — 30 000 строк с нулевой связностью. Сначала проверяется, что парсер не расходится на две копии.

  11. ШАГ 10

    Capability audit поверх data и vectors. CLI-граница уже существует. Не забыть резолв scripts_registry из TableRegistry.

  12. ШАГ 11

    Разделение зависимостей: из requirements.txt агента уходят sqlglot, duckdb, pyarrow, faiss и клиентский LLM-пакет. Офисные остаются — решение принято осознанно.
