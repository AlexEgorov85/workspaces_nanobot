# Контракты вызовов MCP

**Сервер:** `enterprise-mcp` — один процесс, capability-каталоги внутри.
**Ветка:** `refactor/mcp-platform` · **Коммит:** `4f4e8a8`
**Связанные документы:** `TARGET-ARCHITECTURE.md` (что и почему), `design.md`
(решения), `../openspec/changes/enterprise-mcp-platform/specs/` (WHEN/THEN).

---

## 0. Как читать этот документ

Каждый контракт разделён на три части, и их важно не путать:

| Пометка | Значение |
|---|---|
| **Сегодня** | Поведение проверено в текущем коде. Это факт, на который опирается перенос |
| **Новое** | Работы, которых в коде нет. Контракт их вводит |
| **Опасность** | Поведение, которое тихо ломает контракт, если его не учесть |

Каждая операция описана: что делает, параметры, что возвращает, какие ошибки
возможны, какие побочные эффекты и что в ней не так.

**Ничего из этого ещё не реализовано.** Документ — контракт, под который
пишется код в фазах 1–5 плана. Расхождения между ним и кодом, найденные при
подготовке, вынесены в §7 и уже исправлены в проектной документации.

## 1. Общие соглашения

**Имена.** Плоские и уникальные в пределах сервера. Capability в имя не
входит: MCP-клиент Nanobot и так приклеивает префикс сервера, поэтому модель
видит `mcp_enterprise_query_sql`, а `mcp_enterprise_data_query_sql` только
удлиняет имя без добавления смысла. Принадлежность к capability живёт в
поле `category`.

**Синхронность.** Все операции — синхронные. `query_sql` ждёт результат БД,
`complete` ждёт провайдера, `vector_search` может ждать прогрева индекса.
Асинхронность появится только вместе с потоковой выдачей результатов, и это
отдельное решение, а не режим по умолчанию.

**Точка входа.** Одна на сервер, в файл `servers/enterprise/server.py`. Она
поднимает реестр и отдаёт его MCP-клиенту, не зная состава заранее.

```text
capabilities/<name>/tools/*.py
  → discovery → import → create_tool(container) → validate → register → MCP
```

**Изоляция — не аргумент.** Ни одна операция не принимает `user_id` или
`session_id` от вызывающей стороны. Изоляция выводится сервером из
идентичности транспорта. Иначе модель подставит чужой идентификатор, и
изоляция перестанет быть изоляцией. Сегодня это ровно то, что уже сделано в
`history_search`: идентичность берётся из `RequestContext`, а не из аргумента.

**Форма ответа.** JSON-объект. Успех и ошибка различаются полем `status` либо
типом ошибки, а не HTTP-кодом: транспорт не видит разницу, MCP возвращает
результат вызова.

## 2. Модель ошибок

Один набор кодов на весь сервер. Операция может возвращать только из своего
списка.

| Код | Когда | Что делает вызывающий |
|---|---|---|
| `invalid_params` | Значение не прошло проверку типа или диапазона | Исправить вызов. Повтор с теми же аргументами бессмыслен |
| `policy_denied` | SQL-guard отказал в выражении | Переписать запрос. Это не сбой, это отказ |
| `isolation_denied` | Запрошенная область шире доступной вызывающему | Сузить область. Повтор без изменений бесполезен |
| `not_found` | Неизвестный индекс, capability или ресурс | Проверить имя. Частая ошибка модели при опечатке |
| `identity_missing` | У вызывающего нет ни session, ни user | Ошибка конфигурации транспорта, не модели |
| `timeout` | Истёк серверный срок операции | Повтор допустим, но с меньшим объёмом |
| `upstream_unavailable` | Провайдер эмбеддингов или LLM недоступен | Повтор с задержкой. Данные не потеряны |
| `index_build_failed` | Ленивая сборка FAISS упала | Проверить целостность векторной таблицы |
| `queue_full` | Очередь задач переполнена | Повтор позже. Данные не потеряны, запрос не выполнен |
| `internal` | Всё остальное | Сообщение уже содержит детали |

**Правило отказа.** Ошибка всегда несёт `code` и `message`. `message`
пишется для человека, `code` — для машины и для модели. Модель не должна
угадывать причину по тексту.

## 3. Capability `data`

Доступ к PostgreSQL. Пул один на сервер: `libs/enterprise_data/db.py`, N
воркеров, у каждого своё соединение с `autocommit=True`, задания в общей
очереди. Очередь и лиза — внутри библиотеки, наружу не выходят.

### 3.1 `query_sql`

**Что делает.** Выполняет один произвольный `SELECT` к PostgreSQL и
возвращает строки. Перед выполнением выражение проходит AST-политику
read-only, после — усекается по `max_rows` на стороне сервера.

> **Не путать с нынешним `query_sql` в `CacheProvider`.** Тот ходит в
> DuckDB, **не** проходит `sql_safety` и не имеет никакой защиты от записи.
> Он умирает вместе с DuckDB. Новая операция — новый код поверх
> существующего PostgreSQL-guard'а, который сегодня охраняет только
> сгенерированный SQL аудита.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `sql` | `string` | — | Одно `SELECT`-выражение |
| `max_rows` | `integer` | `200` | Верхняя граница строк, `1..10000` |
| `params` | `array` | `null` | Позиционные значения для `%s`. Никогда не интерполируются в текст |

**Возвращает**
```json
{ "status": "ok", "row_count": 12, "truncated": false,
  "columns": ["id", "status"],
  "rows": [[1, "closed"], [2, "open"]],
  "query_hash": "sha256:…", "elapsed_ms": 41 }
```

**Ошибки:** `invalid_params`, `policy_denied`, `timeout`, `queue_full`,
`not_found` (таблица отсутствует), `internal`.

**Побочные эффекты:** нет. Соединение не удерживается после возврата.

**Сегодня.** `sql_safety.validate_sql_report(sql) -> ValidationReport` с
полями `allowed`, `reason`, `normalized_sql`, `query_hash`, `issues`.
Deny-list из 26 функций (`pg_read_file`, `pg_sleep`, `pg_terminate_backend`,
`lo_import`, `dblink`, `copy`, `setval`, …) и 2 системных схем
(`pg_catalog`, `information_schema`). Блокируются DDL/DML по первому слову,
`SELECT INTO`, `exp.Command` кроме `EXPLAIN`, несколько операторов
подряд. Guard использует `sqlglot` 30.17.0, подключаемый лениво.

**Новое.** Усечение по `max_rows` на сервере (сегодня `fetch` возвращает всё).
`statement_timeout` — его в коде **нет вообще**, см. §7.1. `params` в текущих
`fetch`/`execute` уже поддерживаются, но для новой операции это надо
проверить на сквозном пути.

**Опасность.** Guard деградирует при отсутствии `sqlglot` и **перестаёт быть
защитой**. См. §7.2 — это блокирующее требование, а не рекомендация.

### 3.2 `history_search`

**Что делает.** Ищет события журнала `agent_gateway_logs` — по тексту, типу
события, имени инструмента и временному диапазону. Отдаёт готовое
представление: для агента после сжатия контекста это единственный способ
увидеть, что происходило.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `query` | `string` | `null` | Подстрока: `summary ILIKE` **или** `payload::text ILIKE` |
| `event_type` | `string` | `null` | Фильтр по типу. Пусто = любой |
| `tool_name` | `string` | `null` | Фильтр по колонке `name` |
| `since` | `string` | `null` | Нижняя граница по `"timestamp"` |
| `until` | `string` | `null` | Верхняя граница по `"timestamp"` |
| `scope` | `"current" \| "all"` | `"current"` | `current` — сессия вызывающего, `all` — все его сессии |
| `limit` | `integer` | `50` | `1..500` |
| `offset` | `integer` | `0` | Для постраничного обхода |

**Возвращает**
```json
{ "status": "ok", "count": 3, "scope": "current",
  "has_more": true, "next_offset": 3,
  "truncated": false,
  "events": [ { "event_id": "…", "timestamp": "…", "event_type": "tool_call",
                "name": "query_sql", "level": "INFO", "summary": "…",
                "payload": "…", "payload_truncated": false } ] }
```

**Ошибки:** `invalid_params` (плохой `scope`, нечисловой `limit`),
`identity_missing`, `not_found`, `queue_full`, `internal`.

**Изоляция.** `scope="current"` → `RequestContext.session_key`;
`scope="all"` → `RequestContext.sender_id`. Пустая идентичность — ошибка **до**
выполнения SQL, запрос не уходит. `user_id` в ответе не возвращается.

**Сегодня.** Инструмент уже существует: `workspace/tools/history_search_tool.py`.
Таблица и схема резолвятся из `logging.db.table_name` и `logging.db.schema`
(дефолт `public.agent_gateway_logs`) **на каждый вызов**, а не при старте.
Значения фильтров уходят только как `%s`-параметры, интерполяции нет.
Порядок: `ORDER BY "timestamp" DESC, "id" DESC`, лишняя строка добирается
для вычисления `has_more`.

**Опасность.** Граница `scope="all"` — это `user_id` в журнале. Строки с
`user_id IS NULL` для неё **невидимы**: это не потеря, это фильтр. Но если в
экспортируемой копии журнала `user_id` не заполняется, `scope="all"`
молча вернёт пустоту. См. §7.3.

### 3.3 `schema_check`

**Что делает.** Проверяет наличие шести обязательных runtime-таблиц одним
`SELECT` к `information_schema.tables` и возвращает список отсутствующих.
Вызывается агентом на старте, чтобы упасть с внятной ошибкой, а не с
неразбираемым.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `tables` | `array<string>` | `null` | `null` = проверять штатные шесть |
| `timeout_ms` | `integer` | `5000` | Было в API, **не применяется** — см. §7.4 |

**Возвращает**
```json
{ "status": "ok", "ok": false,
  "expected": ["public.agent_conversation_messages", "…"],
  "missing": [ { "schema": "public", "name": "agent_gateway_logs" } ] }
```

**Ошибки:** `invalid_params`, `queue_full`, `internal`. Отсутствие таблиц —
**не** ошибка, а поле в успешном ответе: вызывающий сам решает, фатально это
или нет.

**Сегодня.** `SchemaValidationService.validate(settings, fetch=…, timeout_sec=…)`
→ `expected_table_names` → `check_tables`. Шесть ключей:
`channels.postgres.{table_name, messages_table, meta_table, claims_table}`,
`logging.db.{table_name, question_runs_table}`. Имена берутся из
merged SETTINGS, **схема захардкожена** `public`. `table_type='BASE TABLE'` —
представление не считается таблицей. Исключения: `SchemaValidationError`
(список `MissingTable`) и приватный `_MissingConfigKeys` (нет ключей
конфига, `.missing` при этом пуст).

**Новое.** `timeout_ms` в контракте заявлен, но в текущем коде параметр
удаляется без применения. Либо реализовать, либо убрать из контракта —
молчаливый параметр хуже отсутствующего. Решение за шагом 3.

### 3.4 `log_event`

**Что делает.** Кладёт событие в очередь и возвращается. Событие уходит в
`agent_gateway_logs` батчем, в своём потоке, не позже чем через
`flush_interval`. Никогда не блокирует ход.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `event_type` | `string` | — | До 64 символов |
| `level` | `"DEBUG"\|"INFO"\|"WARN"\|"ERROR"` | `"INFO"` | Ниже порога событие отбрасывается |
| `session_id` | `string` | `null` | Идентификатор сессии |
| `user_id` | `string` | `null` | **Заполняет границу для `history_search(scope="all")`** |
| `name` | `string` | `null` | Имя инструмента или объекта |
| `summary` | `string` | `null` | До 200 символов, обрезается на сервере |
| `payload` | `object` | `{}` | JSONB |
| `metadata` | `object` | `{}` | JSONB |

**Возвращает** `{ "status": "ok", "accepted": true }` либо
`{ "status": "ok", "accepted": false, "reason": "queue_full" | "level" }`.

**Ошибки:** `invalid_params`. Потеря события **не** является ошибкой — это
заложенное поведение.

**Побочные эффекты:** строка в журнале. Очередь ограничена по умолчанию
10 000 записей, переполнение — **безвозвратный дроп** с ростом счётчика.
Без файлового fallback: нечего писать, если БД недоступна.

**Сегодня.** `DbLoggingService.log_event(event: LogEvent) -> bool` плюс
`try_log_event(svc, event, producer=…, event_type=…)`. Таблица:
`public.agent_gateway_logs`, `DISTRIBUTED BY (request_id)`, **без
первичного ключа**, `level` ограничен `CHECK`-констрейнтом. INSERT
выполняется батчем из 12 колонок; `"timestamp"` не пишется — дефолт БД.
`payload` и `metadata` пишутся как `{}`, а не `NULL`.

### 3.5 `upsert_records`

**Что делает.** Запись по явному контракту ресурса: строки известной формы
для известной таблицы с известным ключом. Никакого произвольного DML.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `table` | `string` | — | Зарегистрированное имя ресурса, не `schema.table` произвольно |
| `records` | `array<object>` | — | Строки ресурса |
| `key` | `string` | `null` | Колонка конфликта. Без неё — замена целиком |
| `mode` | `"upsert" \| "replace"` | `"upsert"` | `replace` = таблица берётся целиком |

**Возвращает** `{ "status": "ok", "written": 12, "replaced": false }`.

**Ошибки:** `not_found` (неизвестный ресурс), `invalid_params`, `timeout`,
`queue_full`, `internal`.

**Сегодня.** Прямого аналога в коде нет: `CacheIngestion.upsert_records` и
`replace_records` умирают вместе с DuckDB. Реестр ресурсов
(`TableRegistry`) существует и переносится, поэтому «известное имя ресурса»
проверяемо, а не декларативно.

**Новое.** Вся операция. Это **единственная** точка записи, которую
получает модель, и потому самая узкая: никаких `UPDATE` по произвольному
условию, никакого `DELETE`, никакого DDL. Всё остальное — `log_event`.

## 4. Capability `vectors`

FAISS в памяти, без персиста. Векторы читаются из PostgreSQL при первом
обращении к индексу и дальше переиспользуются.

### 4.1 `vector_search`

**Что делает.** Эмбедит запрос, достаёт или собирает индекс, ищет
ближайшие чанки и сворачивает их в документы.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `query` | `string` | — | Текст запроса. Эмбедится на сервере |
| `index` | `string` | `"audits_index"` | Имя индекса из конфигурации |
| `top_k` | `integer` | `5` | Сколько документов вернуть, `1..100` |
| `threshold` | `number` | `null` | Отсечка по score. `null` = не применять |

**Возвращает**
```json
{ "status": "ok", "index": "audits_index", "metric": "cosine",
  "results": [ { "content": "…", "score": 0.83,
                 "source": "audits_index", "table": "audits",
                 "pk_value": 41, "chunk": "2/4", "matched_chunks": 2,
                 "row": { "…": "исходная строка" } } ] }
```

**Ошибки:** `not_found` (неизвестный индекс), `upstream_unavailable`
(сервис эмбеддингов недоступен), `index_build_failed`, `timeout`,
`internal`.

**Побочные эффекты:** ленивая сборка индекса при первом вызове — блокирующая
для этого вызова. Индекс кэшируется в памяти процесса.

**Сегодня.** `CacheProvider.search_vector(query, index_name="default_index",
index_path=None, top_k=5, threshold=None) -> list[SearchResult]`.
`SearchResult` — ровно те поля, что выше. `build_faiss_index` возвращает
`(index, metadata)` или `(None, None)`. Индекс — **`faiss.IndexFlatIP`**.
Сборка: `np.zeros((n, dim), float32)`, при `metric == "cosine"` —
`faiss.normalize_L2`, затем `index.add`. Метаданные приклеивает вызывающий.
`group_vector_hits` сворачивает чанки в документы по ключу
`(source, table, pk_value)`, оставляя лучший чанк представителем, и удаляет
`chunk_index` из ответа.

**Опасность, влияющая на контракт.** Две вещи ломают смысл полей ответа,
если их не починить. См. §7.5 и §7.6.

### 4.2 `list_indexes`

**Что делает.** Перечисляет индексы, объявленные в конфигурации, вместе с
числом векторов в хранилище. **Не поднимает индекс** — отвечает сразу.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled_only` | `boolean` | `true` | Только включённые в конфигурации |

**Возвращает**
```json
{ "status": "ok",
  "indexes": [ { "name": "audits_index", "table": "oarb.audits",
                 "enabled": true, "metric": "cosine",
                 "dimension": 1024, "vector_count": 184320,
                 "state": "ready" } ] }
```

**Ошибки:** `queue_full`, `internal`.

**Сегодня.** `read_vector_index_config()` даёт по каждому индексу
`table`, `pk`, `source_table`, `content_columns`, `embedding_columns`,
`track_column`, `chunk_size`, `chunk_overlap`, `metric`, `enabled`.
`list_runtime_vector_indexes(store_table)` делает
`SELECT source, COUNT(*) … GROUP BY source ORDER BY source`.

**Новое.** Склейка конфигурации и фактического счётчика. Сейчас эти две
функции живут отдельно, а `list_runtime_vector_indexes` возвращает
четыре жёстко зашитых `None` вместо реальных значений — см. §7.7.

### 4.3 `index_stats`

**Что делает.** Состояние конкретного индекса: прогрет ли, сколько векторов,
какая размерность, когда собран. Для диагностики, не для выбора.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `index` | `string` | — | Имя индекса |

**Возвращает**
```json
{ "status": "ok", "index": "audits_index", "state": "cold",
  "vectors_in_memory": 0, "vector_count_in_store": 184320,
  "dimension": 1024, "metric": "cosine",
  "note": "первый vector_search соберёт индекс в памяти" }
```

**Ошибки:** `not_found`, `internal`.

**Новое.** В коде нет ни состояния, ни наблюдаемости. Сегодня загрузка на
старте пишет в stderr, недоступный для агента, и ошибки прогрева глушатся
полностью. Наблюдаемость — часть контракта, а не украшение.

## 5. Capability `llm`

### 5.1 `complete`

**Что делает.** Один вызов OpenAI-совместимого чата и возврат текста ответа.
Обёртка над `llm_client.call_llm` для доменов, которым нужен LLM внутри
платформы, и для агента, которому нужен вызов без диалога.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `messages` | `array<object>` | — | `[{role, content}, …]`. Роли не валидируются |
| `model` | `string` | `null` | `null` = модель из конфигурации |
| `max_tokens` | `integer` | `8192` | Фолбэк конфигурации, если не передан |
| `temperature` | `number` | `0.1` | Аналогично |
| `max_attempts` | `integer` | `3` | **Всего попыток**, не «повторов» |
| `timeout_ms` | `integer` | `60000` | Таймаут HTTP-запроса |

**Возвращает**
```json
{ "status": "ok", "content": "…", "model": "…",
  "attempts": 1, "elapsed_ms": 1840 }
```

**Ошибки:** `upstream_unavailable` (провайдер недоступен или 429),
`invalid_params`, `timeout`, `internal`.

**Сегодня.** `call_llm(messages, *, cfg=None, context=None, model=None,
max_tokens=None, temperature=None, max_retries=3, timeout=60.0) -> str`.
Запрос: `POST {api_base}/chat/completions`, ровно четыре ключа — `model`,
`messages`, `max_tokens`, `temperature`. `Authorization` добавляется только
при непустом ключе. `context` приклеивается **в начало** `messages`. Ответ
извлекается как `choices[0].message.content` и `.strip()`; пустой ответ
считается ошибкой. Повторы ловят `HTTPStatusError`, `TimeoutException`,
`ConnectError`, база 1.0 с, потолок 16 с; 429 повторяется, любой другой
статус пробрасывается сразу.

**Новое.** Обёртка и возврат метаданных попытки. Называется `max_attempts`,
а не `max_retries`, намеренно: в коде это именно **число попыток подряд**, и
дефолт `3` означает три HTTP-запроса, а не один плюс три.

**Опасность.** `call_llm_json` в коде проглатывает любую ошибку и
возвращает `None`. Такое поведение в контракте недопустимо: вызывающий
обязан различать «модель ответила не-разобранным JSON» и «провайдера нет».
Если понадобится JSON-режим — он возвращает `status: "unparseable"` с
исходным текстом, а не `null`.

## 6. Доменные capability

`audit` и `legal` добавляются в фазах 9–10. Контракт пишется по тому же
шаблону, но наполнение выводится из существующей CLI-поверхности домена,
а не придумывается.

Требования к каждой доменной операции:

1. Один логический вопрос — один вызов. Если операция требует «сначала
   найти, потом посчитать», это **одна** операция: в одном процессе это
   работает, через две операции модель будет склеивать результат сама.
2. Параметры — из предметной области, а не из SQL. `audit_id`,
   `question`, `document_id` — да; `schema`, `where`, `order_by` — нет.
3. Изоляция, если она есть, выводится сервером.
4. Ошибки только из §2.
5. Операция не возвращает сырой сыр: ни `rows`, ни `payload` целиком.

## 7. Найденные при подготовке опасности

Каждый пункт проверен на реальном коде. Три из них требуют решения **до**
того, как соответствующая операция будет отдана модели.

### 7.1 `statement_timeout` не существует

Поиск по всему репозиторию: ноль совпадений. `psycopg2.connect(dsn,
gssencmode="disable")` не передаёт `options=`. Бегущий запрос держит воркер
пула, пока его не убьёт сервер или клиент.

Для `query_sql` это значит, что «ограничение стоимости запроса задаёт сервер»
на сегодня — обещание, а не механизм. Варианты:

* **на соединении**, в момент коннекта: добавить
  `options=f"-c statement_timeout={ms}"` в `_Worker._connect_with_backoff`.
  Действует на все задания воркера, что соответствует модели переиспользования
  соединений;
* **на запрос**, внутри замыкания задания. Оговорка: соединения работают
  с `autocommit=True`, где `SET LOCAL statement_timeout` — **no-op**, а
  обычный `SET` утечёт в следующее задание на том же соединении. Нужен явный
  сброс.

Рекомендация: вариант на соединении плюс отдельный, меньший лимит для
`query_sql`, если понадобится различать.

### 7.2 SQL-guard без `sqlglot` перестаёт быть защитой

Проверено подменой импорта на реальном пути. Без `sqlglot` модуль
деградирует до регулярных выражений, и регулярный путь проверяет **только**
три вещи: первый блоклируемый оператор, `INTO`, несколько операторов подряд.

| Запрос | С `sqlglot` | Без `sqlglot` |
|---|---|---|
| `DROP TABLE t` | отказ | отказ |
| `SELECT 1 INTO x` | отказ | отказ |
| `SELECT 1; DROP TABLE t` | отказ | отказ |
| `SELECT pg_sleep(10)` | отказ | **пропускает** |
| `SELECT * FROM information_schema.tables` | отказ | **пропускает** |
| `SELECT * FROM pg_catalog.pg_tables` | отказ | **пропускает** |
| `-- комментарий` + `UPDATE t SET x=1` | отказ | **пропускает** |
| `-- комментарий` + `DELETE FROM t` | отказ | **пропускает** |

Причина в двух местах: построчные комментарии `--` не вырезаются перед
проверкой первого слова (вырезаются только блочные `/* */`), и deny-list
функций и системных схем живёт только в AST-ветке.

**Требование к контракту `query_sql`:** сервер SHALL отказывать стартовать, если
`sqlglot` недоступен. Тихая деградация к регуляркам недопустима, пока
регулярный путь не приведён к тому же уровню. Это отличается от текущей
политики модуля, где деградация разрешена сознательно.

Дополнительно, независимо от `sqlglot`: в `sql_safety` **есть только
deny-list** функций — списка разрешённых нет. Любая не перечисленная
функция, включая пользовательскую с побочным эффектом, проходит. Для
поверхности агента это осознанный размен: полный allow-list здесь стоит
дороже, чем даёт.

### 7.3 `user_id` в журнале — невидимая граница изоляции

`history_search(scope="all")` фильтрует строго по `user_id`. Поле
заполняется либо производителем явно, либо разрешается по совпадению
`request_id`. Строки с `user_id IS NULL` для `scope="all"` не видны, и
`scope="all"` вернёт пустой результат **без ошибки**.

Пока журнал остаётся в той же таблице, что и runtime, это правильное
поведение. Как только журнал станет внешним приёмником, граница требует
явной гарантии заполнения. Сейчас её нет.

### 7.4 Таймаут в `schema_check` заявлен, но не применяется

`check_tables` делает `del timeout_sec` с комментарием «enforced at pool
level». С учётом §7.1 это означает, что ограничения на самом деле нет.
Параметр `timeout_ms` либо реализуется, либо убирается из контракта.

### 7.5 `threshold` отключает `top_k`

`group_vector_hits` усекает до `top_k` только когда `threshold` не задан и
не положителен. При `threshold > 0` возвращаются **все** прошедшие отсечку
хиты, `top_k` игнорируется.

В контракте это выглядит как «вернулось 812 результатов, хотя просили 10».
Нужно либо починить, либо зафиксировать в описании операции как намеренное
поведение. Сейчас оно не зафиксировано нигде.

### 7.6 `metric` объявлен, но не применяется

Все три индекса объявлены с `"metric": "cosine"`. Значение читается
конфигурацией, но в рантайм не попадает: индексы собираются без
нормализации, и вектор запроса тоже не нормализуется. Возвращаемый `score` —
сырое скалярное произведение, а не косинусная близость.

Это молчаливая порча данных в ответе: модель сравнивает значения, которые
не означают того, что написано в описании. Исправление — протянуть `metric`
из `read_vector_index_config()[index]["metric"]` в сборку и в вектор запроса.
До исправления поле `metric` в ответе `vector_search` вводить нельзя.

### 7.7 Целостность индекса объявлена, но не проверяется

`IndexIntegrityError` не поднимается нигде в репозитории — единственное
упоминание это `except` в CLI. Поля `signature_status` и `signature_reason`
в `SearchResult` не заполняются никогда. `list_runtime_vector_indexes`
возвращает `dimension`, `updated_at`, `metric`, `signature` как жёсткие `None`.

Механизм подписи индекса существует и считает хеш по десяти полям конфигурации,
но его результат никто не сверяет. Контракт обязан либо реализовать сверку,
либо не обещать её полями ответа. Обещать несуществующую проверку хуже, чем
не иметь её.

### 7.8 Дрейф документации

`call_llm_async` не существует. Клиент полностью синхронный, `async def` в
модуле нет. Имя встречается в `AGENTS.md`, `CHANGELOG.md`,
`docs/ARCHITECTURE.md` и `project.json` — то есть агент, читающий
инструкции, может искать функцию, которой нет. Исправлено в рамках этого
изменения.
