# Контракты вызовов MCP

**Сервер:** `enterprise-mcp` — один процесс, capability-каталоги внутри.
**Ветка:** `refactor/mcp-platform` · **Коммит:** `776593e`
**Связанные документы:** `TARGET-ARCHITECTURE.md` (что и почему), `design.md`
(решения), `../openspec/changes/enterprise-mcp-platform/specs/` (WHEN/THEN).

---

## 0. Как читать этот документ

Каждый контракт разделён на три части, и их важно не путать:

| Пометка | Значение |
|---|---|
| **Сегодня** | Поведение проверено в текущем коде. Это факт, на который опирается перенос |
| **Новое** | Работы, которых в коде нет. Контракт их вводит |
| **Опасность** | Поведение, которое тихо ломает контракт, если его не учесть |

Каждая операция описана: что делает, параметры, что возвращает, какие ошибки
возможны, какие побочные эффекты и что в ней не так.

**Ничего из этого ещё не реализовано.** Документ — контракт, под который
пишется код в фазах 1–5 плана. Расхождения между ним и кодом, найденные при
подготовке, вынесены в §8 и уже исправлены в проектной документации.

## 1. Общие соглашения

**Имена.** Плоские и уникальные в пределах сервера. Capability в имя не
входит: MCP-клиент Nanobot и так приклеивает префикс сервера, поэтому модель
видит `mcp_enterprise_run_script`, а `mcp_enterprise_audit_run_script` только
удлиняет имя без добавления смысла. Принадлежность к capability живёт в
поле `category`.

**Синхронность.** Все операции — синхронные. Запрос к данным ждёт БД, `complete`
ждёт провайдера, `vector_search` может ждать прогрева индекса. Асинхронность
появится только вместе с потоковой выдачей результатов, и это отдельное
решение, а не режим по умолчанию.

**Точка входа.** Одна на сервер, в файл `servers/enterprise/server.py`. Она
поднимает реестр и отдаёт его MCP-клиенту, не зная состава заранее.

```text
capabilities/<name>/tools/*.py
  → discovery → import → create_tool(container) → validate → register → MCP
```

**Изоляция — не аргумент модели.** Идентичность обязательна в контракте каждой
операции и всегда заполняется агентом, но **не** приходит от модели.

> **Новое (change `enterprise-mcp-platform`, дельта `runtime/call-contract`,
> фаза 8).** Идентичность переносится из параметров `handler` в
> **`params._meta` вызова** — штатный канал application metadata в MCP. Сегодня
> (ниже) она объявляется аргументами обработчика; целевой контракт такой:
>
> ```json
> {
>   "jsonrpc": "2.0", "id": 42, "method": "tools/call",
>   "params": {
>     "name": "history_search",
>     "arguments": { "query": "...", "limit": 20 },
>     "_meta": {
>       "workspaces/request_id": "01J...",
>       "workspaces/session_id": "session-...",
>       "workspaces/user_id": "user-..."
>     }
>   }
> }
> ```
>
> Обработчик идентичность **не** объявляет и получает доменные аргументы плюс
> `ToolExecutionContext`. `_meta` обязателен для всех операций, включая те, кому
> пользовательская изоляция не нужна. Собирает его агент в одной точке —
> `EnterpriseMcpClient.call()`, который передаёт `meta=` в `session.call_tool`.
> Нарушение — `identity_missing` до входа в домен.
>
> **Почему `_meta`, а не свой конверт `{request,session,user}_id` внутри
> `arguments`.** Свой конверт ломал бы форму вызова всех операций: доменные
> параметры перешли бы во вложенный объект, то есть изменилась бы каждая
> опубликованная `inputSchema`. С `_meta` этого не происходит — `arguments`
> остаётся доменным объектом, а служебные поля не появляются в схеме вовсе. Плюс
> валидация `arguments` по `inputSchema` не видит `_meta` и не может на нём
> сломаться. Наконец, это не изобретение формата: `_meta` для этого и
> предназначен.
>
> **Namespace обязателен.** MCP резервирует `io.modelcontextprotocol/*` под свой
> служебный обмен (в SDK — `types.py:540`, `request_context.py:174`; в спецификации
> 2026-07-28 — перенос `clientInfo` в `_meta`). Голые `session_id`/`user_id`/
> `request_id` без префикса — шаг к коллизии с чужим расширением.
>
> **Реализуемо проверено на закреплённой версии**, а не по документации: в
> `mcp==1.27.1` есть `ClientSession.call_tool(..., meta=...)`, сервер разбирает
> `params.meta` (`mcp/shared/session.py:367` → `mcp/server/lowlevel/server.py:756`)
> и отдаёт его обработчику как `server.request_context.meta`, а
> `RequestParams.Meta` объявлен с `extra="allow"`, то есть namespaced-ключи
> принимаются. Спецификацию 2026-07-28 и SDK v2 внедрять **не требуется** — на них
> контракт сохраняется, потому что `_meta` остаётся каналом application metadata.
>
> **Опасность.** Контракт работает только пока операции не выставлены модели
> напрямую: `MCPToolWrapper.execute()` вызывает
> `session.call_tool(self._original_name, arguments=kwargs)` **без** `meta=`, то
> есть прямой вызов модели придёт без метаданных и закончится `identity_missing`
> (`tools.mcpServers` в агенте пуст, страж это проверяет).
> **Отдельная опасность:** вызовы из подпроцессов скиллов
> (`libs/enterprise_client/llm.py`) сегодня не передают идентичность вовсе; под
> контракт они получают её из `ENTERPRISE_SESSION_ID`/`USER_ID`/`REQUEST_ID`.

**Сегодня (форма до фазы 8).** `session_id` и `user_id` — обязательные параметры
`handler`; в опубликованной схеме инструмента они необязательные, чтобы модель их
не заполняла; агент подставляет их из `RequestContext` с перезаписью присланного
моделью значения.

> **Дрейф кода (закрыт фазой 8).** Обязательное объявление идентичности
> **никогда не проверялось** загрузчиком: `loader.py` валидирует только импорт
> модуля, наличие `create_tool`, непустые `name`/`description` и вызываемость
> `handler`. Идентичность объявляли 3 операции (`history_search`, `log_events`,
> `upsert_question_run`), а весь `audit` — ни одной. Фаза 8 ввела `_meta` и
> проверку формы обработчика: **все** операции получают идентичность из `params._meta`
> и ни одна не объявляет её параметром. Объявление личностного параметра теперь
> отвергается проверкой формы — см. `IDENTITY_PARAMS` в
> `libs/enterprise_common/registry.py`.
>
> **Дыра, которую это закрывает.** Пока операция вызывается только через
> агентский tool (`history_search`), идентичность транспорта есть: tool живёт в
> процессе агента и читает `RequestContext`. Но операции, выставленные модели
> напрямую как `mcp_enterprise_*`, идут мимо tool'а, и у `stdio`-сервера,
> который обслуживает много сессий одним процессом, **транспортной идентичности
> нет**. Правило «изоляция выводится из транспорта» там, где транспорт слепой,
> превращалось в «изоляции нет».

Обоснование прежнее: `MCPToolWrapper.execute()` отправляет в `tools/call`
ровно аргументы модели (`arguments=kwargs`), поэтому объявить идентичность
обычным аргументом — значит отдать её модели.

Отсутствие идентичности — отказ с `identity_missing`, а не работа без
изоляции.

**Корреляция — сверх изоляции.** Третий идентификатор, `request_id`, — это PK
оборота в `public.agent_question_runs`, то есть существующее понятие, а не новое.
Отдельного `question_id` не заводим — у журнала уже есть ключ оборота, и второй
идентификатор с тем же смыслом размножил бы сущности, связанные сейчас одним
ключом.

> **Новое.** В конверте `request_id` **обязателен**: отсутствие любого из трёх
> полей — нарушение контракта, а не «просто не коррелирует». Для вызовов вне
> оборота его создаёт агент до отправки; сервер не генерирует его никогда —
> подстановка сделала бы корреляцию ненаблюдаемой. Признак того, что `request_id`
> ссылается на существующий оборот, передаётся в `metadata.correlated`.

Агент берёт его из `DbLoggingService.get_request_id(session_key)`. Отсутствие
не является ошибкой: вызов вне оборота, после `clear_request` или в локальном
REPL просто не коррелирует.

`request_id` — **только** корреляция. Он не участвует в авторизации и выборе
данных: операция с ним и без него обязана видеть одно и то же. Иначе
идентификатор, живущий один оборот, стал бы несущей конструкцией безопасности.
По этой же причине доменный `operation_id` в `legal` (производный от
содержимого, стабильный между оборотами) остаётся отдельным полем и из
`request_id` не выводится.

**Форма ответа.** JSON-объект. Успех и ошибка различаются полем `status` либо
типом ошибки, а не HTTP-кодом: транспорт не видит разницу, MCP возвращает
результат вызова.

**Кто владеет ресурсом.** У каждого дорогого или разделяемого ресурса — ровно
один владелец, и всё ходит через него. Capability получают **готовый сервис**
и описывают операции, а не управление ресурсами.

| Ресурс | Владелец |
|---|---|
| Пул и очередь PostgreSQL | `libs/enterprise_data` |
| Векторные индексы, их кэш, клиент эмбеддингов | `libs/vector_index` |
| LLM-клиент и его политика попыток | `libs/llm` |

Capability SHALL NOT создавать свой пул, свою очередь, свой FAISS или свой
HTTP-клиент. Это не стиль, а требование корректности: вторая копия индекса —
это вторая сотня тысяч векторов в памяти и второй десяток секунд сборки на
старте; второй пул — второе число соединений против той же базы.

Домен внутри процесса ходит в эти сервисы напрямую, а не через MCP: MCP —
протокол для модели, а не внутренняя шина.

### 1.1 Где проходит граница доверия

Это главное, что изменилось в контрактах. **Модель не пишет SQL.**

```text
                         ┌─────────────────────────────────────┐
вызов от модели ───────► │  ни одного пути, где SQL приходит    │
                         │  от вызывающей стороны               │
                         └─────────────────────────────────────┘
```

Три входа к данным, и все три ведут внутрь платформы:

| Вход | Кто пишет SQL | Чем ограничен |
|---|---|---|
| `run_script` | Реестр `agent_predefined_scripts` | Шаблон из реестра; вызывающий приносит только имя и типизированные значения |
| `generate_sql` | LLM внутри сервера | Список таблиц, проверка read-only, `EXPLAIN`, потолок строк |
| `history_search` | Код платформы | Жёстко заданный `SELECT`, изоляция из идентичности транспорта |

Следствия, которые видно сразу:

* **Граница изоляции перестаёт обходиться.** Раньше произвольный SQL позволял
  выбрать `agent_gateway_logs` в обход `history_search`. Теперь такого пути нет.
* **Список таблиц становится границей, а не подсказкой.** Сегодня он живёт
  только в тексте промпта — см. §8.4. Это надо доделать в коде.
* **AST-guard не исчезает, а меняет роль.** Он больше не охраняет вызов
  снаружи, а охраняет вывод LLM, который является недоверенным входом. Поэтому
  требование «сервер не поднимается без `sqlglot»» сохраняется.

## 2. Модель ошибок

Один набор кодов на весь сервер. Операция может возвращать только из своего
списка.

| Код | Когда | Что делает вызывающий |
|---|---|---|
| `invalid_params` | Значение не прошло проверку типа или диапазона | Исправить вызов. Повтор с теми же аргументами бессмыслен |
| `not_found` | Неизвестный скрипт, индекс или ресурс | Проверить имя. Частая ошибка модели при опечатке |
| `no_match` | Данных для ответа нет ни в одном разрешённом источнике | Это **не** ошибка. Честный ответ «не знаю», см. §4.3 |
| `not_answerable` | Не удалось построить запрос за отведённое число попыток | Переформулировать вопрос. Повтор с тем же текстом бесполезен |
| `registry_unavailable` | Реестр скриптов не прочитан | Не пользовательская ошибка. Ретраить позже |
| `identity_missing` | У вызывающего нет ни session, ни user | Ошибка конфигурации транспорта, не модели |
| `timeout` | Истёк серверный срок операции | Повтор допустим, но с меньшим объёмом |
| `upstream_unavailable` | Провайдер эмбеддингов или LLM недоступен | Повтор с задержкой. Данные не потеряны |
| `index_build_failed` | Ленивая сборка FAISS упала | Проверить целостность векторной таблицы |
| `queue_full` | Очередь задач переполнена | Повтор позже. Данные не потеряны, запрос не выполнен |
| `internal` | Всё остальное | Сообщение уже содержит детали |

**Правило отказа.** Ошибка всегда несёт `code` и `message`. `message`
пишется для человека, `code` — для машины и для модели.

Отказ приходит **конвертом** `{"error": {"code", "message", "retryable"}}`, а не
префиксом в тексте: код читается разбором, а не глазами, и `retryable` отвечает
на вопрос «повторять ли» без догадок по формулировке сообщения.

Отдельно: **доменный `code` сохраняется**. `not_found` и `no_match` различаются
осмысленно, и приведение их к одному коду стёрло бы разницу, на которой держится
решение «спросить иначе» против «сказать, что не нашлось».

## 2.1 Слой исполнения: что обвязывает вызов

Между разбором метаданных и возвратом ответа проходит конвейер
(`libs/enterprise_common/execution/`). Вызывающий видит его в двух местах: в
форме ответа и в журнале. Оба описаны здесь; остальные девять шагов — внутреннее
дело платформы (§ `runtime/tool-execution`).

### Форма ответа

Тело ответа — это то, что вернула операция, без изменений. Метаданные
исполнения лежат в зарезервированном поле `_execution`:

```json
{ "hits": [], "next_offset": null,
  "_execution": {
    "request_id": "…", "tool": "history_search", "capability": "data",
    "duration_ms": 12, "result_size": 2048,
    "quality": { "policy": "vector_result", "ok": true, "flags": [], "checks": [ … ] }
  } }
```

Правило одно для всех форм:

* тело — объект без своего `_execution` → `_execution` добавляется ключом в
  тот же объект;
* тело любой другой формы (список, строка) либо объект, у которого `_execution`
  уже занят доменом → ответ оборачивается в `{"result": <тело>, "_execution": …}`;
* добавлять нечего (результат в пределах порога, проверки выключены) → ответ
  **побайтово равен** доменному.

Последний пункт — причина, по которой поле зарезервировано, а не размазано по
верхнему уровню: операция вправе вернуть `_execution` в своих данных, и платформа
не должна ни красть ключ, ни ломать разбор ответа у вызывающего.

### Крупный результат

Результат больше `execution.max_inline_result_bytes` сохраняется **до**
возврата ответа, и вместо тела уходит ссылка:

```json
{ "result_saved": true, "large_result": true,
  "artifact_id": "…", "size": 8388608,
  "content_type": "application/json",
  "uri": "session://results/<request_id>/…", "preview": "…" }
```

Ответ со ссылкой на несуществующий файл хуже явного отказа: по ссылке вызывающий
пошёл бы читать и не нашёл бы ничего. Поэтому неудачная запись — `infrastructure_error`
(повторять имеет смысл), а не ссылка. При `persist_large_results: false` тело
возвращается целиком, а в `_execution` появляется `large_result: true`, и событие
`artifact.created` **не** отправляется — артефакта нет, и событие о нём было бы
ложью, расходящейся с каталогом сессии.

#### Как выбрать порог на живом трафике

Значение `execution.max_inline_result_bytes` равно **65536** — столько же, сколько
объявляет спека конвейера
`openspec/changes/enterprise-mcp-platform/specs/runtime/tool-execution/spec.md`.
Промежуточное значение 5000 стояло недолго и обоснования не имело: его поставили
вместе с появлением `read_result`, а эффект получился обратный задуманному.
При 5000 байт конверт со ссылкой настолько мал, что второй уровень — вынос
крупных результатов, который делает сам нанобот, — не срабатывал вовсе: ссылка
с превью укладывалась в его собственный порог. То есть новый порог не добавил
экономии, а просто отключил второй рубеж. Откат вернул согласие кода со
спецификацией; окончательная величина выбирается по статистике продакшна,
локальные логи (`logs/gateway.log`) для этого не годятся — в них 15 строк:

```sql
-- Распределение размеров результатов за последние сутки.
SELECT width_bucket(result_bytes, 1000, 500000, 20) AS bucket,
       count(*)                                      AS операций
  FROM agent_gateway_logs
 WHERE event_type = 'artifact.created'
   AND occurred_at > now() - interval '1 day'
 GROUP BY 1 ORDER BY 1;
```

Как читать: если в первых бакетах (до ~5 КБ) лежит заметная доля вызовов, порог
низкий и агент будет получать ссылку вместо тела там, где тело влезло бы в контекст
без потерь. Если бакета 4–8 КБ почти пуста, порог можно поднимать — ссылок станет
меньше, а бюджет контекста на оборот не пострадает. Менять нужно только
`mcp-platform/platform.json → execution.max_inline_result_bytes`; настройка одна
и на порог сохранения, и на страницу `read_result`.

#### Чтение сохранённого результата

Ссылка из ответа — не украшение: её разрешает операция `read_result`, и она же
закрывает контракт до конца.

```json
read_result(artifact_id="…")            // или uri из ответа
read_result(artifact_id="…", offset=2048, limit=4096)
```

```json
{ "artifact_id": "…", "uri": "session://results/<request_id>/…",
  "size": 8388608, "offset": 0, "returned": 2048, "total_chars": 412003,
  "next_offset": 2048, "truncated": true, "content": "…" }
```

Почему постранично: файл лежит на диске именно потому, что в контекст не
влезает, и вернуть его целиком значило бы сделать то же самое, только с лишней
файловой операцией. `next_offset` — смещение следующей страницы, на последней он
`null`. Размер страницы по умолчанию — `execution.preview_bytes`, тот же порог,
что и превью в ответе конвейера: одна настройка на оба места.

Сессия берётся из `params._meta`, поэтому выбрать чужую нечем, а чужая всё
равно не читается. Файл, который не UTF-8, не «чинится» подменой символов:
`is_text: false`, `content: null` и причина — читать его нужно по расширению
имени, а не как текст.

Операция платформенная, а не из capability: файлами сессии владеет платформа,
и страж `tests/test_tool_execution_boundaries.py` не пускает к ним capability.
Хранилище достаётся composition root'ом из слоя исполнения и в контейнер не
кладётся — иначе в контейнере появился бы второй путь к файлам сессии.
Сервер для скиллов (`--capabilities llm`) операцию не поднимает: у него нет ни
оборота, ни сессии.

### Проверка качества

`_execution.quality` появляется, только когда проверки включены и политика
операции не `none`. Отсутствие поля и пустой отчёт — разные утверждения:
«проверок не было» и «проверки прошли».

Провал **технической** проверки (результат не сериализуется, форма ответа не та,
длина эмбеддинга не совпадает с `dimension`) — отказ `internal`. Провал
**семантической** (пустой результат, источник усек ответ) — признак в
`_execution.quality.flags` и **не** отказ: ноль строк в `run_script` — законный
ответ, и подмена его на ошибку научила бы модель переписывать вопрос вместо того,
чтобы сказать «ничего не нашлось».

### Предел времени

`execution.execution_timeout_sec` — «перестать ждать», а не «убить поток»: поток
Python прервать нельзя. Операция, не уложившаяся в срок, продолжает работать
в фоне, а её результат отбрасывается целиком — он не попадает ни в ответ, ни в
артефакт, ни в `tool.completed`. Событие — `tool.timeout`, код отказа —
`timeout`.

### Журнал вызова

Каждый вызов пишет `tool.started` и один из `tool.completed` / `tool.failed` /
`tool.timeout`; крупный результат добавляет `artifact.created`, включённые
проверки — `quality.check`. В `payload` уходят **размеры и хеши** аргументов и
результата (sha256 канонического JSON, усечённый до 16 hex-символов), а не сами
аргументы и не тело результата: журнал читают через `history_search`, и полный
ответ каждой операции в нём размножал бы объём и затащил чувствительные данные.
Структурированно в журнал попадают только поля из белого списка
`execution.log_argument_fields`.

**Отдельно про `no_match`.** Это не ошибка, а выделенный исход: сервер
проверил, что данных для ответа нет ни в одном разрешённом источнике, и
вернул пустой результат с явной пометкой. Смешивать его с ошибкой нельзя —
иначе вызывающий не отличит «данных нет» от «сервис упал» и начнёт
переформулировать вопрос вместо того, чтобы сказать пользователю правду.

## 3. Capability `data` — инфраструктура, без SQL для модели

Пул, очередь и **12 операций** в четырёх группах: журнал (`log_events`,
`log_event`, `purge_logs`, `upsert_question_run`), чтение (`history_search`,
`schema_check`), очередь задач (`claim_task`, `update_task_status`,
`unstick_tasks`) и работа с сообщениями (`append_assistant_message`,
`delete_assistant_message`, `patch_message_metadata`). **Модель не получает отсюда
ничего, кроме событий и результата проверки схемы.** Запрос к данным живёт в
capability `audit` (§4) — там, где лежит реестр скриптов.

Пул один на сервер: `libs/enterprise_data/db.py`, N воркеров, у каждого своё
соединение с `autocommit=True`, задания в общей очереди. Очередь и лиза внутри
библиотеки, наружу не выходят.

### 3.1 `log_events`

> **Правка 2026-10-02 (фаза 8, п. 8.16).** Раздел описывал `log_event` в
> единственном числе: одно событие, пять параметров, ответ `accepted`/`dropped`.
> Фактическая операция — **`log_events`**, батчевая: параметр один
> (`events: list[dict]`), элемент описывается отдельно, а ответ — `accepted` и
> `dropped` **одновременно**, потому что в батче часть событий может приняться,
> а часть быть отброшена. Ниже — фактическая сигнатура.

**Что делает.** Принимает пачку событий и возвращает счётчики приёма. События
уходят в `agent_gateway_logs` батчем, в своём потоке, не позже чем через
`flush_interval`. Никогда не блокирует ход.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `events` | `array<object>` | — | Обязателен. Элемент — см. ниже |

**Элемент `events[]`.** Схема входа задана руками, а не `build_input_schema`:
та выводит из подписи `{"type": "array"}` без описания элемента, а контракт
здесь и есть в элементе.

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `event_type` | `string` | — | **Обязателен.** Тип события, до 64 символов |
| `id` | `string` | `null` | Ключ события (UUID). Не задан — сгенерирует сервер |
| `name` | `string` | — | Имя producer'а |
| `level` | `"DEBUG"\|"INFO"\|"WARN"\|"ERROR"` | `INFO` | `WARNING` приходит как `WARN`. Неизвестное значение — **отказ**, а не тихая замена: опечатка, съеденная молча, выглядит в журнале как событие иной важности. Ниже порога событие отбрасывается |
| `summary` | `string` | — | Краткое описание одной строкой, до 200 символов, обрезается на сервере |
| `payload` | `object` | `{}` | JSONB |
| `metadata` | `object` | `{}` | Служебные признаки (source, component), JSONB |

**Идентичность ни одним из трёх способов не передаётся** (§ 1,
`runtime/call-contract`): `session_id`, `user_id` и `request_id` приходят в
`params._meta`, и конвейер достаёт их каждому событию **сам**. Принимать их из
тела батча означало бы разрешить вызовцу подписать журнал чужой сессией. В
опубликованной `inputSchema` этих полей нет вовсе, и присланные моделью
значения с такими именами вырезаются из аргументов до входа в домен.

**Возвращает** строку `{"status": "ok", "accepted": N, "dropped": M}` — оба
счётчика сразу, так как в батче принятие и отбрасывание не исключают друг
друга. Операция неблокирующая, и её ответ обязан быть таким же простым, как
«ушло в буфер».

**Ошибки:** `invalid_params`. **Fail-fast:** батч не разбирается частично —
отказ по первому негодному событию, предыдущие не пишутся. Потеря события
ошибкой **не** считается — это заложенное поведение.

**Опасность.** `log_events` — единственная операция, вызываемая не из оборота
с пользователем, а из батчевого flush'а локального буфера. Буфер живёт в
процессе агента и переживает запрос, поэтому к моменту flush'а `RequestContext`
уже не существует: идентичность события должна быть снята **при записи** в буфер,
а не при отправке. Иначе отказ по `identity_missing` начнёт молча ронять
события — а потеря события не сопровождается ошибкой и заметна только
post hoc.

**Побочные эффекты:** строка в журнале. Очередь ограничена по умолчанию
10 000 записей, переполнение — **безвозвратный дроп** с ростом счётчика.
Файлового fallback нет: нечего писать, если БД недоступна.

**Журнал не встаёт в очередь за дорогой работой.** Одна очередь означает, что
slow и fast конкурируют за одни и те же воркеры, а `generate_sql` умеет
занимать воркер надолго: до четырёх вызовов LLM и одно неограниченное во
времени исполнение. Если бы запись журнала ждала ту же очередь, всплеск таких
запросов глушил бы `log_events` — а потеря события безвозвратна и не
сопровождается ошибкой.

Поэтому сервис владельца пула имеет **два входа**: `submit(job)` — блокирующий,
для работы с данными; `accept(event)` — неблокирующий, буфер писателя журнала.
Пул, очередь и владелец при этом одни: разделение сделано внутри сервиса, а не
вторым пулом.

**Сегодня.** `DbLoggingService.log_event(event: LogEvent) -> bool` плюс
`try_log_event(svc, event, producer=…, event_type=…)`. Таблица
`public.agent_gateway_logs`, `DISTRIBUTED BY (request_id)`, **без первичного
ключа**, `level` ограничен `CHECK`. INSERT — батчем из 12 колонок;
`"timestamp"` не пишется, дефолт БД. `payload` и `metadata` пишутся как `{}`,
а не `NULL`.

Писатель платформы пишет **тот же набор из 12 колонок** — и это проверяется
(`tests/test_journal_writer_columns_contract.py` в репозитории агента сверяет
множества колонок обоих писателей, `tests/test_event_model.py` — со стороны
платформы). Канонический список задан один раз:
`JOURNAL_FIELDS` в `libs/enterprise_common/eventing/models.py`.

До фазы 8 `INSERT` платформы объявлял девять колонок и терял `request_id`,
`metadata`, `channel` и `actor`: события писались, оборот не коррелировался.

### 3.2 `schema_check`

**Что делает.** Проверяет наличие **собственных** таблиц платформы одним
`SELECT` к `information_schema.tables`. Отсутствие — **не** ошибка, а поле в
ответе: вызывающий сам решает, фатально это или нет.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `expected` | `array<string>` | `null` | `null` = таблицы, объявленные платформой в `platform.json` |

**Возвращает**
```json
{ "expected": 8, "found": 7, "missing": ["public.agent_gateway_logs"],
  "ok": false, "tables": ["oarb.audits", "…"] }
```

`expected` и `found` — **счётчики**, а не имена; имена лежат в `tables` и
`missing` (список строк `schema.table`, отсортированный).

**Ошибки:** `invalid_params` (не задан ни одной ожидаемой таблицы), ошибки пула —
`infrastructure_error`, `timeout`.

**Сегодня.** `DataService.schema_check(expected=None, *, audience=…)` поверх
`submit()`. Список по умолчанию приходит из composition root'а:
`_declared_tables(settings)` в `servers/enterprise/server.py` — это то, что
платформа объявила **себе**: таблица журнала, таблица прогонов вопросов, реестр
скриптов, таблицы `audit.tables` и таблица очереди задач. На штатных значениях
`platform.json` — восемь имён (`oarb.audits`, `oarb.violations`,
`oarb.audit_reports`, `oarb.report_items`, `public.agent_predefined_scripts`,
`public.agent_gateway_logs`, `public.agent_question_runs`,
`public.agent_conversation_messages`).

**Чужие таблицы сюда не входят.** Раньше список приезжал из окружения агента, и
проверка отвечала на вопрос «на месте ли то, чем пользуется агент». Теперь
`schema_check` спрашивает «на месте ли то, чем пользуется платформа», а
runtime-таблицы агента агент проверяет сам, на своём старте
(`lib/services/schema_validation.py`, отдельная операция). Сверка имён между
сторонами — `gateway._verify_platform_table_alignment`.

Запрос — `SELECT table_schema, table_name FROM information_schema.tables WHERE
(table_schema || '.' || table_name) = ANY(%s)`; отбор по паре «схема + имя», без
фильтра `table_type` и без захардкоженной схемы `public`.

**Опасность.** Проверка идёт через тот же пул, что и работа с данными, то есть
занимает воркер на время `statement_timeout` (§8.1). Отдельного лимита на неё
нет, и при недоступной БД она падает вместе с остальными операциями
`data`.

### 3.3 `history_search`

**Что делает.** Ищет события в долговечном журнале `agent_gateway_logs`. Нужен
агенту после сжатия контекста: то, чего уже нет в живой переписке, лежит
здесь. Место жительства — `data`, а не `audit`: журнал обслуживает runtime
целиком, а не домен.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `session_id` | `string` | **обязателен** | Подставляет агент. `session_scope="current"` фильтрует по нему |
| `user_id` | `string` | **обязателен** | Подставляет агент. `session_scope="all"` фильтрует по нему. В ответе не возвращается |
| `query` | `string` | `null` | Подстрока `ILIKE` по полям события |
| `event_type` | `string` | `null` | Тип события |
| `tool_name` | `string` | `null` | Имя инструмента. Осмысленно для `tool_call`/`tool_result` |
| `since` | `string` | `null` | Нижняя граница времени, ISO-8601 |
| `until` | `string` | `null` | Верхняя граница времени, ISO-8601 |
| `session_scope` | `"current"\|"all"` | `"current"` | `all` — все сессии текущего пользователя |
| `limit` | `integer` | по конфигурации | Размер страницы |
| `offset` | `integer` | `0` | Смещение. Продолжение — через `next_offset` из ответа |

**Возвращает**
```json
{ "status": "ok", "count": 12, "session_scope": "current",
  "has_more": true, "next_offset": 12, "results_truncated": false,
  "events": [ { "event_id": "…", "timestamp": "…", "event_type": "tool_call",
                "name": "…", "level": "INFO", "summary": "…",
                "payload": "…", "payload_truncated": false } ] }
```

**Ошибки:** `identity_missing` (`session_scope="all"` вне запроса, когда
идентичность пользователя недоступна), `invalid_params`, `timeout`,
`queue_full`, `internal`.

**Сегодня.** `HistorySearchTool.execute(query, event_type, tool_name, since,
until, session_scope, limit, offset)` в `workspace/tools/history_search_tool.py`.
SQL написан руками, никакой генерации. Порядок детерминированный:
`timestamp DESC, id DESC`, где UUID — tie-breaker против потери и дублей строк
одного батча flush'а на границе страниц. Выборка берёт `LIMIT N+1`: лишняя
строка служит маркером следующей страницы и в ответ не попадает.
Усечение двухступенчатое: `per_event_cap` символов на событие через
`truncate_middle`, затем общий `max_result_chars` — с отбрасыванием самых старых
событий. Если не влезает даже одно, `cap` делится пополам, и в последнем
крайнем случае payload обнуляется, а само событие остаётся.

**Новое.** Перенос операции на сервер без изменения формы ответа. Флаг
`next_offset` обязателен именно потому, что при `results_truncated` часть
выбранных событий не показана, поэтому смещение считается через `count`, а не
`offset + limit` — иначе страница перескочит через потерянное.

**Опасность.** `user_id` в ответе не возвращается никогда — это граница, а не
недосмотр. Строки с `user_id IS NULL` не видны при `session_scope="all"`, и
поиск вернёт пустой результат **без ошибки**. См. §8.10.

### 3.4 Операции runtime — журнал, очередь задач, сообщения

**Девять операций capability `data` добавлены в документ при разведке фазы 8** —
до этого дрейф был ровно тот, что §8.12 описывает как «документ отстаёт от
кода».

| Операция | Permission | Что делает |
|---|---|---|
| `upsert_question_run` | `data:upsert_question_run` | Контекст оборота в `agent_question_runs`: `request_id`, статус, summary, `session_id`, `user_id` |
| `purge_logs` | `data:purge_logs` | Retention журнала по `retention_days` и чистка пустых outbound |
| `log_events` | `data:log_events` | Батч событий журнала; fail-fast по первому негодному событию, `accepted`/`dropped` в ответе |
| `claim_task` | `data:claim_task` | Атомарный захват одной задачи очереди; `error_retry_delay_sec=5.0`, `priority_contents=None` |
| `update_task_status` | `data:update_task_status` | Смена статуса задачи с записью текста, вложений и `metadata_patch`; `role`, `content`, `media`, `error`, `max_stuck_retries` — необязательные |
| `unstick_tasks` | `data:unstick_tasks` | Возврат зависших в `processing` задач; `processing_timeout_sec` и `max_stuck_retries` обязательны |
| `append_assistant_message` | `data:append_assistant_message` | Вставка сообщения ассистента по `chat_id`/`reply_to`; возвращает id вставленной строки |
| `delete_assistant_message` | `data:delete_assistant_message` | Удаление сообщения по `task_id` и `role` (по умолчанию `assistant`) |
| `patch_message_metadata` | `data:patch_message_metadata` | Слияние `patch` в `metadata` сообщения; возвращает `{updated, metadata}` |
| `merge_tool_delivery` | `data:merge_tool_delivery` | Дописывает текст, вложения и `metadata_patch` в ещё не закрытый ответ; статус остаётся `processing` |
| `finalize_turn` | `data:finalize_turn` | Записывает финальный ответ и переводит задачу в `completed` одной транзакцией; при отмене возвращает `outcome=cancelled_drop` |
| `fail_task` | `data:fail_task` | Помечает оборот ошибочным, увеличив `metadata.retry_count`; `error` до лимита повторов, `failed` — после |
| `release_claimed_tasks` | `data:release_claimed_tasks` | Возврат захваченных задач в `pending` при остановке worker'а, с удалением assistant-заглушек |
| `get_message` | `data:get_message` | Чтение одной строки очереди: `id`, `role`, `status`, `reply_to`, `chat_id`; `found=false` — строки нет |
| `queue_stats` | `data:queue_stats` | Число задач `pending` и `error` среди user-строк — для вывода активности воркера |
| `append_history_notice` | `data:append_history_notice` | Служебная строка истории без `reply_to` и сразу `completed`; возвращает `message_id` |

Все объявлены как runtime (`AUDIENCE_RUNTIME`): журналирование не
должно попадать в `history_search`, который сам пишет в журнал, а очередь
задач обслуживает канал, а не модель. Модель получает в capability `data`
только `history_search` и `schema_check` — обе помечены `AUDIENCE_MODEL`.

Четыре последних закрывают то, что в агенте было транзакциями. Пока они
были вызовами «по одной операции на строку», обрыв между ними оставлял
состояния, которых не бывает: счётчик попыток без смены статуса, `completed`
на задаче без ответа, заглушка, пережившая откат. Ни один из этих дефектов не
падает — он выглядит как «обработано».

**Заметка в историю — отдельная операция, а не «ещё один `assistant`.**
`append_history_notice` пишет строку сразу `completed` и без `reply_to`, потому
что она не ответ ни на одну задачу. Переиспользовать `append_assistant_message`
было бы нельзя: он создаёт плейсхолдер, который обязан закрыть `finalize_turn`,
и незакрытый плейсхолдер навсегда остаётся в `processing`. Имя таблицы приходит
из `platform.json` — раньше сервис сжатия писал эту строку напрямую по DSN и
имени таблицы из своего конфига, и при тестовом профиле уходил в БОЕВУЮ
`agent_conversation_messages`: оверлей профиля объявлен в двух файлах, и агент
видел только один. `user_id` операция не принимает — авторство строки задаёт
владелец таблицы, иначе вызывающий мог бы подписать заметку чужим именем.

**Очередь задач — в составе capability, а не на стороне канала.** `claim_task`
и `update_task_status` не удалены: обе лежат в
`servers/enterprise/capabilities/data/tools/`, загружаются реестром и
публикуются в MCP. Имя таблицы задач вызывающей стороней не передаётся — оно
приходит из `platform.json → data.task_table` и уходит в сервис параметром
`task_table`; пустое значение означает «операции очереди не настроены», а не
«искать таблицу по умолчанию».

**На диске остались надгробия.** Рядом лежат `_claim_task.py` и
`_update_task_status.py` — файлы с подчёркиванием в начале имени. Реестр их
пропускает (`libs/enterprise_common/loader.py`: `path.name.startswith("_")`),
то есть они инертны и ни одной операции не публикуют. Читать их как
действующие нельзя.

**Опасность (общая для всех девяти).** Permission **объявлен, но не проверяется**:
`ToolDefinition.permissions` читается только тестами (`assert tool.permissions`),
в рантайме его никто не потребляет, а `build_server(registry, ...)` публикует все
зарегистрированные операции. То есть модель сегодня может вызвать `purge_logs`.
См. §8.13.

**Опасность.** Ни одна из девяти не объявляет идентичность — см. §1: под контрактом
(фаза 8) все они получают `request_id`/`session_id`/`user_id` так же, как
`schema_check`.

## 4. Capability `audit` — весь запрос к данным

Здесь модель ходит в базу. Не через SQL, а через три операции: посмотреть
каталог, выполнить известный скрипт, задать вопрос на естественном языке.

Источник истины — `public.agent_predefined_scripts`, объявленная в
`skills.audit_analyzer.tables` с меткой `scripts_registry`. Метка важна:
таблицы с меткой **не попадают в описание схемы, которое уходит в LLM**, то
есть реестр не протекает в генератор.

### 4.1 `list_scripts`

**Что делает.** Возвращает каталог зарегистрированных скриптов с полными
описаниями параметров. Это единственный источник, из которого модель узнаёт,
что вообще можно спросить, — поэтому описания здесь важнее, чем где-либо ещё
ещё.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `query` | `string` | `null` | Подстрока по имени и описанию. `null` = весь каталог |
| `include_sql` | `boolean` | `false` | Текст шаблона. Оператору — да, модели — не нужно |

**Возвращает**
```json
{ "status": "ok", "count": 5,
  "scripts": [ {
    "name": "audit_status_summary",
    "description": "Сводка по статусам проверок",
    "long_description": "Когда использовать, edge cases",
    "returns": "status, cnt",
    "max_rows_default": 100,
    "parameters": { "status": { "type": "enum", "required": false,
                                "description": "…", "validation": {"values": ["done","planned"]} } } } ] }
```

**Ошибки:** `registry_unavailable`, `queue_full`, `internal`.

**Сегодня.** Две реализации одной идеи, и они расходятся:

* `predefined.mode.list_scripts(db, table) -> list[dict[str, str]]` отдаёт
  `{name, description, parameters}`, где `parameters` — это `", ".join(...)`,
  то есть **склеенная строка имён**. Ни типов, ни обязательности, ни значений по
  умолчанию. Для вызова `run_script` этого недостаточно: модель не знает, что
  именно передавать.
* `cli.py::_list_scripts()` — то, что реально вызывается по `--list-scripts`, —
  богаче: `{name, description, long_description, parameters: {pname: {type,
  required, description}}, max_rows_default}` в конверте `{predefined_table,
  count, scripts}`. Но docstring у него обещает `sql_template`, которого в
  ответе нет.

Контракт берёт форму CLI-варианта и достраивает его: `parameters` объектом с
полями `type`, `required`, `default`, `description`, `validation`; плюс
`long_description` и `returns` — обе колонки существуют именно «для
LLM-промпта», по комментарию в DDL, и сейчас используются только для few-shot.
`include_sql` по умолчанию выключен: шаблон — внутренность, а не часть
поверхности.

**Опасность.** `load_all` проглатывает исключение и возвращает `{}`. Сломанный
реестр неотличим от пустого, и модель решит, что данных нет. См. §8.6.

### 4.2 `run_script`

**Что делает.** Выполняет зарегистрированный скрипт с переданными
параметрами. SQL берётся из реестра, из вызова приходит только имя и
типизированные значения.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `script` | `string` | — | Имя скрипта из `list_scripts` |
| `params` | `object` | `null` | Значения по именам параметров скрипта; не задан — берутся умолчания |

Отдельного параметра `max_rows` у операции нет: потолок строк задаёт сам
зарегистрированный скрипт — `max_rows_default` из реестра либо параметр типа
`limit`, который сборщик превращает в `max_rows` и подставляет как
`LIMIT :max_rows`, если в шаблоне его нет.

**Возвращает**
```json
{ "status": "ok", "script": "audit_status_summary",
  "applied_params": { "status": "done" },
  "row_count": 3, "columns": ["status", "cnt"],
  "rows": [ {"status": "done", "cnt": 42} ] }
```

**Ошибки:** `not_found` (нет такого скрипта), `invalid_params` (нарушен тип или
обязательность), `timeout`, `queue_full`, `internal`.

**Побочные эффекты:** нет. Соединение освобождается после возврата.

**Сегодня.** `predefined.mode.run(script_name, db, params=None, *,
predefined_table=None) -> dict`. Пайплайн:

1. `db_loader.load_script(...)` — поиск по имени одним `SELECT ... WHERE name = ?`
2. `ParameterValidator.validate(script, params)` — слияние со значениями по
   умолчанию, проверка обязательности и типов
3. `DynamicQueryBuilder.build(script, merged)` — сборка шаблона
4. `db.query_sql(sql, sql_params)` — выполнение

**Реестр читается не из PostgreSQL, а из локального снимка DuckDB.**
`db_loader` ходит в тот же `CacheProvider`, то есть в снимок, который
`CacheLoadService` загрузил на старте. Никакого Python-реестра нет — об этом
прямо написано в `db_loader` и `mode`, и поиск по `REGISTRY` по всему skill'у
не даёт совпадений. Снимок остаётся в проекте, поэтому переносить реестр на
PostgreSQL не требуется: capability `audit` получает его операцией capability
`data` и файл не открывает. Решение зафиксировано в
`specs/data/duckdb-cache/spec.md`.

Python-фолбэка нет, и это не то же самое, что «читаем живой PostgreSQL».
Отсутствие фолбэка означает «единственный источник — этот loader». Момент
актуальности снимка вызывающему виден: он несёт метку времени загрузки.

Сборщик умеет: подстановку значений по умолчанию; форматирование по типу
(`like` оборачивает в `%…%`, `limit` превращается в `max_rows`, `number` в
`int`, `boolean`, `date`, `enum`, `exact`); списки значений переписывают
`ILIKE :param` в `= ANY(?)`; рендеринг блоков `{% if param %}…{% endif %}`
с веткой `{% else %}` и чисткой артефактов `WHERE 1=1 AND` → `WHERE`;
авто-добавление `LIMIT :max_rows`, если в шаблоне его нет; конвертацию
`:param` → `?`.

**Параметризация настоящая.** Пользовательские значения не подставляются в
текст запроса: они лежат отдельным списком позиционных аргументов. Шаблон
переписывается, значения — нет. Значение, повторяющееся в шаблоне дважды,
передаётся дважды.

**Опасности.**

* **Плейсхолдеры `?` — это диалект снимка.** И сборщик, и загрузчик реестра
  используют `?`. У PostgreSQL и `psycopg2` — `%s`. Значит, смена исполнителя
  затронет оба места сразу, иначе скрипты молча перестанут работать.
* Схема по умолчанию в `_qualified_table` — `"main"`, то есть схема снимка,
  а не `public`. Значение связано с диалектом: правка одной строки без смены
  исполнителя ломает все шаблоны без указания схемы.
* Нынешний `run()` кладёт в ответ `data.sql` — интерполированный текст
  запроса. В контракте его нет: показывать модели SQL значит провоцировать
  цикл «дай мне поправить», то есть вернуть ту поверхность, которую убираем.
* **Форма ошибок разъезжается между слоями.** `predefined.run` возвращает
  словарь и **не добавляет `mode`** ни на одном пути ошибки. У
  `generated_sql_mode.run` `mode` есть, но `error_type` нет. CLI добавляет
  `error_type` только для двух случаев — `registry_unavailable` и
  `unknown_index`. Итог: у одного и того же отказа на трёх уровнях три разных
  тела ответа, и ни на одном нет машиночитаемого кода.
* Ошибки возвращаются словарём, а не исключением, а часть путей (`load_all`,
  `load_script`) глотает исключения. Молчаливый пустой реестр — хуже явной
  ошибки, см. §8.6.

Контракт снимает расхождение: единый конверт §2, код ошибки в **обязательном**
поле на каждом неуспешном пути, включая те, что сегодня отдаются словарём без
кода. Молчаливые пути (`load_all → {}`, `load_script → None`) обязаны
превратиться в `registry_unavailable`.

### 4.3 `generate_sql`

**Что делает.** Принимает вопрос на естественном языке, строит SQL внутри
сервера через LLM, проверяет его и выполняет. Это единственный путь, где SQL
пишет машина, — и поэтому единственный, где AST-guard остаётся обязательным.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `query` | `string` | — | Вопрос на естественном языке |

Параметра `max_rows` у операции нет, и потолок строк не выбирает вызывающая
сторона: он задаётся платформой — `platform.json → audit.row_ceiling` (500), при
отсутствии настройки берётся `DEFAULT_ROW_CEILING = 1000` из
`libs/audit/guard.py`. Оба значения применяются одинаково — см. §8.4.

**Возвращает**
```json
{ "status": "ok", "outcome": "answered",
  "row_count": 2, "columns": ["object", "cnt"],
  "rows": [ … ], "attempts": 1 }
```

Два особых исхода:

```json
{ "status": "ok", "outcome": "no_match", "row_count": 0, "columns": [], "rows": [] }
{ "status": "error", "code": "not_answerable", "attempts": 4 }
```

`outcome` обязателен и различает три вещи, которые иначе сливаются: данные
есть, данных нет, данных не найти не удалось. Пустой `rows` без `outcome`
модель прочитает как «ответ пустой» и попробует переформулировать.

**Ошибки:** `not_answerable`, `upstream_unavailable`, `timeout`, `queue_full`,
`internal`.

**Сегодня.** `generated_sql_mode.run(query, db, context=None) -> dict`.
Пайплайн, `MAX_ATTEMPTS = 4`:

1. Описание схемы по разрешённым таблицам
2. Список полностью квалифицированных имён таблиц — уходит в промпт как
   «whitelist». Собирается с удвоением схемы, см. §8.11
3. Few-shot: `_select_few_shot(query, registry, limit=2)` — два ближайших по
   пересечению слов скрипта из того же реестра. Сходство считается по словам
   длиной от трёх символов из `name + description`; недоступность реестра даёт
   пустой few-shot и ошибкой **не** считается
4. System prompt: только безопасный `SELECT`, без пояснений и разметки;
   при невозможности ответа вернуть **ровно** `<NO_MATCH>`; все имена
   квалифицированы. Схема уходит не в system, а в user-сообщение
5. Цикл попыток: вызов LLM → `sanitize_sql_response` (достаёт SQL из ответа,
   tolerating рассуждения и markdown-обёртки)
6. **`<NO_MATCH>` — короткое замыкание до любых проверок.** Возвращается
   успех с пустыми строками. Это защита от тихой подмены: раньше модель
   подставляла похожую таблицу и возвращала чужие данные как успех
7. `validate_sql(sql)` — при отказе ошибка уходит обратно в LLM, попытка повторяется
8. `EXPLAIN` — проверка синтаксиса и существования объектов
9. Выполнение

Отдельной ветки «ответ не распознан» нет. Если модель вернула прозу, а не SQL,
`is_no_match` даёт `false`, `validate_sql` отклоняет это как не-`SELECT`, и
попытка считается израсходованной. Для контракта это означает, что исход
`not_answerable` может означать как «запрос не построился», так и «модель
ответила ерундой» — и различать их вызывающий не должен, потому что действия
у него одинаковые.

Признак отказа распознаётся строго: `<NO_MATCH>` в любом регистре, с
пробелами, точкой или точкой с запятой вокруг. Фраза вроде «результат —
`<NO_MATCH>`» отказом **не** считается.

При ошибке вида «временно занята» цикл прерывается, а не повторяется: это
конкуренция за блокировки, повтор её не решит.

**Новое.**

* **Проверка списка таблиц в коде — выполнено.** Сегодня она есть:
  `assert_tables_allowed()` (`libs/audit/guard.py`) вызывается до `EXPLAIN`
  (`libs/audit/generated_sql.py`), а разрешённый список приходит из
  `platform.json → audit.tables`. Подробности и ссылка — §8.3.
* **Потолок строк — выполнено.** Сгенерированный запрос больше не уходит в
  базу без `LIMIT`: `enforce_row_limit()` навешивает предел перед `EXPLAIN`,
  значение — `platform.json → audit.row_ceiling`. Подробности — §8.4.
* **`context` от вызывающей стороны не принимается.** Аргумент существует и
  подклеивается в начало сообщений. Это прямой путь для текста агента внутрь
  генератора запроса. Для MCP-операции переписка не передаётся.

**Опасность.** AST-guard без `sqlglot` деградирует до регулярных проверок и
перестаёт быть защитой — см. §8.2. Здесь он защищает не пользователя, а вывод
LLM, но вывод LLM выполняется в базе, поэтому требование остаётся: сервер не
поднимается без `sqlglot`. Требование **выполнено** — старт fail-fast, §8.2.

## 5. Capability `vectors`

FAISS в памяти, без персиста. Векторы читаются из снимка DuckDB на старте
сервера, до запуска event loop: ленивой сборки на первом запросе нет — она
означала бы, что первая операция платит за все индексы сразу.

### 5.1 `vector_search`

**Что делает.** Эмбедит запрос, достаёт или собирает индекс, ищет
ближайшие чанки и сворачивает их в документы.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `query` | `string` | — | Текст запроса. Эмбедится на сервере |
| `index_name` | `string` | `"default_index"` | Имя индекса из конфигурации |
| `top_k` | `integer` | `5` | Сколько документов вернуть. Снизу ограничен единицей, сверху потолка в коде нет |
| `threshold` | `number` | `null` | Отсечка по score. `null` = не применять |

**Возвращает**
```json
{ "index_name": "default_index", "index_state": "ready", "found": 1,
  "results": [ { "content": "…", "score": 0.83,
                 "source": "audits_index", "table": "audits",
                 "pk_value": 41, "chunk": "2/4", "matched_chunks": 2,
                 "row": { "…": "исходная строка" } } ] }
```

`index_state` — состояние индекса на момент поиска (`missing` / `building` /
`ready` / `error`), `found` — число элементов в `results`. Поля `status`, `index`
и `table` на верхнем уровне ответа нет.

**Ошибки:** `not_found` (неизвестный индекс), `upstream_unavailable`
(сервис эмбеддингов недоступен), `index_build_failed`, `timeout`, `internal`.

**Побочные эффекты:** индексы собраны на старте сервера, поэтому время
подъёма включает их сборку; после этого поиск блокирующих затрат не имеет.
Индекс кэшируется в памяти процесса.

**Сегодня.** `CacheProvider.search_vector(query, index_name="default_index",
index_path=None, top_k=5, threshold=None) -> list[SearchResult]`.
`SearchResult` — ровно те поля, что выше. `build_faiss_index` возвращает
`(index, metadata)` или `(None, None)`. Индекс — `faiss.IndexFlatIP`.
Сборка: `np.zeros((n, dim), float32)`, при `metric == "cosine"` —
`faiss.normalize_L2`, затем `index.add`. `group_vector_hits` сворачивает
чанки в документы по ключу `(source, table, pk_value)`, оставляя лучший чанк
представителем.

**Зависимость от эмбеддингов остаётся.** Векторы документов предрассчитаны,
но **вектор запроса эмбедится в рантайме**: `get_embedding(query)` ходит в
сервис эмбеддингов, и при недоступности возвращает пустой результат, а не
ошибку. В контракте это превращено в `upstream_unavailable` — иначе вызывающий
не отличит «ничего не нашлось» от «сервис лежит».

**Опасность, влияющая на контракт.** Из двух вещей одна осталась: смысл полей
ответа ломает поведение §8.7 (`threshold` отключает `top_k` — подтверждено
кодом). §8.8 закрыт: `metric` применяется, вектор запроса нормализуется.

### 5.2 `list_indexes`

**Что делает.** Перечисляет индексы, объявленные в конфигурации, вместе с
числом векторов в хранилище. **Не поднимает индекс** — отвечает сразу.

Параметров нет: `handle_list_indexes()` не принимает аргументов вообще.

**Возвращает**
```json
{ "count": 1, "note": "состояние отдаётся без сборки индекса",
  "indexes": [ { "index_name": "audits_index", "state": "ready",
                 "declared": true, "vector_count": 184320,
                 "dimension": 1024, "metric": "cosine",
                 "error": "", "error_code": "" } ] }
```

Элемент списка — это `VectorIndexOwner.describe()` целиком. Полей `name`,
`table`, `enabled`, `status`, `vectors_in_memory`, `vector_count_in_store` в
ответе нет.

**Ошибки:** `queue_full`, `internal`.

**Сегодня.** `read_vector_index_config()` даёт по каждому индексу `table`,
`pk`, `source_table`, `content_columns`, `embedding_columns`, `track_column`,
`chunk_size`, `chunk_overlap`, `metric`, `enabled`. Фактический счётчик строк
берётся из `vector_source_stats()` снимка, а `list_runtime_vector_indexes()`
(`SELECT source, COUNT(*) … GROUP BY source ORDER BY source`) операцией
`list_indexes` **не** используется.

**Склейка уже сделана.** `VectorIndexOwner.describe()` соединяет объявление и
счётчик и возвращает восемь полей элемента, перечисленных выше. `metric` в
ответе есть и берётся из объявления индекса, а нормализация вектора запроса при
`metric == "cosine"` выполняется — §8.8. `list_runtime_vector_indexes()` при этом
по-прежнему возвращает `dimension`, `updated_at`, `metric` и `signature` как
жёсткие `None`: незаполненные поля остались в этой функции, но в ответе
операции они не видны.

### 5.3 `index_stats`

**Что делает.** Состояние конкретного индекса: прогрет ли, сколько векторов,
какая размерность. Для диагностики, не для выбора.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `index_name` | `string` | `"default_index"` | Имя индекса |

**Возвращает** — описание индекса из `list_indexes` плюс четыре счётчика:
```json
{ "index_name": "audits_index", "state": "ready",
  "declared": true, "vector_count": 184320, "dimension": 1024,
  "metric": "cosine", "error": "", "error_code": "",
  "vectors": 184320, "dim": 1024,
  "last_built_at": "2026-10-02T12:00:00", "queries": 7, "builds": 1 }
```

`vectors` дублирует `vector_count`, а `dim` — `dimension`: это размерность как
число, а не как объект сэмпла. `last_built_at` — `null`, если индекс ещё не
собирался. Полей `vectors_in_memory`, `vector_count_in_store` и `note` в ответе
нет.

**Ошибки:** `not_found`, `internal`.

**Наблюдаемость — в коде.** Состояние индекса (`state`), время последней сборки
(`last_built_at`), число запросов (`queries`) и число сборок (`builds`) отдаёт
`VectorIndexOwner.index_stats()`, а `describe()` отдаёт `error` и `error_code`
независимо от того, удалась сборка или нет. Отдельного «нового» по наблюдаемости
не осталось: то, что обещала первая редакция раздела, в ответе есть.

## 6. Capability `llm`

Capability — тонкая граница протокола. Всю работу делает внутренний сервис
`libs/llm/gateway.py` (см. README, «Внутренний сервис общения с LLM»):
настройки, HTTP-вызов, разбор ответа. Capability проверяет аргументы, запрещает
вызов от профиля `model` и переводит сбой провайдера в доменную ошибку.

Ответ операции — **текст без обёртки** (`TextContent`), ошибка — `[код] текст`.

### 6.1 `complete`

**Что делает.** Один вызов чата и возврат текста ответа. Обслуживает
инфраструктуру платформы (генерация SQL в `audit`); профиль вызова —
`runtime`, вызов от `model` отклоняется.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `prompt` | `string` | — | Текст запроса; пустой — `invalid_request` |
| `system` | `string` | `""` | Системная инструкция; пустая не отправляется |
| `context` | `array<object>` | `null` | История диалога, добавляется перед `prompt` |
| `model` | `string` | `null` | `null` = модель из `platform.json` (секция `llm`) |
| `max_tokens` | `integer` | `null` | `null` = значение из конфигурации |
| `temperature` | `number` | `null` | `null` = значение из конфигурации; диапазон `[0, 2]` |
| `max_retries` | `integer` | `3` | Обязателен: `null` — `invalid_request` |
| `timeout` | `number` | `60.0` | Секунды. Обязателен: `null` — `invalid_request` |

**Возвращает** — текст ответа провайдера.

**Ошибки:** `invalid_request` (аргументы, вызов от профиля `model`),
`infrastructure_error` (провайдер не настроен, не ответил или ответил пустотой).

**Почему `max_retries` и `timeout` обязательны, а `model` нет.** На проводе MCP
`null` означал бы «параметр не задан», и дефолт подставился бы молча:
выключенный таймаут выглядел бы как «провайдер перестал отвечать», а не как
«параметр не передан». У `model` другой смысл — «возьми у сервиса», поэтому
там `null` честный.

**Внутренне, не операция.** `LlmService.send(messages=…)` зовёт тот же сервис с
готовым списком сообщений: конвейер генерации SQL дописывает к предыдущей
попытке текст ошибки и терять историю ему нельзя.

### 6.2 `embed`

**Что делает.** Векторизацию текста. Обслуживает `vectors`; профиль вызова —
`runtime`.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `text` | `string` | — | Текст для векторизации; пустой — `invalid_request` |
| `model` | `string` | `null` | `null` = модель эмбеддера из конфигурации |
| `max_retries` | `integer` | `3` | Обязателен |
| `timeout` | `number` | `60.0` | Обязателен |

**Возвращает**
```json
{ "vector": [0.1, 0.2], "dimension": 2, "model": "…" }
```

**Ошибки:** `invalid_request`, `infrastructure_error` (включая пустой вектор).

Модель эмбеддера приходит из своих настроек (`ENTERPRISE_EMBED_*`), а не из
модели чата: уход в эндпойнт эмбеддингов с именем модели чата вернул бы вектор
не той размерности, и подпись индекса разошлась бы с фактически использованной
моделью.

### 6.3 Чего в контракте нет

Настроек провайдера. Ни одна операция не принимает URL, заголовки, тело запроса
или ключ: адрес собирает владелец из своего конфига, и подсунуть провайдеру
свой endpoint через вызов операции нельзя. Секция `llm` в `platform.json` —
единственное место, где значения живут в репозитории.

JSON-режима у операции тоже нет. `call_llm_json` в коде проглатывает любую
ошибку и возвращает `None`, и такое поведение в контракте недопустимо:
вызывающий обязан различать «модель ответила не-разобранным JSON» и
«провайдера нет». Разбор JSON живёт на стороне владельца
(`LlmGateway.ask_json`, `libs.enterprise_client.llm.complete_json`), который
пропускает доменную ошибку и отдаёт `None` только за форматом ответа.

## 7. Доменные capability

`legal` добавляется в фазе 9. Контракт пишется по тому же шаблону, но
наполнение выводится из существующей поверхности домена, а не придумывается.

Требования к каждой доменной операции:

1. Один логический вопрос — один вызов. Если операция требует «сначала
   найти, потом посчитать», это **одна** операция: в одном процессе это
   работает, через две операции модель будет склеивать результат сама.
2. Параметры — из предметной области, а не из SQL. `audit_id`, `question`,
   `document_id` — да; `schema`, `where`, `order_by` — нет.
3. Изоляция, если она есть, выводится сервером.
4. Ошибки только из §2.
5. Операция не возвращает сырой сыр: ни `rows`, ни `payload` целиком.

## 8. Найденные при подготовке опасности

Каждый пункт проверен на реальном коде. Пункты 8.1–8.4 требовали решения **до**
того, как соответствующая операция будет отдана модели — на 2026-10-02 все
четыре закрыты и помечены соответствующим заголовком.

### 8.1 ЗАКРЫТО — предел стоимости запроса добавлен

**Статус: закрыто.** Реализовано **на запрос**, внутри замыкания задания, а не на
соединении: `DataService._guarded()` ставит `SET statement_timeout` перед
работой и сбрасывает его в `finally` (`capabilities/data/service/main.py`).
Значение приходит из `platform.json → data.statement_timeout_ms` — **30 000 мс**
по умолчанию — и передаётся сервису в `servers/enterprise/server.py`
(`statement_timeout_ms=int(settings.get("ENTERPRISE_STATEMENT_TIMEOUT_MS"))`).
Оговорка про `autocommit=True`, из-за которой `SET LOCAL` неприменим, учтена
явным сбросом.

**Что из рекомендаций не сделано:** отдельного меньшего лимита для операций,
порождённых LLM, нет — порог один на все задания пула, и
`platform.json → data.max_rows` (1000) ограничивает число строк отдельно.

Ниже — исходная запись находки, сохранённая как есть.

Поиск по всему репозиторию: ноль совпадений `statement_timeout`.
`psycopg2.connect(dsn, gssencmode="disable")` не передаёт `options=`. Бегущий
запрос держит воркер пула, пока его не убьёт сервер или клиент.

С появлением `generate_sql` это стало важнее, а не менее важно: запрос,
написанный машиной по вопросу, в среднем хуже выверенного руками.

Хуже всего именно там. В `generated_sql_mode` **единственный** таймаут во всей
цепочке — это HTTP-вызов LLM (`timeout_sec` из конфига, по умолчанию 60).
`db.explain` и `db.query_sql` не имеют времени выполнения вообще. `MAX_ATTEMPTS`
ограничивает число итераций, но не длительность: четыре попытки по
бесконечному `SELECT` — это четыре бесконечности подряд.

Два места для правки:

* **на соединении**, в момент коннекта: `options=f"-c statement_timeout={ms}"`
  в `_Worker._connect_with_backoff`. Действует на все задания воркера, что
  соответствует модели переиспользования соединений;
* **на запрос**, внутри замыкания задания. Оговорка: соединения работают с
  `autocommit=True`, где `SET LOCAL statement_timeout` — **no-op**, а обычный
  `SET` утечёт в следующее задание на том же соединении. Нужен явный сброс.

Рекомендация: вариант на соединении, плюс отдельный меньший лимит для
операций, порождённых LLM.

### 8.2 ЗАКРЫТО — старт без `sqlglot` запрещён

**Статус: закрыто.** Требование выполнено: `_check_dependencies()` в
`servers/enterprise/server.py` (`REQUIRED_PACKAGES = ("sqlglot",)`) отказывает
поднимать сервер, если пакет недоступен, и вызывается из `build_server()` до
сборки контейнера. AST-ветка `libs/enterprise_data/sql_safety.py`, ради которой
требование и существовало, доступна всегда.

**Что осталось открытым:** списка разрешённых функций по-прежнему нет — есть
только список запрещённых (см. абзац ниже). Это отдельная граница, и она не
закрыта.

Ниже — исходная запись находки, сохранённая как есть.

Проверено подменой реального импорта. Без `sqlglot` модуль деградирует до
регулярных выражений, и регулярный путь проверяет **только** три вещи: первый
блокируемый оператор, `INTO`, несколько операторов подряд.

| Запрос | С `sqlglot` | Без `sqlglot` |
|---|---|---|
| `DROP TABLE t` | отказ | отказ |
| `SELECT 1 INTO x` | отказ | отказ |
| `SELECT 1; DROP TABLE t` | отказ | отказ |
| `SELECT pg_sleep(10)` | отказ | **пропускает** |
| `SELECT * FROM information_schema.tables` | отказ | **пропускает** |
| `SELECT * FROM pg_catalog.pg_tables` | отказ | **пропускает** |
| `-- комментарий` + `UPDATE t SET x=1` | отказ | **пропускает** |
| `-- комментарий` + `DELETE FROM t` | отказ | **пропускает** |

Причина в двух местах: построчные комментарии `--` не вырезаются перед
проверкой первого слова (вырезаются только блочные `/* */`), и списки
запрещённых функций и системных схем живут только в AST-ветке.

**Требование:** сервер SHALL отказывать стартовать, если `sqlglot`
недоступен. Тихая деградация недопустима, пока регулярный путь не приведён к
тому же уровню. Это отличается от текущей политики модуля, где деградация
разрешена сознательно.

Дополнительно, независимо от `sqlglot`: в `sql_safety` **есть только
список запрещённых функций** — списка разрешённых нет. Любая не перечисленная
функция, включая пользовательскую с побочным эффектом, проходит.

### 8.5 Плейсхолдеры в реестре — диалект исполнителя

`sql_template` в `agent_predefined_scripts` описан как шаблон с позиционными
`?`-плейсхолдерами. Сборщик конвертирует `:param` в `?`, и загрузчик реестра
тоже использует `?` в `WHERE name = ?`. Это диалект снимка, а не PostgreSQL:
у `psycopg2` — `%s`. Менять плейсхолдеры без смены исполнителя нельзя, скрипты
перестанут работать. Смена исполнителя — миграция реестра целиком, и в текущем
плане она не выполняется.

Смежное: `_qualified_table` при отсутствии точки в имени схемы подставляет
`"main"` — схема снимка. Пока исполнитель не сменён, подстановка `public`
сломала бы шаблоны, записанные без указания схемы.

### 8.6 Сломанный реестр выглядит как пустой

`load_all` ловит исключение и возвращает `{}`, `load_script` — `None`. Если
таблица реестра недоступна или миграция не применена, модель получит «скриптов
нет» вместо ошибки и сделает вывод, что данных нет. Ошибки возвращаются
словарями, а не исключениями, поэтому отличить одно от другого сейчас нечем.

Доктрина «не молчаливый fallback», которая записана в докстринге `db_loader`,
относится к **отсутствию Python-реестра**, а не к обработке ошибок. На
поведение кода это не влияет, но читается как гарантия, которой нет.

Контракт вводит `registry_unavailable` и требует различать «реестр пуст
намеренно» и «реестр не прочитан».

### 8.7 `threshold` отключает `top_k` — ПОДТВЕРЖДЕНО

**Подтверждено кодом:** `libs/vectors/grouping.py`, `group_vector_hits()` —
`threshold_active = threshold is not None and threshold > 0`, и усечение до
`top_k` выполняется только при `if top_k and not threshold_active`. Поведение
не менялось и в контракте не описано.

`group_vector_hits` усекает до `top_k` только когда `threshold` не задан и не
положителен. При `threshold > 0` возвращаются **все** прошедшие отсечку
хиты, `top_k` игнорируется.

В контракте это выглядит как «вернулось 812 результатов, хотя просили 10».
Нужно либо починить, либо зафиксировать как намеренное поведение. Сейчас не
зафиксировано нигде.

### 8.8 ЗАКРЫТО — `metric` применяется, векторы нормализуются

условии, поэтому возвращаемый `score` — косинусная близость, а не сырое
скалярное произведение.

Ниже — исходная запись находки, сохранённая как есть.

Все индексы аудита объявлены с `"metric": "cosine"`. Значение читается

### 8.9 ЗАКРЫТО — `IndexIntegrityError` поднимается, сверка подписи есть

**Статус: закрыто по главному пункту.** Сверка подписи выполняется, и отказ

`signature_status` заполняется в `preload()` (`libs/vectors/owner.py`), и
`libs/vectors/preload.py` разбирает его на `stale` / `ready`.

**Что осталось открытым (проверено, утверждение ниже верно):**

* поля `signature_status` и `signature_reason` в `SearchResult`
  (`libs/enterprise_data/snapshot/contracts.py`) по-прежнему имеют дефолт `""`
  и в пути поиска не заполняются — сверка живёт в владельце индекса, а не в
  элементе результата;
* `list_runtime_vector_indexes()` по-прежнему возвращает `dimension`,
  `updated_at`, `metric`, `signature` как жёсткие `None`. На ответ операции
  `list_indexes` это не влияет — он строится из `describe()`.

Ниже — исходная запись находки, сохранённая как есть.

`IndexIntegrityError` не поднимается нигде в репозитории — единственное
упоминание это `except` в CLI. Поля `signature_status` и `signature_reason`
в `SearchResult` не заполняются никогда. `list_runtime_vector_indexes`
возвращает `dimension`, `updated_at`, `metric`, `signature` как жёсткие `None`.

Механизм подписи существует и считает хеш по десяти полям конфигурации, но
его результат никто не сверяет. Контракт обязан либо реализовать сверку, либо
не обещать её полями ответа. Обещать несуществующую проверку хуже, чем не
иметь её.

### 8.10 `user_id` в журнале — невидимая граница изоляции

`history_search(session_scope="all")` фильтрует строго по `user_id`. Поле
заполняется либо производителем явно, либо разрешается по совпадению
`request_id`. Строки с `user_id IS NULL` для `session_scope="all"` не видны,
и такой поиск вернёт пустой результат **без ошибки**.

Пока журнал остаётся в той же таблице, что и runtime, это правильное
поведение. Как только журнал станет внешним приёмником, граница требует
явной гарантии заполнения. Сейчас её нет.

### 8.11 Промпт получает удвоенную схему

Список таблиц для LLM собирается как
`[f'"{get_db_schema()}"."{t}"' for t in tables]`, а `t` — уже строка вида
`schema.table`. Результат — `"oarb"."oarb.audits"`, `"oarb"."oarb.violations"` и
так далее. Схема в имени присутствует дважды.

Модель справляется с этим сегодня, но правило промпта при этом «все имена
схемно-квалифицированы» противоречит тому, что модель реально видит: она
вынуждена выбирать между очевидной формой и формальной инструкцией. При
переносе на PostgreSQL это место всё равно переписывается — и правильный вид
должен быть `oarb.audits`, без кавычек и без удвоения.

Проверить фактическое поведение генератора на живой БД не удалось: в
репозитории нет доступа к данным, а seed отражает снимок состояния.

### 8.12 Дрейф документации

`call_llm_async` не существует. Клиент полностью синхронный, `async def` в
модуле нет. Имя встречалось в `AGENTS.md`, `CHANGELOG.md`,
`docs/ARCHITECTURE.md` и `config.json`. Исправлено в рамках этого изменения.

Ещё три расхождения, найденных в этом же проходе:

* `predefined/models.py` в докстринге утверждает, что реестр скриптов живёт
  в `scripts.py`, а не в PostgreSQL. Кодом это опровергнуто: Python-реестра
  нет вообще, единственный источник — `db_loader` и таблица.
* `SKILL.md` перечисляет шесть скриптов с другими именами
  (`analytics_by_year_month`, `audit_dynamics`, …) и утверждает, что все
  параметры необязательны. Seed кладёт пять других имён, и в `violations_by_period`
  параметры помечены `required: true`. Какая из двух картин соответствует живой
  базе — по репозиторию не определить. Авторитетен `list_scripts`, а не текст.
* `docs/DATABASE.md` документирует `skills.audit_analyzer.llm.max_tokens` и
  `.temperature` как существующие ключи. Секций `cli.*` и `llm.*` у этого skill'а
  в `config.json` больше нет — они удалены, значения берутся из общего резолва.

Общий класс проблемы один: **каталог скриптов и его схема описаны в трёх
местах, и все три разошлись.** В новой схеме описание параметров приходит из
одной таблицы, поэтому разойтись ему больше не с чем.

### 8.13 Permission объявлен, но не проверяется

Каждая операция объявляет `ToolDefinition.permissions` (`data:log_events`,
`data:purge_logs`, `llm:complete`, …), и тест требует, чтобы объявление было
(`test_data_log_events.py::test_operation_is_runtime_only_with_permission`,
`test_server_bootstrap.py`). Но **в рантайме поле никто не читает**: единственное
чтение — `loader.py:142`, который переносит объявление из `ToolDefinition` в
`LoadedTool`. Ни фильтрации при публикации, ни проверки при вызове нет.

`build_server(registry, name="enterprise-mcp", …)` получает весь реестр, то есть
**все 22 операции**: 21 из `capabilities/*/tools/` плюс платформенная
`read_result` (§2.1), которую регистрирует composition root. Модель, увидевшая
сервер в discovery, может вызвать `purge_logs` — то есть стереть журнал, — а
также `claim_task` и `update_task_status`: очередь задач в перечень входит и
объявлена runtime (`AUDIENCE_RUNTIME`), но публикуется наравне со всем
остальным.

Почему это не «мелочь»: метки `AUDIENCE_RUNTIME`/`AUDIENCE_MODEL` в коде
разделяют запись журнала и чтение журнала (чтобы `history_search` не писал в
тот же журнал, который читает), то есть идея «операция не для модели» в проекте
есть и работает. Но доведена она до уровня журнала, а не до уровня поверхности
вызова.

Что это меняет: объявление permission сегодня — документация, а не граница.
Настоящая граница появится либо фильтрацией при публикации в MCP, либо контрактом
`_meta` плюс правилом «операции runtime не выставляются модели» (дельта
`runtime/call-contract`, фаза 8). До этого решения считать permission защитой
нельзя.

## 9. Что осталось открытым

| Вопрос | Почему не решён |
|---|---|
| Показывать ли SQL в ответе `run_script` | Сегодня `run()` его возвращает. Для оператора полезно, для модели это приглашение вернуть ручную правку. По умолчанию убрано, флаг `include_sql` не вводился |
| Переносить ли `long_description` в описание самого MCP-инструмента | Скрипты приходят из базы, а описание MCP-инструмента статично. Нужен ли отдельный вызов `describe_script` или хватит `list_scripts` с фильтром |
| Сколько попыток генерации | Сегодня `MAX_ATTEMPTS = 4`, то есть до четырёх вызовов LLM на один вопрос. Стоимость на вопрос не ограничена ничем |
| Снимать ли потолок `max_tokens` в `complete` | Сейчас модель может заказать `max_tokens: 10**9`, и стоимость не ограничена |
| Что отдавать в `row` у `vector_search` | Полная строка источника может быть большой. Нужен потолок и признак усечения в ответе |
| Проверять ли `permissions` при вызове | Сегодня поле объявлено, но не читается рантаймом (§8.13): публикуются все 22 операции. Нужно решение — фильтровать ли при публикации в MCP или опираться на контракт `_meta` и правило «runtime-операции модели не выставляются» |

Один технический факт ограничивает любой из этих вопросов: `SkillSettings`
объявлен с `extra="forbid"`. Любой новый ключ под `skills.audit_analyzer`
останавливает старт gateway с `ConfigurationError`. Поэтому «просто добавим
настройку» — не бесплатное действие, и часть открытых вопросов заканчивается
правкой схемы конфигурации, а не одной строкой в коде.
