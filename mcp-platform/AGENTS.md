# Инструкции для работы в `mcp-platform/`

## Кому этот файл

Ассистенту, который работает **внутри этого поддерева**. Он читается вместе с
корневым `AGENTS.md` и не заменяет его: корневой описывает весь проект, этот —
границу между двумя деревьями.

Инструкции для **нано-агента**, работающего в бою, лежат отдельно и в этом каталоге
не действуют — это `workspace/AGENTS.md`.

## Канон лежит не здесь, и это осознанно

Спецификации — в корне репозитория, `openspec/specs/`. Переносить их в
`mcp-platform/` **не надо**, и вот три причины, каждая проверяема:

1. **Настоящее требование проекта запрещает.** `openspec/specs/architecture/component-model`
   → требование «единственный источник истины»: «Component-specific contracts
   ДОЛЖНЫ вестись в `openspec/specs/<domain>/<component>/spec.md`». Исключения для
   платформы там нет.
2. **Перенос вывел бы спеки из-под валидатора молча.**
   `tools/validate_component_specs.py:84` жёстко берёт
   `SPECS_DIR = ROOT / "openspec" / "specs"`, а `iter_spec_files` (`:285-286`) обходит
   `**/spec.md` **только внутри неё**. Спеки в этом каталоге стали бы невалидируемыми
   без единого сообщения — то есть зелёный прогон перестал бы что-то значить. Плюс 12
   файлов в `tests/` ссылаются на `openspec/specs` напрямую.
3. **Подсистемы мигрируют между деревьями постоянно.** Сейчас один репозиторий,
   одна ветка, общая история. Change `2026-10-04-close-cache-provider-canon-gap`
   существует именно потому, что кэш-кластер переехал из агента сюда; без переноса
   дельты архив нечего мержить. Физическое разделение превращало бы каждую такую
   миграцию в перенос файла — в тот момент, когда канон трогать опаснее всего.

## Какие спеки твои

Владелец объявляется в `## Scope`, и по правилу
`openspec/specs/OWNERSHIP.md` берётся **первая метка в обратных кавычках** — не
первое вхождение слова `platform` в тексте. На 2026-10-06: **5 `platform`,
5 `shared`, 18 `agent`**.

Твои (`Scope: platform`):

- `data/cache-provider` → capability `data`
- `data/operation-schema`
- `data/vector-indexes` → capability `vectors`
- `runtime/db-queue-classes`
- `skills/legal-summarizer-query` → capability `legal_summarizer`

Общие с агентом (`Scope: shared`) — правки согласуются с обеими сторонами:

- `configuration/profiles` — читает агент, применяет платформа
- `logging-db` — writer в агенте, транспорт записи идёт в операцию платформы
- `runtime/platform-settings` — блок пишет агент, читает платформа
- `testing/unified-test-contract`
- `tools-history-search` — область задаёт вызывающая сторона

Пересчитать после правок, а не верить этому списку. Команды — **из корня
репозитория**; даны через `git grep`, потому что обычный `grep` и `..` вверх
здесь работают ненадёжно. Точная разборка — первая метка в обратных кавычках
тела `## Scope`:

```bash
git grep -l '^## Scope' -- 'openspec/specs/*/spec.md' 'openspec/specs/*/*/spec.md'
git grep -l '`platform`' -- 'openspec/specs/*/spec.md' 'openspec/specs/*/*/spec.md'
```

Первая команда даёт все 28 спек. Вторая ловит и `shared`-спеки, в тексте которых
упомянута платформа, поэтому **завышает** и для ответа «чей это код» не годится.
Автоматической проверки соответствия между `## Scope` и реальным расположением
реализации в проекте нет, и задачи на неё там тоже нет: в
`openspec/changes/2026-10-06-spec-integrity/tasks.md` про `## Scope` есть 1.6
(внести раздел в канонический перечень) и закрытая 2.2, а 1.12 — это «Паритет
реестра и спек» (`COMPONENTS.md` ↔ дерево спек).

## Проверки

Команды взяты из `.github/workflows/ci.yml`, `working-directory: mcp-platform`.

```bash
# быстрые тесты платформы: 6214 собрано, 8 отсеяно маркерами
# число пересчитывается: cd mcp-platform && python -m pytest tests --collect-only -q
python -m pytest tests -q --tb=short -m "not live and not integration"

# отдельно — 8 тестов живой stdio-контракта, они дешёвые, но требуют живой сессии
python -m pytest tests/test_live_stdio_contract.py -q --tb=short

# линт
python -m ruff check servers libs
```

Локально `ruff` в агентском `.venv` **не установлен** (`No module named ruff`) — он
приходит из CI. Прогоны тестов локально работают.

Перед сдачей change проверь дельту: `openspec validate <id> --strict`. Требование
инструмента, а не вежливость: у change без дельт должен стоять `skip_specs: true`
в `.openspec.yaml`, а `MODIFIED`-блок обязан содержать **все** сценарии требования,
иначе `archive` откажется их выбросить.

## Своя документация

В `docs/` уже есть платформенный слой, и он не дублирует канон:

- `TARGET-ARCHITECTURE.md` — нормативные архитектурные правила платформы
- `MCP-CONTRACTS.md` — контракты операций и их границы
- `BASELINE.md` — зафиксированное состояние
- `MIGRATION.md` — переезды
- `architecture.html` — визуальная схема
- `../platform.json` — объявления: capability, индексы, журнал, профиль контура

По правилу «единственный источник истины» нормативные правила платформы пишутся
в `mcp-platform/docs/TARGET-ARCHITECTURE.md`, контракты компонентов — в
`openspec/specs/`, детали реализации — в `docs/`. Не смешивай: реализация в
каноне выглядит как норма и протухает первой (в `data/cache-provider` именно так и
получилось — `## Scope` правдив, тело описывает снятый код).

## Границы

Платформа **не** знает про агента: она получает плоские ключи идентичности
(`request_id` / `session_id` / `user_id`, `platform.json → execution.require_call_meta=false`)
и не различает модель агента и его runtime. Агент **не** владеет файлами сессии —
инструменты платформы читают состояние через файлы, и это запрещено capability
стражем `tests/test_tool_execution_boundaries.py`. Из-за этого чтение состояния
операции уехало из capability `legal_summarizer` в платформенную операцию
`platform.query_operation`.

## Чего здесь не делать

- **Не переносить спеки в этот каталог** — см. три причины выше.
- **Не заводить второй канон.** `openspec/` в корне остаётся единственным.
- **Не объявлять платформенную спеку `agent`,** даже когда правка идёт с этой
  стороны: владелец отвечает на вопрос «кто это чинит», а не «кто сейчас пишет».
- **Не выдумывать числа про владение.** Если пересчитал — пересчитай по правилу
  первой метки, а не по вхождению слова.
