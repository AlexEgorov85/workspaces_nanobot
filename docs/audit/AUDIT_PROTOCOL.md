# Протокол глубокого аудита кода

Единые правила для всех аудиторов. Каждый аудитор отвечает за свою подсистему и
пишет ровно один файл отчёта. Цель — не описание кода, а **оценка**: зачем он
существует и что с ним делать.

## 1. Что такое «продуктовый код» в этом проекте

Платформа нано-агента поверх библиотеки `nanobot 0.3.0`:

| Слой | Путь | Роль |
|---|---|---|
| Точки входа | `config.py`, `gateway.py`, `cli_agent.py`, `streamlit_app.py` | загрузка конфига, HTTP-сервер, REPL, UI |
| Ядро | `lib/core/`, `lib/lifecycle/` | composition root, DI, настройки, валидация |
| Сервисы | `lib/services/` | кэш DuckDB, логирование, патчи рантайма, health, LLM |
| Интеграция | `lib/hooks/`, `lib/channels/`, `lib/session/`, `lib/events/`, `lib/cli/` | хуки, каналы (Postgres/Redis), сессии, REPL |
| Утилиты | `lib/utils/`, `workspace/utils/` | SQL-guard, текст, session key, коннекторы |
| Плагины | `workspace/tools/`, `workspace/hooks/` | авто-сканируемые tool'ы и хуки |
| Скиллы | `workspace/skills/*/scripts/` | `audit_analyzer` (CLI-режимы), `legal_summarizer` (суммаризация документов) |
| Dev-утилиты | `tools/`, `benchmarks/` | миграции, диагностика, бенчмарки |

`lib/` — **всегда нужен**: это фреймворк рантайма. `tools/` и `benchmarks/` —
standalone-скрипты, запускаются вручную из CLI, поэтому у них по определению
нет импортёров; это **не** повод объявить их мёртвыми.

## 2. Входные данные

1. **Бриф** `docs/audit/_data/_briefs/<group>.md` — автоматический AST-каркас:
   строки, сигнатуры, docstrings, число ссылок, `self.<method>(` call-sites,
   импортёры, тесты. Э economy — каркас, **не** источник выводов.
2. **Сам код** — читать обязательно. Бриф не заменяет чтение: смысл, инварианты
   и реальные вызовы видны только в исходниках.
3. Общие находки: `docs/audit/_data/{dead_symbols,orphans,duplicates,test_gaps}.md`
   — сверяйся, но **перепроверяй**: статика ошибается (динамические регистрации,
   плагин-сканирование, entry points, строковые ссылки).

## 3. Обязательный формат отчёта

Пиши в `docs/audit/reports/<group>.md`.

```markdown
# Аудит: <название группы>

## Сводка группы
Файлов: N · LOC: N · классов: N · методов: N · функций: N

**Ключевые находки** (5–12 пунктов, каждый — с путём и строкой):
- ...

**Вердикты:** Оставить N · Упростить N · Удалить N · Перенести N

---

## `path/to/file.py` — N LOC

**Назначение.** одна фраза — что это за вещь в системе.
**Что делает.** 2–5 предложений о фактической работе, включая неочевидные
побочные эффекты (запись в БД, файлы, monkey-patch, глобальное состояние).
**Зачем нужен.** какую проблему закрывает; что сломается без него.
**Вердикт.** `Оставить` | `Упростить` | `Удалить` | `Перенести` | `Слить с <файл>`
**Обоснование.** 1–3 предложения с опорой на факты.
**Доказательства.** кто импортирует (файлы), какие тесты покрывают, счётчик ссылок.

#### class `Name` (строки A–B, N методов)
Назначение / зачем нужен / вердикт / обоснование.
Атрибуты и классовые переменные — одной строкой, если есть.

| Метод | Строки | Назначение | Зачем нужен | Кто вызывает | Вердикт |
|---|---|---|---|---|---|
| `name` | A–B | ... | ... | `file.py:LNN` | Оставить |

#### Функции уровня модуля
| Функция | Строки | Назначение | Зачем нужна | Кто вызывает | Вердикт |
|---|---|---|---|---|---|
```

Вложенные функции (`def` внутри `def`) тоже перечисляй — в колонке «Кто
вызывает» указывай `вложена в <родитель>`.

## 4. Правила вынесения вердиктов

**Покрытие обязательно полное.** Каждый класс, каждый метод, каждая функция из
брифа получают строку. Символ, который ты не разобрал, считается невыполненной
работой. Если файл или символ разобрать не успел — явно помечай
`НЕ РАЗОБРАНО` в отчёте, не молчи.

**`Удалить` — только с доказательством.** Перед тем как написать `Удалить`,
обязательно проверь вручную (grep по всему репозиторию, включая `tests/`,
`sql/`, `docs/`, `.github/`, `project.json`, `SKILL.md`):

- не вызывается ли через `getattr` / `importlib` / `__all__` / `globals()[...]`;
- не подключается ли сканированием каталога (`workspace/hooks/`,
  `workspace/tools/`, `lib/cli/hook_loader.py`, `RuntimePatcher`);
- не является ли точкой входа (`python -m`, `python path/to.py`, `main()`,
  console-script, `gateway.py`/`cli_agent.py`/`streamlit_app.py`);
- не нужен ли как шаблон/документация (`workspace/tools/example.py` — это
  **осознанный** шаблон из AGENTS.md, вердикт `Оставить` с оговоркой);
- не используется ли в тестах, SQL, CI, конфиге, доках как контракт.

Формулировка вердикта: что именно удалять (символ / класс / файл), что
останется, что сломается, какая предварительная работа нужна (заменить
вызовы, обновить docstring, поправить `REQUIRED_KEYS` в `tests/test_config_keys.py`).

**`Оставить` — тоже обоснованное утверждение.** Не пиши «нужен» без причины.
Хорошая формулировка: «нужен как публичный контракт для `X.py:NN`; удаление
ломает `Y`».

**`Упростить`** — когда суть нужна, а текущая форма избыточна (дублирование,
лишние абстракции, мёртвые ветки, legacy-обёртки). Обязательно укажи, что
именно можно убрать и какой выигрыш.

**`Слить с <файл>`** — когда реализация дублирует соседний модуль (сверься с
`duplicates.md`).

## 5. Что искать помимо вердиктов

- **Дублирование** — две реализации одного и того же; сверься с `duplicates.md`.
- **Мёртвые ветки / недостижимый код** — `if False`, `return` в конце, ветки
  после `raise`, флаги, которые никогда не выставляются.
- **Скрытые контракты** — порядок вызовов, который нигде не enforced; monkey-patch
  приватных методов upstream `nanobot` (риск при апгрейде); рефлексия.
- **Отсутствие docstring** там, где соседние функции документированы.
- **Строки, которые лгут** — docstring/comment описывает удалённое поведение
  (в проекте это уже было: `cache_ownership` удалён, а упоминания остались).
- **Состояние по умолчанию, которое никто не переопределяет**; `TODO`/`FIXME`/
  `XXX`/`HACK`; закомментированный код.
- **Риски при upgrade** `nanobot` — обращение к приватным API (`_`-имена),
  reliance на порядок полей, `from nanobot.x import _private`.

## 6. Стиль

- Язык отчёта — русский, термины/идентификаторы — как в коде (англ.).
- Таблицы — для символов; проза — для файлов и классов.
- Не пересказывай docstring: docstring отвечает «как задумано», ты отвечаешь
  «что это реально делает и зачем».
- Указывай `путь:строка` для каждого существенного утверждения.
- Не выдумывай: нет данных — пиши `не проверено` / `требует запуска`.

## 7. Что вернуть в чат

После записи файла отчёта верни **только**:
1. путь к написанному файлу;
2. 8–15 самых важных находок (путь:строка + суть + вердикт);
3. счётчики: сколько символов разобрано, сколько вердиктов `Удалить` /
   `Упростить` / `Слить`, сколько символов осталось `НЕ РАЗОБРАНО`;
4. любые находки, выходящие за пределы твоей подсистемы (кросс-подсистемные
   дубли, мёртвый код, который видно только извне).
