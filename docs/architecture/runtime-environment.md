# Целевая среда развёртывания

Канон целевой конфигурации. Три оси: операционная система, версия Python,
СУБД. Каждая объявлена здесь и **проверяется тестом**
`tests/test_runtime_environment_contract.py` — не для того, чтобы тест был
красивым, а потому что расхождение объявления и кода обнаруживалось только
после применения к боевой базе.

| Ось       | Значение                    | Где проверяется                                    |
|-----------|-----------------------------|-----------------------------------------------------|
| ОС        | Linux                       | `tests/test_runtime_environment_contract.py`        |
| Python    | 3.12                        | `tests/test_runtime_environment_contract.py`        |
| СУБД (боевая)   | Greenplum 6.5 (ядро PostgreSQL 9.4) | `tests/test_runtime_environment_contract.py`, `sql/README.md` |
| СУБД (тестовая) | PostgreSQL 13.22            | `tests/test_runtime_environment_contract.py`        |

Окно проверено и **уже** соответствует коду: в проекте нет ни одного API,
появившегося в Python 3.13/3.14, нет ни одного модуля, удалённого в 3.12/3.13,
нет `multiprocessing`/`os.fork`. По СУБД — не соответствует, см. «Долг».

## Одна СУБД боевая, другая тестовая

Это не «выбираем движок», а два движка сразу, и DDL обслуживает оба:

- **Greenplum 6.5** — боевая среда, ядро PostgreSQL 9.4.
- **PostgreSQL 13.22** — тестовый контур, на нём гоняются тесты.

Файлы из `sql/` применяются к обоим. Отсюда правило, которое выглядит
контринтуитивным, но обязано выполняться буквально:

> **Клауза `DISTRIBUTED BY` в теле `CREATE TABLE` запрещена.** На
> PostgreSQL это синтаксическая ошибка, и тестовый контур перестанет
> подниматься. На Greenplum без явной клаузы движок выбирает распределение
> сам — по первичному ключу, а при его отсутствии по первому подходящему
> столбцу. То есть клауза нужна, но не там, где её привычно писать.

Поэтому распределение объявляется отдельным ограждённым шагом:

```sql
DO $distribution$
BEGIN
    IF EXISTS (
        SELECT 1 FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
        WHERE c.relname = 'pg_dist_partition' AND n.nspname = 'pg_catalog'
    ) THEN
        EXECUTE 'ALTER TABLE public.example SET DISTRIBUTED BY (id)';
    END IF;
END
$distribution$;
```

`pg_dist_partition` — служебный каталог Greenplum; на PostgreSQL его нет,
поэтому шаг становится no-op. Исполняемый путь в коде (`tools/migrate.py`)
поступает так же: определяет движок по `version()` и добавляет клаузу только
на Greenplum. Статический файл обслуживает `psql -f`, код — запуск через
runner, и оба приходят к одному ключу распределения.

Идемпотентные конструкции, которых нет на 9.4, заменены по той же причине:
`CREATE INDEX IF NOT EXISTS` (9.5) и `ADD COLUMN IF NOT EXISTS` (9.6) —
на `DO`-блоки с проверкой `pg_indexes` и `information_schema.columns`.

Локальная разработка идёт на Windows и на более новом Python — это осознанно:
расхождение сред не должно быть поводом писать код, который работает «и так
и так». Сканирование ловит позитивные случаи, карантин задаёт известный долг.

## Почему Greenplum 6.5, а не «просто PostgreSQL»

Greenplum 6.x основан на PostgreSQL 9.4. Отсюда три следствия, каждое из
которых уже однажды стоило проекту работы:

1. **Нет `SKIP LOCKED`** (появился в 9.5). Очередь зада берётся без него, а
   эксклюзивность обеспечивает предикат в `WHERE`
   (`AND status = 'pending'`) — см. `docs/ARCHITECTURE.md` § «Почему не
   FOR UPDATE SKIP LOCKED».
2. **`SELECT ... FOR UPDATE` берёт блокировку уровня таблицы**, а не строки.
   Такой захват заблокировал бы всех читателей и писателей таблицы. Поэтому
   арбитраж строится на предикате, а не на блокировке строки.
3. **`DISTRIBUTED BY (...)` обязателен для каждой таблицы**, иначе она
   распределяется случайно, а первичный ключ на случайно распределённой
   таблице не допускается.

Конструкции новее 9.4 в исполняемом SQL — блокеры запуска, а не
предупреждения: `ON CONFLICT` (9.5), `CREATE INDEX IF NOT EXISTS` (9.5),
`ADD COLUMN IF NOT EXISTS` (9.6), `ALTER COLUMN ... SET NOT NULL` на
существующей колонке (12.0), `GENERATED ... AS IDENTITY` (10.0).

Замена идемпотентных конструкций — `DO $...$`-блок с проверкой
`information_schema.columns` / `pg_indexes`; `DO` доступен с 9.0. Замена
`ON CONFLICT` в данных, где VALUES-литерал нельзя переиспользовать во втором
запросе, — `DO`-блок с циклом по нему, а не дублирование данных.

`sql/README.md` § «Совместимость» предписывал `BIGINT GENERATED BY DEFAULT AS
IDENTITY` — это PostgreSQL **10.0**, то есть сам README предъявлял к
Greenplum 6.5 требование, которого тот не выполняет. DDL переведены на
`BIGSERIAL`, README поправлен на это же, и в него добавлены запреты
`DISTRIBUTED RANDOMLY` рядом с ключом, `ON CONFLICT` и `FOR UPDATE`.

## Долг: что в дереве не соответствует

Известные и зафиксированные нарушения. Список отдан стражу как карантин:
он зелёный сегодня и красный при **любом новом** нарушении.

**Закрыто 2026-10-03: было 25, стало 8.** Реестр миграций больше не падает на
синтаксисе; зеркало сессий не блокирует таблицу и не требует `ON CONFLICT`;
`IDENTITY` заменена на `BIGSERIAL`; весь DDL сессий, журнала, каналов и `oarb`
получил ограждённое объявление распределения, а конструкции 9.5/9.6 заменены
на `DO`-блоки с проверкой `pg_indexes` и `information_schema.columns`.

Оставшийся долг — только два вида: применённые миграции (переписывать нельзя,
DRIFT по checksum) и два seed-скрипта с `ON CONFLICT`.

| Файл | Нарушение | Почему не закрыто |
|------|-----------|-------------------|
| `sql/migrations/V002__vector_chunk_params.sql` | `ADD COLUMN IF NOT EXISTS` (9.6) | применённую миграцию не переписывают — DRIFT по checksum |
| `sql/migrations/V004__agent_gateway_logs_user_id.sql` | `ADD COLUMN IF NOT EXISTS` (9.6), `CREATE INDEX IF NOT EXISTS` (9.5) | то же |
| `sql/migrations/V008__agent_gateway_logs_event_time_columns.sql` | `ADD COLUMN IF NOT EXISTS` (9.6), `SET NOT NULL` (12.0) | то же |
| `sql/migrations/V009__agent_gateway_logs_event_time_indexes.sql` | `CREATE INDEX IF NOT EXISTS` (9.5) | то же |
| `sql/migrations/V010__agent_session_mirror_replica_key.sql` | `ADD COLUMN IF NOT EXISTS` (9.6), `SET NOT NULL` (12.0) | то же |
| `sql/migrations/V011__agent_session_mirror_indexes.sql` | `CREATE INDEX IF NOT EXISTS` (9.5) | то же |
| `sql/audit_analyzer/seed_predefined_scripts.sql` | `ON CONFLICT` (9.5) | нужна эмуляция многострочного upsert |
| `sql/audit_analyzer/seed_default_indexes.sql` | `ON CONFLICT` (9.5) ×3 | то же; файл помечен LEGACY |

### Открытый блокер: два ключа на одной таблице

`sql/session/create_public_agent_session_messages.sql` и его тестовый клон
объявляют **два** уникальных ключа: `PRIMARY KEY (id)` и
`UNIQUE (replica_id, session_key, seq)`. Greenplum 6 на хеш-распределённой
таблице допускает ровно один `UNIQUE`/`PRIMARY KEY`, и он обязан включать
все столбцы распределения (Summary of Greenplum Features, Greenplum 6).
Такая таблица на Greenplum 6.5 **не создаётся вовсе** — независимо от клаузы
распределения.

Правкой совместимости это не закрывается: нужно решить, какой из двух ключей
остаётся. Сам файл называет `id` суррогатным, а настоящим ключом —
`(replica_id, session_key, seq)`, то есть кандидатура очевидна, но это
решение о схеме, а не о синтаксисе. Пока его нет, позиция держится в
`KNOWN_TWO_KEY_TABLES` стража.

### Про `DISTRIBUTED RANDOMLY`

Страж ловит отдельно: `DISTRIBUTED RANDOMLY` проходит проверку «есть ли
`DISTRIBUTED BY`», но неверно на **обоих** движках сразу — на Greenplum
первичный ключ на случайно распределённой таблице не создаётся, а на
обычном PostgreSQL такой клаузы в синтаксисе нет. В
`create_public_agent_predefined_scripts.sql` это стояло и исправлено на
`DISTRIBUTED BY (name)`.

План устранения: `docs/architecture/runtime-environment-remediation.md`.

## Linux

Специфичного кода, ломающегося на Linux, не найдено. Проверено:

- `sys.platform` в `gateway.py` обусловливает Windows-ветку правильно;
- `lib/utils/windows_terminal.py` импортируется безусловно, но внутри только
  `ctypes`/`os`/`re`/`sys`, остальное — под `sys.platform`, то есть на Linux
  модуль безопасен и является no-op;
- `lib/cli/console_loop.py` и `tools/run_tests.py` обращаются к `win32`
  только в Windows-ветках.

Что требует проверки в среде, а не в коде:

- **NFS.** Рабочий каталог заказчика смонтирован по NFS. Upstream
  `JsonlSessionStore.save` переписывает файл сессии через `os.replace` —
  атомарность этого вызова на NFS зависит от версии протокола и является
  внешним фактом. Эмпирически у заказчика уже подтверждено, что DuckDB
  `ATTACH` по NFS даёт «PID 0»; тот же класс отказов возможен и здесь.
  Проверяется замером, не чтением кода.
- **Регистр путей и окончания строк.** Рабочее дерево ведётся на Windows, и
  окончания строк в нём смешанные (`main.py` и `context_compaction.py` —
  CRLF, `application_context.py` и `channel_factory.py` — LF). Для Python и
  SQL это безобидно, но при сборке образа из репозитория на Linux разница
  видна в диффах и стоит привести к одному виду при случае.

## Python 3.12

Окно соответствует коду. `nanobot-ai 0.3.5` требует `>=3.11`, значит 3.12
поддерживается библиотекой.

Направление риска здесь асимметрично и именно поэтому важно: локально стоит
3.14, поэтому API, **удалённые** в 3.12/3.13, проявились бы сразу. Опасно
обратное — использование того, что **появилось** в 3.13/3.14. Проверено явно:
`warnings.deprecated`, `copy.replace`, `typing.TypeIs`/`NoDefault`/`ReadOnly`,
`os.process_cpu_count`, `dbm.sqlite3`, `Path.move`/`move_into`/`info`,
`base64.z85encode`, `compression.zstd`, `uuid.uuid8`, `annotationlib`,
`InterpreterPoolExecutor` — ни одного.

`multiprocessing` и `os.fork` в проекте отсутствуют, поэтому характерное для
Linux предупреждение 3.12 («`fork()` в многопоточном процессе ведёт к
дедлокам в потомке») здесь не применимо: на Linux старт-метод по умолчанию
`fork`, на Windows — `spawn`, и код, безопасный на Windows, на Linux завис бы
только при наличии `multiprocessing`.
