# План устранения: приведение к Greenplum 6.5 / Python 3.12 / Linux

Канон среды — `runtime-environment.md`. Здесь план работ, которые нужны, чтобы
дерево ему соответствовало. Обнаружено сканированием; каждая позиция проверена
сканером, а не прочитана «на глаз».

**Сводка на 2026-10-03:** было 25 файлов с нарушениями против СУБД, стало
**17**. Закрыто: реестр миграций, зеркало сессий, пять `create_oarb_*.sql`,
`predefined_scripts`. Не закрыто: миграции `V002…V011` (переписывать нельзя),
DDL журнала (занят стражем чужой работы), распределение ключа в DDL сессий и
журнала (требует решения владельца, см. 1.4), два seed-скрипта. По Python 3.12
и Linux нарушений в коде нет.

### Решения, принятые при починке

- **Условный `UPDATE` вместо `ON CONFLICT DO UPDATE`.** Одно и то же
  выражение работает и на 9.4, и на 13, поэтому код не привязан к выбранной
  СУБД. Решение принимает `rowcount` самого `UPDATE`, а не вывод из чтения:
  между чтением и записью строку могла удалить уборка той же реплики, и
  «запись только обновлением» потеряла бы сессию молча.
- **Арбитраж в уборке — счётчик, а не блокировка.** Рассинхронизация с
  параллельным `mirror_session` может дать лишь одну лишнюю инкременту
  счётчика пропусков, а он обнуляется при следующем успешном зеркалировании.
  Удаление идёт только после нескольких циклов подряд.
- **Клауза распределения выбирается по факту движка, а не по канону.**
  Статический DDL обслуживает один движок; исполняемый путь способен
  определить движок и потому безопаснее. `sql/migrations/schema_migrations.sql`
  и `tools/migrate.py` создают одну и ту же таблицу, и после починки они
  расходятся — это осознанно и отмечено в карантине.

## Уровень 1. Блокеры запуска

### 1.1 Реестр миграций не запускается на Greenplum 6.5

`tools/migrate.py:142` регистрирует применённую версию через
`INSERT ... ON CONFLICT (version) DO NOTHING`. `ON CONFLICT` появился в
PostgreSQL 9.5, ядро Greenplum 6.5 — 9.4. **Без этого не применяется ни одна
миграция**, а значит не накатывается ни зеркало, ни ключ реплики.

Замена: `SELECT 1 FROM public.schema_migrations WHERE version = %s` и `INSERT`
только при отсутствии строки, всё внутри уже существующей транзакции runner'а.
Проверка и вставка в одной транзакции дают ту же гарантию, что и `ON CONFLICT`.

*Объём: ~15 строк. Эффект: разблокирует всю дальнейшую работу.*

### 1.2 Миграции с синтаксисом новее 9.4

| Миграция | Конструкция | Релиз |
|---|---|---|
| `V002__vector_chunk_params.sql` | `ADD COLUMN IF NOT EXISTS` ×3 | 9.6 |
| `V004__agent_gateway_logs_user_id.sql` | `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS` | 9.6 / 9.5 |
| `V008__agent_gateway_logs_event_time_columns.sql` | `ADD COLUMN IF NOT EXISTS` ×2, `SET NOT NULL` ×3 | 9.6 / **12.0** |
| `V009__agent_gateway_logs_event_time_indexes.sql` | `CREATE INDEX IF NOT EXISTS` ×2 | 9.5 |
| `V010__agent_session_mirror_replica_key.sql` | `ADD COLUMN IF NOT EXISTS` ×6, `SET NOT NULL` ×4 | 9.6 / **12.0** |
| `V011__agent_session_mirror_indexes.sql` | `CREATE [UNIQUE] INDEX IF NOT EXISTS` | 9.5 |

**Здесь нужно решение владельца, потому что влияет на объём.** Правило
`sql/README.md:97-98` запрещает менять применённые миграции (checksum в
`schema_migrations` даёт DRIFT). Отсюда развилка:

- **Базы уже накатили эти миграции** — файлы менять нельзя, и на них ничего не
  сломается: они уже отработали. Проблема только на **новых** установках,
  где `V002…V011` применяются с нуля.
- **Новых установций не будет** — тогда риск нулевой, и в карантин попадает
  не «долг», а «осознанно оставлено ради истории». Фиксируется запиской, а
  не переписыванием файлов.
- **Новые установции будут** — тогда появляется отдельная ветка «миграции для
  PG 9.4», а канонические файлы остаются для истории. Либо применяется
  вручную на старой базе и `--baseline`, как README уже предлагает для V001.

Мой совет: выяснить, какие версии фактически зафиксированы в
`schema_migrations` на рабочих базах, и не трогать то, что уже применено.
Это замер, а не правка кода.

### 1.3 DDL не соответствует канону

Отсутствует `DISTRIBUTED BY` в 10 файлах: все четыре `sql/session/*`, все три
`sql/logs/*` (`agent_gateway_logs`, его `_test` и `agent_question_runs_test`),
`sql/channels/*_test`, `sql/migrations/schema_migrations.sql`,
`sql/audit_analyzer/create_public_agent_predefined_scripts.sql`.

На **новой** установке инструкция из `sql/README.md § Порядок применения`
(`psql -f`) эти файлы не выполнит. На **существующей** базе таблицы уже
созданы, и `DISTRIBUTED BY` — свойство распределения, которое добавляется
только перезаписью таблицы.

Плюс `sql/audit_analyzer/create_oarb_*.sql` (5 файлов) используют
`GENERATED BY DEFAULT AS IDENTITY` — это PostgreSQL **10.0**, Greenplum 6.5
такую колонку не создаст. Замена — `BIGSERIAL`, доступный в 9.4.

### 1.4 Конфликт со стражем соседней работы

`tests/test_journal_event_time_columns.py:247-250` требует, чтобы в DDL
журнала **не было** `DISTRIBUTED BY` и слова `Greenplum`, и объявляет
PostgreSQL 13.22 фактической СУБД. Это прямо противоречит `sql/README.md §
Совместимость`, и **блокирует любую попытку починить DDL журнала**: страж
упадёт на первом же исправлении.

Оценка: страж написан на фактах верным для своего участка (конкретная база
журнала может быть отдельной), но формулировка «фактическая СУБД — PostgreSQL
13.22» в `sql/README.md` не оставляет места такой развилке. Требуется решение:
либо журнал действительно живёт в отдельной PostgreSQL, и тогда канон надо
дополнить исключением, либо страж перестаёт быть стражем и переписывается.

**Уточнение от 2026-10-03.** Противоречие шире, чем страж: то же объявление
«PostgreSQL 13.22 (фактическая база)» стоит в шапке
`sql/session/create_public_agent_session_meta.sql` с обоснованием «pg_dist_partition
на сервере отсутствует». Написано это было моим же коммитом `fd69ed3`, то есть
наблюдение о сервере настоящее, а вывод о каноне — поспешный: канон требует
Greenplum 6.5, и `DISTRIBUTED BY` — клауза, которую обычный PostgreSQL не
понимает. Статическим DDL-файлом оба движка не обслуживаются.

Отсюда развилка, которую нельзя закрыть чтением кода: **какая база фактическая
сейчас и какая станет.** Пока не сказано, `DISTRIBUTED BY` нельзя ни добавить
(сломает PostgreSQL 13.22), ни считать долгом (на Greenplum DDL не выполнится
вовсе).

## Уровень 2. Деградация под нагрузкой

### 2.1 `SELECT ... FOR UPDATE` блокирует таблицу целиком

`mirror_session` читает строку зеркала под `FOR UPDATE`, чтобы закрыть окно
гонки между решением и записью. `docs/ARCHITECTURE.md:1282-1284` (дважды)
фиксирует: **на Greenplum 6.5 `SELECT ... FOR UPDATE` берёт блокировку
уровня таблицы**, и такой захват заблокировал бы всех читателей и писателей
`agent_conversation_messages` — а по аналогии `agent_session_meta`.

Система при этом запустится, но зеркальный цикл каждые 30 секунд будет
блокировать таблицу на всё время своей транзакции. При двух репликах и
внешних читателях (BI, disaster-recovery) это риск остановки.

**Решение — убрать `FOR UPDATE` вовсе, а не заменить.** Смысл блокировки был
в защите от гонки двух писателей на одну строку `session_key`. Составной
первичный ключ `(replica_id, session_key)` эту гонку снял по построению: одну
сессию пишет ровно одна реплика, и другой реплики эта строка не принадлежит.
Оставшийся случай — два процесса с одинаковым `replica_id`, то есть
неверная настройка реплики; он должен падать громко (нарушение первичного
ключа), а не сглаживаться блокировкой.

Замена: `UPDATE ... WHERE replica_id = %s AND session_key = %s`, а при
`rowcount == 0` — `INSERT`. Условный `UPDATE` работает и как арбитраж, и без
блокировки, что уже применено в проекте для очереди задач.

*Это правка моего же кода (`7f1d23a`); по объёму — удаление одной строки плюс
переход на `UPDATE`-затем-`INSERT` вместо `ON CONFLICT`.*

### 2.2 `jsonb` и `jsonb_set` на Greenplum 6.5

`jsonb` появился в 9.4, то есть формально доступен, и исходный DDL на нём
стоял. Но `append_history_notice` (канал и журнал) использует
конкатенацию через `jsonb_set` — стоит проверить на живом кластере, а не по
версии. Деградация, не блокер: при отказе пропадает только заметка о сжатии,
журнал продолжает писаться.

### 2.3 `gen_random_uuid()` требует `pgcrypto`

Требуется `CREATE EXTENSION pgcrypto` — в README упомянуто, но ни в одном DDL
расширение не создаётся. На базе без него DDL с `gen_random_uuid()` не
выполнится. Затрагивает `tests/integration/test_postgres_channel_lifecycle_stress.py`
и любые DDL, которые это используют.

## Уровень 3. Проверяется в среде, а не в коде

- **NFS и атомарность `os.replace`.** Upstream `JsonlSessionStore.save`
  переписывает файл сессии через `os.replace`; атомарность этого вызова на
  NFS — внешний факт, зависящий от версии протокола. У заказчика уже
  подтверждён отказ того же класса на NFS (DuckDB `ATTACH` → «PID 0»).
  Проверяется замером: цикл записи сессии под нагрузкой на смонтированном
  каталоге, счётчик неудачных `os.replace`.
- **Смешанные окончания строк.** `main.py` и `context_compaction.py` хранятся
  с CRLF, `application_context.py` и `channel_factory.py` — с LF. Для Python и
  SQL безобидно, но при сборке образа на Linux разница видна в диффах.
  Приведение к одному виду — гигиена, не блокер.

## Порядок работ

1. **Развилка по 1.2** — выяснить, какие версии применены на рабочих базах.
   От ответа зависит, держим ли историю миграций или чиним её.
2. **1.1** — реестр миграций. Без него остальное не проверяемо.
3. **2.1 + 1.4-совместимая часть** — снять `FOR UPDATE` и `ON CONFLICT` из
   `mirror_session`. Это моя зона, конфликта с соседом нет.
4. **1.4** — решение по стражу DDL журнала: он сейчас блокирует починку.
5. **1.3** — `DISTRIBUTED BY` и `BIGSERIAL` в DDL. Объём зависит от шага 1.
6. **2.2, 2.3** — проверки на живом кластере.
7. **Уровень 3** — замеры NFS и гигиена окончаний строк.

Каждый пункт снимает запись из `KNOWN_DEBT` в
`tests/test_runtime_environment_contract.py` и строку из таблицы долга в
`runtime-environment.md`. Карантин пустеет по мере починки, а не остаётся
константой.

## Чего делать не нужно

- **Не переписывать применённые миграции ради красоты.** Проверка checksums
  в `tools/migrate.py` превратит такой «ремонт» в DRIFT на каждой базе.
- **Не заводить вторую СУБД «на всякий случай».** Развилка 1.2 снимается
  замером, а не новой веткой DDL.
- **Не снимать `FOR UPDATE` «на всякий случай» в других операциях.** Проверка
  показала `FOR UPDATE` в исполняемом SQL платформы в четырёх местах; прежде
  чем трогать остальные, надо установить, какие из них берут блокировку
  таблицы в Greenplum, а какие — строки. Это проверяется на кластере.
